## 7. Review findings

- [x] 7.1 `pnpm --dir web check` was red: `contracts.ts` exports `Requirement` **twice** (line 81 from `internal/ai/enrich`, line 870 from `internal/candidate/matchanalysis`, both emitted into one file by `cmd/gen-contracts`), and TypeScript merges same-name interfaces, so the exported name demands five members. Pre-existing — `types.ts` sidesteps it by aliasing the second as `MatchRequirement` and nothing had imported the bare name. Declared the two-field shape locally in `enrichment.ts` with the reason written down; disambiguating the generator is a change to every consumer of that alias and not this feature's to make. **Task 6.3 previously recorded "0 errors" for this command; that was measured before the cast was removed in an earlier review fix and was stale, not true.**
- [x] 7.2 The extractor's section state machine was wrong in both directions, confirmed by reproducing all seven shapes as failing tests first. An empty spacer `<p></p>` or a short lead-in `<p>You will need:</p>` closed an open section (rich-text-editor markup is everywhere in ATS descriptions); a long paragraph or a table did NOT close one, so "the first list after the heading" could be the benefits list further down; and a short wrapper `<div>` around a heading and its list was classified as a heading, discarding the list inside it — which made whether a posting yielded anything depend on how long its bullets happened to be. Now: a wrapper containing a list is never a heading, an inline element outside the vocabulary leaves the section as it was, prose and tables close it, and only h1–h6 close it by being unrecognized. Live yield on the same 164-posting sample rose 12.8% → 14.0%, with no benefits lists in it. Both figures are that sample's, not the catalogue's — see task 9.1.
- [x] 7.3 The keep-the-stored-value guard keyed on the empty DERIVATION, which also kept a stale list when a real edit deleted the requirements section — the page would then quote a posting that no longer says it, the exact failure the design calls worst, arriving through the guard meant to prevent it. Now keyed on the incoming DESCRIPTION being empty, which is the actual failed-detail-fetch signal `description` itself uses one branch up.
- [x] 7.4 `jsonb_array_length` RAISES on a non-array and `COALESCE` catches only SQL NULL, not JSON `null`, so a payload carrying `"requirements": null` would have made every enrichment write for that job a permanent 22023. Guarded on the VALUE rather than in the `WHEN`, because Postgres does not promise to short-circuit an `AND`/`OR`. Six integration cases cover it.
- [x] 7.5 Nothing could ever clear a wrongly derived list: the ingest guard kept it, `RefreshUnchangedJob` skips the column when `content_hash` has not moved (a vocabulary change does not move it), and the backfill skipped rows yielding nothing. The backfill now writes `[]` too, which makes it the repair path for a vocabulary fix; the `IS DISTINCT FROM` guard keeps that nearly free.
- [x] 7.6 `TestUpsertJob_RequirementsDerived` never called `UpsertJob` — it executed a hand-written UPDATE restating the conflict branch's own CASE, so deleting that branch left the test green. Rewritten to call the real query, and extended to cover the clear-on-edit and replace-on-new-list cases.
- [x] 7.7 The chunk read had no `LIMIT`, so an id RANGE decided how many ~1 MB descriptions pgx buffered at once. Added a row limit with keyset resume from the last id when a chunk comes back full — bounds memory without skipping rows.
- [x] 7.8 `envInt64` fell back silently on an unparseable value; a typo in `BACKFILL_REQUIREMENTS_FROM_ID` would have silently re-walked the whole table and looked like an ordinary run. Now fails the run, matching `HYDRATION_RETRY_DAYS`'s documented reasoning, and the knobs are read before the pool is touched.

## 8. Two-axis code review (Standards + Spec)

- [x] 8.1 **An inline out-of-vocabulary heading did not close a section.** `headingDecision` returned the open priority for anything that was not `h1`–`h6`, which task 7.2 chose deliberately to protect spacers and lead-ins. But rich-text-editor markup — the very case 7.2 invokes — is where `Benefits:` is a `<p>`, not an `<h2>`. Reproduced: `<p>Requirements:</p><p>Benefits:</p><ul><li>Free lunch</li></ul>` yielded `Free lunch` as **required**. Structure cannot separate `<p>Benefits:</p>` from `<p>You will need:</p>` — they are the same shape — so the closing headings are now their own closed vocabulary (`closingHeadings`). An unrecognized inline line still leaves the section open, so 7.2's fix stands.
- [x] 8.2 **The `SetJobEnrichment` overlay materialised the derived list into the blob, and nothing revises a blob.** A later crawl rewrites `requirements_derived` and leaves the copy, so a description edit deleting the requirements section left the page quoting a posting that no longer says it — the exact failure 7.3 claimed to close, which it had closed only at the column level. It also falsified 7.5: for any job enriched since, the wrong list sat in the blob out of the backfill's reach. **The overlay is deleted.** The read-path fold in `jobview.FromDomain` (task 4.4) already re-reads the column on every projection, so the overlay was pure duplication with a staleness bug attached; the column is now the single source and the blob holds only what the model said. The SQL comment records why an overlay must not come back.
- [x] 8.3 The backfill checked its per-run maximum only between chunks, so a run overshot by up to `rowsPerChunk`. The last chunk's `LIMIT` is now narrowed to what is left of the budget.
- [x] 8.4 **A factual claim in the proposal and design was false**: `matchanalysis` and `coverletter` do NOT read `enrichment.requirements` — `matchanalysis` builds its own list from a first LLM stage (`analyzer.go`'s `s1.Requirements`) and `coverletter` takes that one. That claim was the main argument for storing the derivation rather than parsing per request. Corrected in all three documents; the storage decision stands on its remaining ground (the backfill needs somewhere to put its answer, and re-parsing every body on every read repeats work whose input never changes).
- [x] 8.5 `internal/job/reqextract/AGENTS.md` added and linked from the root module table. Two hand-curated vocabularies and a heading-tail set is what the root `AGENTS.md` means by a substantial package; the rules had been documented a block away, in `internal/ai/enrich/AGENTS.md`.

## 9. Rollout

- [x] 9.1 **Measure the real coverage, and record how the first two attempts got it wrong.** Migration 0139 applied, `cmd/backfill-requirements` run to completion over the open catalogue in five bounded batches. Result, `TABLESAMPLE SYSTEM (5)` over 350k open rows on 2026-09-05: **28.0%** carry a derived list, **1.9%** carry the model's own, **29.3%** carry one or the other — up from 1.9%, fifteen-fold. The two barely overlap (6,806 + 98,410 sampled entries union to 102,707), which is this change's central bet holding: the model reads the prose postings, the parser reads the marked-up ones.
  - The planning figure was 12.8%, from 164 postings in the API's default order. A later re-measurement over 300k rows by `ORDER BY id` said 43.5%. Both are wrong, in opposite directions, for one reason: **id order and recency each proxy for the posting's SOURCE**, and the source is exactly what decides whether requirements appear as a list. Newest-first skews to flat-text aggregators; oldest-first skews to ATS boards. `TABLESAMPLE` is the only one of the three that answers the question asked, and it is what `internal/job/reqextract/AGENTS.md` now tells the next reader to use.
- [x] 9.2 **The migration needed a hand.** It failed its first deploy with `55P03` — `ALTER TABLE jobs` could not win ACCESS EXCLUSIVE inside `migrate`'s 5s `lockTimeout` against ordinary traffic. `release.sh` correctly refused to flip the live colour, so prod stayed on the old code rather than new code missing a column. Raising the timeout was considered and rejected: `internal/platform/migrate/migrate.go` documents the 2026-07-30 incident where a waiting ALTER blocked every new reader of the table. Retried by hand instead, at a moment with no long transactions — it took 216ms.
- [x] 9.3 **The worker was not in `release.sh`'s build list**, so its binary was absent from the host and the operator built it by hand for the first batches. Fixed in #2485 and applied to the host; the two copies are byte-identical. This is the fourth time that list has been found short.
- [x] 9.4 Prod impact measured during AND after a batch: the job page held 0.10–0.21s throughout. `stats/catalog` sat at ~0.68s against a 0.30s baseline during the run — **and stayed there after it stopped**, so the elevation was not this worker's. Comparing during-vs-after is what separates your own load from the background's.
- [x] 9.5 Tuning found by measurement, not guessed: `BACKFILL_REQUIREMENTS_CHUNK=100000` runs **ten times faster** than the 5k default. The narrow default existed to bound memory, but the row `LIMIT` added later already does that — the chunk width was left doing nothing except stepping through a 1.6-billion id space 5,000 at a time. Consider making 100k the default.
