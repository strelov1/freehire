## 1. Schema

- [x] 1.1 New migration `0128_add_username.sql` (`-- migrate: no-transaction`, per design.md's Migration Plan / the 0085 hot-table precedent): `ALTER TABLE users ADD COLUMN username text, ADD COLUMN username_updated_at timestamptz` (nullable, metadata-only), then `ADD CONSTRAINT users_username_check CHECK (char_length(username) BETWEEN 3 AND 30 AND username ~ '^[a-z0-9]+(-[a-z0-9]+)*$') NOT VALID`, then `VALIDATE CONSTRAINT users_username_check`
- [x] 1.2 `cmd/backfill-username-from-mailbox`: one-off Go worker (not raw SQL — see design.md's Migration Plan for why). Reads `mailboxes` joined to `users WHERE username IS NULL` (`ListMailboxesWithoutBackfilledUsername`, unpaged — small by construction); for each row, strips the domain (`localPart`) and calls `accounts.EnsureUsernameFromBase`, which runs the address through `internal/identity/username.Sanitize`/`Candidate`/`IsReserved` exactly as a fresh claim would, leaving `username_updated_at` `NULL`. Idempotent (only ever considers `username IS NULL` rows); needs only `DATABASE_URL`
- [x] 1.2b Unit test coverage for the transform: the sanitize/collapse/trim/fallback/truncate cases live in `internal/identity/username`'s table-driven tests (2.5) and the collision-suffix/idempotency cases in `accounts`'s `EnsureUsernameFromBase` tests (3.4) — the worker reuses both rather than reimplementing them, so only its own `localPart` split gets a dedicated test (`cmd/backfill-username-from-mailbox/main_test.go`)
- [x] 1.3 New migration `0129_users_username_uniq_idx.sql` (`-- migrate: no-transaction`, per the 0086 hot-table precedent): `CREATE UNIQUE INDEX CONCURRENTLY IF NOT EXISTS users_username_key ON public.users (username) WHERE username IS NOT NULL` — run **before** 1.2's backfill worker, not after (an earlier draft had this backwards; code review caught that the backfill's own collision resolution depends on this constraint already existing when it runs — see design.md's Migration Plan step 2/3 for the full reasoning). Both new migrations pass `pnpm check:sql` — note for anyone touching this file again: squawk-cli 2.63.0's per-statement `-- squawk-ignore prefer-robust-stmts` comment does not suppress that rule (verified empirically); `-- squawk-ignore-file prefer-robust-stmts` does and is what 0128 uses for its unavoidable `ADD CONSTRAINT ... NOT VALID` / `VALIDATE CONSTRAINT` pair
- [x] 1.4 Stop relying on `mailboxes.address` going forward — leave the column in place (dropped in a later cleanup migration per design.md's Migration Plan), but stop it being written by any query added in this change. Required an additional migration, `0130_mailboxes_address_nullable.sql` (`ALTER COLUMN address DROP NOT NULL`, discovered while implementing group 5): the column's original `NOT NULL` blocked an insert that no longer supplies one
- [x] 1.5 `internal/platform/db/queries/users.sql`: add `GetUsernameByUser`, `SetUsername` (writes `username` + `username_updated_at = now()`, for `ClaimUsername`), `SetUsernameIfAbsent` (writes `username` only, `username_updated_at` untouched, for `EnsureUsername`'s lazy default and for the backfill worker), `GetUserIDByUsername` (availability check / mailbox inbound resolution); regenerated via `make sqlc`. Also added `internal/platform/db/queries/mailbox.sql`'s `ListMailboxesWithoutBackfilledUsername` for the backfill worker

## 3. `internal/identity/accounts` claim service

- [x] 3.1 `Repository` gains `UsernameByUser`/`SetUsernameIfAbsent`/`SetUsername` (mapping a Postgres unique violation to a typed `ErrUsernameTaken`), implemented by `QueriesRepository` — mirrors the existing `Repository`/`QueriesRepository` split already in this package rather than `mailbox`'s separate-`Store` pattern
- [x] 3.2 `EnsureUsername(ctx, userID, email) (string, error)`: returns the existing username if set; otherwise derives via `username.Suggest` + `username.Candidate` collision retry and writes via the "if absent" path (`username_updated_at` left `NULL` — see design.md Decision 2), idempotent under a concurrent call for the same user (re-read on conflict, matching `mailbox.GetOrCreate`'s pattern). Code review caught a bug in the collision-resolution loop's re-read step: a real repository error there was silently swallowed and treated as "try the next suffix" instead of propagating — fixed, with `TestEnsureUsernamePropagatesARecheckError` pinning it
- [x] 3.3 `ClaimUsername(ctx, userID, desired string) error`: validates format + reserved list, enforces the 30-day cooldown (checked only when `username_updated_at` is non-nil, via `Service.now`), then a direct write; a unique violation on the desired name returns `ErrUsernameTaken` with no suffix retry
- [x] 3.4 Unit tests with a fake `Repository`: lazy default allocation + idempotency, explicit claim success, taken/reserved/invalid rejection (no suffixing), cooldown rejection and the "first explicit claim is never rate-limited even after a lazy default exists" case, reclaim-after-change

## 5. Mailbox integration

- [x] 5.1 Removed `Handle`, `Candidate`, `Address`, `reservedHandles`, `isReserved`, and the whole `mailbox.go` file (nothing pure was left) — moved to `internal/identity/username`; the package doc comment moved to `allocate.go`
- [x] 5.2 Rewrote `mailbox.GetOrCreate` to take a `UsernameEnsurer` (satisfied by `*accounts.Service`) and compose `<username>@<domain>`; `Store` shrank to one method, `EnsureRow` (idempotent enrollment via `EnsureMailbox`'s `ON CONFLICT (user_id) DO NOTHING`) — `mailboxes` no longer stores or derives its own address. Code review caught that the initial ordering (enroll, then resolve username) manufactured an avoidable anomaly on partial failure; swapped to resolve the username first (`TestGetOrCreate_ResolvesUsernameBeforeEnrolling`/`TestGetOrCreate_DoesNotEnrollWhenEnsureUsernameFails`) — a partial failure now leaves the ordinary "has a username, no mailbox" state instead of the reverse
- [x] 5.3 Rewrote the SES inbound resolver (`internal/application/mailingest.DBStore.MailboxByAddress`): strips the domain, resolves the local-part via `GetUserIDByUsername`, then confirms a `mailboxes` row exists for that user (`GetMailboxByUser`) — unknown username or no mailbox row is dropped exactly as an unknown recipient was before
- [x] 5.4 Rewrote `internal/application/mailbox/allocate_test.go` for the new `Store`/`UsernameEnsurer` contract (deleted `mailbox_test.go`, which tested the removed functions); `internal/api/handler/mailbox_integration_test.go` needed no changes — it asserts HTTP behavior, which is unchanged
- [x] 5.5 `internal/platform/db/queries/mailbox.sql`: replaced `InsertMailbox`(address) with `EnsureMailbox` (user_id-only, `ON CONFLICT DO NOTHING`), dropped `GetMailboxByAddress` entirely (superseded by `GetUserIDByUsername` + `GetMailboxByUser`), and `GetMailboxByUser` no longer selects the retired `address` column; regenerated via `make sqlc`. Also added migration `0130_mailboxes_address_nullable.sql` (see 1.4) and an integration test for the new resolution logic (`internal/application/mailingest/dbstore_integration_test.go`)
