## Context

Today `internal/application/mailbox` (block `application`, layer 6) owns the only "claim a short unique name" logic in the codebase: `Handle`/`Candidate`/`reservedHandles` (pure, `internal/application/mailbox/mailbox.go`) plus a `Store`-backed `GetOrCreate` allocator (`internal/application/mailbox/allocate.go`) that derives a handle from the user's email and resolves collisions with a numeric suffix, writing straight into `mailboxes.address` (`migrations/0015_hosted_mailbox.sql`, `UNIQUE`). There is no `users.username` column and no naming concept above the mailbox feature. `talent-network-profile-visibility` addresses public profiles by an opaque ID, not a name — a future change swaps that in `public` visibility mode, but is not part of this change. See `proposal.md` - Why.

## Goals / Non-Goals

**Goals:**
- Move the claim/collision/reserved-word logic from `mailbox` (layer 6) down into `identity` (layer 3), as an account-level concept both `application` and (later) `api`/`candidate`-adjacent talent-network code can depend on.
- Preserve every currently-claimed mailbox address across the migration wherever the existing handle is already valid under the new, stricter `username` format (the common case). A legacy handle that used a character the new format disallows (only `.`, since `mailbox.Handle`'s charset was `[a-z0-9.-]`) is sanitized (`.` → `-`) rather than left broken — seeing their address gain a hyphen where a dot was is a smaller surprise than the mailbox silently stopping working.
- Keep the mailbox address always in sync with the account's current username, with no separate mailbox-level claim step.

**Non-Goals:**
- Wiring `/u/<username>` into the talent-network public profile (future change).
- Any `web/` UI.
- Dropping the now-unused `mailboxes.address` column — kept as dead data this change, removed in a later cleanup migration once the new code path has run in production for a while (see Migration Plan).

## Decisions

**1. `internal/identity/username` is pure; allocation lives in `internal/identity/accounts`.**
The pure/allocation split mirrors `mailbox` (pure `mailbox.go` + `Store`-backed `allocate.go`). `username` package: `Valid(s string) error`, `Suggest(email string) string`, `Sanitize(s string) string` (the shared core both `Suggest` and the backfill worker's transform reduce to), `Candidate(base string, n int) string`, and `IsReserved` over a reserved-word set (ported from `mailbox.reservedHandles` and extended with product-identity terms relevant to a *public* name: `freehire`, `official`, `staff`, `moderator`, in addition to the existing RFC 2142 / CA-Browser-Forum / bounce names). For the allocation side, `accounts` already has its own `Repository`/`QueriesRepository` split (unlike `mailbox`, whose db-backed `Store` adapter lives at the handler layer) — `EnsureUsername` and `ClaimUsername` are added as `*Service` methods, and `Repository` gains `UsernameByUser`/`SetUsernameIfAbsent`/`SetUsername` (implemented by `QueriesRepository`, mapping a Postgres unique violation to `ErrUsernameTaken`), so both stay unit-testable with the package's existing `fakeRepo` test double rather than introducing a second, parallel `Store` abstraction into a package that already has one.

**2. Lazy default allocation never starts the rate-limit clock.**
`EnsureUsername` (called the first time a feature needs a username — e.g. mailbox `GetOrCreate`) writes `username` but leaves `username_updated_at` `NULL`. Only `ClaimUsername` (an explicit, user-initiated pick) sets `username_updated_at`, and the 30-day cooldown is evaluated only against a non-`NULL` value. Rationale: if the lazy default consumed the user's "free first change," someone who never knew a username existed until they opened their inbox would already be locked out of picking their own name for 30 days — clearly wrong. This is why the spec's "first claim" scenario is defined as "no prior *explicit* claim," not "no prior username at all."

**3. `mailboxes.address` becomes derived, not stored.**
The mailbox's Postgres row keeps only `id, user_id UNIQUE, created_at` (columns unrelated to naming) — `address` is dropped from being written; the effective address is always `<users.username> + "@" + MAIL_DOMAIN>`, computed at read time and at inbound-resolution time. This is what makes "change username → mailbox address updates automatically" (see `specs/hosted-mailbox`) true by construction instead of requiring a sync step. SES inbound resolution changes from "look up `mailboxes` by `address`" to "strip the domain from the recipient, look up `users` by `username`, then confirm a `mailboxes` row exists for that `user_id`" (unknown username or no mailbox row: dropped, same as today's unknown-recipient path).

**4. Explicit claim conflicts are rejected outright, never auto-suffixed.**
`ClaimUsername` treats a UNIQUE violation on the desired name as a hard "taken" error returned to the caller. Only `EnsureUsername`'s system-generated default goes through `Candidate`'s suffix search — a user who typed a specific name asked for exactly that one.

**5. Format is enforced both in Go and as a DB `CHECK` constraint.**
`CHECK (char_length(username) BETWEEN 3 AND 30 AND username ~ '^[a-z0-9]+(-[a-z0-9]+)*$')` on `users.username`, alongside `username.Valid` in Go. The repo already uses DB `CHECK` constraints for similarly small closed-ish domains (`users.role`); a column reused across two features (and, later, exposed in a public URL) is worth the same belt-and-suspenders.

## Risks / Trade-offs

- **A pre-existing mailbox address changes meaning under the covers.** → Mitigated by backfilling `users.username` from each user's current `mailboxes.address` before any code reads the new column; the computed address is byte-identical to today's for the common case (no dot, 3+ chars) and only cosmetically different (`.` → `-`) for the rare legacy handle the new stricter format wouldn't otherwise accept — see Goals.
- **Reserved-word list must anticipate the future public-profile use even though that feature isn't built yet.** → Extended now (item 1) rather than left mailbox-scoped, since adding words later is cheap but a username already claimed as `official` before the list catches up is not.
- **Dropping `mailboxes.address` later is a separate migration someone has to remember to do.** → Left as a known follow-up rather than attempted in this change, consistent with the repo's migration discipline (`migrate` runs before code that depends on new/changed schema; a column removal needs the reading code gone from production first, which this change alone can't guarantee).

## Migration Plan

`users` is one of the hottest tables in the app (read/written on nearly every authenticated request) — `migrations/0085_talent_network_visibility.sql` and `0086_talent_network_public_id_uniq_idx.sql` already hit, and document, the incident this causes when a `CHECK` validation or index build takes a blocking lock across the whole table. This change follows that established split rather than a single combined migration:

1. `ALTER TABLE users ADD COLUMN username text, ADD COLUMN username_updated_at timestamptz` (nullable, no default — metadata-only, instant) plus `ADD CONSTRAINT ... CHECK (...) NOT VALID` then a separate `VALIDATE CONSTRAINT` statement, all in one `-- migrate: no-transaction` file (mirrors 0085: `NOT VALID` skips the scan, `VALIDATE` takes only `SHARE UPDATE EXCLUSIVE`, and every existing row's `username` is `NULL`, which a `CHECK` always treats as satisfied, so validation cannot fail).
2. `CREATE UNIQUE INDEX CONCURRENTLY IF NOT EXISTS users_username_key ON public.users (username) WHERE username IS NOT NULL`, its own `-- migrate: no-transaction` migration file (mirrors 0086 — `CONCURRENTLY` cannot run inside a transaction block, and a plain unique index/constraint would hold a blocking `SHARE` lock for the whole build). Run this **before** the backfill worker, not after: every `username` is still `NULL` at this point, so the partial index starts and stays empty until the backfill begins writing (no existing-row scan for `CONCURRENTLY` to do), and — more importantly — the backfill's own collision resolution depends on this constraint already existing (see step 3; an earlier draft of this plan had the order reversed, which a code review caught as a real correctness gap before it shipped).
3. `cmd/backfill-username-from-mailbox`, a one-off Go worker (not a plain SQL `UPDATE`): `mailboxes.address` is a full `<handle>@<domain>` address, and the pre-existing `mailbox.Handle` charset (`[a-z0-9.-]`, no minimum length) is looser than the new `username` format (no dots, 3-30 chars) — a legacy handle can contain a dot or be 1-2 characters, which a raw copy would either write as an invalid `username` (failing the `CHECK` from step 1) or, if naively sanitized in SQL, collide two different legacy handles into the same value with no collision resolution. The worker strips the domain (`localPart`) and hands the raw local-part straight to `accounts.EnsureUsernameFromBase`, which sanitizes it (`.`→`-`, collapse/trim hyphens, fallback `"user"` when empty or under 3 characters, truncate to 30, via `internal/identity/username.Sanitize`) and resolves any resulting collision with `Candidate`'s suffix search (`-2`, `-3`, ...) — the exact same allocator a fresh claim goes through, so backfilled and freshly-claimed usernames obey one rule with no second implementation to drift. That resolution works by reacting to a real Postgres unique violation (`pgerr.IsUniqueViolation`) on an attempted write — which is exactly why step 2's index must already exist: `SetUsernameIfAbsent`'s `WHERE username IS NULL` has no cross-row uniqueness check of its own, so without a live constraint, two legacy handles that collide only after sanitization (e.g. `ivan.doe` and `ivan-doe`, both → `ivan-doe`) would both silently succeed with the identical username instead of the second one retrying with a suffix. (A separate, unrelated bug was also caught here: an earlier draft sanitized in the worker itself and passed an already-clean base to `EnsureUsernameFromBase`; moving the sanitize call inside that method instead — so it no longer trusts a caller to have done it — is what the integration test in tasks.md 6.3 caught missing.) Idempotent (`WHERE username IS NULL`-guarded per row) and bounded by `mailboxes`' row count, which is small (an opt-in feature) — nowhere near the row counts the repo's chunked `cmd/backfill-*` workers exist for.
4. `ALTER TABLE mailboxes ALTER COLUMN address DROP NOT NULL` — discovered while wiring `mailbox.GetOrCreate` onto `EnsureUsername`: a new mailbox enrollment no longer supplies an address at all, and the column's original `NOT NULL` (from `0015_hosted_mailbox.sql`) would otherwise reject that insert. Metadata-only regardless of table size (dropping `NOT NULL` never scans), and `mailboxes` is small besides, so this needs none of steps 1/3's lock-avoidance machinery.
5. Deploy code: `internal/identity/username` + `accounts.EnsureUsername`/`ClaimUsername`; `mailbox.GetOrCreate` and the SES inbound resolver switch to the username-derived address; the two new API endpoints ship.
6. Verify in production that every previously-mailboxed user's derived address still matches what was in `mailboxes.address` (a one-off read-only check, not a worker) before the follow-up column-drop migration is even proposed.
7. (Separate, later change) drop `mailboxes.address`.

No rollback complexity beyond the usual: steps 1-4 are additive (new nullable columns, a bounded backfill, a concurrently-built index, a relaxed constraint), so reverting the code deploy alone leaves the schema harmless and unused.
