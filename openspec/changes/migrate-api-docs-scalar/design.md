## Context

See `proposal.md` - Why. Current state, needed for the decisions below:

- `web/src/lib/docs/api-spec.ts` (~4400 lines) is a hand-authored TS module describing 253 endpoints (`Endpoint`, `Group`, `Overview` types). It feeds two consumers today: the `/docs/api` Svelte pages, and `scripts/gen-api-docs.mjs` → `docs/API.md`.
- `web/static/openapi.yaml` is an unrelated, pre-existing artifact: the ChatGPT Actions schema. It is pinned to OpenAPI 3.0.3 and ~9 read-only paths because the GPT Actions importer chokes on OpenAPI 3.1 idioms and has an operation-count ceiling (see commits `370de74d`, `48ed4708`, `ac361f80`). It is not touched by this change.
- `/docs/api`'s current Svelte implementation has, besides per-endpoint content, cross-cutting prose that has no natural per-operation home: response envelope, a global pagination rule (`offset + limit <= 10000` → 400), an error-code table, a 5-level auth model, and a "What is not here" section explaining deliberately undocumented routes (OAuth redirects, Telegram webhook, OG images).
- Scalar (`@scalar/api-reference`) builds its sidebar and search index from Markdown headings inside `info.description`, and renders GitHub-flavored Markdown (tables, fenced code, alerts). This is the capability that makes the previously-rejected OpenAPI-based approach viable now (see proposal's Why).

## Goals / Non-Goals

**Goals:**
- Single generation path from `api-spec.ts` to a new OpenAPI 3.1 document that Scalar renders, with no hand-maintained duplicate of endpoint data.
- Preserve every requirement in the current `api-documentation` spec, including SSR (SEO) and the cross-cutting Overview/Filtering content.
- Match the design system's visual language, not Scalar's default theme.

**Non-Goals:**
- Touching `web/static/openapi.yaml` or the ChatGPT Actions integration in any way.
- Changing `docs/API.md`'s generation behavior beyond reading the new `deprecated` field where present.
- Preserving exact per-endpoint SvelteKit routes (`/docs/api/<group>/<endpoint>`) — they redirect instead (see spec delta).
- Authoring OpenAPI by hand — `api-spec.ts` remains the authored source (see Decision 1).

## Decisions

### 1. `api-spec.ts` stays the authored source; OpenAPI is a generated artifact

Alternative considered: author the OpenAPI document directly (YAML/JSON) and drop `api-spec.ts`. Rejected — hand-authoring 253 operations directly in OpenAPI loses TS type-checking and the DRY helpers `api-spec.ts` presumably already has for repeated auth/pagination shapes; it would trade a maintenance problem for a worse one. A new generator script, sibling to `gen-api-docs.mjs`, produces the OpenAPI document; both scripts read the same `Endpoint`/`Group`/`Overview` data.

`api-spec.ts`'s data model gains two structured additions needed by the generator (and usable by `gen-api-docs.mjs` too):
- `deprecated?: { since: string; replacement: string }` on `Endpoint` — does not exist today; deprecation is currently only implied in free-text `description`.
- Structured Overview/Filtering section data (heading + Markdown body) in place of whatever free-form shape the current landing page consumes, so the OpenAPI generator can assemble `info.description` from the same data the Markdown generator and the previous Svelte page used.

### 2. New OpenAPI artifact is separate from `web/static/openapi.yaml`

Naming must make the distinction unmistakable in the codebase (e.g. `web/static/api-reference.openapi.json`, exact name decided during implementation) — never a name that could be confused with the ChatGPT Actions file. It is OpenAPI 3.1 (no GPT Actions importer constraint applies to it), and covers all 253 endpoints.

### 3. Content mapping into OpenAPI

- Per-endpoint fields → `summary` / `description` (Markdown) / `parameters` / `requestBody` / `responses` / `tags`. Curl (and other languages) generated by Scalar itself from the operation, not hand-authored — a strict superset of today's curl-only example.
- 5 auth levels (Public / Session-or-API-key / Session-only / Moderator / Browser-extension-only) → named `securitySchemes` (e.g. `cookieAuth`, `apiKeyAuth`); OpenAPI's security model cannot express "Moderator" or "Browser-extension-only" as a scheme distinction on its own, so these two continue to be stated in the operation's `description` prose, same as today.
- `deprecated` field → native OpenAPI `deprecated: true` plus a description note naming the replacement — an upgrade over today (no such structured field exists yet).
- Overview and Filtering content (base URL, response envelope, pagination rule, error table, auth model, "What is not here", filter modifiers/table, recipes) → `info.description`, as Markdown sections with headings. Scalar surfaces each heading in its sidebar and search index.
- Endpoint groups → OpenAPI `tags`, one-to-one with current groups; a coarser category, if the current grouping has one, uses `x-tagGroups`.

### 4. Embedding: SSR fragment + client hydration, not `@scalar/sveltekit`'s full-page handler

`@scalar/sveltekit` renders a full standalone HTML response from a `+server.ts` route, bypassing the app's SvelteKit layout (site header/footer/design-system chrome). Instead: `+page.server.ts` calls `renderApiReferenceToString` (from `@scalar/server-side-rendering`) to produce an HTML *fragment* (no `<!doctype html>` wrapper), rendered into a `<div id="scalar-app">` inside an ordinary `+page.svelte` — kept within the existing layout. The client then mounts `createApiReference('#scalar-app', config)` (from `@scalar/api-reference`, imported normally and bundled by Vite — SvelteKit already has a client bundler, so there is no need for Scalar's `getJsAsset()` standalone-bundle mechanism, which exists for non-bundled Node servers like Hono).

Verified against the packages' actual exports rather than assumed: `renderApiReference()`/`getJsAsset()` (the functions an earlier web search surfaced) belong to `@scalar/server-side-rendering` and produce a *complete* HTML document with its own hydration script tags — the wrong shape for embedding in an existing layout. `renderApiReferenceToString()` (fragment-only) is the one this design actually uses. `@scalar/client-side-rendering` (a third, CDN-oriented package also surfaced by search) is not used at all — it targets a different integration shape (pointing a static page at a CDN-hosted bundle) that doesn't fit a Vite-bundled SvelteKit app.

Server and client build the *same* config from a small shared factory (`$lib/docs/scalarConfig.ts`), differing only in how the OpenAPI document reaches them: the server imports the generated `web/static/api-reference.openapi.json` directly (`content`, no self-fetch), the client fetches the same file as an ordinary cacheable static asset (`url`) rather than duplicating ~370KB inline in the page's own data payload.

### 5. Dark mode: Scalar does not observe the site's `.dark` class — it must be told, and `updateConfiguration` cannot tell it

Scalar tracks its own light/dark state independently; left alone, it never reacts to the site's theme toggle at all (verified in a real browser: toggling the site's theme flipped the header instantly but left the embedded reference on its initial mode). `forceDarkModeState` picks the state at mount time (matching whatever the site's no-FOUC inline script already decided before this component hydrates). Making it track *later* toggles turned out to need more than `updateConfiguration`: `@scalar/use-hooks`' `useColorMode` destructures `overrideColorMode` from its options once, at composable-setup time, with no reactive watch on it — the option is documented as part of `AnyApiReferenceConfiguration` and `updateConfiguration()` does update the merged config object, but nothing inside Scalar re-reads that specific field afterward. Confirmed directly against the installed package (`node_modules/@scalar/use-hooks/.../useColorMode.js`), not inferred. The only mechanism that actually re-derives color mode is a fresh call to the composable — i.e. a fresh mount. The working fix: a single `$effect` keyed on the site's `themeStore.isDark`-derived state that calls `instance?.destroy()` then `createApiReference(...)` again with the new `forceDarkModeState`, replacing the whole component instance on every toggle rather than patching its config in place. `hideDarkModeToggle: true` removes Scalar's own manual toggle button, which would otherwise be a second, unsynced dark-mode control.

### 6. Theming via CSS custom properties mapped to design-system tokens, targeted at `.light-mode`/`.dark-mode` wherever they appear — including `<body>`

Scalar exposes its theme surface as CSS custom properties, applied via a `.light-mode`/`.dark-mode` class that `useColorMode`'s `applyBodyColorMode()` sets on **`document.body`** — an ANCESTOR of the `#scalar-app` mount point, which no selector requiring the class as `#scalar-app`'s *descendant* can ever match (confirmed directly: `document.body.className` reads `light-mode`/`dark-mode` after a toggle; walking every ancestor from an `<h1>` inside `#scalar-app` up to `#scalar-app` itself never encounters either class). An earlier version of this override scoped the selector to `#scalar-app :global(.light-mode)`/`:global(.dark-mode)`, on the theory that Scalar only re-declares the variables per-component; that part is also true (request/response example cards each carry their own literal copy of the class, as a *descendant* of `#scalar-app`), so the scoped selector happened to theme the always-dark example cards correctly while silently never reaching the general sidebar/heading/body text — a gap masked in review because a screenshot of near-black-on-near-white vs. Scalar's own near-black-on-near-white defaults looks correct at a glance. The working rule drops the `#scalar-app` qualifier entirely — plain `:global(.light-mode)`/`:global(.dark-mode)` — so it matches the class both on `<body>` and on any component that re-applies it locally, with `!important` (an unqualified vendor rule inside Scalar's own bundle otherwise wins the tie in some cases), mapping the design system's existing Tailwind tokens (`--background`, `--secondary`, `--muted-foreground`, `--brand-strong`, `--brand-muted`, etc.) onto Scalar's property names (`--scalar-background-1`, `--scalar-color-2`, `--scalar-color-accent`, ...) rather than using one of Scalar's built-in presets. This is a hard requirement (see spec delta "The embedded reference matches the site's theme"), not a nice-to-have — the visual mismatch of a preset theme is the dissatisfaction that motivated this change in the first place. Verified by reading the actual computed CSS color values in a real browser, live-toggling the site's theme with no page reload: heading text resolves to exactly the site's `--foreground` value in both modes (`oklch(0.13 0 0)` light, `oklch(0.985 0 0)` dark), not Scalar's own defaults. A few deep-internal accents (e.g. the HTTP-method badge color) stay Scalar's own hardcoded values not exposed as variables — an acceptable, minor divergence rather than a reason to fork Scalar's styles.

### 7. Retired routes redirect, they don't 404

`web/src/routes/docs/api/[group]/[endpoint]/+page.svelte` and its `+page.server.ts` are replaced by a redirect stub returning HTTP 301 to `/docs/api`, not deleted outright — avoids turning any indexed/bookmarked URL into a dead link. `+layout.svelte`, `DocsNav.svelte`, and `DocsEndpoint.svelte` are deleted outright (no external caller can reach them directly).

## Risks / Trade-offs

- **[No official SvelteKit SSR recipe for Scalar]** → mitigated by following the generic Node-server pattern (`renderApiReference()` + `getJsAsset()`); budget extra implementation time versus a hypothetical drop-in package, and verify the rendered HTML actually contains endpoint content (not just an empty mount point) before considering this done.
- **[Two independent OpenAPI-shaped artifacts in the repo]** (`web/static/openapi.yaml` for ChatGPT Actions, and the new one for Scalar) → could be confused by a future contributor. Mitigated by the naming requirement in Decision 2 and by leaving a comment at the top of each file stating its distinct purpose and consumer.
- **[Scalar's theme surface may not expose a CSS variable for every design-system token]** → some visual properties may need a documented, intentional approximation rather than an exact match. This is normal design-system integration risk, not unique to this change.
- **[Auth nuance loss risk]** — "Moderator" and "Browser-extension-only" aren't real OpenAPI security-scheme distinctions → mitigated by keeping them stated in operation description prose, matching today's behavior (no regression, just no native-OpenAPI representation either).
- **[Golden-fixture generator test could rot silently if the fixture isn't updated alongside `api-spec.ts` changes]** → acceptable; the fixture only needs to cover generator logic, not track every endpoint, and `@redocly/cli lint` on the full generated output catches structural breakage independently.

## Migration Plan

1. Extend `api-spec.ts`'s data model (`deprecated`, structured Overview/Filtering sections) with no consumer changes yet — verify `docs/API.md` generation is unaffected.
2. Build the new OpenAPI generator script and its golden-fixture test; validate output with `@redocly/cli lint` as a new, separate CI step.
3. Build the SSR-capable `/docs/api` page (Scalar web component + `renderApiReference()`/`getJsAsset()`), themed via design-system CSS custom properties, behind local testing only (not yet linked from nav).
4. Manually verify in a browser: light/dark theme, several endpoints of varying complexity (none/cookie/moderator auth; simple GET; body+auth POST; SSE), mobile width, and that the server response contains real HTML content (view-source, not just an empty mount div).
5. Add the 301 redirect stubs for legacy per-endpoint routes; delete `+layout.svelte`, `DocsNav.svelte`, `DocsEndpoint.svelte`, and the old landing implementation.
6. Confirm `knip`/`deadcode` report no orphaned files from the old implementation.
7. Ship. Rollback is a plain revert — nothing in this change is destructive to data, and `web/static/openapi.yaml`/ChatGPT Actions are untouched throughout.
