## 9. Independent review follow-ups

Found by an independent code review of the finished diff; fixed test-first before merge.

- [x] 9.1 **Critical**: `closeOrCountOneBoard` board-scoped a chronic board by name alone (`externalid.BoardPattern(r.Board)`), with no equivalent of the ordinary sweep's `ambiguousRegionBoards` check — a board id repeated per region for one provider (Adzuna's `it-jobs` once per country; `board_health`'s key is `(provider, board, region)`) has no region in `jobs.external_id`, so `--apply` on a chronic `it-jobs/gb` row would have closed `it-jobs/us`'s healthy postings too. Added `CountBoardHealthRegions` (a direct `board_health` check, since this worker has no crawl-run board list to consult) and `isRegionAmbiguous`, which skips and reports (`boardsSkippedAmbiguous`) rather than closes such a board — mirroring the sweep's own refusal. New spec requirement ("A region-ambiguous board name is never board-scoped by the safety net") and design.md Decision 5a. Tests: `TestCloseChronicBoardsSkipsRegionAmbiguousBoardNames`, `TestCloseChronicBoardsDryRunSkipsRegionAmbiguousBoardNames`.
- [x] 9.2 **Important**: `chronicBoardsSummary` dropped the region its sibling `unhealthyBoardsSummary` prints (`TestUnhealthyBoardsSummaryKeepsRegion` had no chronic equivalent), which compounded 9.1 — a curator reading the 30-day report had no way to notice a board was chronic in only one region. Fixed to match `unhealthyBoardsSummary`'s region-appending; added `TestChronicBoardsSummaryKeepsRegion`.
- [x] 9.3 **Important**: `closeChronicBoards` never surfaced truncation past `maxChronicBoardsPerRun`, unlike `chronicBoardsSummary`/`unhealthyBoardsSummary`'s "N more" convention — a run at exactly the cap looked identical to one with thousands more chronic boards behind it. Added a log line when `ListChronicBoardsRow.Total` exceeds the returned row count. Tests: `TestCloseChronicBoardsLogsWhenTheCapTruncates`, `TestCloseChronicBoardsDoesNotLogTruncationWhenNotCapped`.
- [x] 9.4 **CI-caught (CodeQL, "Incorrect conversion between integer types")**: the "considered and declined" call on the `int32(days)`/`int32(closeWindowDays)` casts above was wrong — CodeQL flagged both as high-severity on the PR (`cmd/close-chronic-boards/run.go:37`, `cmd/ingest/board_health.go:195`): an unchecked `int64→int32` narrowing on a destructive-close code path silently wraps an out-of-range `CHRONIC_BOARD_CLOSE_WINDOW_DAYS`/`CHRONIC_BOARD_WINDOW_DAYS` value into an arbitrary (possibly negative) `pgtype.Interval.Days` rather than refusing it. Added `worker.EnvInt32` (parses directly at `ParseInt`'s 32-bit size, so an out-of-range value is a parse error, not a truncation) alongside the existing `worker.EnvInt64`; both call sites and `closeChronicBoards`'s signature now carry `int32` throughout, with no cast left to flag. Tests: `TestEnvInt32TakesTheFallbackWhenUnsetOrBlank`, `TestEnvInt32ReadsASetValue`, `TestEnvInt32RefusesAValueItCannotRead`, `TestEnvInt32RefusesAValueThatOverflowsInt32`.

## 10. CodeRabbit review follow-ups (PR #2641)

Three findings on the finished PR; one verified and declined with reasoning, one fixed test-first, one accepted as a documented residual risk.

- [x] 10.1 **Fixed**: `closeChronicBoards` reads chronic rows via `ListChronicBoards`, then closes/counts them via a SEPARATE later call — a board can recover (a real crawl succeeds, calling `RecordBoardSuccess`) in that gap, and the close would still fire on the caller's now-stale read. `CloseChronicBoardJobs`/`CloseChronicProviderJobs` and their `Count*` dry-run siblings now carry an `EXISTS` subquery against `board_health` that re-evaluates the identical chronic predicate at the moment the statement runs (design.md Decision 5b; new spec requirement "A board that recovers before the close reaches it is never closed"). Required adding `board`/`age_window` params to all four queries and threading the same `pgtype.Interval` through `closeOrCountOneBoard`. Tests: `TestCloseChronicBoardJobsDoesNotCloseARecoveredBoard`, `TestCloseChronicProviderJobsDoesNotCloseARecoveredProvider`.
- [x] 10.2 **Declined, with reasoning** (design.md's new `[Declined]` risk bullet): CodeRabbit suggested `ListChronicBoards` should also require `consecutive_failures > 0`, reasoning that a board `ClearProviderCooldowns` recovered should stop being chronic. Verified this is incorrect for this schema: `ClearProviderCooldowns` resets failure/cooldown state when a recovery PROBE proves the provider reachable, to let its boards retry sooner — it never touches `last_success_at` and proves nothing about whether that specific board has actually succeeded since. Adding the condition would exclude a board that is still genuinely broken the moment ANY board of that provider's cooldown clears administratively — a correctness regression, not a fix.
- [x] 10.3 **Accepted as a documented residual risk** (design.md's new risk bullet): retiring a SINGLE region of a multi-region board (`boardcatalog.Retire`, the per-board `cmd/add-board --retire` path, as opposed to `cmd/prune`'s bulk `retireBoards` which always retires every region of a board together) deletes only that region's `board_health` row, which can un-flag a board `isRegionAmbiguous` previously refused. Verified the consequence is narrow: closing a retired board's already-uncrawlable leftover postings (arguably overdue) rather than closing a board still genuinely being crawled — a near-identical shape to the already-accepted "board retired from the catalog never reaches the closure window" risk, not a new exposure class. Declined as disproportionate to fix given how narrow, low-severity, and already-adjacent to an accepted risk it is.
