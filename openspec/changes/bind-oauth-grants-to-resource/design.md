## Decisions

- **Identifiers**: `<origin>/api/v1/mcp` and `<origin>/api/v1/mcp/account`, what the two protected-resource documents advertise. The value is parsed as a URI: scheme and host compare case-insensitively with the default port (:443 / :80) ignored, the path exactly (case-sensitive) with one trailing slash tolerated; relative URIs, userinfo, any query (a bare `?` too) or fragment are `invalid_target`.
- **Stored form**: only the canonical PATH (`/api/v1/mcp`, `/api/v1/mcp/account`) is stored in `resource`, never the origin, so a later `FRONTEND_ORIGIN` change (domain move, www/apex) does not orphan bound grants. The origin is validated when the resource is requested at /authorize and /token.
- **Multiple `resource` values**: a binding is to one resource, so several distinct values are `invalid_target`; repeats of the same value are one.
- **/authorize error**: once client and redirect_uri are validated, `invalid_target` goes back as a redirect (`error`, `error_description`, `state`) per RFC 6749 4.1.2.1. At /token it is a 400 `{"error":"invalid_target","error_description":...}`.
- **/token**: a `resource` is validated before the code is consumed. If the code was bound, a differing `resource` is `invalid_target`; if the code was unbound, the `resource` sent at /token binds the grant.
- **Refresh**: this server issues no refresh tokens (`grant_types_supported` is `authorization_code`), so there is nothing to carry over.
- **Enforcement**: only the two MCP endpoints compare the binding, inside the `AuthenticateOAuthGrant` query (it takes the endpoint path; NULL for REST), so a wrong-endpoint token is refused like an unknown one and does not touch `last_used_at`. A grant with NULL resource is valid on both (legacy and clients that do not send it).
- **REST**: unchanged. An OAuth grant is admitted wherever an API key is (`RequireAuthOrKey`); the binding scopes which MCP server a token is for, and REST is not an MCP server. Revisit if a grant should be narrowed further.
- Clients that connected to `/mcp/account` through the root metadata send `resource=<origin>/api/v1/mcp/account` and keep working there; they are refused at `/mcp`.
- **Superseded in part (freehire#4539)**: `/api/v1/mcp/account` was removed and `/api/v1/mcp` requires sign-in, so `<origin>/api/v1/mcp` is the only accepted resource. A grant already bound to `/api/v1/mcp/account` is refused at `/api/v1/mcp` like any wrong-resource grant; the two-endpoint wording above describes the state this change shipped into. **Restored as an alias**: `/api/v1/mcp/account` serves the same server again and `<origin>/api/v1/mcp/account` is accepted as a resource, bound as `/api/v1/mcp` (saved connectors 404'd after the removal).
