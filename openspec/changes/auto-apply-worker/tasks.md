Lever/Ashby DOM-scan deferred: see 6.3's note.
- [x] 6.3 Implement reconciliation (`internal/atsapply/reconcile.go`) against `internal/applyform.Form` (reused directly — `applyform.Fetchers` covers Greenhouse's REST API, Ashby's GraphQL API, and Lever's own DOM-only parse, so no HTTP call is re-implemented here). DOM decides existence; **required is the union of DOM and API**, not DOM alone — the spike measured a required field (`country`) rendered with no HTML `required` attribute, contradicting a pure "DOM decides required" reading of the brainstormed design (see `TestReconcile_RequiredIsTheUnionOfDOMAndAPI`). Scope narrowed from the original task: only Greenhouse gets a live browser DOM-scan; Lever and Ashby reconcile against `applyform.Form` alone for v1 (Lever parks on its captcha regardless — see 6.6 — so this costs nothing there; Ashby's completeness is an unverified assumption for 7.1's smoke test).
- [x] 6.4 Implement answer resolution (`internal/atsapply/resolve.go`): matches reconciled fields against the incoming `answers` map by a DOM-id→answer-key table (identity/work-authorization only); a select/checkbox's answer must match one of the platform's own offered option labels or it parks rather than guessing. **Two scope gaps found and left explicit, not silently handled**: file uploads (résumé/cover letter) always park — no artifact-attachment plumbing built; `country` has no answer key at all (the candidate profile carries one combined `location` string). Practically, on Greenhouse — which renders `country` as its own required field on nearly every posting, and always requires a résumé upload — this means v1 is expected to park essentially every real attempt, not just the edge cases. Widening past this (a country fact, file attachment, Tier C answers) is future work per design.md's Non-Goals, but worth flagging as a real product-readiness gap, not just a technical footnote.
- [x] 6.5 Implement fill + submit via chromedp (`internal/atsapply/fill.go`, `browser.go`): text/textarea fields (which also cover react-select-backed autocompletes — Greenhouse's DOM renders both as a plain `<input type="text">`, indistinguishable in this package's scan), checkbox groups by name+value, submission by clicking Greenhouse's known submit button id, confirmed/refused by text marker. **Not unit-tested and not yet verified against a live posting** — this is the least-verified part of the package by design (see design.md's Testing section); task 7.1 is where it gets checked for real. **Known gaps left explicit**: no upload handling at all (resolve.go already always parks required file fields, so nothing here needs to attach one yet); no assertion that a react-select-style field's typed value actually "stuck" the way the reference implementation's fill.py asserts (§9 in its own notes) — a typed-but-unmatched autocomplete value could silently submit empty.
- [x] 6.6 Implement captcha detection: a static per-provider map (`requiresCaptcha`), not DOM-based detection — Lever renders one on *every* posting per the design's own risk note, so this is a deterministic short-circuit before any fetcher or browser is touched, not a page-content heuristic. Ashby/Greenhouse aren't known to gate on one; a live posting that does would still park via the ordinary unresolved-field path today (no generic captcha-DOM detector built).
- [x] 6.7 Tied 6.1-6.6 together as `atsapply.Client.Submit`, implementing `autoapply.SidecarClient`. Ashby and any other provider reconcile against the API schema alone (`mergedFromAPIOnly`) — no live DOM-scan built for them — and a fully-resolved non-Greenhouse form still parks rather than submitting through a fill path never built, so nothing here can attempt a submission it hasn't been verified to make correctly.

## 7. Verification and documentation

- [x] 7.1 (partial — the safe half only; fill/submit still unverified) Ran the real `applyform.Fetchers`→`atsapply.ScanGreenhouseForm`→`Reconcile`→`Resolve` chain against the same live Greenhouse posting the 2026-09-02 spike used (throwaway driver, not committed — mirrors how the spike itself was run). Deliberately stopped before `fillAndSubmit`/the submit click: no real employer received a submission. Two real findings that correct earlier, pre-live-data assumptions:
  - `country` was **not required** on this live posting (`Required=false`) — the "country is nearly always required" claim in 6.4's note does not hold here. Good news, narrower than feared.
  - The actual dominant blocker is different from what 6.4 flagged: **5 of 7 unmapped required fields were Webflow's own custom questions** (consent, language proficiency, work authorization, visa sponsorship, "where did you hear about us") — `question_67131487/488/490/491/492`. `resolve.go`'s `answerKeyFor` is an **ID-based** lookup that only works for Greenhouse's own standardized field names (`first_name`, `email`, ...); a custom question's numeric id can never match it, even when `candidateprofile` genuinely holds relevant data (`authorized_countries`, `visa_sponsorship_needed` sat unused here because nothing connects them to `question_67131490`/`491`'s *labels*, which is what would actually have to be matched). Label/keyword-based matching for the handful of near-universal custom questions (work authorization, sponsorship) is the highest-value next increment, not the country/file gap 6.4 emphasized — flagging for a follow-up change rather than building it into this one's already-decided scope.
  - Also found and not yet handled: one required field scanned with an empty id AND an empty answer-key match (`id=""`) — a widget shape `ScanGreenhouseForm` does not yet name correctly.
  - Ashby, and the actual fill/submit path (this posting's required résumé upload alone means it can never reach `fillAndSubmit` under this change's scope) remain unverified against a live posting — a full end-to-end run needs the résumé/country/custom-question gaps closed first, which is follow-up work, not this task.
