# Worker commands: users, billing and mail

Part of the [worker index](../workers.md): what each `cmd/<name>` worker does, when it runs, what it needs, and the trap behind it. Billing, Discord, lifecycle mail, mentorship, messaging, social, LinkedIn, retention.

- `billing-sync` — reconciles Pro subscriptions against Stripe: applies `billing_events` the webhook recorded but could not apply, then re-reads subscription state for accounts whose `pro_until` is within a day of lapsing. Hourly, and **not optional** — the provider retries a webhook for up to three days and can disable an endpoint it decides is broken sooner than that, and past either point this worker is the only path by which a paid subscription becomes Pro. Needs `DATABASE_URL` and the `STRIPE_*` credentials; without them it is a **no-op that never opens the pool**. `BILLING_SYNC_MAX_PER_RUN` (default 500) bounds one run. The second pass reaches candidates through `users.stripe_customer_id`, so it walks the accounts that have actually transacted rather than every account. **A third pass settles referral rewards** — it grants the ones whose invitee has an invoice that actually collected (`amount_paid > 0`, never merely an active subscription) and places the granted ones on their referrers' balances, creating a provider customer for a referrer who has never bought. Stripe only: a store subscription produces no invoice we can read. `INVITE_REWARD_MAX_PER_USER` (default 12) bounds how many rewards one referrer may ever earn, and an unparseable value falls back and logs rather than stopping the run that also reconciles subscriptions. See [internal/identity/billing/AGENTS.md](../../../internal/identity/billing/AGENTS.md) and [internal/identity/promo/AGENTS.md](../../../internal/identity/promo/AGENTS.md).
- `discord-sync` — keeps the paid role on the community Discord server in step with the subscription: for each linked account it resolves the tier the ordinary way (`plan.TierOf` over `users.pro_until`/`ultra_until` — **never** a payment provider, which would be wrong for every app-store subscriber) and grants or revokes ONE role. Hourly. Needs `DATABASE_URL` and all five `DISCORD_CLIENT_ID` / `DISCORD_CLIENT_SECRET` / `DISCORD_BOT_TOKEN` / `DISCORD_GUILD_ID` / `DISCORD_PAID_ROLE_ID`; any one missing and it is a **no-op that never opens the pool**, which is both how the feature ships before the Discord application exists and how it is rolled back. Not a pass inside `cmd/billing-sync` even though it reconciles the same subscriptions on the same schedule: `billing` is `identity` (layer 3), this is `engage` (layer 7), and the layering guard forbids the import. `DISCORD_SYNC_MAX_PER_RUN` (default 500) bounds one run and loses nothing — the page is ordered by least-recently-synced, so a run that cannot reach everybody leaves the rest at the front of the queue. A per-account failure is counted and stepped over; only failing to read the work at all exits non-zero. **Which channels the role opens, and whether the bot may move it, are configured by hand in Discord** — see `freehire-ops`' `provision/host2/AGENTS.md` and [internal/engage/discordlink/AGENTS.md](../../../internal/engage/discordlink/AGENTS.md).
- `pro-welcome-mail` — welcomes an account the first time it becomes entitled to a paying tier (Pro or Ultra) with a one-time, personal email from the founder (Reply-To a human inbox, not the sending address — the same tone `internal/engage/onboarding`'s signup sequence uses, not the machine-toned digest mailer). Every 10 minutes, deliberately tighter than `billing-sync`/`discord-sync`'s hourly cadence: a purchase confirmation that arrives an hour late reads as broken in a way a Discord role does not. Resolves the tier the same way `discord-sync` does — `plan.TierOf` over `users.pro_until`/`ultra_until`, never a payment provider — and for the same layering reason lives in `internal/engage/prowelcome` rather than as a pass inside `cmd/billing-sync`: `billing` is `identity` (layer 3), this is `engage` (layer 7), and the layering guard forbids the import. Idempotent on `users.pro_welcome_sent_at` (nullable, stamped only after a successful send, never cleared) — a renewal, a tier change, or a lapse-and-resubscribe never re-sends it, which is deliberate: a returning subscriber is not a new one. A failed send is counted and stepped over, leaving the stamp unset so the next run retries — the opposite of `onboarding`'s own delivery, which burns the slot on a failed send because that sequence is a courtesy and this one is a payment confirmation. Needs `DATABASE_URL`, `AWS_REGION`/`NOTIFY_EMAIL_FROM` (the SES transport — a no-op that never opens the pool without them) and `ONBOARDING_REPLY_TO` (the same human inbox `cmd/onboarding` already answers from — a missing value here is a hard failure, not a soft-skip, because this letter asks for a reply). `PRO_WELCOME_MAX_PER_RUN` (default 200) bounds one run. See [internal/engage/AGENTS.md](../../../internal/engage/AGENTS.md).
- `cv-lifecycle-mail` — up to three letters to a verified free user whose CV parsed, on days 1 (ATS score and top gaps), 6 (potential score after tailoring) and 13 (the first-month offer) after the upload, until they pay or unsubscribe, plus the paywall letter: one letter, about an hour after a free user was refused by the paid-AI gate, naming the feature and the job and company when the hit has one (once per account, sent ahead of the CV letters, never to the holdout; `-step 4` previews it). Hourly is plenty — the paywall letter is due once its hit is `PaywallAfterMinutes` (60) old and goes out on the next pass after that, so the timer's cadence comes on top of the hour (a 10:01 hit on an hourly timer is sent at 12:00, not 11:00); each pass observes who has started paying, enrolls newly parsed CVs, and sends what is due. Needs SES (`AWS_REGION`, `NOTIFY_EMAIL_FROM`), `ONBOARDING_REPLY_TO` (it refuses to run without it), CV storage (`S3_*`) and `MEILI_URL`/`MEILI_MASTER_KEY` for the score. `CV_LETTER_PROMO_CODE` is letter 3's code: unset, or refused by `promo.Preview`, letter 3 is skipped and the others go out; the code is never stored or logged. `CV_LIFECYCLE_MAX_PER_RUN` (default 200) bounds a run. Flags: `-dry-run` counts and writes nothing; `-to ADDR -to-user ID [-step N]` sends one real letter for inspection and touches no table. **The traps:** a sender takes the shared one-letter-a-day claim (`mail_day_claims`, `internal/engage/maildaily`) before SES, so this worker leaves a letter pending when onboarding, the limit nudge or a broadcast got the account first; a definite send failure burns the step (re-arm by deleting its `cv_lifecycle_sends` row), a crash keeps the claim; "started paying" means a Stripe or RevenueCat tier, a granted one is `entitled` and is not a conversion — all in [internal/engage/cvlifecycle/AGENTS.md](../../../internal/engage/cvlifecycle/AGENTS.md). It exits non-zero when a send failed or an input could not be read. Its SES whole-run hold key is `cv-lifecycle-mail` (class lifecycle).
- `mentorship-remind` — sends the 24-hour and 1-hour reminders a booked mentorship session is due. Every 10 minutes. For each offset it takes the confirmed sessions starting inside a ONE-HOUR window ending at that offset, CLAIMS each reminder, and sends only the ones it won — the claim comes first because a worker that sends and then records sends twice whenever the second step fails, and on this schedule "whenever" is often. **The window is bounded at BOTH ends**: without a lower bound the 24-hour reminder fires for a session three hours away and calls it "in 24 hours", so a session booked closer than an offset simply never gets that reminder. A session already STARTED is never reminded about — a late run does nothing rather than catching up, and the timer is therefore `Persistent=false`, unlike the reconciling workers beside it. A failed DELIVERY releases its claim so the next run retries: a missing reminder costs somebody the session, a duplicate costs them a duplicate. Needs `DATABASE_URL` and the mail configuration, and **the unit must read `/opt/freehire/.env.notify` as well as `.env`** — without the mail credentials it is a no-op that never opens the pool, which would otherwise mean every run exiting 0 having reminded nobody, indefinitely. `MENTORSHIP_REMIND_MAX_PER_RUN` (default 500) bounds one run per offset. The same run reminds buddy mock interviews (`buddy.MockService.SendDueMockReminders`: same offsets, windows and claim order); a failure in one pass does not skip the other, and the run exits non-zero if either could not read its work. See [internal/engage/mentorship/AGENTS.md](../../../internal/engage/mentorship/AGENTS.md) and [internal/engage/buddy/AGENTS.md](../../../internal/engage/buddy/AGENTS.md).
- `message-notify` — tells people about conversation messages they have left unread, for every messaging kind (today only interview buddies). Every 5 minutes. A participant is due once the oldest message another participant wrote since its read cursor is five minutes old, and is not due again until it has read and a newer message ages the same way (`conversation_participants.notified_at` is compared with that message, not cleared on read). Open conversations notify every participant, a pending one only those who did not start it, so a starter is never told about their own request; declined and closed never. **Claim first**: the participant's stamp is moved before anything is sent and only the run that moved it sends; when every channel fails the claim is released (on a context the run's own cancellation cannot kill) so the next run retries, and one channel succeeding counts as sent. Delivers by email (honouring the `activity` mail group), Telegram when linked, and a notification-center row, worded by the conversation's kind. **The notice carries no message text and no account detail** — only that a message or request is waiting and a link (for buddies, `/buddies/chats?c=<id>`). A failed delivery exits non-zero. Needs `DATABASE_URL`, `AWS_REGION`/`NOTIFY_EMAIL_FROM`, `FRONTEND_ORIGIN` (https, or it refuses), `JWT_SECRET` (32+ bytes, or it refuses); `TELEGRAM_BOT_TOKEN` optional; **the unit must read `/opt/freehire/.env.notify` as well as `.env`** — without the mail transport it is a **no-op that never opens the pool** and exits 0. `MESSAGE_NOTIFY_MAX_PER_RUN` (default 500) bounds one run. See [internal/engage/messaging/AGENTS.md](../../../internal/engage/messaging/AGENTS.md).
- `mentor-busy-sync` — reads every mentor who has opted in to busy-time sync's Google Calendar free/busy state and reconciles it into `mentor_busy_intervals`, the table the slot engine has read since migration 0145 and nothing wrote to until now. Hourly, offset from `cal-sync`/`gmail-sync`. Each run replaces the WHOLE 60-day forward window per mentor in one transaction (delete then re-insert), never a row-by-row diff — the table holds only bounds, no title or attendee, since Google's `freeBusy` endpoint (not `events.list`) has nothing else to offer. Best-effort per mentor: a revoked grant marks `needs_reconsent` and the run continues; a non-revocation failure (Google having a bad day) never touches that flag, since it is SHARED with the account's other Google grants. Needs `DATABASE_URL`, the Google OAuth client, and `GMAIL_TOKEN_KEY` — without them it is a no-op that exits 0. See [internal/engage/mentorship/AGENTS.md](../../../internal/engage/mentorship/AGENTS.md).
- `email-events` — drains the SES engagement queue into `email_events` and reduces rows past 90 days to `email_event_daily`. Every few minutes. Without `EMAIL_EVENTS_QUEUE_URL` it runs retention only. Stores no recipient. See [docs/agents/notifications.md](../notifications.md#engagement-tracking).
- `social-digest` — publishes the day's ten most-viewed postings to the configured social channels (today: a Discord webhook), one post a day per channel, rotating through themed tops by weekday (`socialdigest.ThemeFor`). **Ranks on `job_daily_views.page_uniques`, never on `uniques`** — `uniques` fuses bot-filtered page opens with unfiltered API reads, and crawlers are most of this host's traffic, so a list built on it publishes what robots fetched as though it were what people liked. **The day is discovered, not computed**: it reads the freshest day `job_daily_views` holds, because whether `cmd/rollup-views` (rotated logs) has yesterday or the day before depends on the host's logrotate timing; a freshest day more than 3 days old fails the run rather than publishing something stale. `-dry-run` renders each channel's real payload and sends nothing. **The view floor was 10 and is now 3**, lowered 2026-09-08 against a measurement: on 2026-09-07 exactly ONE posting in the catalogue cleared 10 and the best scored 12, so the floor was not selecting the popular from the ordinary, it was emptying the list. Revisit it upward as page traffic grows. The quarantine window (7 days) is still a guess. `-day YYYY-MM-DD` replays one day. Idempotent on `(day, channel)`, so a re-run publishes nothing twice and a run that posted to one channel and failed on another retries only the second. Needs `DATABASE_URL` and `FRONTEND_ORIGIN`; a channel with no credentials is skipped, and with none configured the run is a clean no-op. **The second channel is our own LinkedIn company page** (`LINKEDIN_CLIENT_ID` / `LINKEDIN_CLIENT_SECRET` / `LINKEDIN_REDIRECT_URI` / `LINKEDIN_ORGANIZATION_ID` — all four or the channel is off). Its access token is NOT configuration: it expires every 60 days and lives in `social_tokens`, put there by `cmd/linkedin-auth` and renewed by `cmd/linkedin-token-refresh`. See [internal/engage/socialdigest/AGENTS.md](../../../internal/engage/socialdigest/AGENTS.md).
- `linkedin-auth` — **run by hand**, roughly once every sixty days: grants, records and inspects the credential the digest posts to LinkedIn with. `-url` prints the address to open in a browser, `-code <value>` exchanges what that browser handed back, `-token <value>` stores one minted in the Developer Portal's own token generator instead, `-status` reports what is stored and when it dies (never the token itself). Not a route on purpose — a sign-in flow for an audience of one, whose authorization would then be whatever that route's turned out to be; a command needs SSH, which is authorization we already have. **The exchange is also the only way to learn whether LinkedIn issued a refresh token**, which decides whether the credential renews itself or needs a person; it logs the answer explicitly. Needs `DATABASE_URL` and the four `LINKEDIN_*` values.
- `linkedin-token-refresh` — daily: renews that credential a fortnight before expiry when LinkedIn permits it, and warns when it does not. Both paths ship because programmatic refresh tokens go to approved Marketing Developer Platform partners only and the Community Management API is not that program — so a null refresh token is the EXPECTED case, not an error. **A warning is a published gauge, not a red unit**: this fleet already runs ~37 permanently failing ingest units, so a non-zero exit repeated daily for two weeks trains an operator to ignore it. `freehire_social_token_expires_in_seconds`, `freehire_social_token_grant_expires_in_seconds` and `freehire_social_token_renewable` go to the node_exporter textfile collector when `PROM_TEXTFILE_DIR` is set (negative seconds mean "no credential stored", which must not look like a broken exporter). A non-zero exit is reserved for a credential that is ALREADY dead. Needs `DATABASE_URL` and the four `LINKEDIN_*` values; without them it is a no-op that never opens the pool. See [internal/engage/linkedinauth/AGENTS.md](../../../internal/engage/linkedinauth/AGENTS.md).
- `sweep-tracer-clicks` — daily: deletes CV tracer-link clicks (`cv_link_clicks`) older than `TRACER_CLICK_RETENTION_DAYS` (default 180, read through the strict worker reader). The privacy policy promises those records are gone after 180 days, so it **deletes by default** — there is no dry run, because a retention promise that only reports keeps nothing. The tracer tokens stay: an old PDF must keep redirecting. Idempotent, so a missed or repeated run costs nothing. Needs only `DATABASE_URL`.
