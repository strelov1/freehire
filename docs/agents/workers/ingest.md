# Worker commands: ingest and the job lifecycle

Part of the [worker index](../workers.md): what each `cmd/<name>` worker does, when it runs, what it needs, and the trap behind it. Crawling boards, closing and re-checking postings, apply forms.

- `ingest` — takes one PROVIDER NAME: `go run ./cmd/ingest <provider>` (or `INGEST_PROVIDER`), and reads that provider's live boards from the `boards` table. Handing it a file path is not an error — the path becomes the provider it looks up, which finds nothing, logs `providers=0` and exits 0. **`INGEST_RUN_TIMEOUT_SECONDS` (the unit's own timeout) gives the crawl a deadline `INGEST_SWEEP_RESERVE_SECONDS` (default 600) short of it**, so the stale sweep still runs when the crawl overruns — the scheduler passes it on every launch; a static unit must set it itself, net of any slot wait, or its crawl stays unbounded and a timed-out run sweeps only in the 90s after SIGTERM. A run stopped early closes through the board scope only (see [docs/agents/job-lifecycle.md](../job-lifecycle.md) (1c)). `HYDRATION_RETRY_DAYS` widens the window (default 14 days, measured from `created_at`) during which a stored row with NO description is withheld from the seen-set so a hydrating adapter re-attempts its detail fetch. Set it only for a deliberate repair run — `HYDRATION_RETRY_DAYS=365 ingest hh` re-offers every body-less row of that provider, one extra detail request each (hh's detail pages are ~1 MB), and expect to repeat it: a run that hits its timeout still persists what it hydrated and the fixed rows leave the set, so successive runs shrink the backlog. An unparseable or non-positive value fails the run rather than falling back, because a typo here would look exactly like a repair that found nothing. **`INGEST_REFETCH_ALL=1` empties the seen-set for the run**, so every listed posting is treated as new and the pipeline re-WRITES it instead of only refreshing its liveness. That is the repair path for an adapter fix that changes what the LISTING yields (a mis-read remote flag, a location built from the wrong place): the fix reaches new postings on the next crawl and reaches the stored ones never, and `backfill-derive` cannot recover them either — it re-derives FROM the stored columns, which hold the wrong reading. Costs one detail request per stored posting (nofluffjobs: ~19k postings, ~20 min at 8 workers), re-enqueues only what actually changed for search, and re-enqueues nothing for enrichment (that queue is gated on `enrichment_version`, not on the write). A failed detail fetch cannot wipe a body — `UpsertJob` keeps the stored description when the incoming one is empty — so a run that hits its timeout is simply repeated. **`BODY_REFRESH_DAYS` re-reads a stored body that has gone stale**, so an employer's later EDIT reaches the catalogue at all: a hydrating adapter fetches detail only while the catalogue lacks the posting, so once stored a body is never read again and a posting that gains a "this position is 100% on-site" paragraph keeps whatever we read the day we first saw it (freehire#2555). It ships UNSET, which is disabled — turning it on costs one detail request per re-read posting against a crawl fleet that is already the host's bottleneck, so enable it one provider at a time and watch the load — in `/opt/freehire/ingest-env/<provider>.env` on the crawl host, which the scheduler hands each run of that provider after the shared `.env` (a value there wins; no file, no change). Putting it in the shared `.env` turns it on for the whole fleet. `BODY_REFRESH_SLICE` (default 30) bounds one run: a posting belongs to one slice for its life and a run takes the slice named by the day of the year, so a full sweep takes SLICE days and no run faces a provider's whole catalogue (1.27M postings on workday). Setting the slice without the days fails the run rather than doing nothing. What records a body's age is `job_activity.hydrated_at`, written by both ingest write paths and NOT by the liveness-only `TouchJob`; `updated_at` cannot serve, because the cheap write deliberately leaves it alone and a body that came back identical is the common case. **An adapter fix that changes what the DETAIL yields needs an entry in `detailFieldAdded` (`internal/ingest/sweep/body_refresh.go`)**: it re-reads that provider's rows hydrated before the fix, a seventh a day for three weeks, with no operator step (freehire#4124). A fix to what the LISTING yields stays `INGEST_REFETCH_ALL=1`'s job. **`INGEST_RECENT_DAYS=<1..30>` starts a recent-only run** for sources that can filter by date (`sources.RecentSource`; Adzuna today): it reads only the last N days, so new postings reach the catalogue between full crawls. Pair a frequent recent run with a rarer full one — the full run is the only one that finds removals. A recent run closes nothing (the sweep is skipped outright), records no `board_health` success, yield or failure (so `close-chronic-boards` never reads it), skips cooldown recovery, and skips and counts (`recent_unsupported`) every board whose adapter has no date filter rather than crawling it in full. Unset is a full crawl; a bad value fails the run. The scheduler does not launch recent runs: operators own that schedule. A new adapter joins only in its own change, with a cited and live-verified date parameter — see [internal/ingest/sources/AGENTS.md](../../../internal/ingest/sources/AGENTS.md).
- `close-chronic-boards` — dry-run-first safety nets for unreachable, empty-feed, and explicit board-gone evidence. `--apply`, `--apply-empty-feed`, and `--apply-board-gone` arm those passes independently; `BOARD_GONE_CLOSE_WINDOW_DAYS` controls the board-gone age window (default 7 days). See [job-lifecycle.md](../job-lifecycle.md) for the evidence and close reasons.
- `capture-apply-form` — drains the apply-form capture queue: fetches each queued posting's application form from `greenhouse`/`ashby`/`workable`/`lever` and stores it in `apply_forms`. Needs nothing but `DATABASE_URL`; `APPLY_FORM_CONCURRENCY` (default 4) bounds how hard one run leans on a platform and `APPLY_FORM_MAX_PER_RUN` (default 5000) how much of the backlog it takes — the second matters because the first drain faces a ~185k backlog and an unbounded run would work for hours, which `Type=oneshot` turns into silently skipped timer firings. `recruitee` forms never reach this queue — its listing carries them, so ingest writes them directly.
- `auto-apply` — drains `auto_apply_queue`: resolves a candidate's known profile answers against a job's live application form via a headless Chrome (`internal/api/atsapply`, `chromedp` — no second language or process) and submits only when every required question is answered; otherwise it touches nothing on the page. Needs `DATABASE_URL`, a Chrome/Chromium binary on the host, and (to fill the résumé field at all) a `TYPST_BIN` the CV renderer resolves — an entry only ever reaches this worker with an approved tailored CV attached (`openspec/changes/auto-apply-tailored-resume`), rendered on demand to a temp PDF; nothing else it fills needs `S3_*`, which stays read-but-not-required. The queue is populated by the job page's auto-apply button and by the signed-in MCP server's `auto_apply_start` tool (behind the account's `agents_may_apply` switch, `openspec/changes/auto-apply-over-mcp`); every queue UPDATE lands in `auto_apply_events` through a trigger, while the deletes (submission, cancel) and a retry write their own event in the same statement — a new delete path must too — and a stopped attempt is re-armed by the candidate's retry, never by this worker. See [internal/application/autoapply/AGENTS.md](../../../internal/application/autoapply/AGENTS.md) and [internal/api/atsapply/AGENTS.md](../../../internal/api/atsapply/AGENTS.md).
- `liveness` — closes stale postings through source-specific evidence, with an advisory lock preventing concurrent runs. Needs `DATABASE_URL`; closures queue their search removals atomically. Instaffo, Remote.com, The Hub and Reed each get a paced status-only pass over at most 500 stale postings per run, spaced two seconds apart. These passes require the posting URL to retain its host and path, stop on 403/429, and use the existing two-strike closure rule. The other evidence readers, age fallback and source eligibility are described in [job lifecycle](../job-lifecycle.md). A manual `-job-ids=1,2` run probes only up to 500 distinct positive IDs, intersected with `-source` when set. It preserves source eligibility, the registered-source staleness gate and two-strike confirmation, and skips every bulk deadline/age closure.
- `adzuna-liveness` — closes the adzuna and wellfound postings the source itself has taken down (it began with adzuna and kept the name, since the binary and its crawl-host unit are deployed under it). Neither existing close reaches them: Adzuna's feed is far deeper than the crawl's request budget (157k US it-jobs postings in 14 days, 750 read per run), so "unseen" there is not evidence, and `cmd/liveness`'s age rule is a guess Adzuna's own retention defeats (57% of its live US feed is older than 21 days). Adzuna's hosted `/details/<id>` page IS evidence — 404/410 for a removed posting, 200 with a JobPosting block for a live one — but sits behind a challenge about nine requests in ten fail, so each posting is retried from up to 25 exit IPs through the Scrapling tier's rotating proxy. A run samples `ADZUNA_LIVENESS_MAX_PER_RUN` (default 2000) open postings unseen for 3+ days in RANDOM order, because an unanswered probe leaves the row untouched and a fixed order would hand every run the same unanswered rows. Closes on ONE 404/410 (`closed_reason = 'probe_expired'`): it is Adzuna's own statement, and a posting the crawl lists again is reopened by it. **Runs on the crawl host**, where Scrapling listens on loopback — not on fsn beside `cmd/liveness`; without `SCRAPLING_FETCH_URL` it is a no-op that never opens the pool. First measured run (2026-10-23, 50 postings): 41 closed, 7 live, 2 unanswered, 98 s. **Wellfound** runs in the same worker, side by side with adzuna: its role-slice crawl is swept by company, so a posting whose company left every slice is out of every run's scope (measured 2026-10-30: 954 open postings unseen since mid-September, 20 of 20 sampled answering 410 on Wellfound's own page). Its page is the STORED url and never one rebuilt from the id — Wellfound answers 404 for a live posting asked for without its title slug — so a row whose url does not name exactly its own posting id is skipped. One request in flight, like the crawl's own cap, at most `WELLFOUND_LIVENESS_MAX_PER_RUN` (default 1000) a run.
- `hydrate-adzuna-description` — drains the Adzuna full-description capture queue (`cmd/ingest` enqueues eligible postings; see [internal/ingest/sources/AGENTS.md](../../../internal/ingest/sources/AGENTS.md)). `ADZUNA_DESCRIPTION_MAX_PER_RUN` (default 500) is deliberately conservative — untested against Adzuna at real crawl-host volume. `seed-adzuna-description-queue` is the one-off companion that queues the pre-existing backlog; run it once, then let the cron drain handle the rest.
- `close-chronic-boards` — the safety net for a board (or boardless provider) that has proven unreachable for a long time, not merely cooling down from a recent run of failures (issue #2017): the ordinary per-run unseen sweep never closes a board's jobs unless that run proved it covered the board (`shouldSweep`/`boardQualifies`/`sweepableCompanies`), which is correct against a transient failure but leaves a permanently broken board's jobs open forever, since it can never re-qualify. `board_health.ListChronicBoards` answers two separate windows off the same evidence (`last_success_at`, or `first_seen_at` for a board that has never once succeeded): `CHRONIC_BOARD_WINDOW_DAYS` (default 30) is what `cmd/ingest`'s per-run health summary reports for curation — fix the adapter, retire the board, or wait; `CHRONIC_BOARD_CLOSE_WINDOW_DAYS` (default 60, deliberately longer, giving a curator the gap between the two to act first) is what this worker acts on, closing the board's own open jobs with `closed_reason = 'board_unreachable'` — distinct from the sweep's `'unseen'`, so the two are never conflated. Scoped to exactly the `(provider, board)` health record that qualified: a multi-board provider's other boards are untouched; a boardless provider's single record already stands for its whole crawl, so going chronic there closes the whole provider. **Refuses a region-ambiguous board name outright** — a board id repeated per region for one provider (e.g. Adzuna's `it-jobs` once per country) has no region in `jobs.external_id`, so a board-scoped close cannot tell one region's postings from another's; such a board is skipped and counted separately in the run's report rather than risking a healthy region's jobs, the same refusal the ordinary sweep's `ambiguousRegionBoards` already makes. **Dry-run by default, reporting what it would close; `--apply` writes** — ships dry-run-only on its timer until a human has read at least one full closure window's report (`freehire-ops' provision/host2/systemd/freehire-close-chronic-boards.service`'s own comment is the reminder to flip it). Idempotent (`closed_at IS NULL` guarded) and cheap regardless of when it runs — daily. Needs only `DATABASE_URL`. **A SECOND pass in the same worker closes the opposite failure**: a board whose crawls all SUCCEED and whose feed carries nothing. `last_success_at` cannot see it — an empty-but-reachable feed refreshes that column on every single run, leaving `consecutive_failures` at 0 and the unit green — so `board_health.last_yield_at` (migration 0158) records when a board last actually YIELDED a posting, written only by a crawl whose LISTING named one (`pipeline.boardListedAnyPosting` — ingested, rejected, already-covered, unreadable OR failed-to-save, deliberately the most generous reading available and deliberately NOT the `boardReachedPostings` permission gate beside it: there, false costs a crawl cycle, but stamped here false accumulates into "this feed is empty" and eventually CLOSES, so a board whose listing works while its detail requests all fail would lose every live posting on it). `EMPTY_FEED_CLOSE_WINDOW_DAYS` (default 30, deliberately SHORTER than the unreachable window — that one waits out a problem on OUR side, this one has already been answered successfully on every run) closes with `closed_reason = 'feed_empty'`, a third distinct label because "every crawl succeeded and there was nothing there" points at the source's inventory while `'board_unreachable'` points at our access. The pass refuses a board with NULL `last_yield_at` permanently: that means no yield has been OBSERVED, not that the feed is empty, and it was true of all 155k rows the day the column landed — which is why **migration 0158's backfill (`last_yield_at = last_success_at`) is load-bearing, not cosmetic**, and why nothing can be closed by this pass until it has been observably empty for a full window AFTER that migration. Found by the WhatJobs incident of 2026-09-10: a market's publisher account was emptied, 107 postings sat open for a month, and neither existing net could reach them.
