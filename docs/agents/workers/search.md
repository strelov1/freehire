# Worker commands: enrichment and search

Part of the [worker index](../workers.md): what each `cmd/<name>` worker does, when it runs, what it needs, and the trap behind it. The enrichment queue, the Meilisearch and facet indexes, search announcements.

- `enrich` / `tg-extract` — need `LLM_BASE_URL` / `LLM_API_KEY` / `LLM_MODEL`.
- `search-drain` / `rollup-facets` / `reindex-companies` — need `MEILI_URL` / `MEILI_MASTER_KEY`. `embed` never touches Meilisearch: it embeds through the TEI backend at `EMBED_URL` (empty = the default host2 TEI), with `EMBED_API_KEY` only for an authenticated endpoint. `search-drain` drains `search_outbox` (queued by `cmd/ingest`, atomically with each write) into the live facet index in batches — run it frequently (e.g. every 1-2 min); see [internal/search/searchdrain/AGENTS.md](../../../internal/search/searchdrain/AGENTS.md). **`FACETD_URL` (optional) mirrors every applied wave to facetd after Meilisearch accepted it, and `FACETD_WRITE_TIMEOUT` (default `10s`) bounds that write**: a facetd failure never fails or delays the Meilisearch path — the wave's job ids go to `facetd_outbox` and a retry pass at the end of the run re-sends their current state while facetd is ready; unset, nothing changes. `rollup-facets` (daily) rebuilds two snapshots: `insights_facet_stats` for `/open`, then `insights_skill_neighbours` — one engine query per described skill (the ones with a glossary page, read from `skilltag.Descriptions()`, one at a time, a few minutes) — which the `/skills/<slug>` pages read instead of a live skills facet count; that count costs 100-700 ms and a crawler sweep over cold glossary URLs starved the engine into 500s on 2026-11-07 and 08. A failure in the second pass leaves the first committed and the previous neighbours serving.
- `reindex` — rebuilds the Meilisearch jobs index. **Run it by hand, after a backfill that writes around `search_outbox` — it is no longer on a timer** (since 2026-11-05): every routine document change reaches the index through the drain, and [internal/search/searchdrain/AGENTS.md](../../../internal/search/searchdrain/AGENTS.md) lists the writers that make that true; a new one that skips the queue is a bug, not a reason to schedule the rebuild again. **`REINDEX_DEDUP=1` additionally refreshes the duplicate markers** (role clusters, aggregator suppression, fuzzy collapse) before the rebuild; without it the rebuild uses the markers the last dedup run left. Off by default since 2026-08-16: aggregator suppression alone measured ~23h against a 12h unit timeout, so the run was cancelled mid-dedup and never reached the rebuild — 3 days with zero successful reindexes. Run the dedup invocation on its own, rarer schedule. **`REINDEX_DEDUP_ONLY=1` runs just the marker passes and exits** — no Meilisearch client, no disk guard, no rebuild, so no need to pause `search-drain` for it. It is the scheduled half of `reindex` now that the rebuild is not: the marker passes queue every row they flip, so their result reaches search through the drain, and the same run queues the postings whose document changed with time alone (`EnqueueSearchTimeCrossings`: a reality-class age, an unseen window running out). Takes precedence over `REINDEX_DEDUP` if both are set. **The fuzzy pass works on `REINDEX_FUZZY_WORKERS` companies at once (default 4, strict reader) and RESUMES**: it walks the companies in sorted order, saves the last one it finished (the oldest unfinished, never the newest — freehire#2869) in `marker_pass_cursors` as it goes, so a run its unit's timeout kills is picked up by the next one after that company, and a run that reaches the end clears the point so the next starts from the top — before this, every run walked the same head of ~383k companies into its 4h timeout and the tail was never deduplicated. **A rebuild also writes the match sort's skill vectors** (`internal/dict/skillvec`), which grows the index by roughly 10 GB and makes the rebuild materially slower — the cost is HNSW graph construction, so it lands here and not on the incremental `search-drain` pushes. Schedule it deliberately, and note the embedder must be in the LIVE index settings before a binary that queries it rolls out — see [internal/search/search/AGENTS.md](../../../internal/search/search/AGENTS.md).
- `facetd` — the in-memory facet engine beside Meilisearch (`openspec/changes/facetd`, package [internal/search/facetidx](../../../internal/search/facetidx/AGENTS.md)). **Long-lived like `mail-ingest`** (`Restart=always`), not a cron worker, and it **needs no `DATABASE_URL`**: it serves `/facets`, `/distinct`, `/write`, `/rebuild/begin|push|commit|abort`, `/ready` and `/metrics` over HTTP, with no authentication, so it stays on localhost next to the API. Env: `FACETD_ADDR` (default `127.0.0.1:8095`), `FACETD_SNAPSHOT_PATH` (empty disables snapshots), `FACETD_SNAPSHOT_INTERVAL` (default `5m`; a snapshot is written only when the generation changed, atomically, and once more on SIGTERM), `FACETD_WAL_PATH` (default `FACETD_SNAPSHOT_PATH` + `.wal`; no snapshot path means no log). **An acknowledged `/write` survives a crash:** every batch is appended to the write-ahead log (length + CRC-32 + JSON) and fsynced BEFORE it is applied and before the 200; a write that cannot be logged is a 500 and is not applied. On start facetd loads the snapshot and replays the whole log over it (batches are per-job full replaces and marks, so re-applying ones the snapshot already holds is harmless); a torn last record is ignored with a warning, a bad record anywhere else keeps facetd not-ready and moves the log aside as `*.corrupt-<unix>`; a log without a snapshot is not an index and also stays not-ready. A successful snapshot rotates the log (temp file + rename) keeping only what was appended after the snapshot's index was captured. Metrics: `facetd_wal_bytes`, `facetd_wal_records`, `facetd_wal_replayed_total`, `facetd_wal_errors_total`, `facetd_write_batch_jobs`, and `go_*`/`process_*` for heap, RSS and GC (the unit's `MemoryHigh` counts page cache too, so compare it with `systemctl show -p MemoryCurrent freehire-facetd`, not RSS). Its callers read `FACETD_URL` (the API's facet client, `reindex`). **It is rebuilt by `reindex`, not by itself**: `FACETD_URL=http://127.0.0.1:8095 reindex` tees every batch into Meilisearch and facetd (a facetd failure is logged and aborts only facetd's rebuild, never the Meilisearch one; once Meilisearch is promoted, the run lifts the drain pause and rebuilds facetd alone once more, because the drain never replays the derived fields a full rebuild recomputes, such as `reality.class`), and `reindex -facetd-only` rebuilds facetd alone — no Meilisearch key, disk guard, drain pause, description vectors or outbox purge. **The trap: it starts not-ready (503) without a loadable snapshot**, and a corrupt snapshot is logged loudly and treated the same; the API's facet router then falls back to Meilisearch per request until a rebuild commits. `/write` batches that arrive during a rebuild are applied to the live index and re-applied on top of the rebuilt one at commit. **One rebuild at a time**: `/rebuild/begin` while one is open is a 409; a rebuild idle for 30 minutes (its `reindex` died without `/rebuild/abort`) is dropped by the next `/write` or `/rebuild/begin`, so its recorded writes stop growing. **A commit whose snapshot fails answers 500** although the rebuilt index is live: it is not durable until snapshotted, so rerun the reindex. Needs nothing else.
- `build-suggestions` — rebuilds the search box's suggestion dictionary: the posting titles the catalogue actually carries, plus the skill/category/company vocabularies, each with its open-posting count and how often visitors have searched for it. Needs `DATABASE_URL`, `MEILI_URL`, `MEILI_MASTER_KEY`; `SUGGEST_TITLE_FLOOR` (default 25) and `SUGGEST_COMPANY_FLOOR` (default 5) decide how much of the long tail becomes vocabulary. It writes a SEPARATE index (`suggestions`) through the same rebuild-and-swap the jobs index uses, so **it must not be scheduled on top of `freehire-reindexw`** — Meilisearch runs one serial task queue, and a swap queued behind a 2.5h rebuild holds a `Type=oneshot` unit open and looks like a hang. Daily at 06:45 UTC, in the clear window between reindex runs. A run that would produce an EMPTY dictionary refuses to swap: a catalogue yielding nothing is a failed measurement, not an empty catalogue. See [internal/search/AGENTS.md](../../../internal/search/AGENTS.md).
- `search-settings-drift` — checks whether the live Meilisearch jobs and companies indexes carry every sortable attribute, filterable attribute, and embedder the deployed binary may ask for, and publishes the gap count (`freehire_search_settings_drift_count`) via the node_exporter textfile collector. Every 5 minutes. It exists because a sortable/filterable attribute or an embedder rolled out in the binary before its settings patch reaches the live index turns every request for it into a Meili 400, which the search package maps to a 500 for every caller of the affected sort/filter/match ranking — not only the one who picked the new value, since a settings patch replaces `sortableAttributes`/`filterableAttributes` wholesale (see [internal/search/search/AGENTS.md](../../../internal/search/search/AGENTS.md), "Adding a sortable/filterable attribute" and "Skill vectors and the match sort"). It does not fix the ordering — settings-before-binary is still a human decision — it makes a gap visible on a schedule instead of by a caller hitting the 500 first. Read-only; it only reports the hazardous direction (a live index still declaring something the binary no longer asks for is never drift). Needs `MEILI_URL`/`MEILI_MASTER_KEY`, and is a **no-op that opens no Meilisearch connection** without `PROM_TEXTFILE_DIR` or `MEILI_MASTER_KEY`.
- `serve-probe` — samples ~500 random open postings (`SERVE_PROBE_SAMPLE`) and checks that every field a posting STORES reaches what it SERVES, publishing `freehire_serve_probe_gap{layer,field}` beside its denominator `freehire_serve_probe_stored` via the node_exporter textfile collector. Hourly. It exists because the opposite failure is silent: an empty value is omitted from the JSON and every endpoint still answers 200, so the ATS salary that only the enrichment write copied into the payload went unserved on 872,117 of 891,859 open postings until a user asked (freehire#3964). **Two layers, read differently**: `projection` runs `jobview.FromRow` over the row — a gap there is a code bug; `index` reads the live Meilisearch document — a gap there with none in `projection` means a reindex is owed. A posting with no document is counted apart, never as a field gap, under the reason it has none (`freehire_serve_probe_unindexed{reason}`): one of `search.WithheldBy`'s rules — the same predicate every index writer asks — or `missing` when none holds, which is the only one that means the index LOST a posting (or the drain has not reached it yet). Measured 2026-10-31 over 2,000 rows: 798 had no document, 699 for no category, 97 unseen, 1 no body, 1 missing — so the unsplit count read as a 40% loss while the real one was zero. A new served column belongs in `internal/search/serveprobe`'s rule table. A gap exits 0, the same rule `search-settings-drift` follows. Needs `DATABASE_URL`, `MEILI_URL`/`MEILI_MASTER_KEY`; a **no-op that opens nothing** without `PROM_TEXTFILE_DIR` or `MEILI_MASTER_KEY`. First run on prod (2026-10-31, 500 postings): projection 0 gaps; index salary 23/27, employment_type 1/103.
- `search-ping` — announces the newest job pages to the external search engines that accept being TOLD rather than waiting to be crawled: Google's Indexing API and IndexNow (Bing/Yandex/Seznam/Naver). Hourly. It exists because waiting does not work at this catalogue's size — measured 2026-09-14, Googlebot fetched **65 distinct job pages in a day** against ~690k in the sitemap, and Search Console's URL Inspection answers `URL is unknown to Google` for postings sampled from it (pages Google has never once fetched) while the site publishes ~14k new technical postings daily. **The budget is the design constraint, not the plumbing.** Google grants 200 publish calls a day by default, so this is deliberately a LEDGER (`job_search_pings`, migration 0162) and not an outbox: an outbox fed by `cmd/ingest` would grow without bound forever and its oldest row would never be reached, while recording what was SENT lets each run choose the newest eligible postings afresh. The day's remaining allowance is read back from that ledger because **the API offers no way to ask** — and the day is measured to midnight **Pacific**, where Google resets it, not UTC. Eligibility is what the search index admits — open, canonical, public, with a body and a resolved category, technical or NOT — and lives in the SQL beside the query, because the API's terms admit only `JobPosting` and `BroadcastEvent` pages and the penalty for anything else is the quota. **`is_tech` orders the budget, it does not gate it**: each run asks for the technical tier first and offers the postings beyond IT (healthcare, retail, logistics and the rest) only what that left of Google's day, so at 200/day the second tier waits until technical intake no longer fills it; IndexNow, unbounded, takes a full batch of each tier every run. Enrichment, embeddings and the social digest stay `is_tech`-gated — they cost money or speak for the brand. **Company pages are announced too, and only through IndexNow** — measured 2026-09-15 via the Bing Webmaster API, Bing holds **255,038** of this site's pages and its highest-impression ones are `/companies/<slug>`, answering the query shape "<company name> careers"; Google's own August data agrees, and bingbot crawls company pages half again as often as job pages. Google's Indexing API may NOT be told about them — it admits only `JobPosting` and `BroadcastEvent`, and the penalty for anything else is the quota — so `Engine.Accepts` declines that pass for Google and the runner skips it without reporting it. Eligibility is `companies.job_count > 0`, the same gate the sitemap uses; their ledger is `company_search_pings` (migration 0164) with no `kind` column, because a company page has one event and its URL survives its postings closing. **Each posting is announced twice** — once when it appears and once after it closes, both as `URL_UPDATED`: a closed posting's page stays at HTTP 200 with its `JobPosting` markup and a `validThrough` moved into the past, which is one of the three ways Google documents for retiring a posting, so a closure needs a re-crawl and `URL_DELETED` would be a misuse of the API against a live page. The two events SHARE one engine's daily allowance and **new postings take it first** — a new posting brings a visitor, a closure only tidies an index we do not own — so at 200/day the closure pass does nothing until the quota grows, which is correct. `SEARCH_PING_BATCH` (default 200) bounds one run per engine and per event (each tier of new postings counting as one); `GOOGLE_INDEXING_DAILY_BUDGET` (default 200) tracks an approved increase. An engine with no credential is skipped without error, and with neither configured the run is a **no-op that never opens the pool** — which is also the rollback. Google needs `GOOGLE_INDEXING_KEY_FILE` (a service account key ON THE HOST, not in `.env`, which cannot hold a multi-line value; the account must be an **owner** in Search Console, not merely a full user — a full user gets `Permission denied. Failed to verify the URL ownership.`). IndexNow needs `INDEXNOW_KEY`, whose matching `web/static/<key>.txt` is public by design; the worker fetches that file once at startup and refuses to run if the two have drifted, because IndexNow's own answer to a mismatch is a 403 on every submission. `-dry-run` prints the exact URLs and sends nothing. See [internal/job/searchping/AGENTS.md](../../../internal/job/searchping/AGENTS.md).
