# Worker commands: backfills and company data

Part of the [worker index](../workers.md): what each `cmd/<name>` worker does, when it runs, what it needs, and the trap behind it. One-off backfills and the company identity and logo workers.

- `backfill-derive` — re-derives every deterministic column (facets, `engagement`, `requirements_derived`, `role_fingerprint`, `company_slug`) in one keyset pass; it is the one pass to run after any dictionary, `internal/dict/engagement` or `reqextract` change. **It keeps a stored country and region** (and a set `work_mode`) as the structured signal, because many adapters state the country and the pass cannot tell theirs from a derived one — re-deriving it moved SEEK's "Perth WA" rows to the US and blanked ~16k SEEK/JobStreet rows; a row with no stored country is re-derived in full, and correcting a stored one is `INGEST_REFETCH_ALL=1`'s job. **Never `public_slug`**: that is a published URL minted once at insert, and re-deriving it from a title the source changed later 404'd every link to the posting — one run on 2026-10-19 moved 42,226 before it was stopped (freehire#3284). The job page resolves such a dead slug through its last eight characters (the shortcode, derived from `(source, external_id)` alone) and 301s to the current one; `BACKFILL_CONCURRENCY` tunes the pool. Follow with `REINDEX_DEDUP=1 make reindex` — that is what collapses newly-clustered reposts and unions their geography. **It is RESUMABLE, and that is not a convenience**: the pass walks 12.7M rows de-TOASTing a description each, which outlasts any sane unit timeout, and until freehire#2864 it had no resume point — `afterID` started at 0 every time. A hand-made transient `taxonomy-backfill-night` unit (`systemd-run`, so in `/run` and in nobody's git) therefore ran it nightly under `TimeoutStartSec=10h`, got killed about two thirds through, restarted at the first id the next night and never once finished — ~29h of CPU a night on the host whose bottleneck is the crawl fleet, while five merged dictionary fixes waited on it. `BACKFILL_DERIVE_FROM_ID` names the first id a run must DO — **inclusive** — and `BACKFILL_DERIVE_MAX` bounds how many rows it scans, **unset for unbounded, never `0`** (`worker.EnvInt64` refuses a non-positive value, so a typo cannot silently mean "scan nothing"). **`BACKFILL_DERIVE_CLOSED_WITHIN_DAYS` narrows the scan to the rows that can still reach the catalogue** — open postings, plus ones closed within that many days — which is what makes a dictionary fix affordable: measured 2026-09-23 the table holds ~12.7M rows against 1.9M open ones, so an unbounded pass spends ~85% of its ~30h on postings no search, sitemap or page will read. It is expressed in DAYS CLOSED and **not** as an open-only flag on purpose: a closed posting is not permanently gone, since ingest's `Toucher` refreshes liveness "(last_seen_at, reopen if closed) ... WITHOUT rewriting its content" and a posting that merely drifts out of a feed for 48h is routinely closed and reopened as it drifts back (see the notes in `sources/seek.go` and `sources/whatjobs.go`) — so a pass that skipped on `closed_at IS NULL` would hand those rows back to the catalogue carrying the OLD dictionary's facets, with nothing downstream reporting the staleness. **A reopen now re-derives the row itself** (`internal/ingest/rederive`, the same function this pass runs): ingest's `Touch` reopens a closed posting and re-derives it in ONE transaction (`TouchJob` defers the reopen to it), so a failed re-derive leaves the row closed for the next crawl rather than open on stale facets, so a posting closed longer than the window still comes back on the current dictionary — company slug and fingerprint excepted, which only this pass moves. The number is how far back a posting might still return from; unset keeps the whole table, so the cautious behaviour stays the default and the knob is the deliberate act. A run that stops early says so in as many words and prints the id to continue from — from ONE report every exit path reaches, because deciding that at each `return` is what made the cursor vanish twice in one evening: the scan failing is only one ending, and the companies reconcile that follows it is two more (freehire#2876); a run that reached the end prints `done`, so "there is more" and "that was all" are never inferred from a row count. **The resume point is the oldest row the run did not FINISH, never the newest row its reader read** — the two differ by up to a full page and that gap is silent data loss: `jobsCh` is buffered at `backfillBatchSize`, so the reader hands over a whole page and advances its keyset cursor past it long before a worker writes any of it, and the review that caught this measured a cursor of 500 while id 5 was still unwritten (freehire#2869). A row whose write failed is deliberately left unfinished so the resume point falls before it. Re-reading what an interrupted run had in flight costs nothing, since the write is `changed`-guarded. **There is no timer** — `freehire-ops' provision/host2/systemd/freehire-backfill-derive.service` ships without one, because systemd has nowhere to keep the cursor between runs and a schedule that cannot advance it re-derives the same first rows forever.
- `backfill-company-type-hint` — one-off: force-requeues the existing open postings of the companies in `enrich.CompanyTypeHints` (a small, hand-curated `company_slug → outsource/outstaff` map — there is no open dataset of IT outsourcing/outstaffing companies to import instead) back into `enrichment_outbox`, so the next `cmd/enrich` runs rewrite their `company_type` using the new "Known company type" prompt hint. A single job posting rarely states its employer's business model in so many words, so this field came back `null` for these companies far more often than the rest of the enum. Run once after adding an entry to the map — the ordinary `EnqueuePendingJobs` only re-queues rows BELOW the target enrichment version, which skips a company's postings already enriched under it. Idempotent (`ON CONFLICT`-guarded on `(job_id, target_version)`), so re-running before the drain finishes costs nothing. No `make reindex` is needed: `cmd/enrich` requeues each job on `search_outbox` in the same transaction as `SetJobEnrichment`, so the corrected values reach Meilisearch through the drain. Needs `DATABASE_URL`.
- `backfill-telegram-prefilter` — **run it after any change to the Telegram prefilter's markers**, which is what makes it recurring rather than one-off. `cmd/tg-ingest` decides a crawled post with `telegram.AdmitsPost` and, when it declines, `InsertTelegramPost` stamps `extracted_at` at INSERT time; nothing revisits that row. So a widened marker reaches NEW posts only, and the stored ones stay refused forever with nothing reporting it. Measured 2026-09-23 over the 15,203 posts the filter had declined: **96** (all `job_it_junior`) already matched the then-current markers and were merely crawled under an older set, and the Spanish `empresa:` marker that landed the same day left **6,335** more behind it — 42% of everything the filter had ever refused, real vacancies carrying a LinkedIn or Workday link. The pass keyset-walks the declined posts, re-asks the SAME rule the crawl uses — `AdmitsPost`, then the Jev vacancy judge when `TYPESAFE_API_KEY` is set — so it can never requeue what the next crawl would refuse, and clears `extracted_at` on the ones it admits. **Reports by default; `--apply` writes** — the markers are hand-maintained, and the per-channel breakdown in the report is where a widening that suddenly admits an unintended channel becomes visible. `BACKFILL_TG_PREFILTER_MAX` bounds one run, **unset for unbounded, never `0`**, through the same strict reader every one-off knob uses; a bounded run prints the `(channel, msg_id)` to continue from as the exact environment to set, and a run that reached the end prints `done`, so "there is more" is never inferred from a count. **`BACKFILL_TG_PREFILTER_AFTER_CHANNEL` / `_AFTER_MSG_ID` are what make that bound a bound rather than a trap**: a post the filter still REFUSES never leaves the predicate, so a second bounded run starting from the top rescans exactly what the first one rejected — and a dry run, where nothing leaves the predicate at all, repeats its report forever. That is the failure `backfill-derive` carried until freehire#2864, where `afterID` started at 0 every time. The two are ONE cursor and the run refuses half of it, because a channel with no message id re-reads that channel whole while an id with no channel lands on the first channel alphabetically, and neither looks like a mistake in the output. They are **EXCLUSIVE** — the first row done is the one after the key — and named `AFTER` rather than `FROM` for exactly that reason: the sibling passes' `BACKFILL_*_FROM_ID` is inclusive, and two knobs sharing a name and a shape while disagreeing about whether the key is done or to-do lose one row per hop. Idempotent and free to interrupt: the UPDATE repeats the read's predicate, so a post already requeued — or claimed by `cmd/tg-extract` since this run read it — changes nothing. **Needs no reindex**: a requeued post reaches the catalogue through the extractor's ordinary write path. Needs only `DATABASE_URL`. See [internal/ingest/telegram/AGENTS.md](../../../internal/ingest/telegram/AGENTS.md).
- `backfill-company-info-wikipedia` — periodic (daily, `freehire-backfill-company-info-wikipedia.timer`), unlike the backfills above it: fills `companies.tagline`/`company_info` for companies no curated company-info source has ever matched (the YC directory, an external company-info dump — see `openspec/specs/company-info/spec.md`), a population that keeps growing as ATS crawling discovers new companies rather than being a fixed historical backlog. Looks each eligible company up against Wikidata (`internal/job/wikicompany`, no API key, no billing) and accepts a match only when the resolved entity's own type data — walked transitively via `wdt:P31/wdt:P279*`, both a positive business/organization walk AND a negative geographic/administrative-entity exclusion (a same-named commune or country is rejected even when Wikidata's multi-parent hierarchy also places it under organization — found in production, not the design spike: `Lookup("Nissan")` first resolved to a French commune), never a keyword scan of the description. **Reports by default; `--apply` writes.** `WIKIPEDIA_BACKFILL_MAX_PER_RUN` (default 500, the deployed timer sets 3000) bounds one run — daily rather than the design's original "e.g. monthly" guess, once rollout measured the real backlog (~341k companies, 2026-09-09) and the real throughput (~3s/candidate against Wikidata's public endpoints); monthly would take years to make a dent. A per-company failure (a slow or erroring Wikidata request) is counted and stepped over, never fatal to the run, and is retried on the next one — the company is not marked checked. Idempotent by construction: `companies.company_info_wikipedia_checked_at` (migration 0154) records that a company was resolved — matched or rejected — so it is never looked up twice, the same shape `job_activity.hydrated_at` gives ingest. Never overwrites a `tagline`/`company_info` key another source already set. Needs no reindex: neither field is part of `content_hash` or a Meilisearch facet. Needs only `DATABASE_URL`.
- `backfill-catalog-history` — one-off: fills `catalog_size_daily` (the `/open` size chart, `GET /stats/catalog-history`) for the days before `rollup-stats` began recording the catalogue size. Replays today's `jobs` as daily created/closed flows over the listed set and adds back `pruned_jobs`, dated by id. Every row is `reconstructed` and never overwrites a measured day. `-pruned-share` is required: the removed prune also took closed postings and duplicates, so pick the share by comparing the dry run with sizes the site published at the time (the old hard-coded figures in git history). Reads go through `ANALYTICS_DATABASE_URL` (falling back to `DATABASE_URL`) and are full scans, so point it at the replica (operator's local Postgres); `--apply` writes through `DATABASE_URL`, the primary.
- `publish-logo-domains` — daily: writes the company-name-to-domain map `logo.freehire.me` consults, so a logo resolves by the employer's own domain instead of by a name string. Company logos are requested by NAME (`web/src/lib/logo.ts`), taken verbatim from whichever adapter ingested the row, and one employer arrives spelled several ways — `g2i`, `G2i` and `G2i Inc.` all carry `company_slug = 'g2i'`, and the first two resolved to an unrelated leadership-training firm **at HTTP 200**, so no consumer could detect it and fall back to its monogram. The proxy has accepted `?domain=` since it was written and folds it into its cache key (so a name that gains a domain gets a fresh key and the stale rendition simply goes cold — nothing to bust); nothing ever supplied one. **The fix is deliberately not at the call sites**: of ~25 places that draw a logo, roughly fifteen never see a company slug (the experience bank, search suggestions, community subjects, the tailored-CV list), so threading a domain would fix a third of the surfaces and leave the rest guessing. Covers the **17,859** of 239,879 job-carrying companies whose `company_info` records a website; the rest keep today's name guess, and `backfill-company-info-wikipedia` grows that population daily for free. A name two DIFFERENT companies share while disagreeing about the domain is **dropped, never resolved** — a wrong domain returns a confident logo belonging to someone else, which is the failure this removes. **The spellings query is a deliberate sequential scan** (53s, 412,648 rows): joining it to the companies that have a website is four times slower (200s), because the narrow plan drives 17,859 index searches fetching ~102 heap rows each at random — 1.59M blocks of random I/O against the seq scan's sequential read of the same heap. Fewer rows, more work. A run that would publish an **empty** map refuses to swap, the rule `cmd/build-suggestions` already follows. Needs `DATABASE_URL`; without `LOGO_DOMAIN_MAP_OUT` it is a **no-op that never opens the pool**, which is also the rollback. **The consumer is a different repository** (`freehire-logo`, whose `internal/domainmap` reads the file) that `release.sh` does not carry and that is copied to the host by hand — so this half alone changes nothing visible, and a half-delivered change looks exactly like a working one.
- `report-company-website-twins` — hand-run, read-only: lists the companies with open jobs that state the same website host (`company_info.website`, or `company_info.feed_website` where a source stated one and nothing curated did) while their names fold apart. These are merge candidates for a person to propose from the company page, and a moderator decides them (`internal/job/companyrelation`, see [docs/agents/company-identity.md](../company-identity.md)). It never merges anything, because a shared host is evidence and not a decision: one agency's branches share one, and so can a job board's many employers. Needs only `DATABASE_URL`. Hand-run reports are not in `release.sh`'s build list, so run it with `go run`.
- `merge-companies` — collapses the company slugs that are one employer written more than one way (`ringcentral` + `ringcentral-inc`, `dollar-tree` + `dollartree`). Most groups it finds by folding the NAME; the pairs no fold can reach — one employer whose own boards disagree about the name, `Exadel` beside `Exadel Inc (Website)` — come from the hand-written list in `cmd/merge-companies/curated.go`, which argues why a list and not a rule (`Intel` and `intel471` are different employers). **Reports by default; `--apply` writes.** `--min-jobs N` bounds a wave to the folded groups whose combined open jobs reach N, which is how the backlog is taken in reviewed passes (1000, then 100, then 10, then 1) rather than one 333k-row leap. Chunked and idempotent — the chunk statement selects rows still carrying the retired slug, so a re-run moves nothing and an interrupted wave resumes. **It does not queue its rows for search** — a facet-index push costs minutes per wave, so feeding a merge through `search_outbox` is hours of pushes — **so follow a wave (or a day of waves) with one by-hand `freehire-reindexw` run**: no timer rebuilds the index since 2026-11-05, and until the run a merged company under-counts its jobs without anything 404ing. `REINDEX_DEDUP` stays unset. Needs only `DATABASE_URL`. See [docs/agents/company-identity.md](../company-identity.md).
