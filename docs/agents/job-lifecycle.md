# Job lifecycle conventions

## Scope
The open/closed state of a job row, the six mechanisms that write `closed_at`, and the filtering semantics that depend on it.

## Always true
- A job is open while `closed_at IS NULL`. Closing is a soft state, and the lifecycle never deletes.
- Nothing hard-deletes jobs. `cmd/prune`, a former campaign that removed postings not belonging on an IT job board (archived in `pruned_jobs`), was retired once the catalogue became broader than IT. `closed_at` keeps meaning "the employer took this down".
- A closed row keeps its `public_slug`, enrichment, and `user_jobs` references, and reopens for free.
- List, search, and company surfaces filter `closed_at IS NULL`. Detail still serves a closed job (with `closed_at`) so links and history don't break.
- The ingest write stamps `last_seen_at` on every crawl — `RefreshUnchangedJob` when the posting is unchanged, `UpsertJob` otherwise; the post-run sweep closes a provider's jobs unseen for 48h.
- A reappearing posting reopens via the upsert.
- A board the run SKIPPED — in failure cooldown, or in the quiet pause of a board whose listing keeps coming back unchanged (up to 72h, see `internal/ingest/pipeline/AGENTS.md`) — is excluded from the company- and source-scoped sweeps (`Stats.SkippedBoards`). Its rows were not looked at, so their age since last seen proves nothing. The board-scoped close never reaches it anyway, since it acts only on boards the run finished.
- Self-closing sources (`jobtech`, etc.) are excluded from the unseen sweep — the feed's `removed` events are the authoritative close signal.
- The liveness worker closes only on positive evidence (two consecutive `expired` reads) and never reopens.
- A source carrying no close signal at all — no re-crawl, no feed, and a URL that outlives the vacancy — is closed by age instead: `telegram` today, at 45 days. It is the only close that rests on a guess.
- Every close records WHICH mechanism wrote it in `closed_reason`; a reopen clears it. Rows closed before that column existed carry `''`, meaning unknown, and are never relabelled.
- A board (or boardless provider) that has proven unreachable for a long time — not merely cooling down from a recent run of failures — is eventually closed by `cmd/close-chronic-boards`, a safety net separate from the ingest sweep: `closed_reason = 'board_unreachable'`.
- A board whose crawls all SUCCEED but whose feed has carried nothing for a long time is closed by the same worker's second pass: `closed_reason = 'feed_empty'`.
- An open posting its source has not shown for more than 14 days (`last_seen_at`) is **hidden from search, not closed** — see "The unseen safety net" below. It stays open, its page keeps serving, and it returns when its source lists it again.

## How it works
Closing is a soft state on one column (`closed_at`) written by six independent mechanisms, each covering a gap the others can't reach. Five of them close on evidence; the age rule (4) closes on a guess, which is why every close now records which one wrote it. The two safety nets, (5) and (6), differ from the rest in what their evidence is ABOUT: the first four read a posting, while (5) and (6) read a board's history and close on what the crawl has been unable to learn for weeks — (5) because nothing could reach the board, (6) because everything reached it and found nothing there.

**(1) Ingest sweep** (`cmd/ingest`, `CloseUnseenJobs`): for board sources, the ingest write stamps `last_seen_at` every crawl — the cheap `RefreshUnchangedJob` on the common path, `UpsertJob` for a new, edited or reopening posting. The post-run sweep closes a provider's jobs unseen for 48h — if a posting drops off a board we crawl, it closes. A reappearing posting reopens via the upsert (the `ON CONFLICT` path clears `closed_at`). The sweep runs per provider, and only for providers that ingested at least one job, so a total crawl outage can't mass-close a catalogue. It is scoped to the `company_slug`s the run actually crawled, so a partial or targeted run closes only the companies it saw — a deliberate under-close that *leaks the last postings of a company that vanished from the feed entirely* (its slug drops out of the crawled set), since the scope can't tell "company gone" from "company not reached this run". A recency-budgeted aggregator (`himalayas` pages only its freshest slice per run — see `internal/ingest/sources/himalayas.go`) leaks this way routinely, not just on a company's actual last posting: any company that ages out of that window stops appearing in *any* future crawl, so its slug never re-enters scope again.

**(1a) Board-scoped close** (`CloseUnseenJobsForBoard`, freehire#2328): the company scope above cannot retire a company whose LAST posting drops off a board the fleet still crawls — that company's slug never re-enters `company_slug`s, so its row leaks forever, not just until mechanism (2) catches it (board sources are excluded from the liveness probe; see (2) below). The board scope closes it directly, per board a run structurally proved it covered: the board's crawl did not fail (`Stats.Failed == 0` for that board, read directly off the run's own report rather than through `BoardHealth`'s tolerant health verdict — a streaming board that dies mid-crawl after partial progress is deliberately recorded as *healthy* there, but its `Stats.Failed` still carries the failure, and a board caught mid-crawl must not qualify), the board yielded at least one posting (`Ingested + Rejected + ATSCovered > 0`, deliberately excluding `Skipped` — a board whose every save is failing must not prove itself on the strength of those failures), the crawl READ the postings it listed (`boardReadWhatItListed`, below), the crawl was not cut short by the run's context ending (`Stats.Interrupted == 0`, below), and the entry names a board (a boardless entry has no board scope; `BoardPattern("")` would match the provider's whole catalogue). Every qualifying board of a run closes in ONE statement (`CloseUnseenJobsForBoards`, `LIKE ANY` over the boards' patterns), falling back to one statement per board only if that fails; one statement per board was ~50 ms a board over the crawl host's link to the database, enough for the unit's timeout to cancel 1,431 of one recruitee run's closes.

**(1c) The crawl deadline.** A run's unit timeout is a hard kill, and from 2026-10-18 — when the crawl moved a WireGuard hop away from the database — the large providers routinely outran it: 0 of 33 greenhouse runs, 0 of 31 smartrecruiters and 0 of 29 ukg runs reached the sweep, leaving ~307k dead workday postings open behind boards `board_health` called healthy. `cmd/ingest` therefore stops its crawl `INGEST_SWEEP_RESERVE_SECONDS` (default 600) short of `INGEST_RUN_TIMEOUT_SECONDS` — which the scheduler passes with every launch, and which a static unit must set itself, net of any slot wait — and runs the sweep on a context detached from the crawl's (and from the signal), bounded by the timeout. A board still in flight at the deadline is `Stats.Interrupted` and never qualifies for the board scope: it stopped at an arbitrary point, with no `Failed` to say so. A run whose crawl stopped early — deadline or signal — is **truncated** and closes through the board scope ONLY: the company and source scopes are skipped, because one company can span several boards of a provider and a deadline reaches the same leading boards every cycle, so a company written by a finished board would close its unreached boards' postings run after run with nothing re-crawling them to reopen them. A timed-out run used to sweep nothing at all, so this withholds nothing a run used to do; a provider without the `fullBoardListing` marker still sweeps only on a run that finishes.

**(1b) A posting the crawl could not read withholds both scopes for its board.** On the ATS adapters whose detail request is a posting's ONLY source and which are not hydrating (`jazzhr`, `icims`, `careerplug`, `jobvite`, `successfactors`, `breezy`, `bamboohr`, `smartrecruiters`), the detail is re-fetched for every stored posting on every run, and a failed one was simply dropped: `Fetch` returned a shorter list, `Stats.Failed` stayed 0, and the board was recorded healthy — so a posting unreadable across the whole 48h window was closed by both sweeps as unseen, dropped from the index and counted as a phantom removal. The adapter now tells the two apart (`sources.detailUnreadable`): a **404/410 is the platform saying the posting is gone** and is still dropped, so a board whose listing has gone stale can still be retired; anything else, including a 200 carrying no posting, becomes a `Job{Unreadable: true}` marker counted in `Stats.Unreadable`. When more than 5% of a board's yielded postings are unread, the run withholds BOTH close scopes for that board — the board scope via `boardQualifies`, the company scope via `Stats.UnprovenCompanies`, which `cmd/ingest` subtracts from the crawled slugs — while still writing everything it did read. It is deliberately not a board failure: that would cool the board to its 24-hour ceiling and freeze its whole catalogue over a per-posting hole. Hydrating adapters never hit this: a seen posting yields a `SeenRefresh` with no detail request at all.

None of that is sufficient on its own. A run can satisfy every condition above while its adapter still returns fewer postings than the board actually has — solidjobs' first attempt at this feature (#2337, reverted within 18 minutes after closing 110 live postings) is the proof: it reaches only the first 500 of a board's ~1,400 postings and reports that as an unqualified success. The fourth, load-bearing gate is `sources.fullBoardListing`: a provider's adapter must be *registered* as structurally proving it lists a board to completion — verifying a fetched count against the source's own reported total, or paginating to the source's natural end with no artificial page/offset cap — and treating any failure to establish that proof as a failed `Fetch`, never a partial success. A provider absent from `sources.FullBoardListingProviders()` never contributes to the board scope, however its crawl went. As of this writing the marker covers the Phase-1 wave of large ATS platforms (`workday`, `ukg`, `greenhouse`, `lever`, `ashby`, `workable`, `paylocity`, `careerplug`, `smartrecruiters`, `personio`, `recruitee`, `bamboohr`, `jazzhr`, `icims`, `successfactors`, `jobvite`, `breezy`, `eightfold`, `taleo`) and, since 2026-10-29, `paycom` — whose runs mostly meet their deadline, so before the marker a truncated run could close nothing of it at all; the rest of the registry — including `solidjobs`, kept as the marker's negative control — stays on the company scope alone until a later audit wave earns them the marker. Also excluded, even if registered: a `sweepGrace` provider (its crawl deliberately reaches only a slice, so a board-scoped close on the default window would close postings that merely drifted past the crawl's depth) and a `fullCatalog` provider (already closes by source alone on a clean run, strictly broader than board scope). The one way a `sweepGrace` provider enters the board scope is the opposite marker, `sources.sliceBoardListing`: an adapter that reads each board only as a bounded slice (`whatjobs`, a keyword read to a 40-page budget or until relevance collapses) and whose stored ids are still board-namespaced. Its finished boards close on the provider's GRACE window (14 days), never the default, so a posting that merely sat past the budget is back before the window ends. Without it a whatjobs posting closed only through the company scope, which leaked every posting whose company had drifted out of all the keyword slices — measured 2026-10-28, 5,835 of whatjobs-uk's 5,880 open postings unseen past 14 days belonged to a company no run that day wrote, and only (2c)'s 45-day age rule reached them.

**(1d) An emptied board closes through the board scope too, on adapters that can prove it is empty.** The yield condition above refuses a board whose finished crawl listed nothing, and the company scope cannot reach it either (a run that wrote nothing for a company never puts its slug in the crawled set), so an employer that took every posting down left its last postings open until the empty-feed net (6) closed them 30 days later — greenhouse `skedda`, ashby `umbrel` and `gruntwork` on 2026-10-29. `pipeline.boardListedEmpty` reports such a board apart (`Stats.EmptyBoards`: crawled, not failed, not interrupted, not skipped, and its listing named NOTHING — `boardListedAnyPosting`'s generous reading, so a board of unreadable or unsaved postings is not empty), and `cmd/ingest` adds it to the board scope on the ordinary window only for a provider carrying `sources.emptyBoardListing` on top of `fullBoardListing`. That second marker exists because `fullBoardListing` proves a listing was read to its END, not that an empty answer was a listing at all: a challenge page, a 200 error page, an envelope without its posting array or markup that stopped parsing all end a walk on page one and look exactly like an empty board. It is granted per adapter after checking the source's own answers: a non-2xx or an undecodable answer is already a failed `Fetch`, and the adapter must fail an answer that decodes without its posting collection (`errListingAbsent`) — only the collection present and empty is an empty board. As of this writing: `greenhouse`, `ashby`, `lever`, `workable`, `recruitee`, `breezy`, `bamboohr`. `smartrecruiters` is excluded on evidence — it answers an UNKNOWN company identifier with `totalFound: 0`, so its empty answer is also what a failed lookup looks like — and HTML-scraped listings are excluded by construction. Measured 2026-10-29: 9,797 boards of the large ATS providers had a latest successful crawl that listed nothing, with 5,772 open postings unseen past 48h on the seven granted providers' boards (workable 2,444, bamboohr 1,279, breezy 740, greenhouse 602, ashby 272, lever 244, recruitee 191; every board sampled live answered genuinely empty); `jazzhr` (3,654), `ukg` (2,178), `workday` (1,232), `paylocity` (1,121), `taleo` (620) and `icims` (493) stay on the empty-feed net until each is audited.

**(1e) A board id repeated across regions closes per region when the adapter can say where each region's postings live.** `external_id` carries no region, so `ambiguousRegionBoards` / `AmbiguousBoardNames` refuse a board name that appears under two regions of a provider — the LIKE pattern could not tell which region's crawl proved coverage. An adapter implementing `sources.RegionScopedBoards` (`jobstreet` today: subclass `6290` is a board in all six markets) is exempt: `Stats.QualifyingBoards`/`EmptyBoards` carry each board's region (`pipeline.BoardRef`), `sweepableBoards` keeps it, and `sweepBoards` issues one `CloseUnseenJobsForBoards` per region with a `url_pattern` of the region's posting-URL prefix (`sources.BoardURLPrefix`, LIKE-escaped by `externalid.LikePrefix`); every other provider passes `''`. Still region-blind: the skipped-board exclusion of the company and source scopes (`Stats.SkippedBoards`), so a quiet SG `6290` keeps `6290`'s rows in every market out of that run's company scope — the safe direction, and each market's own board scope reaches them once it is crawled.

The company scope is kept beside the board scope because it reaches what the board scope structurally cannot: boardless entries and every provider without the `fullBoardListing` marker. It does NOT reach a zero-yield board — such a board writes no company into the crawled set, so its postings close through the company scope only when another board of the run wrote the same company. An emptied board of a provider without `emptyBoardListing` therefore falls to the empty-feed net (6); mechanism (2) excludes registered providers and reaches none of them.

`CloseUnseenJobs`/`CloseUnseenJobsBySource` are single-statement bulk `UPDATE`s, so one row Postgres can't write (a corrupted index entry — see the 2026-08-11 incident, one duplicated `jobs_pkey` value) aborts the whole statement, leaving *every* closeable row in the provider open, silently, run after run. `cmd/ingest`'s `sweepRowByRow` is the fallback: on a bulk failure it re-fetches the same candidate set (`UnseenJobIDs`/`UnseenJobIDsBySource`) and closes each row in its own statement (`CloseUnseenJobByID`), logging and skipping whichever id still can't be written instead of blocking the rest.

**(1b) Full-catalogue source sweep** (`CloseUnseenJobsBySource`): a *full-catalogue* aggregator (`sources.fullCatalog` marker, e.g. `habr_career`, `geekjob`, `powertofly`) lists its whole catalogue every run, so an unseen job is genuinely gone — including the vanished-company case (1) leaks. For such a provider the sweep drops the `company_slug` scope and closes by source alone. Sound **only** because a full-catalogue adapter errors a *truncated* crawl instead of returning it as a partial success (`habr_career` fails any bad listing page; `geekjob` uses `crawlAllPagedLinks`): `cmd/ingest` gates the source-scoped close on a zero-`Failed` run (`sweepBySource`), so a mid-listing failure (`Failed>0`) falls back to the safe company-scoped close rather than mass-closing every posting past the failed page.

**(3) Stream-driven self-close** (`CloseJobBySourceExternalID`): a *self-closing* source (a streaming aggregator like `jobtech`/Arbetsförmedlingen that consumes an incremental change feed) emits a `Job{Removed: true}` for a posting its feed reports taken down. `pipeline.ingestStream` routes that to the Store's optional `closer` (the ingest `dbStore`), closing by `(source, external_id)`. Such a source implements the `selfClosing` marker and is excluded from the (1) unseen sweep (`sources.SelfClosingProviders`): it re-reports only changed ads, so the sweep's `last_seen_at` cutoff would wrongly close every still-open ad it did not touch. Trade-off: a missed run can leave an orphan open until a future reconcile; the change window is sized wide enough to absorb a skipped cron.

**(4) Age rule** (`cmd/liveness`, `CloseStaleUnsignalledJobs`): the probe cannot judge every orphan. A `telegram` job's stored URL is the post, which stays live after the vacancy is filled, so no fetch of it can ever read as dead — and no crawl re-visits it either. Such a source has no evidence to appeal to, so it is closed once its effective posting date (`COALESCE(posted_at, created_at)`) is older than 45 days, with `closed_reason = 'expired'`. The source list is passed in by the caller rather than derived from "whatever the sweep misses", so a new adapter can never drift into being closed by age; it is the same list the probe excludes, which keeps the two halves of one decision — what cannot be probed is expired instead — from separating. Strictly older than the cutoff, and it never reopens, because nothing re-crawls these rows.

**(2) Liveness probe** (`cmd/liveness`): board sources are not the whole catalogue — jobs from sources not in the `sources.All` registry (manual/`resolve-url` imports and the like) are never re-crawled, so the sweep can't reach them. (Aggregators like `habr_career`/`geekjob` *are* registered providers, swept by (1)/(1b) and excluded from the probe; `telegram` is excluded too, via `unsignalledSources`, because its URL outlives the vacancy — mechanism (4) closes it instead.) The liveness worker URL-probes those orphans, classifies the page via `internal/job/liveness` (pure heuristics — HTTP 404/410, error/listing redirect, curated EN/DE/FR closed-posting phrases, or near-empty content — no browser, no LLM), and closes a job after two consecutive `expired` reads (the `liveness_strikes` counter; any healthy probe resets it). It closes only on positive evidence and never reopens, biasing toward under-closing (an orphan has no re-ingest to reopen it). Run-once-and-exit, cron-scheduled.

**(2b) Backstop for a registered provider's scope leak** (`probeDespiteRegistered` in `cmd/liveness`): a source stays a normal registered provider — the sweep still owns its regular closes — but is *also* added back as a candidate, restricted via `SelectStaleRegisteredCandidates` to jobs already past the sweep's own 48h staleness window (mirroring `cmd/ingest`'s `staleAfter`), so it only ever picks up what (1) is structurally unable to reach rather than racing it. This is the shape shared by every boardless, recency-ordered aggregator whose crawl budget (a page cap, an offset ceiling, or a freshness window) is smaller than its live catalogue — `himalayas`, `echojobs`, `jobicy`, `remoteok`, and `hh` are members as of this writing (`hh` is board-scoped, one board per professional role, but every board is read only as its newest ~2000 postings of the last 7 days, so a posting older than that is never listed again). `empregos` joins them without a crawl budget: it reads every posting that names a state but cannot prove it read the location-less rest, so it is not `fullCatalog` and its sweep is company-scoped, with the same leak. `djinni`, `4dayweek` and `torre` joined on 2026-10-29, three boardless aggregators swept only by company: `djinni`'s listing names only about the last month of postings, `4dayweek`'s list feed omits a third of the postings its site still serves, and `torre`'s sitemap still names a few closed postings, so none is `fullCatalog`. Measured that day, 3.4k of djinni's 8k open rows, 21.5k of 4dayweek's 27k and ~250 of torre's 2.7k had gone unseen for more than a week, and nothing closed them.

Each member needs its own evidence path — there is no generic per-source plugin here, by design, since a GET probe is not guaranteed to work for any given source (`probeDespiteRegisteredGET` in `cmd/liveness/main.go` is the subset that *is* verified this way):
- `jobicy`, `remoteok`, `empregos`: the plain-GET probe already used for (2) works as-is — jobicy's job page answers a definitive `410` for a removed posting; remoteok answers `200` with a detectable "this job post is closed" banner in the body (`internal/job/liveness`'s `hardExpired` patterns); empregos redirects a removed posting to `/404`, which answers `404`.
- `himalayas`: its job page is Cloudflare-blocked (403 on every plain GET, verified from both a dev machine and prod, even with a browser User-Agent). `cmd/liveness/himalayas.go` instead downloads `himalayas.app`'s own sitemap (unprotected, ~114k URLs across 3 gzipped shards discovered from a `sitemapindex`) once per run and checks each candidate's URL for membership — real evidence (the site's own record of what is still live), not a guess, and one run-wide fetch instead of one request per candidate.
- `echojobs`: its stored `jobs.url` is the *employer's own* ATS link (Workday, Greenhouse, …), not an echojobs.io page — probing it inherits the reliability of whichever of ~330k postings' employer happens to be up. `cmd/liveness/echojobs.go` instead GETs echojobs.io's own server-rendered job page, keyed on the posting's `external_id`, and reads the plain HTTP status: `200` means still listed, `404`/`410` means removed — the same pair `internal/job/liveness`'s shared classifier treats as "gone" — and anything else is unverifiable rather than a false death signal. (An earlier version of this probe hit echojobs.io's JSON detail API and matched a distinguishable error body at `HTTP 500`; that API was retired and the probe moved to the page GET.)
- `hh`: `cmd/liveness/hh.go` GETs `https://hh.ru/vacancy/<id>` (the id from `external_id`) and reads the page's own `analyticsParams` flag — `"archived": "true"` is archived, `"false"` is live — while a `404` is deleted. It cannot share the plain-GET probe: every hh.ru page, live ones included, embeds the site's translation table and with it the string "Вакансия в архиве", which `Classify`'s RU banner phrase would read as a death signal on every live posting. hh's API (`api.hh.ru/vacancies/{id}`) answers `403 forbidden` to anonymous requests, so the page is the only evidence. hh.ru rate-limits by redirecting to a `200` captcha page, and the crawl reads hh's listing from the same host, so the pass probes ONE page a second, takes a sample of at most 1500 candidates per run, and stops at the first captcha or `429`. A `403` (measured on ~7% of stale postings, the same ids every time) is Uncertain, like every refusal.
- `djinni`: the plain-GET probe's evidence — a removed posting answers `200` with the alert "The job ad is no longer active" (one of `Classify`'s phrases) or a plain `404` — but paced like `hh`, since djinni answers a fast burst from a datacenter IP with `403` and the crawl reads it from the same host: one page a second, at most 1500 a run, stopping at the first `403`/`429` (`cmd/liveness/djinni.go`). Of 120 stale rows sampled on 2026-10-29, 94 carried the alert, 12 answered 404 and 14 were live, all posted more than a month earlier — which is why djinni carries `livenessProbed` (below).
- `4dayweek`: `cmd/liveness/fourdayweek.go` asks the per-posting API `/api/v2/jobs/<slug>` (robots.txt allows `/api/v2`; the slug comes from the stored url, since the API answers 404 for the UUID external id even on a live posting): `200` is live, `404`/`410` gone. It agreed with the job page on all 120 stale rows sampled (77 gone, 43 live) at ~7 KB a request against the page's ~250 KB. Cloudflare refuses every self-identifying client there, so it sends `sources.BrowserUserAgent`, and meters by IP, so it is paced too: one request a second, at most 3000 a run, stopping at the first `403`/`429`.
- `torre`: `cmd/liveness/torre.go` reads the posting page's embedded state, which assigns the opportunity's own status right after its `prefilledStatus` — `"closed"` is Expired, `"open"` Live. Torre serves a closed posting's page as a full `200`, so the status code alone says nothing; an unknown id redirects to `/404`, which answers `404`. Torre's API (`/api/suite/opportunities/<id>`) carries the same field in fewer bytes, but robots.txt disallows `/api/`. Paced at one page every two seconds (two requests a second drew `503`s); of 41 stale rows sampled, 36 were closed, 4 answered 404 and 1 was open.

The paced passes (`hh`, `djinni`, `4dayweek`, `torre` — `cmd/liveness/paced.go`) run side by side, each against its own site, and each run reads candidates that already carry a strike first, then a shuffle of the rest: a close needs two consecutive expired reads, and on a backlog several runs deep a struck row left to the shuffle would wait runs for its second.

**Which probed sources search still hides.** A probed source's adapter normally carries `livenessProbed`, which exempts it from the unseen safety net below: its crawl cannot re-list every live posting, so going unseen says nothing and the probe closes what is gone. Two members deliberately do not. `torre`'s sitemap IS the live catalogue, so a posting unseen for two weeks is gone and hiding it is right. `4dayweek` has the marker's shape but not yet the rate: ~16k of the ~22k rows it had stopped listing were dead (72% of 376 sampled) when the probe landed and the probe reads ~6k a day, so the marker would put them back in search for days — grant it once the backlog is worked off. `cmd/liveness`' `probedButWithheld` (in its tests) records both, and fails when either stops being true.

**(2c) Age fallback for a registered provider with no evidence at all** (`expireDespiteRegistered` in `cmd/liveness`, `CloseStaleUnseenUnprobeableJobs`): same company_slug/keyword-scope leak as (2b), but for a source (2b)'s "find *some* evidence" approach cannot serve at all. `whatjobs` is the member as of this writing: its `jobs.url` is the CPC ad network's own billing/tracking landing page, not the employer's posting, so it answers identically whether the underlying posting is live or long gone (see `internal/ingest/sources/whatjobs.go`). Rather than invent a signal that doesn't exist, `cmd/liveness` applies mechanism (4)'s same 45-day `expiryWindow` here — the same "what cannot be probed is expired instead" guess, just applied on top of a source the sweep otherwise closes on real evidence via its own extended `sweepGrace`. Kept as a separate list from `unsignalledSources` because the two guards are opposite: an `unsignalledSources` member must NOT be a registered provider (the age guess is its ONLY closer), while an `expireDespiteRegistered` member MUST be one (the sweep still owns the common case; age only backstops the tail it structurally can't re-reach).

It is a separate STATEMENT from (4) for the same reason, and the difference is a second clock: age alone is the only fact available for a source nothing re-crawls, but these sources ARE crawled, so the guess must not contradict what the crawl just saw. `CloseStaleUnseenUnprobeableJobs` additionally requires the posting to have gone unseen for longer than that provider's own `sweepGrace` — i.e. long enough that (1) would already have closed it had its `company_slug` scope been able to reach it. Until 2026-09-06 this path reused (4)'s age-only query, and because `whatjobs` leaves `posted_at` unset the 45-day clock ran from first ingest: every posting older than that was closed on one run and reopened by the next crawl through `UpsertJob`, twice a day, restamping `updated_at` (the sitemap's `<lastmod>`), recomputing its semantic chunks, and mailing everyone who had applied that their posting had closed.

**(5) Chronic-board safety net** (`cmd/close-chronic-boards`, openspec change close-chronically-unreachable-boards, issue #2017): mechanism (1)'s board/company scopes are correctly conservative against a TRANSIENT failure — they never close what a run did not itself prove it covered — but that guard has no upper bound. A board that is permanently gone (retired upstream, blocking us, moved) never re-qualifies, so its jobs stay open forever, silently, even though nothing can confirm they still exist. `board_health.ListChronicBoards` answers two separate questions off the same evidence — `last_success_at`, or `first_seen_at` for a board that has never once succeeded (`last_error_at` is overwritten every failed run and cannot say how long ago the FIRST one was): a shorter window (default 30 days, `CHRONIC_BOARD_WINDOW_DAYS`) is what `cmd/ingest`'s per-run health summary surfaces for curation, distinct from the ordinary unhealthy-board list; a longer one (default 60 days, `CHRONIC_BOARD_CLOSE_WINDOW_DAYS`) is what `cmd/close-chronic-boards` acts on. The gap between the two windows is deliberate lead time for a curator to retire or fix the board before the safety net would have closed it anyway. Scoped to exactly the `(provider, board)` record that qualified — a multi-board provider's other boards are untouched; a boardless provider's single health record already stands for its whole crawl, so going chronic there closes the whole provider, which is the correct reading of "this board's jobs" when there is no finer grain, not a broadening of the rule. A board id repeated across regions for one provider (`board_health`'s key is `(provider, board, region)` — e.g. Adzuna's `it-jobs` once per country) is refused outright rather than board-scoped: `jobs.external_id` carries no region, so a LIKE-pattern close on the board name alone cannot tell one region's postings from another's, and closing it could take a healthy region's jobs down with a genuinely dead one — the same refusal mechanism (1a)'s `ambiguousRegionBoards` already makes for the ordinary sweep. Such a board is counted as skipped in the run's report rather than silently closed or silently ignored, so it stays a curator's decision. Ships dry-run-only on its daily timer until a human has read at least one full closure window's report.

**(6) Empty-feed safety net** (`cmd/close-chronic-boards`'s second pass, migration 0158): the exact twin of (5), for the failure mode (5) structurally cannot see. Mechanism (5) measures `last_success_at`, so it catches a board nobody can READ — and is blind to a board that answers perfectly and has nothing IN it. That gap is not hypothetical: on 2026-09-10 a WhatJobs market's publisher account was emptied, every crawl returned HTTP 200 with zero results, `board_health` showed `consecutive_failures = 0` and a `last_success_at` refreshed on every run, and 107 postings stayed open for a month pointing at a feed that no longer carried them. Mechanism (1) could not reach them either — `shouldSweep` requires the run to have ingested at least one job, on the reasoning that "a run that ingested nothing proves only that the crawl failed", which is true of a broken crawl and false of a feed that answered honestly with zero — and the company scope it would have used is empty anyway, since a run that wrote nothing crawled no company. So `board_health.last_yield_at` records when a board last actually YIELDED a posting, written only by a crawl that reached one. **Being listed is not being written**: `pipeline.boardListedAnyPosting` counts ingested, rejected, already-covered, unreadable and failed-to-save postings alike — every outcome that proves the listing named something. Stamping on the ingested count instead would call an all-rejected board empty (the ordinary steady state of a non-tech-heavy national feed) and an aggregator board whose employers we crawl directly empty too (it can reach hundreds of postings and write none), then close their live jobs. It is deliberately NOT `boardReachedPostings`, the permission gate defined beside it, even though the two differ only by `Skipped` and `Unreadable`: there false means "this run may not prove coverage" and costs a crawl cycle, while here false accumulates into "this feed is empty" and eventually closes — so the two callers need opposite safe directions, and this one needs the generous predicate. The case that makes it concrete is a link-only adapter whose listing keeps working while its detail requests all begin failing: every posting becomes `Unreadable`, which is deliberately not `Failed`, so the board records success with a fresh `last_success_at` and would age into this net with every posting on it still live. `ListEmptyFeedBoards` then selects boards that are demonstrably REACHABLE (succeeded inside the same window, `consecutive_failures = 0`) and have not yielded for `EMPTY_FEED_CLOSE_WINDOW_DAYS` (default 30, deliberately shorter than (5)'s 60: (5) waits out a problem on our side that a curator might fix, while an empty feed has already given its answer, successfully, on every run). The close carries `closed_reason = 'feed_empty'` — a third label rather than a reused one, because each existing reason asserts something this close cannot: `'unseen'` claims the run proved coverage, `'board_unreachable'` claims the opposite diagnosis and would send an operator to check our access rather than the source's inventory, and `'feed_removed'` is a streaming source's per-posting takedown notice. **A NULL `last_yield_at` never qualifies, permanently**: it means no yield has been OBSERVED, not that the feed is empty, and on the day the column landed that was true of every one of the 155k rows — so migration 0158 seeds the existing fleet with `last_success_at`, which is what makes the window safe to start counting from and is load-bearing rather than cosmetic. Same region-ambiguity refusal and same dry-run-by-default posture as (5).

**The unseen safety net** (`search.Withheld`): every close above that reads `last_seen_at` waits for a run that PROVED it covered the board, so a board whose crawl keeps failing or timing out never sweeps and its removed postings stayed open and searchable — measured 2026-10-26, 96,479 of 848,549 open canonical technical postings had gone unseen for more than 14 days (eures, phenom, successfactors, trudvsem, the whatjobs markets, 4dayweek and more). Search therefore withholds a posting whose source has not shown it for longer than `search.UnseenWindow` (14 days), or the adapter's own `sweepGrace` when that is wider. It is a filter, not a close: nothing is written to the row, the job page still serves it, and a crawl that lists it again (any write stamps `last_seen_at`) brings it back. The rule is applied where a document is WRITTEN — `cmd/reindex` (deleting it from the rebuild), `cmd/search-drain` and `linkimport` (skipping it) — and mirrored by `RefreshCompanyFacets`' count and the similar-jobs list. It is not a query-time filter on an indexed `last_seen_at` because the liveness refresh (`RefreshUnchangedJob`) deliberately pushes nothing to `search_outbox`, so an indexed value would freeze at the last content write and hide live, unchanged postings. The cost is latency: a posting leaves search at the first full rebuild past its window, and a re-listed one returns at the next rebuild or on its next content write — a few hours either way while the rebuild timer runs. The per-source windows come from `sources.UnseenWindows`, which leaves out every source whose stale `last_seen_at` is not evidence: a `selfClosing` adapter (it re-reports only changes), a `livenessProbed` one (it re-lists only the newest slice of its feed and a probe closes the dead ones: `hh`, `himalayas`, `echojobs`, `jobicy`, `remoteok`, `empregos`, `adzuna`), and every source with no adapter (`telegram`, employer vacancies, manual and pasted-link imports), which nothing re-crawls.

## Limitations
- A missed liveness cron run leaves orphans open longer; no reconciliation beyond the next run.
- The liveness probe uses pure heuristics (no browser, no LLM) — a posting that returns a 200 with a "position filled" message in a language or phrasing not in the curated set stays open.
- Self-closing sources trade missed-run safety for feed-accuracy: a skipped cron leaves orphans open until the next run's change window catches up.
- The age rule is a guess, not a verdict: a Telegram vacancy still genuinely open at 46 days is closed anyway, and nothing reopens it. `closed_reason = 'expired'` is what makes that reversible — the rows it closed can be found and restored as a set.
- Every one of these mechanisms queues the closed row's removal from the facet index in its own statement (`search_delete_outbox`), so the close and the de-indexing commit together. `TestEveryClosingQueryQueuesTheRemoval` enumerates them; it is a hand-written list, and both of `cmd/liveness`' closes were missing from it — and from the queue — until 2026-09-06.
- The unseen safety net reads `last_seen_at` by SOURCE, so a row stored under a crawled provider's name that no crawl of that provider will ever list — a Telegram post linking to an ATS board the fleet does not crawl, a moderator import filed under its origin — is hidden 14 days after it was written, live or not. Its page still serves it.
