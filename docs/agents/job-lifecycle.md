# Job lifecycle conventions

## Scope

The open/closed state of a job row, the seven mechanisms that write `closed_at`, and the filtering semantics that depend on it.

## Always true

- A job is open while `closed_at IS NULL`. Closing is a soft state; nothing hard-deletes jobs. (`cmd/prune`, which removed non-IT postings into `pruned_jobs`, was retired once the catalogue grew broader than IT: `closed_at` means only "the employer took this down".)
- A closed row keeps its `public_slug`, enrichment and `user_jobs` references; reopening is free.
- List, search and company surfaces filter `closed_at IS NULL`. Detail still serves a closed job (with `closed_at`) so links and history don't break.
- The ingest write stamps `last_seen_at` on every crawl (`RefreshUnchangedJob` when unchanged, `UpsertJob` otherwise). The post-run sweep closes a provider's jobs unseen for 48h. A reappearing posting reopens via the upsert.
- A board the run SKIPPED (failure cooldown, or the up-to-72h quiet pause of a board whose listing keeps coming back unchanged, see [internal/ingest/pipeline/AGENTS.md](../../internal/ingest/pipeline/AGENTS.md)) is excluded from the company- and source-scoped sweeps (`Stats.SkippedBoards`): its rows were not looked at, so their age proves nothing. The board-scoped close acts only on boards the run finished, so it never reaches one.
- Self-closing sources (`jobtech`, etc.) are excluded from the unseen sweep; the feed's `removed` events are the authoritative close signal.
- The liveness worker closes only on positive evidence (two consecutive `expired` reads) and never reopens.
- A source with no close signal at all (no re-crawl, no feed, a URL that outlives the vacancy) is closed by age: `telegram` today, at 45 days. It is the only close that rests on a guess.
- Every close records which mechanism wrote it in `closed_reason`; a reopen clears it. Rows closed before the column existed carry `''` (unknown) and are never relabelled.
- `cmd/close-chronic-boards`, separate from the ingest sweep, closes a board (or boardless provider) unreachable for a long time, not merely cooling down (`closed_reason = 'board_unreachable'`), and in a second pass a board whose crawls all SUCCEED but whose feed has carried nothing for a long time (`'feed_empty'`).
- An open posting its source has not shown for more than 14 days (`last_seen_at`) is **hidden from search, not closed** (see "The unseen safety net"). It stays open, its page serves, and it returns when its source lists it again.

## How it works

Seven independent mechanisms write `closed_at`, each covering a gap the others can't reach. Six close on evidence; the age rule (4) guesses, which is why every close records its mechanism. The safety nets (5) and (6) read a board's history, not a posting: (5) nothing could reach the board for weeks, (6) everything reached it and found nothing.

**(1) Ingest sweep** (`cmd/ingest`, `CloseUnseenJobs`): board sources stamp `last_seen_at` every crawl (cheap `RefreshUnchangedJob` on the common path, `UpsertJob` for a new, edited or reopening posting). The post-run sweep closes a provider's jobs unseen for 48h; the upsert's `ON CONFLICT` path clears `closed_at` on reappearance. Company/source scopes require an ingested or refreshed posting, so a total crawl outage cannot authorize them. Board scope separately requires verified finished-board evidence and provider markers, including proven empty boards (1a, 1d). The company scope is limited to the `company_slug`s the run crawled, so a partial run closes only companies it saw. That deliberate under-close *leaks the last postings of a company that vanished from the feed entirely*: the scope can't tell "company gone" from "company not reached". A recency-budgeted aggregator (`himalayas`, see `internal/ingest/sources/himalayas.go`) leaks routinely: a company that ages out of its window never re-enters scope.

**(1a) Board-scoped close** (`CloseUnseenJobsForBoard`, freehire#2328): retires a company whose LAST posting drops off a board the fleet still crawls. Its slug never re-enters the company scope, and (2) excludes board sources, so without this the row leaks forever. A board qualifies only when the run structurally proved it covered it, read off `Stats`, not `BoardHealth` (which deliberately calls a streaming board that died mid-crawl healthy):

- the board did not fail (`Stats.Failed` is 0 for it);
- it yielded at least one posting (`Ingested + Rejected + ATSCovered > 0`; `Skipped` excluded, so a board whose every save fails cannot prove itself on those failures);
- it read what it listed (`boardReadWhatItListed`, (1b) below);
- it was not cut short by the run's context (`Stats.Interrupted`, (1c));
- the entry names a board (`BoardPattern("")` would match the provider's whole catalogue).

Rationale per condition: [internal/ingest/pipeline/AGENTS.md](../../internal/ingest/pipeline/AGENTS.md). All qualifying boards close in ONE statement (`CloseUnseenJobsForBoards`, `LIKE ANY`), falling back to one per board only on failure: per-board statements cost ~50 ms each over the crawl host's link, enough for the unit timeout to cancel 1,431 of one recruitee run's closes.

**(1c) The crawl deadline.** The unit timeout is a hard kill. From 2026-10-18 (crawl moved a WireGuard hop from the database) large providers outran it: 0 of 33 greenhouse, 0 of 31 smartrecruiters and 0 of 29 ukg runs reached the sweep, leaving ~307k dead workday postings open behind boards `board_health` called healthy. So `cmd/ingest` stops its crawl `INGEST_SWEEP_RESERVE_SECONDS` (default 600) before `INGEST_RUN_TIMEOUT_SECONDS` (the scheduler passes it; a static unit sets it itself, net of any slot wait) and sweeps on a context detached from the crawl and the signal, bounded by the timeout. A board in flight at the deadline is `Stats.Interrupted` and never qualifies for the board scope: it stopped at an arbitrary point with no `Failed` to say so. A **truncated** run (crawl stopped early by deadline or signal) closes through the board scope ONLY. Company and source scopes are skipped: one company can span several boards, and a deadline reaches the same leading boards every cycle, so a finished board's company would close its unreached boards' postings run after run with nothing to reopen them. A provider without the `fullBoardListing` marker still sweeps only on a run that finishes.

**(1b) A posting the crawl could not read withholds both scopes for its board.** On non-hydrating adapters whose detail request is a posting's only source, a failed detail used to be silently dropped, so both sweeps closed a posting merely unreadable for 48h. `sources.detailUnreadable` splits the cases: **404/410 means gone** and is dropped; anything else (including a 200 with no posting) becomes a `Job{Unreadable: true}` marker in `Stats.Unreadable`. Over 5% unread on a board withholds BOTH its close scopes (board via `boardQualifies`, company via `Stats.UnprovenCompanies`, subtracted from the crawled slugs) while still writing what was read. Never a board failure: that would cool the board to its 24-hour ceiling and freeze its catalogue over a per-posting hole. Adapter list and rationale: [internal/ingest/pipeline/AGENTS.md](../../internal/ingest/pipeline/AGENTS.md).

None of the above suffices alone: an adapter can satisfy every condition while returning fewer postings than the board has. solidjobs proved it (#2337, reverted within 18 minutes after closing 110 live postings): it reaches the first 500 of a board's ~1,400 postings and reports success. The load-bearing gate is `sources.fullBoardListing`: the adapter must be *registered* as structurally proving it lists a board to completion (verifying a count against the source's reported total, or paginating to the natural end with no silent cap) and must fail `Fetch` when it cannot establish that. A provider absent from `sources.FullBoardListingProviders()` never contributes to the board scope; the bar is in [internal/ingest/sources/AGENTS.md](../../internal/ingest/sources/AGENTS.md). Members: whatever `sources.FullBoardListingProviders()` returns — the large ATS platforms, `paycom` (since 2026-10-29: its runs mostly hit the deadline, so before the marker a truncated run closed nothing of it), and the adapters audited since. `solidjobs` stays out as the negative control. Also excluded even if registered: a `sweepGrace` provider (it reaches only a slice; the default window would close postings that drifted past its depth) and a `fullCatalog` provider (already closes by source, strictly broader).

The one way a `sweepGrace` provider enters the board scope is `sources.sliceBoardListing` (`whatjobs`: each keyword board read as a bounded slice, with board-namespaced ids): its finished boards close on the provider's GRACE window (14 days), never the default. Why and the measurement: [internal/ingest/sources/AGENTS.md](../../internal/ingest/sources/AGENTS.md).

**(1d) An emptied board closes through the board scope too, on adapters that can prove it is empty.** The yield condition refuses a board whose finished crawl listed nothing, and the company scope cannot reach it, so an employer that took everything down stayed open until (6) closed it 30 days later (greenhouse `skedda`, ashby `umbrel`, `gruntwork`, 2026-10-29). `pipeline.boardListedEmpty` reports such a board in `Stats.EmptyBoards` (finished, not failed, interrupted or skipped, and its listing named NOTHING by `boardListedAnyPosting`'s generous reading: unreadable or unsaved postings count). `cmd/ingest` adds it to the board scope on the ordinary window only for a provider carrying `sources.emptyBoardListing` on top of `fullBoardListing`. `fullBoardListing` proves a listing was read to its END, not that an empty answer was a listing: a challenge page, a 200 error page, an envelope missing its posting array or broken markup all look empty. So the second marker is granted per adapter only when an answer that decodes without its posting collection fails `Fetch` (`errListingAbsent`); only a present, empty collection is an empty board. Members: whatever implements `emptyBoardListing()` — on 2026-10-29 `greenhouse`, `ashby`, `lever`, `workable`, `recruitee`, `breezy`, `bamboohr`, since joined by `beehire`, `seamlesshiring` and `workday`. `smartrecruiters` is excluded on evidence: it answers an UNKNOWN company with `totalFound: 0`, so empty looks like a failed lookup. HTML-scraped listings are excluded by construction. Measured 2026-10-29: 9,797 large-ATS boards had a latest successful crawl listing nothing; the seven granted providers held 5,772 open postings unseen past 48h, and every board sampled answered genuinely empty. `jazzhr` (3,654), `ukg` (2,178), `paylocity` (1,121), `taleo` (620) and `icims` (493) stay on (6) until each is audited.

**(1e) A board id repeated across regions closes per region when the adapter can say where each region's postings live.** `external_id` carries no region, so `ambiguousRegionBoards` / `AmbiguousBoardNames` refuse a board name that appears under two regions of a provider. An adapter implementing `sources.RegionScopedBoards` (`jobstreet`: subclass `6290` is a board in all six markets) is exempt: `Stats.QualifyingBoards`/`EmptyBoards` carry each board's region (`pipeline.BoardRef`), `sweepableBoards` keeps it, and `sweepBoards` issues one `CloseUnseenJobsForBoards` per region with a `url_pattern` of the region's posting-URL prefix (`sources.BoardURLPrefix`, LIKE-escaped by `externalid.LikePrefix`); other providers pass `''`. The skipped-board exclusion (`Stats.SkippedBoards`) stays region-blind: a quiet SG `6290` keeps `6290`'s rows in every market out of that run's company scope, the safe direction.

The company scope stays because it reaches boardless entries and every provider without `fullBoardListing`. It does NOT reach a zero-yield board (no company enters the crawled set) unless another board of the run wrote the same company. So an emptied board of a provider without `emptyBoardListing` falls to (6); (2) excludes registered providers and reaches none of them.

`CloseUnseenJobs`/`CloseUnseenJobsBySource` are single-statement bulk `UPDATE`s, so one unwritable row (2026-08-11: one duplicated `jobs_pkey` value from a corrupted index) aborts the statement and silently leaves every closeable row of the provider open, run after run. Fallback: `cmd/ingest`'s `sweepRowByRow` re-fetches the candidates (`UnseenJobIDs`/`UnseenJobIDsBySource`) and closes each alone (`CloseUnseenJobByID`), logging and skipping any id that still fails.

**(1b) Full-catalogue source sweep** (`CloseUnseenJobsBySource`): a `sources.fullCatalog` aggregator (e.g. `habr_career`, `geekjob`, `powertofly`) lists its whole catalogue every run, so an unseen job is gone, including the vanished-company case (1) leaks. It closes by source alone. Sound **only** because a full-catalogue adapter fails a truncated crawl instead of returning a partial success (`habr_career` fails any bad listing page; `geekjob` uses `crawlAllPagedLinks`), and `cmd/ingest` gates the source-scoped close on a zero-`Failed` run (`sweepBySource`). A mid-listing failure falls back to the company scope rather than mass-closing every posting past the failed page.

**(3) Stream-driven self-close** (`CloseJobBySourceExternalID`): a self-closing source (`jobtech`/Arbetsförmedlingen, consuming an incremental change feed) emits `Job{Removed: true}` for a posting its feed reports taken down. `pipeline.ingestStream` routes it to the Store's optional `closer` (the ingest `dbStore`), closing by `(source, external_id)`. Such a source implements `selfClosing` and is excluded from (1) (`sources.SelfClosingProviders`): it re-reports only changed ads, so the `last_seen_at` cutoff would close every untouched open ad. Trade-off: a removal is sent only while inside the change window, so one the crawl misses is never sent again. The window absorbs a skipped cron, a run that cannot read its whole window reports the board failed, and `jobtech`'s misses are closed by its `cmd/liveness` pass (2b).

**(4) Age rule** (`cmd/liveness`, `CloseStaleUnsignalledJobs`): a `telegram` job's URL is the post, which stays live after the vacancy is filled, and no crawl re-visits it. It is closed once `COALESCE(posted_at, created_at)` is strictly older than 45 days, with `closed_reason = 'expired'`, and never reopens. The source list is passed in by the caller, not derived from "whatever the sweep misses", so a new adapter never drifts into age closes; it is the same list the probe excludes, keeping "what cannot be probed is expired instead" one decision.

**(2) Liveness probe** (`cmd/liveness`): sources outside the `sources.All` registry (manual/`resolve-url` imports and the like) are never re-crawled. Registered providers are swept by (1)/(1b) and excluded; so is `telegram` (`unsignalledSources`, closed by (4)). The worker URL-probes those orphans, classifies the page with `internal/job/liveness` (HTTP 404/410, error/listing redirect, curated EN/DE/FR closed-posting phrases, near-empty content; no browser, no LLM), and closes after two consecutive `expired` reads (`liveness_strikes`; any healthy probe resets it). It never reopens (an orphan has no re-ingest to reopen it), so it biases toward under-closing. Run-once, cron-scheduled.

**(2b) Backstop for a registered provider's scope leak** (`probeDespiteRegistered` in `cmd/liveness`): the sweep still owns the provider's regular closes, but the provider is also a probe candidate, restricted via `SelectStaleRegisteredCandidates` to jobs past the sweep's 48h window (mirroring `cmd/ingest`'s `staleAfter`), so it picks up only what (1) cannot reach. Members are recency-ordered aggregators whose crawl budget (page cap, offset ceiling, freshness window) is smaller than the live catalogue:

- `himalayas`, `echojobs`, `jobicy`, `remoteok`.
- `hh`: board-scoped (one board per professional role), but each board is read only as its newest ~2000 postings of the last 7 days.
- `empregos`: no budget, but it reads only postings that name a state and cannot prove it read the location-less rest, so it is not `fullCatalog` and its sweep is company-scoped.
- `djinni`, `4dayweek`, `torre` (2026-10-29), swept only by company and not `fullCatalog`: djinni lists only about the last month, 4dayweek's adapter does not verify it read the whole feed, torre's sitemap names a few closed postings. That day 3.4k of djinni's 8k, 21.5k of 4dayweek's 27k and ~250 of torre's 2.7k open rows were unseen for over a week.
- `arbeitnow` (2026-10-30): its API names only the last week (a full walk read 4,282, none older than seven days); ~11k of 12.7k open rows were unseen for over a week, and of 100 sampled 64 answered 410. Its pass reads the status alone, since a live posting's description can match `liveness.Classify`'s phrases.

Most of 4dayweek's backlog was not the feed (it names the whole 27.5k catalogue): 98% of stale rows belonged to employers the aggregator-coverage gate kept out of the write path without refreshing them. The gate now refreshes rows it skips (`pipeline.CoveredRefresher`) for every aggregator; the probe stays the backstop for an employer that leaves the feed.

Each member needs its own evidence path, by design: a GET probe is not guaranteed to work (`probeDespiteRegisteredGET` in `cmd/liveness/main.go` is the verified plain-GET subset):

- `jobicy`, `remoteok`, `empregos`: the (2) plain-GET probe as-is. jobicy answers `410` for a removed posting; remoteok answers `200` with a "this job post is closed" banner (`internal/job/liveness`'s `hardExpired` patterns); empregos redirects to `/404`, which answers `404`.
- `himalayas`: job pages are Cloudflare-blocked (403 even with a browser User-Agent), so `cmd/liveness/himalayas.go` downloads the unprotected sitemap (~114k URLs, `sitemapindex`) once per run and checks membership.
- `echojobs`: the stored `jobs.url` is the employer's ATS link, as reliable as that employer. `cmd/liveness/echojobs.go` GETs echojobs.io's own job page keyed on `external_id`: `200` listed, `404`/`410` removed, anything else unverifiable.
- `hh`: `cmd/liveness/hh.go` GETs `https://hh.ru/vacancy/<id>` and reads the page's `analyticsParams` flag (`"archived": "true"` archived, `"false"` live); `404` is deleted. It cannot use the plain-GET probe: every hh.ru page, live ones included, embeds the string "Вакансия в архиве", which `Classify`'s RU banner phrase would read as dead. The API (`api.hh.ru/vacancies/{id}`) answers `403 forbidden` to anonymous requests. hh.ru rate-limits with a `200` captcha redirect and the crawl shares the host, so the pass probes one page a second, at most 1500 candidates a run, stopping at the first captcha or `429`. A `403` (~7% of stale postings, the same ids every time) is Uncertain, like every refusal.
- `djinni`: plain-GET evidence (a removed posting answers `200` with "The job ad is no longer active", one of `Classify`'s phrases, or `404`), but paced like `hh` because djinni answers a fast datacenter burst with `403` and the crawl uses the same host: one page a second, at most 1500 a run, stopping at the first `403`/`429` (`cmd/liveness/djinni.go`). Of 120 stale rows sampled 2026-10-29: 94 alert, 12 404, 14 live, all posted over a month earlier, which is why djinni carries `livenessProbed`.
- `4dayweek`: `cmd/liveness/fourdayweek.go` asks `/api/v2/jobs/<slug>` (robots.txt allows it; the slug comes from the stored url, as the API 404s the UUID external id even when live): `200` live, `404`/`410` gone. It agreed with the job page on all 120 sampled stale rows at ~7 KB vs ~250 KB. Cloudflare refuses self-identifying clients (so it sends `sources.BrowserUserAgent`) and meters by IP: one request a second, at most 3000 a run, stopping at the first `403`/`429`.
- `torre`: `cmd/liveness/torre.go` reads the status after `prefilledStatus` in the page's embedded state (`"closed"` Expired, `"open"` Live), since a closed posting's page is a full `200`; an unknown id redirects to `/404`. Its lighter API (`/api/suite/opportunities/<id>`) is disallowed by robots.txt. One page every two seconds (two a second drew `503`s); of 41 stale rows, 36 closed, 4 404, 1 open.
- `jobtech`: a missed removal, not a scope leak. It self-closes from JobStream's 72h change window (3); a missed removal is never re-sent, nor is an unchanged live ad, so `last_seen_at` says nothing after three days. The adapter spools the window and applies removals first (JobStream lists live ads before removals, and writing while decoding let the client's 15-minute timeout end the read before any removal: from 2026-10-27, 32.7k of 46.5k open rows went unseen for a week). `cmd/liveness/jobtech.go` closes what was missed via JobSearch's per-ad API (`jobsearch.api.jobtechdev.se/ad/<id>`; the stored Platsbanken url answers 200 for anything): `"removed": true` or `404` gone, `"removed": false` live. Of 200 stale rows sampled 2026-10-31, 53 answered 404. Not withheld from search: a self-closing source's unseen rows are mostly live.

Two registered providers are probed by `cmd/adzuna-liveness` on the crawl host, since their pages answer only through its loopback Scrapling fetch service: `adzuna` (its `/details/<id>` page, behind a challenge most requests fail) and `wellfound`, whose role-slice crawl is swept by company and strands every posting of a company that left all slices (954 open on 2026-10-30, 20 of 20 sampled answering `410`). Both close on ONE `404`/`410` with `closed_reason = 'probe_expired'` (the source's own statement); a crawl that lists the posting again reopens it.

The paced passes (`hh`, `djinni`, `4dayweek`, `torre`, `arbeitnow`, `jobtech`; `cmd/liveness/paced.go`) run side by side, one per site, each reading struck candidates first, then a shuffle: a close needs two consecutive expired reads, and a struck row left to the shuffle would wait runs for its second.

**Which probed sources search still hides.** A probed source's adapter normally carries `livenessProbed`, exempting it from the unseen safety net (its crawl cannot re-list every live posting). Some deliberately do not. `torre`'s sitemap and `4dayweek`'s feed ARE the live catalogue, so a posting unseen for two weeks is gone. `arbeitnow` has the marker's shape but not yet the rate; grant it once its backlog is worked off. `probedButWithheld` in `cmd/liveness`' tests records each and fails when one stops being true.

**(2c) Age fallback for a registered provider with no evidence at all** (`expireDespiteRegistered` in `cmd/liveness`, `CloseStaleUnseenUnprobeableJobs`): the same scope leak as (2b), for a source with no evidence to find. Member: `whatjobs`, whose `jobs.url` is a CPC ad-network tracking page that answers the same whether the posting is live or gone (`internal/ingest/sources/whatjobs.go`). It gets (4)'s 45-day `expiryWindow`, and additionally requires the posting to be unseen past the provider's `sweepGrace`. A separate list from `unsignalledSources` because the guards are opposite: an `unsignalledSources` member must NOT be a registered provider (age is its only closer); an `expireDespiteRegistered` member MUST be one (the sweep owns the common case).

It is also a separate STATEMENT from (4): these sources ARE crawled, so the guess must not contradict what the crawl just saw. `CloseStaleUnseenUnprobeableJobs` additionally requires the posting to be unseen for longer than the provider's `sweepGrace`. Until 2026-09-06 it reused (4)'s age-only query; `whatjobs` leaves `posted_at` unset, so every posting older than 45 days since ingest was closed one run and reopened by the next crawl, twice a day, restamping `updated_at`, recomputing its chunks, and mailing every applicant that the posting had closed.

**(5) Chronic-board safety net** (`cmd/close-chronic-boards`, issue #2017): (1) never closes what a run did not prove it covered, with no upper bound, so a permanently gone board (retired, blocking us, moved) would stay open forever. `board_health.ListChronicBoards` measures from `last_success_at`, or `first_seen_at` if it never succeeded (`last_error_at` is overwritten every failed run and cannot date the FIRST failure). Two windows: 30 days (`CHRONIC_BOARD_WINDOW_DAYS`) is what `cmd/ingest`'s per-run health summary surfaces for curation; 60 days (`CHRONIC_BOARD_CLOSE_WINDOW_DAYS`) is what `cmd/close-chronic-boards` closes. The gap is curator lead time. The close is scoped to the qualifying `(provider, board)`; a boardless provider's single health record closes the whole provider. A board id repeated across regions (`board_health`'s key is `(provider, board, region)`, e.g. Adzuna's `it-jobs` per country) is refused, not board-scoped: `jobs.external_id` carries no region, so a LIKE close could take a healthy region down with a dead one (the same refusal as (1a)'s `ambiguousRegionBoards`). It is reported as skipped. Ships dry-run-only on its daily timer until a human has read at least one full closure window's report.

The worker also has a separately armed `board_gone` pass for adapters that recognize the platform's explicit no-such-board answer (`sources.ErrBoardGone`). It requires at least three consecutive such failures spanning seven days (`BOARD_GONE_CLOSE_WINDOW_DAYS`), plus another board from the same provider succeeding in the last 48 hours. The three observations are stricter than the two expired reads used for a single posting by the liveness worker because a board can retire many postings at once. The seven-day span allows several crawl/recovery cycles (longer than board health's 24-hour maximum cooldown) while staying shorter than the 30-day successful-empty-feed and 60-day generic-unreachable waits: this path has typed platform-level disappearance evidence, unlike a failed request or a feed that merely returned no jobs. A recent successful sibling is an independent provider-health check; the separate dry-run and apply flag add an operator review before any close. Generic failures reset the gone streak; success resets it as well. This excludes 403/429, transport/adapter failures, provider-wide outages without a healthy sibling, and successful empty listings. The close statement repeats the checks and refuses region-ambiguous identities. It remains dry-run by default; `--apply-board-gone` arms only this pass and jobs receive `closed_reason = 'board_gone'`. The shared lifecycle path covers any provider adapter that returns `sources.ErrBoardGone`; this change adds that classification for Teamtailor's confirmed double-404 response. Providers without a typed board-gone signal, and providers without a separate healthy sibling board, do not qualify.

**(6) Empty-feed safety net** (`cmd/close-chronic-boards`' second pass, migration 0158): the twin of (5) for a board that answers perfectly and has nothing in it, which (5)'s `last_success_at` cannot see. On 2026-09-10 an emptied WhatJobs publisher account returned 200 with zero results every crawl, health clean, and 107 postings stayed open for a month. (1) could not reach them: `shouldSweep` requires at least one ingested job (right for a broken crawl, wrong for an honest zero), and nothing written means no company scope.

So `board_health.last_yield_at` records when a board last YIELDED a posting. **Being listed is not being written**: `pipeline.boardListedAnyPosting` counts ingested, rejected, already-covered, unreadable and failed-to-save postings alike. Stamping on the ingested count would call an all-rejected board (a non-tech-heavy national feed) or an aggregator board whose employers we crawl directly empty, and close live jobs. It is deliberately NOT `boardReachedPostings` (they differ by `Skipped` and `Unreadable`): there false costs one crawl cycle of proof, here false accumulates into a close, so this caller needs the generous predicate. Example: a link-only adapter whose detail requests all fail makes every posting `Unreadable` (not `Failed`); the board keeps a fresh `last_success_at` and would age into this net with every posting live.

`ListEmptyFeedBoards` selects boards demonstrably REACHABLE (succeeded inside the window, `consecutive_failures = 0`) that have not yielded for `EMPTY_FEED_CLOSE_WINDOW_DAYS` (default 30, shorter than (5)'s 60: (5) waits out a problem on our side, while an empty feed has already answered successfully every run). `'feed_empty'` is its own label because `'unseen'` claims proven coverage, `'board_unreachable'` would send an operator to check our access instead of the source's inventory, and `'feed_removed'` is a stream's per-posting notice. **A NULL `last_yield_at` never qualifies**: it means no yield was observed, not an empty feed. When the column landed that was true of all 155k rows, so migration 0158 seeds the fleet from `last_success_at`; the seed is load-bearing. Same region-ambiguity refusal and dry-run default as (5).

**(7) Board retirement** (`boardcatalog.Retire`, `CloseRetiredBoardJobs`): retiring a board (`cmd/add-board --retire`) closes its open postings in the same call, `closed_reason = 'board_retired'` (migration 0212). Nothing else would: no crawl runs for a retired board, so (1) never sweeps it; `Retire` deletes its `board_health` row, so (5) and (6) have no evidence; and its source is still registered, so (2) and (4) leave it to the sweep. aijobs (retired 2026-09-07) kept 2,569 postings open for eight weeks that way (freehire#3796). Re-retiring closes what an earlier retirement left open. Same region-ambiguity refusal as (5): while the board name is live in another region, nothing closes.

**The unseen safety net** (`search.Withheld`): every `last_seen_at` close waits for a run that PROVED coverage, so a board whose crawl keeps failing never sweeps. On 2026-10-26, 96,479 of 848,549 open canonical technical postings were unseen for over 14 days. Search withholds a posting unseen for longer than `search.UnseenWindow` (14 days), or the adapter's `sweepGrace` when wider. A filter, not a close: nothing is written, the page serves it, and a crawl that lists it again (any write stamps `last_seen_at`) brings it back. The rule is applied where a document is WRITTEN (`cmd/reindex` deletes it from the rebuild; `cmd/search-drain` and `linkimport` skip it) and mirrored by `RefreshCompanyFacets`' count and the similar-jobs list. Not a query-time filter on an indexed `last_seen_at`: `RefreshUnchangedJob` deliberately pushes nothing to `search_outbox`, so an indexed value would freeze at the last content write and hide live, unchanged postings. The cost is a few hours' latency either way (next full rebuild or content write). Per-source windows come from `sources.UnseenWindows`, which omits every source whose stale `last_seen_at` is not evidence: `selfClosing` adapters (re-report only changes), `livenessProbed` ones (re-list only the newest slice; a probe closes the dead: `hh`, `himalayas`, `echojobs`, `jobicy`, `remoteok`, `empregos`, `adzuna`), and sources with no adapter (`telegram`, employer vacancies, manual and pasted-link imports), which nothing re-crawls.

## Limitations

- A missed liveness cron run leaves orphans open until the next run.
- The probe is pure heuristics, so a 200 with a "position filled" message in an uncurated language or phrasing stays open.
- The age rule is a guess: a Telegram vacancy still open at 46 days is closed and nothing reopens it. `closed_reason = 'expired'` makes the set findable and restorable.
- Every mechanism queues the closed row's removal from the facet index in its own statement (`search_delete_outbox`), so close and de-indexing commit together. `TestEveryClosingQueryQueuesTheRemoval` enumerates them by a hand-written list; both `cmd/liveness` closes were missing from it, and from the queue, until 2026-09-06.
- The unseen safety net reads `last_seen_at` by SOURCE, so a row stored under a crawled provider's name that no crawl of it will list (a Telegram post linking to an uncrawled ATS board, a moderator import filed under its origin) is hidden 14 days after it was written, live or not. Its page still serves it.

### Boardless catalogue status backstops

The November 2026 audit found dead postings from `instaffo`, `remotedotcom` and
`thehub` outside the company-scoped sweep. Reed's bounded keyword union has the
same scope gap and is covered for its own stored Reed posting URLs; employer
redirect URLs are deliberately excluded. None claims `fullCatalog`, so when an
employer leaves the listing its last postings never re-enter that sweep's scope.
`cmd/liveness` includes their open postings unseen for more than 48 hours. Each
source is paced at two seconds per request, capped at 500 postings per run, and
stops on 403/429. Only a 404/410 on the same host and posting path adds a strike;
a redirect to a listing or another host is uncertain. The ordinary two-run close
threshold, crawl-race cutoff and transactional search-delete enqueue apply.
Search's unseen safety net stays enabled while the backlog is worked off.

For a scoped cleanup after deploying the worker, run `liveness -source=instaffo`,
`liveness -source=remotedotcom`, `liveness -source=thehub` or
`liveness -source=reed`. Repeat in a later
run rather than stacking invocations: two independent expired reads close a
posting with `closed_reason = 'probe_expired'`. Never treat an audit sample or
its canary alone as closure evidence.
