# Worker commands

## Scope

What each `cmd/<name>` worker does, when it runs, what it needs, and the trap behind it. Run one with `go run ./cmd/<name>`; every worker needs `DATABASE_URL`, and `ls cmd/` is the full list. The schedules themselves live in the private `freehire-ops` (`provision/host2/AGENTS.md`).

## Workers

- `migrate` — run **before** deploying code that reads new schema. `-baseline` records on-disk files without executing; a pre-runner database auto-baselines on first run.
- `ingest` — takes one PROVIDER NAME: `go run ./cmd/ingest <provider>` (or `INGEST_PROVIDER`), and reads that provider's live boards from the `boards` table. Handing it a file path is not an error — the path becomes the provider it looks up, which finds nothing, logs `providers=0` and exits 0. **`INGEST_RUN_TIMEOUT_SECONDS` (the unit's own timeout) gives the crawl a deadline `INGEST_SWEEP_RESERVE_SECONDS` (default 600) short of it**, so the stale sweep still runs when the crawl overruns — the scheduler passes it on every launch; a static unit must set it itself, net of any slot wait, or its crawl stays unbounded and a timed-out run sweeps only in the 90s after SIGTERM. A run stopped early closes through the board scope only (see [docs/agents/job-lifecycle.md](../../docs/agents/job-lifecycle.md) (1c)). `HYDRATION_RETRY_DAYS` widens the window (default 14 days, measured from `created_at`) during which a stored row with NO description is withheld from the seen-set so a hydrating adapter re-attempts its detail fetch. Set it only for a deliberate repair run — `HYDRATION_RETRY_DAYS=365 ingest hh` re-offers every body-less row of that provider, one extra detail request each (hh's detail pages are ~1 MB), and expect to repeat it: a run that hits its timeout still persists what it hydrated and the fixed rows leave the set, so successive runs shrink the backlog. An unparseable or non-positive value fails the run rather than falling back, because a typo here would look exactly like a repair that found nothing. **`INGEST_REFETCH_ALL=1` empties the seen-set for the run**, so every listed posting is treated as new and the pipeline re-WRITES it instead of only refreshing its liveness. That is the repair path for an adapter fix that changes what the LISTING yields (a mis-read remote flag, a location built from the wrong place): the fix reaches new postings on the next crawl and reaches the stored ones never, and `backfill-derive` cannot recover them either — it re-derives FROM the stored columns, which hold the wrong reading. Costs one detail request per stored posting (nofluffjobs: ~19k postings, ~20 min at 8 workers), re-enqueues only what actually changed for search, and re-enqueues nothing for enrichment (that queue is gated on `enrichment_version`, not on the write). A failed detail fetch cannot wipe a body — `UpsertJob` keeps the stored description when the incoming one is empty — so a run that hits its timeout is simply repeated. **`BODY_REFRESH_DAYS` re-reads a stored body that has gone stale**, so an employer's later EDIT reaches the catalogue at all: a hydrating adapter fetches detail only while the catalogue lacks the posting, so once stored a body is never read again and a posting that gains a "this position is 100% on-site" paragraph keeps whatever we read the day we first saw it (freehire#2555). It ships UNSET, which is disabled — turning it on costs one detail request per re-read posting against a crawl fleet that is already the host's bottleneck, so enable it one provider at a time and watch the load — in `/opt/freehire/ingest-env/<provider>.env` on the crawl host, which the scheduler hands each run of that provider after the shared `.env` (a value there wins; no file, no change). Putting it in the shared `.env` turns it on for the whole fleet. `BODY_REFRESH_SLICE` (default 30) bounds one run: a posting belongs to one slice for its life and a run takes the slice named by the day of the year, so a full sweep takes SLICE days and no run faces a provider's whole catalogue (1.27M postings on workday). Setting the slice without the days fails the run rather than doing nothing. What records a body's age is `jobs.hydrated_at` (migration 0144), written by both ingest write paths and NOT by the liveness-only `TouchJob`; `updated_at` cannot serve, because the cheap write deliberately leaves it alone and a body that came back identical is the common case. **An adapter fix that changes what the DETAIL yields needs an entry in `detailFieldAdded` (`internal/ingest/sweep/body_refresh.go`)**: it re-reads that provider's rows hydrated before the fix, a seventh a day for three weeks, with no operator step (freehire#4124). A fix to what the LISTING yields stays `INGEST_REFETCH_ALL=1`'s job. **`INGEST_RECENT_DAYS=<1..30>` starts a recent-only run** for sources that can filter by date (`sources.RecentSource`; Adzuna today): it reads only the last N days, so new postings reach the catalogue between full crawls. Pair a frequent recent run with a rarer full one — the full run is the only one that finds removals. A recent run closes nothing (the sweep is skipped outright), records no `board_health` success, yield or failure (so `close-chronic-boards` never reads it), skips cooldown recovery, and skips and counts (`recent_unsupported`) every board whose adapter has no date filter rather than crawling it in full. Unset is a full crawl; a bad value fails the run. The scheduler does not launch recent runs: operators own that schedule. A new adapter joins only in its own change, with a cited and live-verified date parameter — see [internal/ingest/sources/AGENTS.md](../../internal/ingest/sources/AGENTS.md).
- `close-chronic-boards` — dry-run-first safety nets for unreachable, empty-feed, and explicit board-gone evidence. `--apply`, `--apply-empty-feed`, and `--apply-board-gone` arm those passes independently; `BOARD_GONE_CLOSE_WINDOW_DAYS` controls the board-gone age window (default 7 days). See [job-lifecycle.md](../../docs/agents/job-lifecycle.md) for the evidence and close reasons.
- `enrich` / `tg-extract` — need `LLM_BASE_URL` / `LLM_API_KEY` / `LLM_MODEL`.
- `search-drain` / `rollup-facets` / `reindex-companies` — need `MEILI_URL` / `MEILI_MASTER_KEY`. `embed` never touches Meilisearch: it embeds through the TEI backend at `EMBED_URL` (empty = the default host2 TEI), with `EMBED_API_KEY` only for an authenticated endpoint. `search-drain` drains `search_outbox` (queued by `cmd/ingest`, atomically with each write) into the live facet index in batches — run it frequently (e.g. every 1-2 min); see [internal/search/searchdrain/AGENTS.md](../../internal/search/searchdrain/AGENTS.md). **`FACETD_URL` (optional) mirrors every applied wave to facetd after Meilisearch accepted it, and `FACETD_WRITE_TIMEOUT` (default `10s`) bounds that write**: a facetd failure never fails or delays the Meilisearch path — the wave's job ids go to `facetd_outbox` and a retry pass at the end of the run re-sends their current state while facetd is ready; unset, nothing changes. `rollup-facets` (daily) rebuilds two snapshots: `insights_facet_stats` for `/open`, then `insights_skill_neighbours` — one engine query per described skill (the ones with a glossary page, read from `skilltag.Descriptions()`, one at a time, a few minutes) — which the `/skills/<slug>` pages read instead of a live skills facet count; that count costs 100-700 ms and a crawler sweep over cold glossary URLs starved the engine into 500s on 2026-11-07 and 08. A failure in the second pass leaves the first committed and the previous neighbours serving.
- `reindex` — rebuilds the Meilisearch jobs index. **Run it by hand, after a backfill that writes around `search_outbox` — it is no longer on a timer** (since 2026-11-05): every routine document change reaches the index through the drain, and [internal/search/searchdrain/AGENTS.md](../../internal/search/searchdrain/AGENTS.md) lists the writers that make that true; a new one that skips the queue is a bug, not a reason to schedule the rebuild again. **`REINDEX_DEDUP=1` additionally refreshes the duplicate markers** (role clusters, aggregator suppression, fuzzy collapse) before the rebuild; without it the rebuild uses the markers the last dedup run left. Off by default since 2026-08-16: aggregator suppression alone measured ~23h against a 12h unit timeout, so the run was cancelled mid-dedup and never reached the rebuild — 3 days with zero successful reindexes. Run the dedup invocation on its own, rarer schedule. **`REINDEX_DEDUP_ONLY=1` runs just the marker passes and exits** — no Meilisearch client, no disk guard, no rebuild, so no need to pause `search-drain` for it. It is the scheduled half of `reindex` now that the rebuild is not: the marker passes queue every row they flip, so their result reaches search through the drain, and the same run queues the postings whose document changed with time alone (`EnqueueSearchTimeCrossings`: a reality-class age, an unseen window running out). Takes precedence over `REINDEX_DEDUP` if both are set. **The fuzzy pass works on `REINDEX_FUZZY_WORKERS` companies at once (default 4, strict reader) and RESUMES**: it walks the companies in sorted order, saves the last one it finished (the oldest unfinished, never the newest — freehire#2869) in `marker_pass_cursors` as it goes, so a run its unit's timeout kills is picked up by the next one after that company, and a run that reaches the end clears the point so the next starts from the top — before this, every run walked the same head of ~383k companies into its 4h timeout and the tail was never deduplicated. **A rebuild also writes the match sort's skill vectors** (`internal/dict/skillvec`), which grows the index by roughly 10 GB and makes the rebuild materially slower — the cost is HNSW graph construction, so it lands here and not on the incremental `search-drain` pushes. Schedule it deliberately, and note the embedder must be in the LIVE index settings before a binary that queries it rolls out — see [internal/search/search/AGENTS.md](../../internal/search/search/AGENTS.md).
- `facetd` — the in-memory facet engine beside Meilisearch (`openspec/changes/facetd`, package [internal/search/facetidx](../../internal/search/facetidx/AGENTS.md)). **Long-lived like `mail-ingest`** (`Restart=always`), not a cron worker, and it **needs no `DATABASE_URL`**: it serves `/facets`, `/distinct`, `/write`, `/rebuild/begin|push|commit|abort`, `/ready` and `/metrics` over HTTP, with no authentication, so it stays on localhost next to the API. Env: `FACETD_ADDR` (default `127.0.0.1:8095`), `FACETD_SNAPSHOT_PATH` (empty disables snapshots), `FACETD_SNAPSHOT_INTERVAL` (default `5m`; a snapshot is written only when the generation changed, atomically, and once more on SIGTERM), `FACETD_WAL_PATH` (default `FACETD_SNAPSHOT_PATH` + `.wal`; no snapshot path means no log). **An acknowledged `/write` survives a crash:** every batch is appended to the write-ahead log (length + CRC-32 + JSON) and fsynced BEFORE it is applied and before the 200; a write that cannot be logged is a 500 and is not applied. On start facetd loads the snapshot and replays the whole log over it (batches are per-job full replaces and marks, so re-applying ones the snapshot already holds is harmless); a torn last record is ignored with a warning, a bad record anywhere else keeps facetd not-ready and moves the log aside as `*.corrupt-<unix>`; a log without a snapshot is not an index and also stays not-ready. A successful snapshot rotates the log (temp file + rename) keeping only what was appended after the snapshot's index was captured. Metrics: `facetd_wal_bytes`, `facetd_wal_records`, `facetd_wal_replayed_total`, `facetd_wal_errors_total`, `facetd_write_batch_jobs`, and `go_*`/`process_*` for heap, RSS and GC (the unit's `MemoryHigh` counts page cache too, so compare it with `systemctl show -p MemoryCurrent freehire-facetd`, not RSS). Its callers read `FACETD_URL` (the API's facet client, `reindex`). **It is rebuilt by `reindex`, not by itself**: `FACETD_URL=http://127.0.0.1:8095 reindex` tees every batch into Meilisearch and facetd (a facetd failure is logged and aborts only facetd's rebuild, never the Meilisearch one; once Meilisearch is promoted, the run lifts the drain pause and rebuilds facetd alone once more, because the drain never replays the derived fields a full rebuild recomputes, such as `reality.class`), and `reindex -facetd-only` rebuilds facetd alone — no Meilisearch key, disk guard, drain pause, description vectors or outbox purge. **The trap: it starts not-ready (503) without a loadable snapshot**, and a corrupt snapshot is logged loudly and treated the same; the API's facet router then falls back to Meilisearch per request until a rebuild commits. `/write` batches that arrive during a rebuild are applied to the live index and re-applied on top of the rebuilt one at commit. **One rebuild at a time**: `/rebuild/begin` while one is open is a 409; a rebuild idle for 30 minutes (its `reindex` died without `/rebuild/abort`) is dropped by the next `/write` or `/rebuild/begin`, so its recorded writes stop growing. **A commit whose snapshot fails answers 500** although the rebuilt index is live: it is not durable until snapshotted, so rerun the reindex. Needs nothing else.
- `backfill-derive` — re-derives every deterministic column (facets, `engagement`, `requirements_derived`, `role_fingerprint`, `company_slug`) in one keyset pass; it is the one pass to run after any dictionary, `internal/dict/engagement` or `reqextract` change. **It keeps a stored country and region** (and a set `work_mode`) as the structured signal, because many adapters state the country and the pass cannot tell theirs from a derived one — re-deriving it moved SEEK's "Perth WA" rows to the US and blanked ~16k SEEK/JobStreet rows; a row with no stored country is re-derived in full, and correcting a stored one is `INGEST_REFETCH_ALL=1`'s job. **Never `public_slug`**: that is a published URL minted once at insert, and re-deriving it from a title the source changed later 404'd every link to the posting — one run on 2026-10-19 moved 42,226 before it was stopped (freehire#3284). The job page resolves such a dead slug through its last eight characters (the shortcode, derived from `(source, external_id)` alone) and 301s to the current one; `BACKFILL_CONCURRENCY` tunes the pool. Follow with `REINDEX_DEDUP=1 make reindex` — that is what collapses newly-clustered reposts and unions their geography. **It is RESUMABLE, and that is not a convenience**: the pass walks 12.7M rows de-TOASTing a description each, which outlasts any sane unit timeout, and until freehire#2864 it had no resume point — `afterID` started at 0 every time. A hand-made transient `taxonomy-backfill-night` unit (`systemd-run`, so in `/run` and in nobody's git) therefore ran it nightly under `TimeoutStartSec=10h`, got killed about two thirds through, restarted at the first id the next night and never once finished — ~29h of CPU a night on the host whose bottleneck is the crawl fleet, while five merged dictionary fixes waited on it. `BACKFILL_DERIVE_FROM_ID` names the first id a run must DO — **inclusive** — and `BACKFILL_DERIVE_MAX` bounds how many rows it scans, **unset for unbounded, never `0`** (`worker.EnvInt64` refuses a non-positive value, so a typo cannot silently mean "scan nothing"). **`BACKFILL_DERIVE_CLOSED_WITHIN_DAYS` narrows the scan to the rows that can still reach the catalogue** — open postings, plus ones closed within that many days — which is what makes a dictionary fix affordable: measured 2026-09-23 the table holds ~12.7M rows against 1.9M open ones, so an unbounded pass spends ~85% of its ~30h on postings no search, sitemap or page will read. It is expressed in DAYS CLOSED and **not** as an open-only flag on purpose: a closed posting is not permanently gone, since ingest's `Toucher` refreshes liveness "(last_seen_at, reopen if closed) ... WITHOUT rewriting its content" and a posting that merely drifts out of a feed for 48h is routinely closed and reopened as it drifts back (see the notes in `sources/seek.go` and `sources/whatjobs.go`) — so a pass that skipped on `closed_at IS NULL` would hand those rows back to the catalogue carrying the OLD dictionary's facets, with nothing downstream reporting the staleness. **A reopen now re-derives the row itself** (`internal/ingest/rederive`, the same function this pass runs): ingest's `Touch` reopens a closed posting and re-derives it in ONE transaction (`TouchJob` defers the reopen to it), so a failed re-derive leaves the row closed for the next crawl rather than open on stale facets, so a posting closed longer than the window still comes back on the current dictionary — company slug and fingerprint excepted, which only this pass moves. The number is how far back a posting might still return from; unset keeps the whole table, so the cautious behaviour stays the default and the knob is the deliberate act. A run that stops early says so in as many words and prints the id to continue from — from ONE report every exit path reaches, because deciding that at each `return` is what made the cursor vanish twice in one evening: the scan failing is only one ending, and the companies reconcile that follows it is two more (freehire#2876); a run that reached the end prints `done`, so "there is more" and "that was all" are never inferred from a row count. **The resume point is the oldest row the run did not FINISH, never the newest row its reader read** — the two differ by up to a full page and that gap is silent data loss: `jobsCh` is buffered at `backfillBatchSize`, so the reader hands over a whole page and advances its keyset cursor past it long before a worker writes any of it, and the review that caught this measured a cursor of 500 while id 5 was still unwritten (freehire#2869). A row whose write failed is deliberately left unfinished so the resume point falls before it. Re-reading what an interrupted run had in flight costs nothing, since the write is `changed`-guarded. **There is no timer** — `freehire-ops' provision/host2/systemd/freehire-backfill-derive.service` ships without one, because systemd has nowhere to keep the cursor between runs and a schedule that cannot advance it re-derives the same first rows forever.
- `backfill-company-type-hint` — one-off: force-requeues the existing open postings of the companies in `enrich.CompanyTypeHints` (a small, hand-curated `company_slug → outsource/outstaff` map — there is no open dataset of IT outsourcing/outstaffing companies to import instead) back into `enrichment_outbox`, so the next `cmd/enrich` runs rewrite their `company_type` using the new "Known company type" prompt hint. A single job posting rarely states its employer's business model in so many words, so this field came back `null` for these companies far more often than the rest of the enum. Run once after adding an entry to the map — the ordinary `EnqueuePendingJobs` only re-queues rows BELOW the target enrichment version, which skips a company's postings already enriched under it. Idempotent (`ON CONFLICT`-guarded on `(job_id, target_version)`), so re-running before the drain finishes costs nothing. No `make reindex` is needed: `cmd/enrich` requeues each job on `search_outbox` in the same transaction as `SetJobEnrichment`, so the corrected values reach Meilisearch through the drain. Needs `DATABASE_URL`.
- `backfill-telegram-prefilter` — **run it after any change to the Telegram prefilter's markers**, which is what makes it recurring rather than one-off. `cmd/tg-ingest` decides a crawled post with `telegram.AdmitsPost` and, when it declines, `InsertTelegramPost` stamps `extracted_at` at INSERT time; nothing revisits that row. So a widened marker reaches NEW posts only, and the stored ones stay refused forever with nothing reporting it. Measured 2026-09-23 over the 15,203 posts the filter had declined: **96** (all `job_it_junior`) already matched the then-current markers and were merely crawled under an older set, and the Spanish `empresa:` marker that landed the same day left **6,335** more behind it — 42% of everything the filter had ever refused, real vacancies carrying a LinkedIn or Workday link. The pass keyset-walks the declined posts, re-asks the SAME rule the crawl uses — `AdmitsPost`, then the Jev vacancy judge when `TYPESAFE_API_KEY` is set — so it can never requeue what the next crawl would refuse, and clears `extracted_at` on the ones it admits. **Reports by default; `--apply` writes** — the markers are hand-maintained, and the per-channel breakdown in the report is where a widening that suddenly admits an unintended channel becomes visible. `BACKFILL_TG_PREFILTER_MAX` bounds one run, **unset for unbounded, never `0`**, through the same strict reader every one-off knob uses; a bounded run prints the `(channel, msg_id)` to continue from as the exact environment to set, and a run that reached the end prints `done`, so "there is more" is never inferred from a count. **`BACKFILL_TG_PREFILTER_AFTER_CHANNEL` / `_AFTER_MSG_ID` are what make that bound a bound rather than a trap**: a post the filter still REFUSES never leaves the predicate, so a second bounded run starting from the top rescans exactly what the first one rejected — and a dry run, where nothing leaves the predicate at all, repeats its report forever. That is the failure `backfill-derive` carried until freehire#2864, where `afterID` started at 0 every time. The two are ONE cursor and the run refuses half of it, because a channel with no message id re-reads that channel whole while an id with no channel lands on the first channel alphabetically, and neither looks like a mistake in the output. They are **EXCLUSIVE** — the first row done is the one after the key — and named `AFTER` rather than `FROM` for exactly that reason: the sibling passes' `BACKFILL_*_FROM_ID` is inclusive, and two knobs sharing a name and a shape while disagreeing about whether the key is done or to-do lose one row per hop. Idempotent and free to interrupt: the UPDATE repeats the read's predicate, so a post already requeued — or claimed by `cmd/tg-extract` since this run read it — changes nothing. **Needs no reindex**: a requeued post reaches the catalogue through the extractor's ordinary write path. Needs only `DATABASE_URL`. See [internal/ingest/telegram/AGENTS.md](../../internal/ingest/telegram/AGENTS.md).
- `backfill-company-info-wikipedia` — periodic (daily, `freehire-backfill-company-info-wikipedia.timer`), unlike the backfills above it: fills `companies.tagline`/`company_info` for companies no curated company-info source has ever matched (the YC directory, an external company-info dump — see `openspec/specs/company-info/spec.md`), a population that keeps growing as ATS crawling discovers new companies rather than being a fixed historical backlog. Looks each eligible company up against Wikidata (`internal/job/wikicompany`, no API key, no billing) and accepts a match only when the resolved entity's own type data — walked transitively via `wdt:P31/wdt:P279*`, both a positive business/organization walk AND a negative geographic/administrative-entity exclusion (a same-named commune or country is rejected even when Wikidata's multi-parent hierarchy also places it under organization — found in production, not the design spike: `Lookup("Nissan")` first resolved to a French commune), never a keyword scan of the description. **Reports by default; `--apply` writes.** `WIKIPEDIA_BACKFILL_MAX_PER_RUN` (default 500, the deployed timer sets 3000) bounds one run — daily rather than the design's original "e.g. monthly" guess, once rollout measured the real backlog (~341k companies, 2026-09-09) and the real throughput (~3s/candidate against Wikidata's public endpoints); monthly would take years to make a dent. A per-company failure (a slow or erroring Wikidata request) is counted and stepped over, never fatal to the run, and is retried on the next one — the company is not marked checked. Idempotent by construction: `companies.company_info_wikipedia_checked_at` (migration 0154) records that a company was resolved — matched or rejected — so it is never looked up twice, the same shape `jobs.hydrated_at` gives ingest. Never overwrites a `tagline`/`company_info` key another source already set. Needs no reindex: neither field is part of `content_hash` or a Meilisearch facet. Needs only `DATABASE_URL`.
- `publish-logo-domains` — daily: writes the company-name-to-domain map `logo.freehire.me` consults, so a logo resolves by the employer's own domain instead of by a name string. Company logos are requested by NAME (`web/src/lib/logo.ts`), taken verbatim from whichever adapter ingested the row, and one employer arrives spelled several ways — `g2i`, `G2i` and `G2i Inc.` all carry `company_slug = 'g2i'`, and the first two resolved to an unrelated leadership-training firm **at HTTP 200**, so no consumer could detect it and fall back to its monogram. The proxy has accepted `?domain=` since it was written and folds it into its cache key (so a name that gains a domain gets a fresh key and the stale rendition simply goes cold — nothing to bust); nothing ever supplied one. **The fix is deliberately not at the call sites**: of ~25 places that draw a logo, roughly fifteen never see a company slug (the experience bank, search suggestions, community subjects, the tailored-CV list), so threading a domain would fix a third of the surfaces and leave the rest guessing. Covers the **17,859** of 239,879 job-carrying companies whose `company_info` records a website; the rest keep today's name guess, and `backfill-company-info-wikipedia` grows that population daily for free. A name two DIFFERENT companies share while disagreeing about the domain is **dropped, never resolved** — a wrong domain returns a confident logo belonging to someone else, which is the failure this removes. **The spellings query is a deliberate sequential scan** (53s, 412,648 rows): joining it to the companies that have a website is four times slower (200s), because the narrow plan drives 17,859 index searches fetching ~102 heap rows each at random — 1.59M blocks of random I/O against the seq scan's sequential read of the same heap. Fewer rows, more work. A run that would publish an **empty** map refuses to swap, the rule `cmd/build-suggestions` already follows. Needs `DATABASE_URL`; without `LOGO_DOMAIN_MAP_OUT` it is a **no-op that never opens the pool**, which is also the rollback. **The consumer is a different repository** (`freehire-logo`, whose `internal/domainmap` reads the file) that `release.sh` does not carry and that is copied to the host by hand — so this half alone changes nothing visible, and a half-delivered change looks exactly like a working one.
- `report-company-website-twins` — hand-run, read-only: lists the companies with open jobs that state the same website host (`company_info.website`, or `company_info.feed_website` where a source stated one and nothing curated did) while their names fold apart. These are merge candidates for a person to propose from the company page, and a moderator decides them (`internal/job/companyrelation`, see [docs/agents/company-identity.md](../../docs/agents/company-identity.md)). It never merges anything, because a shared host is evidence and not a decision: one agency's branches share one, and so can a job board's many employers. Needs only `DATABASE_URL`. Hand-run reports are not in `release.sh`'s build list, so run it with `go run`.
- `capture-apply-form` — drains the apply-form capture queue: fetches each queued posting's application form from `greenhouse`/`ashby`/`workable`/`lever` and stores it in `apply_forms`. Needs nothing but `DATABASE_URL`; `APPLY_FORM_CONCURRENCY` (default 4) bounds how hard one run leans on a platform and `APPLY_FORM_MAX_PER_RUN` (default 5000) how much of the backlog it takes — the second matters because the first drain faces a ~185k backlog and an unbounded run would work for hours, which `Type=oneshot` turns into silently skipped timer firings. `recruitee` forms never reach this queue — its listing carries them, so ingest writes them directly.
- `auto-apply` — drains `auto_apply_queue`: resolves a candidate's known profile answers against a job's live application form via a headless Chrome (`internal/api/atsapply`, `chromedp` — no second language or process) and submits only when every required question is answered; otherwise it touches nothing on the page. Needs `DATABASE_URL`, a Chrome/Chromium binary on the host, and (to fill the résumé field at all) a `TYPST_BIN` the CV renderer resolves — an entry only ever reaches this worker with an approved tailored CV attached (`openspec/changes/auto-apply-tailored-resume`), rendered on demand to a temp PDF; nothing else it fills needs `S3_*`, which stays read-but-not-required. The queue is populated by the job page's auto-apply button and by the signed-in MCP server's `auto_apply_start` tool (behind the account's `agents_may_apply` switch, `openspec/changes/auto-apply-over-mcp`); every queue UPDATE lands in `auto_apply_events` through a trigger, while the deletes (submission, cancel) and a retry write their own event in the same statement — a new delete path must too — and a stopped attempt is re-armed by the candidate's retry, never by this worker. See [internal/application/autoapply/AGENTS.md](../../internal/application/autoapply/AGENTS.md) and [internal/api/atsapply/AGENTS.md](../../internal/api/atsapply/AGENTS.md).
- `liveness` — closes stale postings through source-specific evidence, with an advisory lock preventing concurrent runs. Needs `DATABASE_URL`; closures queue their search removals atomically. Instaffo, Remote.com, The Hub and Reed each get a paced status-only pass over at most 500 stale postings per run, spaced two seconds apart. These passes require the posting URL to retain its host and path, stop on 403/429, and use the existing two-strike closure rule. The other evidence readers, age fallback and source eligibility are described in [job lifecycle](job-lifecycle.md). A manual `-job-ids=1,2` run probes only up to 500 distinct positive IDs, intersected with `-source` when set. It preserves source eligibility, the registered-source staleness gate and two-strike confirmation, and skips every bulk deadline/age closure.
- `adzuna-liveness` — closes the adzuna and wellfound postings the source itself has taken down (it began with adzuna and kept the name, since the binary and its crawl-host unit are deployed under it). - `search-ping` — announces the newest job pages to the external search engines that accept being TOLD rather than waiting to be crawled: Google's Indexing API and IndexNow (Bing/Yandex/Seznam/Naver). Hourly. It exists because waiting does not work at this catalogue's size — measured 2026-09-14, Googlebot fetched **65 distinct job pages in a day** against ~690k in the sitemap, and Search Console's URL Inspection answers `URL is unknown to Google` for postings sampled from it (pages Google has never once fetched) while the site publishes ~14k new technical postings daily. **The budget is the design constraint, not the plumbing.** Google grants 200 publish calls a day by default, so this is deliberately a LEDGER (`job_search_pings`, migration 0162) and not an outbox: an outbox fed by `cmd/ingest` would grow without bound forever and its oldest row would never be reached, while recording what was SENT lets each run choose the newest eligible postings afresh. Enrichment, embeddings and the social digest stay `is_tech`-gated — they cost money or speak for the brand. **Company pages are announced too, and only through IndexNow** — measured 2026-09-15 via the Bing Webmaster API, Bing holds **255,038** of this site's pages and its highest-impression ones are `/companies/<slug>`, answering the query shape "<company name> careers"; Google's own August data agrees, and bingbot crawls company pages half again as often as job pages. Google's Indexing API may NOT be told about them — it admits only `JobPosting` and `BroadcastEvent`, and the penalty for anything else is the quota — so `Engine.Accepts` declines that pass for Google and the runner skips it without reporting it. Eligibility is `companies.job_count > 0`, the same gate the sitemap uses; their ledger is `company_search_pings` (migration 0164) with no `kind` column, because a company page has one event and its URL survives its postings closing. **Each posting is announced twice** — once when it appears and once after it closes, both as `URL_UPDATED`: a closed posting's page stays at HTTP 200 with its `JobPosting` markup and a `validThrough` moved into the past, which is one of the three ways Google documents for retiring a posting, so a closure needs a re-crawl and `URL_DELETED` would be a misuse of the API against a live page. Google needs `GOOGLE_INDEXING_KEY_FILE` (a service account key ON THE HOST, not in `.env`, which cannot hold a multi-line value; the account must be an **owner** in Search Console, not merely a full user — a full user gets `Permission denied. - `linkedin-auth` — **run by hand**, roughly once every sixty days: grants, records and inspects the credential the digest posts to LinkedIn with. `-url` prints the address to open in a browser, `-code <value>` exchanges what that browser handed back, `-token <value>` stores one minted in the Developer Portal's own token generator instead, `-status` reports what is stored and when it dies (never the token itself). Not a route on purpose — a sign-in flow for an audience of one, whose authorization would then be whatever that route's turned out to be; a command needs SSH, which is authorization we already have. **The exchange is also the only way to learn whether LinkedIn issued a refresh token**, which decides whether the credential renews itself or needs a person; it logs the answer explicitly. Needs `DATABASE_URL` and the four `LINKEDIN_*` values.
- `linkedin-token-refresh` — daily: renews that credential a fortnight before expiry when LinkedIn permits it, and warns when it does not. Both paths ship because programmatic refresh tokens go to approved Marketing Developer Platform partners only and the Community Management API is not that program — so a null refresh token is the EXPECTED case, not an error. **A warning is a published gauge, not a red unit**: this fleet already runs ~37 permanently failing ingest units, so a non-zero exit repeated daily for two weeks trains an operator to ignore it. `freehire_social_token_expires_in_seconds`, `freehire_social_token_grant_expires_in_seconds` and `freehire_social_token_renewable` go to the node_exporter textfile collector when `PROM_TEXTFILE_DIR` is set (negative seconds mean "no credential stored", which must not look like a broken exporter). A non-zero exit is reserved for a credential that is ALREADY dead. Needs `DATABASE_URL` and the four `LINKEDIN_*` values; without them it is a no-op that never opens the pool. See [internal/engage/linkedinauth/AGENTS.md](../../internal/engage/linkedinauth/AGENTS.md).
- `merge-companies` — collapses the company slugs that are one employer written more than one way (`ringcentral` + `ringcentral-inc`, `dollar-tree` + `dollartree`). Most groups it finds by folding the NAME; the pairs no fold can reach — one employer whose own boards disagree about the name, `Exadel` beside `Exadel Inc (Website)` — come from the hand-written list in `cmd/merge-companies/curated.go`, which argues why a list and not a rule (`Intel` and `intel471` are different employers). **Reports by default; `--apply` writes.** `--min-jobs N` bounds a wave to the folded groups whose combined open jobs reach N, which is how the backlog is taken in reviewed passes (1000, then 100, then 10, then 1) rather than one 333k-row leap. Chunked and idempotent — the chunk statement selects rows still carrying the retired slug, so a re-run moves nothing and an interrupted wave resumes. **It does not queue its rows for search** — a facet-index push costs minutes per wave, so feeding a merge through `search_outbox` is hours of pushes — **so follow a wave (or a day of waves) with one by-hand `freehire-reindexw` run**: no timer rebuilds the index since 2026-11-05, and until the run a merged company under-counts its jobs without anything 404ing. `REINDEX_DEDUP` stays unset. Needs only `DATABASE_URL`. See [docs/agents/company-identity.md](../../docs/agents/company-identity.md).
- `close-chronic-boards` — the safety net for a board (or boardless provider) that has proven unreachable for a long time, not merely cooling down from a recent run of failures (issue #2017): the ordinary per-run unseen sweep never closes a board's jobs unless that run proved it covered the board (`shouldSweep`/`boardQualifies`/`sweepableCompanies`), which is correct against a transient failure but leaves a permanently broken board's jobs open forever, since it can never re-qualify. `board_health.ListChronicBoards` answers two separate windows off the same evidence (`last_success_at`, or `first_seen_at` for a board that has never once succeeded): `CHRONIC_BOARD_WINDOW_DAYS` (default 30) is what `cmd/ingest`'s per-run health summary reports for curation — fix the adapter, retire the board, or wait; `CHRONIC_BOARD_CLOSE_WINDOW_DAYS` (default 60, deliberately longer, giving a curator the gap between the two to act first) is what this worker acts on, closing the board's own open jobs with `closed_reason = 'board_unreachable'` — distinct from the sweep's `'unseen'`, so the two are never conflated. Scoped to exactly the `(provider, board)` health record that qualified: a multi-board provider's other boards are untouched; a boardless provider's single record already stands for its whole crawl, so going chronic there closes the whole provider. **Refuses a region-ambiguous board name outright** — a board id repeated per region for one provider (e.g. Adzuna's `it-jobs` once per country) has no region in `jobs.external_id`, so a board-scoped close cannot tell one region's postings from another's; such a board is skipped and counted separately in the run's report rather than risking a healthy region's jobs, the same refusal the ordinary sweep's `ambiguousRegionBoards` already makes. **Dry-run by default, reporting what it would close; `--apply` writes** — ships dry-run-only on its timer until a human has read at least one full closure window's report (`freehire-ops' provision/host2/systemd/freehire-close-chronic-boards.service`'s own comment is the reminder to flip it). Idempotent (`closed_at IS NULL` guarded) and cheap regardless of when it runs — daily. Needs only `DATABASE_URL`. **A SECOND pass in the same worker closes the opposite failure**: a board whose crawls all SUCCEED and whose feed carries nothing. `last_success_at` cannot see it — an empty-but-reachable feed refreshes that column on every single run, leaving `consecutive_failures` at 0 and the unit green — so `board_health.last_yield_at` (migration 0158) records when a board last actually YIELDED a posting, written only by a crawl whose LISTING named one (`pipeline.boardListedAnyPosting` — ingested, rejected, already-covered, unreadable OR failed-to-save, deliberately the most generous reading available and deliberately NOT the `boardReachedPostings` permission gate beside it: there, false costs a crawl cycle, but stamped here false accumulates into "this feed is empty" and eventually CLOSES, so a board whose listing works while its detail requests all fail would lose every live posting on it). `EMPTY_FEED_CLOSE_WINDOW_DAYS` (default 30, deliberately SHORTER than the unreachable window — that one waits out a problem on OUR side, this one has already been answered successfully on every run) closes with `closed_reason = 'feed_empty'`, a third distinct label because "every crawl succeeded and there was nothing there" points at the source's inventory while `'board_unreachable'` points at our access. The pass refuses a board with NULL `last_yield_at` permanently: that means no yield has been OBSERVED, not that the feed is empty, and it was true of all 155k rows the day the column landed — which is why **migration 0158's backfill (`last_yield_at = last_success_at`) is load-bearing, not cosmetic**, and why nothing can be closed by this pass until it has been observably empty for a full window AFTER that migration. Found by the WhatJobs incident of 2026-09-10: a market's publisher account was emptied, 107 postings sat open for a month, and neither existing net could reach them. See [docs/agents/job-lifecycle.md](../../docs/agents/job-lifecycle.md).
- `report-cv-letters` — hand-run, read-only: per CV lifecycle letter, sent, delivered, clicked (SES) and how many recipients started paying within 14 days, against the holdout that was never mailed, on the letter's own clock. Needs only `DATABASE_URL`; run it with `go run`. Reading rules, and why opens are n/a, in [internal/engage/cvlifecycle/AGENTS.md](../../internal/engage/cvlifecycle/AGENTS.md#reports).
- `report-skill-gaps` / `report-classify-drift` — hand-run, read-only reports (`internal/job/dictgap`) that mine LLM enrichment output nothing else reads: `enrichment.skills` is a free-text list the model writes per posting, and `enrichment.seniority`/`category` is the model's own guess at the same facets `internal/dict/classify` derives independently from the title. `report-skill-gaps` ranks the raw skill phrases `internal/dict/skilltag` resolves to no canonical, by frequency; `report-classify-drift` recomputes `classify.Parse` for every distinct enriched title and ranks the titles where that answer disagrees with what enrichment recorded, tracked separately for seniority and category. Neither writes anything — no database row, no dictionary source file, no `--apply` flag — and neither is on a timer: a curator runs one, reads the ranked list, and decides by hand what belongs in `dictionaries.go`/`labels.go`/`descriptions.tsv` or the `classify` title tables. No reindex needed either, since nothing they touch changes. Needs only `DATABASE_URL`. **`report-geo-gaps`** is the third of them, for `internal/dict/location`: it re-runs `location.Parse` on every distinct location string among publishable postings and compares it with `enrichment.countries`, printing GAPS (the dictionary places the location nowhere — no country and no region — while the model names a country) and CONFLICTS (the dictionary names countries most of the location's postings contradict, the `georgia` shape). Its share column is the confidence signal: the model is also asked about `Remote`-only postings and answers those with a guess, so a 40% share is noise and a 97% one is a missing name.
- **Nothing holds a flock** — no file locks in Go or in the systemd units; the word survives only in a few stale comments. What keeps a cron worker from stacking on itself is systemd: a `Type=oneshot` unit will not start a second instance while the first is active. That protects the TIMER path only, so a run started by hand has no lock at all. **Never stack `reindex-companies` with `make reindex`** — Meilisearch runs one serial task queue, so the second rebuild queues behind the first and looks like a hang, and a swap transiently holds ~2x the index's disk. Two workers additionally take a Postgres advisory lock (`cmd/liveness`, `cmd/ghost-crosscheck`), and `reindex`, `reindex-companies` and `build-suggestions` share one more (`worker.HeavyIndexLockKey`), however they were started; their keys are listed in `internal/platform/migrate`. A run that finds the index lock held logs `another catalogue-wide index job is running — skipping this run` and exits 0 having done nothing, so re-run a skipped manual rebuild once the other job is done.
- `sweep-tracer-clicks` — daily: deletes CV tracer-link clicks (`cv_link_clicks`) older than `TRACER_CLICK_RETENTION_DAYS` (default 180, read through the strict worker reader). The privacy policy promises those records are gone after 180 days, so it **deletes by default** — there is no dry run, because a retention promise that only reports keeps nothing. The tracer tokens stay: an old PDF must keep redirecting. Idempotent, so a missed or repeated run costs nothing. Needs only `DATABASE_URL`.
