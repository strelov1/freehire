# Headless error aggregation using existing open-source tools

Research date: 2026-11-01. Primary GitHub source and official documentation only. This is a source/documentation assessment, not a deployed acceptance test. Existing Vector 0.57.0, VictoriaLogs 1.52.0 and Grafana/Prometheus/Telegram infrastructure are supplied investigation context; this note does not independently audit the host.

## Recommendation

Reuse Vector + VictoriaLogs for centralized error events and CLI investigation. Use Grafana-managed alert rules through the native VictoriaLogs datasource and the existing Telegram contact point. The current upstream plugin explicitly declares both backend and alerting support; check the installed plugin version before provisioning. [Plugin manifest](https://github.com/VictoriaMetrics/victorialogs-datasource/blob/main/src/plugin.json). Do not build a query server, alert engine, issue database or dashboard. This is the smallest operational change, but it gives searchable error aggregation rather than Sentry's issue lifecycle and automatic source-map processing.

If automatic exception grouping and private source-map resolution are hard requirements now, evaluate **Traceway** before implementing those features ourselves: its repository already contains the CLI, exception product and Telegram adapter. Its larger deployment and browser SDK are meaningful tradeoffs. No researched option establishes automatic coverage of every WXT execution context without integration work.

## Existing stack: capabilities verified against pinned source

- VictoriaLogs **1.52.0** accepts OTLP/HTTP logs at `/insert/opentelemetry/v1/logs`, including standard Go SDK/Collector exporters. Resource attributes become stream fields unless overridden. Do not make request IDs or user IDs stream identity fields. [Pinned ingestion documentation](https://github.com/VictoriaMetrics/VictoriaLogs/blob/v1.52.0/docs/victorialogs/data-ingestion/opentelemetry.md).
- **vlogscli** is the maintained interactive CLI: history, live tail, search, JSON/logfmt output. Upstream explicitly recommends **curl + jq** for noninteractive processing. Both paths need no UI session. Given the existing external query restriction, run them through SSH or an operator tunnel on local port 19428 to the private query endpoint rather than opening database query access publicly. [Pinned CLI documentation](https://github.com/VictoriaMetrics/VictoriaLogs/blob/v1.52.0/docs/victorialogs/querying/vlogscli.md).
- **Grafana-managed alerts** avoid adding another evaluator or notification service: use the native VictoriaLogs backend datasource for a numeric LogsQL stats query, Grafana reduce/threshold expressions, and the existing Telegram contact point. The upstream manifest requires Grafana >=10.4.0. For the query model use `queryType: stats` (numeric instant) or `statsRange` (time series), not `instant` (raw log rows); expression lives in `expr`. [Backend query schema](https://github.com/VictoriaMetrics/victorialogs-datasource/blob/main/pkg/plugin/query.go). This differs from datasource-managed vmalert alerts, which the VictoriaLogs plugin cannot display. Do not disguise VictoriaLogs as a Prometheus datasource: compatible stats response format does not mean identical URL paths. [Plugin manifest](https://github.com/VictoriaMetrics/victorialogs-datasource/blob/main/src/plugin.json), [documented datasource-managed limitation](https://docs.victoriametrics.com/victorialogs/vmalert/#how-to-display-rules-in-grafana-alerting-ui).
- **vmalert**, an alternative if independent declarative evaluation becomes necessary, evaluates `type: vlogs` groups against VictoriaLogs stats APIs. Rules use LogsQL `stats` and threshold filters; evaluation interval supplies the default lookback. This supports per-service error counts/rates and configurable filters. Notification delivery is delegated to Alertmanager, which has a Telegram receiver. The vmalert binary has its own release version; pin and validate it rather than using the VictoriaLogs version number. [Pinned alerting documentation](https://github.com/VictoriaMetrics/VictoriaLogs/blob/v1.52.0/docs/victorialogs/vmalert.md), [Alertmanager Telegram configuration](https://prometheus.io/docs/alerting/latest/configuration/#telegram_config).
- Existing **Vector 0.57.0** already implements OTLP HTTP and gRPC receiving and separate logs/metrics/traces outputs. Therefore a new OTel Collector is not inherently required. Its `use_otlp_decoding` option differs from newer live docs. The pinned HTTP receiver only accepts `application/x-protobuf`: choose the JS OTLP **proto** exporter, not the HTTP JSON exporter. Native legacy conversion stores body in `message`, resource attributes in `resources`, log attributes in `attributes`, plus `severity_text`, `severity_number`, `trace_id`, `span_id`, `timestamp` and `observed_timestamp`; set `log_namespace: false` to keep this JSON shape. Dotted attribute keys remain literal object keys. [Pinned native mapping](https://github.com/vectordotdev/vector/blob/v0.57.0/lib/opentelemetry-proto/src/logs.rs). The pinned HTTP configuration has TLS/address/header controls but no CORS setting; browser access needs an ingress solution, preferably a same-origin reverse-proxy route with request limits. Prove resource/exception-field preservation through the existing JSON sink before choosing native conversion versus raw OTLP. [Pinned receiver configuration](https://github.com/vectordotdev/vector/blob/v0.57.0/src/sources/opentelemetry/config.rs), [Pinned HTTP implementation](https://github.com/vectordotdev/vector/blob/v0.57.0/src/sources/opentelemetry/http.rs).
- The official **mcp-victorialogs** project provides read-only queries, field discovery, stats and embedded documentation through stdio or HTTP. It can supply an optional agent interface; it does not replace the required CLI. VictoriaLogs and its MCP server are Apache-2.0; Vector is MPL-2.0. [MCP repository](https://github.com/VictoriaMetrics/mcp-victorialogs), [VictoriaLogs license](https://github.com/VictoriaMetrics/VictoriaLogs/blob/master/LICENSE), [Vector pinned license](https://github.com/vectordotdev/vector/blob/v0.57.0/LICENSE).

## Collection: what reusable instrumentation does and does not cover

Go can bridge `log/slog` through the official `otelslog` handler and export standard OTLP logs. Existing structured journald logs can continue through Vector: direct OTLP is optional, and sending both creates duplicate events unless deliberately controlled. Emit exception type, message and stack plus service/version/environment and trace correlation consistently; ordinary log bridges do not automatically turn all returned errors into captured exceptions. [Official bridge](https://pkg.go.dev/go.opentelemetry.io/contrib/bridges/otelslog).

For run-once cron workers, end spans and call provider shutdown/flush before process exit with a fresh bounded context. An `os.Exit` bypasses deferred cleanup; a `run() error` boundary can return through cleanup before the outer main exits. No SDK guarantees delivery after SIGKILL, fatal runtime failure or power loss. [Trace flush](https://pkg.go.dev/go.opentelemetry.io/otel/sdk/trace#TracerProvider.ForceFlush), [Log shutdown](https://pkg.go.dev/go.opentelemetry.io/otel/sdk/log#LoggerProvider.Shutdown).

The new official **opentelemetry-browser** instrumentation includes `ErrorsInstrumentation`: uncaught `window.error` and `unhandledrejection` become exception log events. It is explicitly experimental. This avoids inventing browser exception listeners, but is not proof of extension service-worker compatibility. SvelteKit handled errors, expected application errors, SSE protocol failures and WXT background/content-script contexts still need explicit framework/context integration and a defined capture policy. An HTTP request span ending successfully does not prove that the subsequent SSE application stream succeeded. [Official experimental browser package](https://github.com/open-telemetry/opentelemetry-browser/blob/main/packages/instrumentation/README.md).

**Faro is unsuitable as the universal SDK here.** Its README explicitly excludes browser extensions, Web/Service Workers and server-side rendering runtimes. It is useful for normal browser pages and offers explicit caught-error reporting. Alloy's `faro.receiver` can symbolicate using private filesystem/HTTP maps and release-templated paths, so public sourcemaps are unnecessary; however this adds Faro/Alloy collection and does not remove the extension gap. VictoriaLogs alone does not provide that symbolication pipeline. [Faro support limits](https://github.com/grafana/faro-web-sdk), [Faro API](https://github.com/grafana/faro-web-sdk/blob/main/packages/core/README.md), [Alloy sourcemap receiver](https://grafana.com/docs/alloy/latest/reference/components/faro/faro.receiver/).

## Concrete acceptance checks before implementation is called complete

Use one identifiable synthetic exception per Go request, short-lived worker, SSR request, browser handled/uncaught rejection, WXT side-panel, background worker and content script; query each from a fresh noninteractive CLI session. Verify a failed SSE after headers is captured. Test worker normal/failure shutdown and browser unload/extension suspension; never claim crash-proof delivery. Demonstrate one configurable Telegram trigger with grouping and repeat control. For minified browser/extension stacks, demonstrate a release-matched private map or explicitly accept raw stacks; retaining artifacts alone does not symbolicate them. These are integration acceptance checks, not a reason to write another telemetry platform.
