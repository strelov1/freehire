# AGENTS.md

Guidance for AI agents working in this repository.

## Working principles

- **No overengineering, and no MVP shortcuts.** Hold the middle path: don't build infrastructure before there's a concrete need (note the seam for later instead), and don't ship quick-and-dirty or "for now" hacks. Build each feature correctly and idiomatically — neither gold-plated nor a placeholder.
- **MVP stage — keep the architecture fluid.** The current structure is not load-bearing legacy. When a new feature doesn't fit cleanly, prefer reshaping the affected part over bolting on an awkward special case.
- **Surgical changes.** Clean up what your change orphaned; leave pre-existing dead code alone. Prefer a library's intended API over a clever shim.
- **English only.** All code, comments, identifiers, docs, and commits.

## What this is

`freehire` ([freehire.me](https://freehire.me)) is an open-source IT job aggregator. Many source parsers feed a pipeline that normalizes jobs into one schema, deduplicates them, and enriches them with AI; served over an HTTP API with rich filters, consumed by a SvelteKit app under `web/`.

Stack: **Go + Fiber v2**, **PostgreSQL**, **sqlc**, **Meilisearch**, **Docker Compose**, **langchaingo**.

## Layout

`internal/<block>/<pkg>/` — every package sits in exactly one of **eleven blocks**, and the
blocks form **eight layers**. A block may import only blocks strictly below it; two blocks
sharing a layer may not see each other in either direction. The substantial packages carry
their own AGENTS.md (see the table below), and each block carries one saying what it is and
what it may reach for.

```
8. api           handlers, middleware, realtime, OG images
7. engage        notifications, digests, onboarding, referrals
   ingest        source adapters, crawl pipeline, link import, manual intake
6. application   tracking, stages, the event ledger, mail and calendar
   search        Meili topology, the drain, saved searches, intent
5. job           the posting: identity, facets, wire shape, dedup, ghost signal
4. candidate     CV, structured extraction, experience bank, PII, matching
3. ai            enrichment, embeddings, assistant, speech, plan limits
   identity      accounts, auth, profile
2. dict          the facet dictionaries and normalisation under them
1. platform      db, worker plumbing, outbox, cache, HTTP and LLM transport
```

The rule is enforced twice: `depguard` in `.golangci.yml` fails on the offending import
line, and `internal/platform/arch/layering` holds the same table and reports the whole
graph at once — including imports that exist only in test files, and only because
`run.build-tags` names `integration` and `llmlive`. Without those tags both guards go blind
over 222 files. **Adding a package means adding it to the table in
`internal/platform/arch/layering/blocks.go`**; a package in neither fails the guard.

Two placements surprise people, and both are in the table's comments: the LLM client
(`platform/llm`) is transport, not AI — it knows nothing about the domain, like `safehttp`;
and moderator-authored vacancies plus the public submission queue are `ingest`, because
they are manual job intake rather than applications.

`cmd/<name>/` — every binary is a **run-once-and-exit** worker except `cmd/server`, `cmd/mail-ingest` (a long-lived SES inbound daemon, `Restart=always`), and `cmd/auto-apply-orchestrate` (serves the Inngest function's own HTTP callback protocol between steps, needs no `DATABASE_URL`). The rest are cron-driven, not daemons; they need `DATABASE_URL` and exit non-zero on failure.

Non-obvious:

- `migrations/` — the source for **both** sqlc codegen and Postgres initdb. Never edit an applied migration; add a new file. `pnpm check:sql` (squawk, via `scripts/check-migrations.mjs`) lints the ones a change ADDS — the applied history holds 1322 findings that stay, because rewriting an applied file is a worse hazard than any of them. Whether a file runs inside a transaction is a property of the FILE (the `migrate: no-transaction` marker, which must be a comment line of its OWN — quoted inside a sentence it does not count, and used to), so the check runs two passes; `.squawk.toml` carries the argument. Suppress a rule with `-- squawk-ignore <rule-name>` on the line before the statement, with the reason beside it.
- Dead JS code and unused dependencies: `pnpm check:dead` (knip, the `dead-code` CI job) gates **everything knip reports — files, dependencies, binaries AND exports** across `web/`, `design-system/` and the root scripts. An exported name nothing imports fails the build, an exported *type* included; `knip.config.js` argues why the line ended up there rather than at the usual "report exports, do not gate them", and the two deliberate exemptions carry a JSDoc `@public` tag beside the code rather than an entry in the config. (This paragraph used to describe a narrower gate and a `pnpm check:dead:exports` script that no longer exists — the config is the current answer.) CI only, since knip needs both packages' dependencies installed and a fresh worktree usually has neither.
- Dead **Go** code: `deadcode -test -tags=integration,llmlive ./...` (the `dead-code-go` CI job), which builds the whole call graph and reports what no binary and no test can reach. **Both flags are load-bearing.** Without the tags it does not parse the build-tagged tests and calls their helpers dead — the same blindness `.golangci.yml`'s `run.build-tags` documents for depguard. Without `-test` every test-only helper is dead. The residue it cannot see is a function whose only caller is its own test; that one still needs a reviewer. To run it locally: `go install golang.org/x/tools/cmd/deadcode@v0.49.0` — with a toolchain at least as new as go.mod's `go` directive, or the binary's type checker rejects the module and reports "package requires newer Go version" instead of findings.
- `.github/workflows/` — linted by `actionlint` (the `workflows` CI job), which also runs shellcheck over every `run:` block. Nothing else reads a workflow until GitHub runs it, so a mistake in one that fires on a tag or a schedule surfaces late.
- **The links in these documents are checked.** `pnpm check:links` (the `docs` CI job and a pre-commit hook) resolves every relative Markdown link in the repository. The table below is the map an agent is meant to follow, so a link that no longer resolves does not just fail — it sends the reader somewhere confidently. The hook carries no glob on purpose: what breaks a link is renaming its **target**, usually a `.go` or `.svelte` file.
- **What we hand to someone else is linted too** (the `artifacts` CI job): `web/static/install.sh` is served at `freehire.me/install.sh` to be piped into `sh`, so shellcheck covers every tracked `*.sh`; both Dockerfiles go through hadolint (`.hadolint.yaml` argues its two exclusions, and a finding wrong for one line carries `# hadolint ignore=` beside it); and `web/static/openapi.yaml` is validated against the OpenAPI specification, since it is a static asset nothing else parses.
- **There is no `sources/` directory.** The board catalog is the `boards` table (`internal/ingest/boardcatalog`) and the Telegram channel list is `telegram_channels` — both moved out of YAML, and nothing in the repository parses a board file any more. `internal/ingest/sources` is the *adapters*, not the catalog.
- `design-system/` — a separate pnpm package, sibling to `web/` and `extension/`, linked via
  pnpm's `link:../design-system` (`web/`) or npm's `file:../design-system` (`extension/`) — both
  are symlinks, not copies. **Install it before building either consumer** — neither package
  manager installs a linked/`file:` package's own dependencies for you. Being a symlink also
  means each of the three installs its OWN `node_modules`, so a package all of them depend on
  sits on disk more than once — free for a value, fatal for a TYPE, since TypeScript
  identifies a type by where it was declared and two copies of `LucideIcon` are two unrelated
  types sharing a name. `pnpm check:deps` (`scripts/check-shared-deps.mjs`, the `shared-deps`
  CI job) holds the three manifests to the same version for exactly the packages the design
  system imports as types — a set it DERIVES from `design-system/src` rather than listing, so
  a new type import joins the rule by existing. It reads no lockfile and compares the declared
  range literally: `^1.25.0` and `^1.45.0` overlap perfectly well and are the two ranges that
  put `@lucide/svelte` on disk twice (freehire#2836), so "the ranges are compatible" is the
  wrong question. `peerDependencies` is exempt — a library's peer range is deliberately wider
  than what it develops against. Dependabot cannot see any of this: it reads three
  `package.json` files as three unrelated projects, so it will keep proposing a bump to one of
  them, and that PR is correct once the other two move with it.
- `extension/` — the browser extension (WXT + Svelte side-panel agent client), npm-managed
  unlike the rest of the JS in this repo. See [extension/AGENTS.md](extension/AGENTS.md).
- `internal/platform/db/` — **generated**; edit `internal/platform/db/queries/*.sql` and run `make sqlc`. The pre-commit hook and the `sqlc` CI job regenerate and diff, so a query edited without regenerating no longer ships the old Go with every check green. Both use `make sqlc`, which holds the only version pin — a second pin would be a second answer, and the drift between them would look exactly like stale code.
- `services/pii-filter` — a standalone service, not a Go package.
- **There is no `deploy/` snapshot of the host any more.** The systemd units, the nginx
  snippets, the operator scripts (`release.sh`, `autodeploy.sh`, `gen-ingest-timers.sh`)
  and the prose explaining them all live in the private `freehire-ops` repository, under
  `provision/host2/` and `scripts/host2/` — that is the only place any of them is edited,
  and `provision/host2/AGENTS.md` is the document to read about this machine. This repo
  carried a third copy of all of it until 2026-09-18. It drifted from the host in BOTH
  directions and was deleted rather than kept in step: measured against the running host,
  this repo's copies were the more accurate ones for the scripts (14 of 17), for most units
  and for all three hand-edited nginx files, while a Sentry gate merged here had never once
  run because the host had never heard of it. Both being partly right, with nothing able to
  say which half, is the whole argument for one copy. `deploy/rollback/` stays: those are a
  migration's SQL, not host configuration.
- **Nothing in `freehire-ops` deploys itself either.** `release.sh` builds and flips the
  app; it never touches a unit, a snippet or a script. Editing one there is half the job —
  the other half is copying it to the host and running `systemctl daemon-reload`. Its own
  `scripts/host2/drift-check.sh` reports what has moved apart.

## Commands

```bash
make up / make down / make logs       # start / stop / tail app + postgres in Docker
make run / make psql / make sqlc      # run server on host / psql into DB / regenerate internal/platform/db
make reindex                          # rebuild the Meilisearch jobs index from Postgres
go build ./...  &&  go vet ./...
go test ./...                             # unit tests (no external deps)
go vet -tags=integration ./...            # compiles the tagged tests — run before EVERY push
go test -tags=integration ./internal/platform/db/  # queue integration tests (needs Docker; testcontainers)
golangci-lint run                         # .golangci.yml; CI only fails on issues new-from-main (ratchet)
```

**Before committing** any `*.go` file: `gofmt -w` those paths (`gofmt -l .` must print
nothing), then `go vet ./...` and `go test ./...`. Do not commit if they fail. Skip this
suite when the commit has no Go. Integration-tagged tests stay push-time (`go vet
-tags=integration ./...` before every push; the full tagged suite when behaviour changed).

**Pre-commit hooks:** [lefthook](https://github.com/evilmartians/lefthook) (`go install
github.com/evilmartians/lefthook@latest`, then `lefthook install` once per clone) runs
gofmt/vet/golangci-lint on staged Go files and eslint on staged files in web/, extension/,
design-system/ — the same ratchet policy as CI (only new issues fail the commit), so it
won't block on the pre-existing backlog.

**Secrets** are the one thing the hooks *prevent* rather than report: `gitleaks` (`brew
install gitleaks`) scans the staged index on every commit and fails hard if the binary is
missing, because a scanner that quietly skips makes a commit look examined. The
`gitleaks` workflow scans the whole history on top, since `--no-verify` walks past the
hook and a credential removed in a later commit is still leaked. A finding that survives
`.gitleaks.toml` means **revoke the credential** — rewriting history does not un-leak
anything. Suppressions in that file allowlist a *line shape*, never a path: gitleaks ORs
`paths` with `regexes` and prunes the file before reading it, so a path entry switches
the scanner off for that file entirely.

**`go test ./...` compiles no `//go:build integration` file, and those files are not
confined to `internal/platform/db`** — there are 187 of them across 20 packages, and `internal/api/handler`
holds 78, which call unexported constructors like `newCVHandlers`. A changed signature
therefore passes every command above except the `vet` line, then fails CI, which runs
`go test -tags=integration ./...` over the whole module. The vet line is the cheap guard:
seconds, no Docker. Run the full tagged suite when you change behaviour rather than a
signature.

Worker gotchas (`go run ./cmd/<name>`, all need `DATABASE_URL`; run `ls cmd/` for the full list):

- `migrate` — run **before** deploying code that reads new schema. `-baseline` records on-disk files without executing; a pre-runner database auto-baselines on first run.
- `ingest` — takes one PROVIDER NAME: `go run ./cmd/ingest <provider>` (or `INGEST_PROVIDER`), and reads that provider's live boards from the `boards` table. Handing it a file path is not an error — the path becomes the provider it looks up, which finds nothing, logs `providers=0` and exits 0. `HYDRATION_RETRY_DAYS` widens the window (default 14 days, measured from `created_at`) during which a stored row with NO description is withheld from the seen-set so a hydrating adapter re-attempts its detail fetch. Set it only for a deliberate repair run — `HYDRATION_RETRY_DAYS=365 ingest hh` re-offers every body-less row of that provider, one extra detail request each (hh's detail pages are ~1 MB), and expect to repeat it: a run that hits its timeout still persists what it hydrated and the fixed rows leave the set, so successive runs shrink the backlog. An unparseable or non-positive value fails the run rather than falling back, because a typo here would look exactly like a repair that found nothing. **`INGEST_REFETCH_ALL=1` empties the seen-set for the run**, so every listed posting is treated as new and the pipeline re-WRITES it instead of only refreshing its liveness. That is the repair path for an adapter fix that changes what the LISTING yields (a mis-read remote flag, a location built from the wrong place): the fix reaches new postings on the next crawl and reaches the stored ones never, and `backfill-derive` cannot recover them either — it re-derives FROM the stored columns, which hold the wrong reading. Costs one detail request per stored posting (nofluffjobs: ~19k postings, ~20 min at 8 workers), re-enqueues only what actually changed for search, and re-enqueues nothing for enrichment (that queue is gated on `enrichment_version`, not on the write). A failed detail fetch cannot wipe a body — `UpsertJob` keeps the stored description when the incoming one is empty — so a run that hits its timeout is simply repeated. **`BODY_REFRESH_DAYS` re-reads a stored body that has gone stale**, so an employer's later EDIT reaches the catalogue at all: a hydrating adapter fetches detail only while the catalogue lacks the posting, so once stored a body is never read again and a posting that gains a "this position is 100% on-site" paragraph keeps whatever we read the day we first saw it (freehire#2555). It ships UNSET, which is disabled — turning it on costs one detail request per re-read posting against a crawl fleet that is already the host's bottleneck, so enable it one provider at a time and watch the load. `BODY_REFRESH_SLICE` (default 30) bounds one run: a posting belongs to one slice for its life and a run takes the slice named by the day of the year, so a full sweep takes SLICE days and no run faces a provider's whole catalogue (1.27M postings on workday). Setting the slice without the days fails the run rather than doing nothing. What records a body's age is `jobs.hydrated_at` (migration 0144), written by both ingest write paths and NOT by the liveness-only `TouchJob`; `updated_at` cannot serve, because the cheap write deliberately leaves it alone and a body that came back identical is the common case.
- `enrich` / `tg-extract` — need `LLM_BASE_URL` / `LLM_API_KEY` / `LLM_MODEL`.
- `embed` / `search-drain` / `rollup-facets` / `reindex-companies` — need `MEILI_URL` / `MEILI_MASTER_KEY`. `search-drain` drains `search_outbox` (queued by `cmd/ingest`, atomically with each write) into the live facet index in batches — run it frequently (e.g. every 1-2 min); see [internal/search/searchdrain/AGENTS.md](internal/search/searchdrain/AGENTS.md).
- `reindex` — rebuilds the Meilisearch jobs index. **`REINDEX_DEDUP=1` additionally refreshes the duplicate markers** (role clusters, aggregator suppression, fuzzy collapse) before the rebuild; without it the rebuild uses the markers the last dedup run left. Off by default since 2026-08-16: aggregator suppression alone measured ~23h against a 12h unit timeout, so the run was cancelled mid-dedup and never reached the rebuild — 3 days with zero successful reindexes. Run the dedup invocation on its own, rarer schedule. **`REINDEX_DEDUP_ONLY=1` runs just the marker passes and exits** — no Meilisearch client, no disk guard, no rebuild, so no need to pause `search-drain` for it. It exists so the markers can refresh on a tighter cadence than the full `REINDEX_DEDUP=1` invocation: the plain (no-flag) rebuild already runs every few hours on its own schedule and picks up whatever markers are current, so a fresher marker-only pass alone shrinks the window a repost sits undeduped in search. Takes precedence over `REINDEX_DEDUP` if both are set. **A rebuild also writes the match sort's skill vectors** (`internal/dict/skillvec`), which grows the index by roughly 10 GB and makes the rebuild materially slower — the cost is HNSW graph construction, so it lands here and not on the incremental `search-drain` pushes. Schedule it deliberately, and note the embedder must be in the LIVE index settings before a binary that queries it rolls out — see [internal/search/search/AGENTS.md](internal/search/search/AGENTS.md).
- `backfill-derive` — re-derives every deterministic column (facets, `role_fingerprint`, slugs) in one keyset pass; `BACKFILL_CONCURRENCY` tunes the pool. Follow with `REINDEX_DEDUP=1 make reindex` — that is what collapses newly-clustered reposts and unions their geography. **It is RESUMABLE, and that is not a convenience**: the pass walks 12.7M rows de-TOASTing a description each, which outlasts any sane unit timeout, and until freehire#2864 it had no resume point — `afterID` started at 0 every time. A hand-made transient `taxonomy-backfill-night` unit (`systemd-run`, so in `/run` and in nobody's git) therefore ran it nightly under `TimeoutStartSec=10h`, got killed about two thirds through, restarted at the first id the next night and never once finished — ~29h of CPU a night on the host whose bottleneck is the crawl fleet, while five merged dictionary fixes waited on it. `BACKFILL_DERIVE_FROM_ID` names the first id a run must DO — **inclusive, like the sibling pass's `BACKFILL_REQUIREMENTS_FROM_ID`**, because two knobs sharing a name and a shape while disagreeing about whether the id is done or to-do lose exactly one row per hop — and `BACKFILL_DERIVE_MAX` bounds how many rows it scans, **unset for unbounded, never `0`**, the same strict-reader rule `backfill-clearance` documents. **`BACKFILL_DERIVE_CLOSED_WITHIN_DAYS` narrows the scan to the rows that can still reach the catalogue** — open postings, plus ones closed within that many days — which is what makes a dictionary fix affordable: measured 2026-09-23 the table holds ~12.7M rows against 1.9M open ones, so an unbounded pass spends ~85% of its ~30h on postings no search, sitemap or page will read. It is expressed in DAYS CLOSED and **not** as an open-only flag on purpose: a closed posting is not permanently gone, since ingest's `Toucher` refreshes liveness "(last_seen_at, reopen if closed) ... WITHOUT rewriting its content" and a posting that merely drifts out of a feed for 48h is routinely closed and reopened as it drifts back (see the notes in `sources/seek.go` and `sources/whatjobs.go`) — so a pass that skipped on `closed_at IS NULL` would hand those rows back to the catalogue carrying the OLD dictionary's facets, with nothing downstream reporting the staleness. The number is how far back a posting might still return from; unset keeps the whole table, so the cautious behaviour stays the default and the knob is the deliberate act. A run that stops early says so in as many words and prints the id to continue from — from ONE report every exit path reaches, because deciding that at each `return` is what made the cursor vanish twice in one evening: the scan failing is only one ending, and the companies reconcile that follows it is two more (freehire#2876); a run that reached the end prints `done`, so "there is more" and "that was all" are never inferred from a row count. **The resume point is the oldest row the run did not FINISH, never the newest row its reader read** — the two differ by up to a full page and that gap is silent data loss: `jobsCh` is buffered at `backfillBatchSize`, so the reader hands over a whole page and advances its keyset cursor past it long before a worker writes any of it, and the review that caught this measured a cursor of 500 while id 5 was still unwritten (freehire#2869). A row whose write failed is deliberately left unfinished so the resume point falls before it. Re-reading what an interrupted run had in flight costs nothing, since the write is `changed`-guarded. **There is no timer** — `freehire-ops' provision/host2/systemd/freehire-backfill-derive.service` ships without one, because systemd has nowhere to keep the cursor between runs and a schedule that cannot advance it re-derives the same first rows forever.
- `backfill-clearance` — one-off: fills `jobs.requires_clearance` for the rows that predate the column (migration 0119). It does NOT walk the catalogue: a `description` predicate de-TOASTs all 8M rows to find the ~38k that mention a clearance, and `backfill-derive` (which would also pick the column up) runs ~15h. Meilisearch already indexes the description, so the worker names its candidates there and reads only those bodies. Over-fetching candidates is free — the dictionary decides, and a declined row simply keeps NULL — so the queries are broad single tokens rather than a second, drifting copy of the phrase list. Idempotent (`IS DISTINCT FROM`-guarded), so a re-run writes nothing and stopping it is free; `BACKFILL_CLEARANCE_MAX` caps one run — **leave it unset for unbounded, never `0`**. Every one-off pass's numeric knob now goes through one strict reader (`worker.EnvInt64`, or `worker.EnvInt32` for a knob that must fit a narrower API like `pgtype.Interval.Days` — parsing directly at that bit size is what turns an out-of-range value into a refusal instead of a silent wraparound), which takes only positive integers because for the chunk-width knobs it also serves a `0` is an infinite loop; a set-but-unreadable value fails the run with the value named rather than quietly taking the default, which is the one outcome an operator who typed a number would never notice. **Follow it with a full `make reindex`**: incremental pushes only send documents whose `content_hash` moved and the new column is not in that hash, so without the rebuild the facet is empty for every pre-existing posting — the same trap `is_tech` fell into. Needs `DATABASE_URL`, `MEILI_URL`, `MEILI_MASTER_KEY`.
- `backfill-company-type-hint` — one-off: force-requeues the existing open postings of the companies in `enrich.CompanyTypeHints` (a small, hand-curated `company_slug → outsource/outstaff` map — there is no open dataset of IT outsourcing/outstaffing companies to import instead) back into `enrichment_outbox`, so the next `cmd/enrich` runs rewrite their `company_type` using the new "Known company type" prompt hint. A single job posting rarely states its employer's business model in so many words, so this field came back `null` for these companies far more often than the rest of the enum. Run once after adding an entry to the map — the ordinary `EnqueuePendingJobs` only re-queues rows BELOW the target enrichment version, which skips a company's postings already enriched under it. Idempotent (`ON CONFLICT`-guarded on `(job_id, target_version)`), so re-running before the drain finishes costs nothing. **Follow the drain with a full `make reindex`**: `SetJobEnrichment` never pushes to `search_outbox`, so the corrected values only reach Meilisearch on the next full rebuild — the same gap `backfill-clearance` documents. Needs `DATABASE_URL`.
- `backfill-profession-it-tech` — one-off: sets `is_tech = true` on the Profession `itdev`/`itops` rows stored before that source began asserting the signal at ingest (issue #2601). Profession crawls only these two dedicated IT category boards, so a posting filed under either is confirmed technical by the source's own filing even when the title dictionary resolves no category for it — but without the signal such a row's `is_tech` stayed unknown, `EnqueuePendingJobs`'s `is_tech IS TRUE` gate never queued it for enrichment, and `search.CategoryUnresolved` excluded it from search forever, not just until the next enrichment cycle. A single `UPDATE`, not chunked: the affected set is bounded to two boards, unlike the multi-million-row backfills that need an id-range walk. Idempotent (`IS DISTINCT FROM`-guarded), so a re-run writes nothing and stopping it is free. **Follow it with a full `make reindex`**: `is_tech` is not part of `content_hash`, so an incremental push alone would never reach these pre-existing rows — the same trap `backfill-clearance` documents. Needs only `DATABASE_URL`.
- `close-apploi-misattributed` — one-off: closes every open apploi posting and retires the provider's 5833 boards, because what the catalogue holds about them is wrong and **cannot be repaired in place**. Measured 2026-09-15: apploi's API stopped honouring its `employer` parameter — `employer=39092`, `employer=999999999` and no parameter at all return byte-identical pages — so every board fetched the same GLOBAL catalogue, and since the adapter attributes with `firstNonEmpty(e.Company, j.BrandName)` and all 5833 board rows carry a company, the real `brand_name` was never once stored. 1,565,701 rows stood for 3,024 real jobs (518 copies each, under 518 mostly-wrong employers), 264,022 of them reaching live search — 12.5% of everything a visitor could find. Repair is impossible (the correct employer is in no stored field, and there is no way to choose which of 518 companies to keep) and the adapter rewrite is not worth it: 5,074 of the 1.47M open rows are `is_tech`, 0.34%, which at 518 copies is on the order of ten real technical jobs. Soft close only, with its own `closed_reason = 'source_misattributed'` (migration 0165) — that label IS the rollback, being the only thing separating these rows from ordinarily-closed ones. Chunked over an id RANGE, paced, idempotent (`closed_at IS NULL`-guarded); `CLOSE_APPLOI_CHUNK` (default 50k) sets the span and `CLOSE_APPLOI_FROM_ID` resumes at the logged cursor. **Deliberately does NOT push to `search_delete_outbox`**, unlike every other close: 1.47M entries against a queue whose ordinary depth is ~7k would sit in front of every other Meilisearch task, and the rebuild reads open rows from Postgres anyway — the same trade `merge-companies` makes. **Follow it with a reindex, or wait for the scheduled one**; until then the postings stay searchable. Needs only `DATABASE_URL`.
- `backfill-remote-perk-false-positive` — one-off: corrects `jobs.work_mode` for the rows freehire#2696 mis-set to `remote` before #2710 fixed `WorkModeFromDescription`'s "work from anywhere" false positive (a bounded travel/PTO perk phrase, not a work-arrangement statement). `backfill-derive` cannot reach these rows — it feeds a row's CURRENTLY STORED `work_mode` back in as the structured-signal input, so the old bug's output is indistinguishable from a real ATS signal and is carried forward unchanged — and ordinary re-ingest doesn't either, since a stored, still-open posting's description is never re-read (see `BODY_REFRESH_DAYS` above). Candidates come from Meilisearch (`work_mode=remote` + the text query "work from anywhere"), the same over-fetch-and-let-the-dictionary-decide shape `backfill-clearance` uses; the write recomputes `work_mode` from the row's stored `location`/`description` alone (no structured-signal input — the whole point is to stop trusting what's stored) and only touches rows where that recompute no longer says `remote`. A row whose current `remote` came from a real ATS signal that also happens to match the candidate query is a false correction in principle, but self-heals on its next ordinary crawl, which passes ingest the adapter's live signal directly; a genuinely wrongly-tagged row has no such backstop, which is why erring toward correction here is deliberate. Idempotent (`IS DISTINCT FROM`-guarded). **Follow it with a full `make reindex`**: `work_mode` is not part of `content_hash`, the same trap `backfill-clearance` documents. `BACKFILL_REMOTE_PERK_MAX` caps one run. Needs `DATABASE_URL` and the mail configuration, and **the unit must read `/opt/freehire/.env.notify` as well as `.env`** — without the mail credentials it is a no-op that never opens the pool, which would otherwise mean every run exiting 0 having reminded nobody, indefinitely. `MENTORSHIP_REMIND_MAX_PER_RUN` (default 500) bounds one run per offset. See [internal/engage/mentorship/AGENTS.md](internal/engage/mentorship/AGENTS.md).
- `mentor-busy-sync` — reads every mentor who has opted in to busy-time sync's Google Calendar free/busy state and reconciles it into `mentor_busy_intervals`, the table the slot engine has read since migration 0145 and nothing wrote to until now. Hourly, offset from `cal-sync`/`gmail-sync`. Each run replaces the WHOLE 60-day forward window per mentor in one transaction (delete then re-insert), never a row-by-row diff — the table holds only bounds, no title or attendee, since Google's `freeBusy` endpoint (not `events.list`) has nothing else to offer. Best-effort per mentor: a revoked grant marks `needs_reconsent` and the run continues; a non-revocation failure (Google having a bad day) never touches that flag, since it is SHARED with the account's other Google grants. Needs `DATABASE_URL`, the Google OAuth client, and `GMAIL_TOKEN_KEY` — without them it is a no-op that exits 0. See [internal/engage/mentorship/AGENTS.md](internal/engage/mentorship/AGENTS.md).
- `social-digest` — publishes the day's ten most-viewed postings to the configured social channels (today: a Discord webhook). **Ranks on `job_daily_views.page_uniques`, never on `uniques`** — `uniques` fuses bot-filtered page opens with unfiltered API reads, and crawlers are most of this host's traffic, so a list built on it publishes what robots fetched as though it were what people liked. **The day is discovered, not computed**: it reads the freshest day `job_daily_views` holds, because whether `cmd/rollup-views` (02:30 UTC, rotated logs) has yesterday or the day before depends on the host's logrotate timing; a freshest day more than 3 days old fails the run rather than publishing something stale. `-dry-run` renders each channel's real payload and sends nothing. **The view floor was 10 and is now 3**, lowered 2026-09-08 against a measurement: on 2026-09-07 exactly ONE posting in the catalogue cleared 10 and the best scored 12, so the floor was not selecting the popular from the ordinary, it was emptying the list. Revisit it upward as page traffic grows. The quarantine window (7 days) is still a guess. `-day YYYY-MM-DD` replays one day. Idempotent on `(day, channel)`, so a re-run publishes nothing twice and a run that posted to one channel and failed on another retries only the second. Needs `DATABASE_URL` and `FRONTEND_ORIGIN`; a channel with no credentials is skipped, and with none configured the run is a clean no-op. **The second channel is our own LinkedIn company page** (`LINKEDIN_CLIENT_ID` / `LINKEDIN_CLIENT_SECRET` / `LINKEDIN_REDIRECT_URI` / `LINKEDIN_ORGANIZATION_ID` — all four or the channel is off). Its access token is NOT configuration: it expires every 60 days and lives in `social_tokens`, put there by `cmd/linkedin-auth` and renewed by `cmd/linkedin-token-refresh`. See [internal/engage/socialdigest/AGENTS.md](internal/engage/socialdigest/AGENTS.md).
- `linkedin-auth` — **run by hand**, roughly once every sixty days: grants, records and inspects the credential the digest posts to LinkedIn with. `-url` prints the address to open in a browser, `-code <value>` exchanges what that browser handed back, `-token <value>` stores one minted in the Developer Portal's own token generator instead, `-status` reports what is stored and when it dies (never the token itself). Not a route on purpose — a sign-in flow for an audience of one, whose authorization would then be whatever that route's turned out to be; a command needs SSH, which is authorization we already have. **The exchange is also the only way to learn whether LinkedIn issued a refresh token**, which decides whether the credential renews itself or needs a person; it logs the answer explicitly. Needs `DATABASE_URL` and the four `LINKEDIN_*` values.
- `linkedin-token-refresh` — daily: renews that credential a fortnight before expiry when LinkedIn permits it, and warns when it does not. Both paths ship because programmatic refresh tokens go to approved Marketing Developer Platform partners only and the Community Management API is not that program — so a null refresh token is the EXPECTED case, not an error. **A warning is a published gauge, not a red unit**: this fleet already runs ~37 permanently failing ingest units, so a non-zero exit repeated daily for two weeks trains an operator to ignore it. `freehire_social_token_expires_in_seconds`, `freehire_social_token_grant_expires_in_seconds` and `freehire_social_token_renewable` go to the node_exporter textfile collector when `PROM_TEXTFILE_DIR` is set (negative seconds mean "no credential stored", which must not look like a broken exporter). A non-zero exit is reserved for a credential that is ALREADY dead. Needs `DATABASE_URL` and the four `LINKEDIN_*` values; without them it is a no-op that never opens the pool. See [internal/engage/linkedinauth/AGENTS.md](internal/engage/linkedinauth/AGENTS.md).
- `merge-companies` — collapses the company slugs that are one employer written more than one way (`ringcentral` + `ringcentral-inc`, `dollar-tree` + `dollartree`). Most groups it finds by folding the NAME; the pairs no fold can reach — one employer whose own boards disagree about the name, `Exadel` beside `Exadel Inc (Website)` — come from the hand-written list in `cmd/merge-companies/curated.go`, which argues why a list and not a rule (`Intel` and `intel471` are different employers). **Reports by default; `--apply` writes.** `--min-jobs N` bounds a wave to the folded groups whose combined open jobs reach N, which is how the backlog is taken in reviewed passes (1000, then 100, then 10, then 1) rather than one 333k-row leap. Chunked and idempotent — the chunk statement selects rows still carrying the retired slug, so a re-run moves nothing and an interrupted wave resumes. **Do NOT reindex afterwards**: a facet-index push costs 90-180s regardless of batch size, so a wave pushed through `search_outbox` is tens of hours; the scheduled `freehire-reindexw` picks it up, and until it does a merged company under-counts its jobs for a few hours without anything 404ing. `REINDEX_DEDUP` stays unset. Needs only `DATABASE_URL`. See [docs/agents/company-identity.md](docs/agents/company-identity.md).
- `close-chronic-boards` — the safety net for a board (or boardless provider) that has proven unreachable for a long time, not merely cooling down from a recent run of failures (issue #2017): the ordinary per-run unseen sweep never closes a board's jobs unless that run proved it covered the board (`shouldSweep`/`boardQualifies`/`sweepableCompanies`), which is correct against a transient failure but leaves a permanently broken board's jobs open forever, since it can never re-qualify. `board_health.ListChronicBoards` answers two separate windows off the same evidence (`last_success_at`, or `first_seen_at` for a board that has never once succeeded): `CHRONIC_BOARD_WINDOW_DAYS` (default 30) is what `cmd/ingest`'s per-run health summary reports for curation — fix the adapter, retire the board, or wait; `CHRONIC_BOARD_CLOSE_WINDOW_DAYS` (default 60, deliberately longer, giving a curator the gap between the two to act first) is what this worker acts on, closing the board's own open jobs with `closed_reason = 'board_unreachable'` — distinct from the sweep's `'unseen'`, so the two are never conflated. Scoped to exactly the `(provider, board)` health record that qualified: a multi-board provider's other boards are untouched; a boardless provider's single record already stands for its whole crawl, so going chronic there closes the whole provider. **Refuses a region-ambiguous board name outright** — a board id repeated per region for one provider (e.g. Adzuna's `it-jobs` once per country) has no region in `jobs.external_id`, so a board-scoped close cannot tell one region's postings from another's; such a board is skipped and counted separately in the run's report rather than risking a healthy region's jobs, the same refusal the ordinary sweep's `ambiguousRegionBoards` already makes. **Dry-run by default, reporting what it would close; `--apply` writes** — ships dry-run-only on its timer until a human has read at least one full closure window's report (`freehire-ops' provision/host2/systemd/freehire-close-chronic-boards.service`'s own comment is the reminder to flip it). Idempotent (`closed_at IS NULL` guarded) and cheap regardless of when it runs — daily. Needs only `DATABASE_URL`. **A SECOND pass in the same worker closes the opposite failure**: a board whose crawls all SUCCEED and whose feed carries nothing. `last_success_at` cannot see it — an empty-but-reachable feed refreshes that column on every single run, leaving `consecutive_failures` at 0 and the unit green — so `board_health.last_yield_at` (migration 0158) records when a board last actually YIELDED a posting, written only by a crawl whose LISTING named one (`pipeline.boardListedAnyPosting` — ingested, rejected, already-covered, unreadable OR failed-to-save, deliberately the most generous reading available and deliberately NOT the `boardReachedPostings` permission gate beside it: there, false costs a crawl cycle, but stamped here false accumulates into "this feed is empty" and eventually CLOSES, so a board whose listing works while its detail requests all fail would lose every live posting on it). `EMPTY_FEED_CLOSE_WINDOW_DAYS` (default 30, deliberately SHORTER than the unreachable window — that one waits out a problem on OUR side, this one has already been answered successfully on every run) closes with `closed_reason = 'feed_empty'`, a third distinct label because "every crawl succeeded and there was nothing there" points at the source's inventory while `'board_unreachable'` points at our access. The pass refuses a board with NULL `last_yield_at` permanently: that means no yield has been OBSERVED, not that the feed is empty, and it was true of all 155k rows the day the column landed — which is why **migration 0158's backfill (`last_yield_at = last_success_at`) is load-bearing, not cosmetic**, and why nothing can be closed by this pass until it has been observably empty for a full window AFTER that migration. Found by the WhatJobs incident of 2026-09-10: a market's publisher account was emptied, 107 postings sat open for a month, and neither existing net could reach them. See [docs/agents/job-lifecycle.md](docs/agents/job-lifecycle.md).
- `report-skill-gaps` / `report-classify-drift` — hand-run, read-only reports (`internal/job/dictgap`) that mine LLM enrichment output nothing else reads: `enrichment.skills` is a free-text list the model writes per posting, and `enrichment.seniority`/`category` is the model's own guess at the same facets `internal/dict/classify` derives independently from the title. `report-skill-gaps` ranks the raw skill phrases `internal/dict/skilltag` resolves to no canonical, by frequency; `report-classify-drift` recomputes `classify.Parse` for every distinct enriched title and ranks the titles where that answer disagrees with what enrichment recorded, tracked separately for seniority and category. Neither writes anything — no database row, no dictionary source file, no `--apply` flag — and neither is on a timer: a curator runs one, reads the ranked list, and decides by hand what belongs in `dictionaries.go`/`labels.go`/`descriptions.tsv` or the `classify` title tables. No reindex needed either, since nothing they touch changes. Needs only `DATABASE_URL`.
- **Nothing holds a flock** — no file locks in Go or in the systemd units; the word survives only in a few stale comments. What keeps a cron worker from stacking on itself is systemd: a `Type=oneshot` unit will not start a second instance while the first is active. That protects the TIMER path only, so a run started by hand has no lock at all. **Never stack `reindex-companies` with `make reindex`** — Meilisearch runs one serial task queue, so the second rebuild queues behind the first and looks like a hang, and a swap transiently holds ~2x the index's disk. Two workers additionally take a Postgres advisory lock (`cmd/liveness`, `cmd/ghost-crosscheck`); their keys are listed in `internal/platform/migrate`.
- `prune` — the **only** hard-delete path. Dry-run by default; archives every removal to `pruned_jobs`.

## Conventions

- **Response shapes:** Lists: `{"data": ..., "meta": {...}}`; single items: `{"data": ...}`; errors: `{"error": msg}`
- **A dropped filter says so:** any endpoint whose answer WIDENS when it does not understand a query param reports the params it did not read, in `meta.ignored_params` (omitted entirely when there are none). Refusing them instead would break saved searches and shared links that still carry a retired facet; staying silent is what let a mistyped `country=it` pass for a search of Italy. `search.UnknownParams` owns the SEARCH filter's vocabulary and only that, so an endpoint reading a different one says so itself — `/companies` through `UnknownCompanyParams`, `/jobs` (which reads no filter at all) through its own two-param list. The same rule decides what may be SUBSCRIBED to: `search.Narrows` asks whether a saved search selects less than the catalogue, and a subscription to one that does not is refused rather than reported, because nobody reads a digest's meta
- **Dedup key:** `jobs.UNIQUE (source, external_id)` — `UpsertJob` is `ON CONFLICT` on it
- **Company key:** `normalize.CompanySlug`, never `normalize.Slug` — the corporate form is not part of who the employer is. One legal-form vocabulary exists (`internal/dict/normalize`) and a test walks the module to keep it that way; there were four, they disagreed, and every resulting miss was silent. Spellings a rule cannot collapse (`dollartree` vs `dollar-tree`) resolve through `company_slug_aliases`, the one company-adjacent table that is NOT derived from `jobs`
- **Auth:** JWT in httpOnly cookie, same-origin, carrying the account's `token_version` so sessions are revocable. `RequireAuth` (cookie only) / `RequireAuthOrKey` (cookie or full-scope Bearer) / `RequireAuthOrScopedKey` (also admits a narrow key)
- **Email ownership:** `users.email_verified`; a password registration starts unverified and is confirmed by a mailed six-digit code. An unverified, password-backed account is **seized** (password cleared, sessions revoked, API keys deleted) when a provider-verified OAuth identity arrives for its address — the account-pre-hijacking defence
- **API keys:** Hashed at rest (SHA-256), scoped `full` or `cv`, and mintable only by an account with a verified address. Key management (create/list/revoke) and password change are cookie-only. A key does not carry the session generation, so a `token_version` bump does not revoke it — that is intentional for sign-out-everywhere and wrong for a takeover, so the seizure and the mailed-code password reset delete the rows in the same statement
- **Enrichment:** Queue-driven (`enrichment_outbox`), provider-agnostic LLM, `Sanitize` + `Validate` gate
- **Embeddings:** Queue-driven (`semantic_outbox`), incremental (`cmd/embed`) — pgvector-backed `job_semantic_chunks` plus a legacy single-vector column, no search index. Reconciled by bumping the embedder-model version string, which re-enqueues the whole catalogue through the existing staleness check
- **Catalogue scale:** Every public figure describing how big the catalogue is — `GET /api/v1/stats/catalog`, the jobs list's `meta.total`, the `/about` and `/open` strips — reads ONE snapshot published by `cmd/rollup-stats` (`internal/ingest/catalogstats`). Never count on a request path: `catalogstats.Load` takes no exact counter, so it cannot. A read never fails; a cold cache, an unreachable Redis or no cache at all degrades to the planner estimate with `exact: false`, which zeroes the figures that exist only in the database — pass `exact` through to whatever renders them, because a zero must not reach a page as if it were a measurement. The snapshot's `open_jobs` is the raw count (every open posting, reposts across boards included, never duplicate-suppressed) — `unique_open_jobs` is the de-duplicated figure Meilisearch's own index holds, what `/jobs` itself would show unfiltered. It is measured the same way as `telegram_channels`: `cmd/rollup-stats` makes one `search.Client.Search` call (limit 1, no filters) before publishing, best-effort — a missing `MEILI_MASTER_KEY` or an unreachable Meilisearch costs that one figure, not the snapshot
- **Per-source figures:** `GET /api/v1/sources` and the public `/sources` page read ONE snapshot, `source_stats`, rebuilt by a pass inside `cmd/rollup-stats` (`internal/ingest/sourcestats`) as an atomic delete-and-reinsert. It carries the same two-count pair `catalogstats` does and for the same reason: `open_jobs` is the raw open count — duplicates included — and is the denominator the ATS-overlap figures are arithmetic on, while `browsable_jobs` is Meilisearch's de-duplicated count, which is what `/jobs?source=<key>` will show and therefore what the PAGE displays. A card whose number the search it links to contradicts is the trap the pair exists to avoid. **`browsable_jobs` is NULL when Meilisearch could not be measured, never 0** — an unreachable index costs that one figure, not the run, and a 0 would state on a public page that every source carries nothing. The snapshot's spine is `sourcestats.Union` over THREE sets, each covering a hole the others leave: the adapter registry (without it a source with postings and no adapter — `telegram`, an extraction pipeline absent from `sources.Taxonomy()` — is dropped), this run's scan (without it every adapter whose postings have all closed is dropped, which is the one case the page most needs to state), and the KEYS of the snapshot being replaced (without it a source in neither of the first two vanishes the moment it goes quiet — the same silent drop, one closure later). Only names carry over; every figure is re-measured. `GET /api/v1/sources` calls the same `Union` rather than keeping its own copy of the rule. The **ATS-overlap** figure counts rows the dedup pass matched to a first-party ATS posting (`jobs.duplicate_of_aggregator`); the remainder is `ats_unmatched` and is **never** called exclusive, on the wire or on the page, because the pass finding no pair is the absence of evidence — two tests enforce the wording — one over the rendered card, one over the source of every file on the surface, including the page's own prose. It is carried for aggregators ONLY: the suppression pass never marks any other row, so a 0 there is arithmetic and would read as "fully exclusive". The aggregate scan reads no `description` column (a guard test on the generated SQL) and excludes `is_private`. **Source logos are resolved in the browser from the source's DISPLAY NAME** (`sourceLogoUrl`), never from a posting host: the first version sampled `min(url)` per source and served the WRONG brand, because an ATS posting's URL usually lives on the employer's own domain — measured on prod, `greenhouse` sampled `bankrate.com` and `successfactors` a staffing agency — while a per-tenant subdomain (`jobs.smartrecruiters.com`) simply 404s. By name, 14 of 15 resolve, and 7 of 8 sampled sources return the byte-identical image whether asked by name or by an explicit `?domain=` — a platform brand is far less ambiguous than an employer name. **That margin is not free, though**: the proxy answers a name it resolves WRONGLY with a 200, so a mismatch is invisible to every consumer (see the `g2i` case behind `cmd/publish-logo-domains`). **`SOURCE_LOGO_DOMAINS` (web/src/lib/logo.ts) is that escape hatch, curated and measured**: of the 145 sources carrying 500+ jobs, 14 had no logo by name and all 14 resolve with the platform's own domain passed as `?domain=`, which wins over the proxy's name map. `successfactors` settles why a nicer NAME was never the whole fix — its label was already correct and the proxy still had nothing. It is an OVERRIDE, not a registry: a source missing from it resolves by name as before, so the map going stale costs a logo rather than breaking one — the deliberate difference from the posting-host sampling it replaced, which was wrong for every source it covered. A curated domain implies a curated display name, and a test holds the two maps together. A miss still 404s, so every call site renders through the `EntityLogo` primitive rather than a hand-rolled `<img>`: besides the `onerror` fallback it catches a 404 that landed BEFORE hydration, which a server-rendered page needs precisely because the browser fetches the image while no handler exists yet. **A user's `excluded_sources` are seeded into the search filter by `filtersFromProfile`**, the same function the saved-search alert is built from — so avoiding a source from the job page's provenance row (`JobSourceRow`) reaches both the feed and the digest. Before that seeding the list was stored, editable in the profile, and read by nobody
- **Dictionaries:** All facet dictionaries are dict-only in production — never guess, emit nothing for unknowns
- **View counts:** anything describing how much a posting was LOOKED AT reads `job_daily_views.page_uniques`, **never `uniques`**. `uniques` fuses bot-filtered page opens with UNFILTERED API reads, and crawlers are most of this host's traffic, so a figure built on it reports what robots fetched. The rule used to live only in `social-digest`, which is why `/api/v1/stats/engagement` and the `/open` grid published 11,027,722 against the real 5,401,347 for months (freehire#2945) — a rule held by one reader is not a rule. Seed the two columns to DIFFERENT totals in any test that asserts on a view figure: `page_uniques` carries a `DEFAULT 0`, so a test seeding only `uniques` passes whichever column the query reads. `page_uniques` is also every VISITOR, signed in or not, so it never belongs beside signed-in counters without its label saying so
- **Job deletion:** The lifecycle only soft-closes; `cmd/prune` is the sole hard-delete path. Its fourth rule, `source_misattributed`, is the one that asks nothing about the POSTING: the other three decide whether a job belongs on an IT board, while this one acts on a closure that already recorded the row as filed under the wrong employer with the right one unrecoverable (apploi, 2026-09 — 1,565,701 rows for 3,024 real postings, 99.81% duplicated by URL). It deliberately runs AHEAD of `knownProvider` and of the technical veto and both board gates: a misattributed row is wrong about who is hiring whatever the posting says, and the gate requiring a listed board would make the rule dead on arrival, since that provider's 5,833 boards are all retired — measured 2026-09-18, a full scan with the check placed below `knownProvider` refused 1,596,766 rows and matched NONE of them, because that gate asks whether the source still has LIVE boards and the campaign that labelled these rows retired them all in the same step
- **In-app assistant:** a bounded tool-calling loop in-process (`internal/ai/assistant`), streamed over SSE, open to every signed-in user. Tools act as the authenticated caller — no credential is minted for an agent
- **Plan limits:** every metered AI action draws on a per-feature, per-UTC-day allowance (`internal/ai/plan`). There is no currency and no balance: a plan differs in how MUCH of a feature it allows in a day — except that today every metered feature's free allowance is zero, a deliberate subscription-only decision rather than a per-feature carve-out; `PLAN_FREE_DAILY_<F>` (below) reopens one without a deploy if that ever changes. Tailoring carries two bounds (sessions per day, turns per session) because either alone leaves the hole this replaced. Enforcement is a per-feature switch — every metered feature ships ENFORCING today, so a refusal is real from day one; `PLAN_ENFORCE` remains the lever that turns a FUTURE feature on one at a time after its own shadow run has been read, which is how auto-apply and then the rest arrived at this state without ever sharing a deploy. Refusal is HTTP 402, and on a stream it must precede the stream. **THREE tiers** since migration 0141: free, pro and ultra, resolved by `TierOf` as the better one still live (`users.pro_until` and `users.ultra_until`, each derived from three source columns). `PLAN_FREE_DAILY_<F>`, `PLAN_PRO_DAILY_<F>` and `PLAN_ULTRA_DAILY_<F>` move a tier's figure without a deploy; `STRIPE_ULTRA_PRICE_IDS` is what makes Ultra sellable at all, and unset it simply is not offered. **`auto-apply` was the first feature that shipped ENFORCING**, because pro's ceiling on it is what Ultra is sold on and a ceiling that only counts sells nothing — its route already refused the free tier with 402 before the allowance took that gate's place
- **LLM spend attribution:** every model call made for a signed-in user goes out on that user's OWN gateway credential (`internal/ai/llmkey` — minted lazily on first use, never shown to them) and carries a `feature:` tag. Work that belongs to nobody — enrichment, Telegram, embeddings — keeps the service credential, and a test enforces that background entrypoints never resolve a user's. Attribution fails open: it can never refuse or fail a call. It measures and does not bound — what BOUNDS a turn is the plan (`internal/ai/plan`)
- **Experience provenance:** every banked achievement records whether the CANDIDATE asserted it (`cv_import`/`stated_in_chat`/`manual`) or the MODEL did (`agent_inferred`). Only the former may be written into a CV, and the check lives in the service path, not in a system prompt
- **Sentry:** Opt-in, env-gated, errors-only — `sentry.Init` with `SendDefaultPII:false`
- **Naming — "CV", not "résumé":** Default new surfaces to **CV**. Don't mass-rename the existing `resume`/`resumeextract` packages and columns — churn without value
