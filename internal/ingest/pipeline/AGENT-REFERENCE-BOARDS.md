# Pipeline conventions: board pacing, health and the board-scoped sweep

Part of [AGENT-REFERENCE.md](AGENT-REFERENCE.md#always-true): the "Always true" rules about crawling a quiet board less often, which skipped boards the sweeps exclude, what counts against board health and the context it is written on, the write reserve, and what the board-scoped sweep requires.

- **A board whose listing does not change is crawled less often** (`QuietFor`, migration 0198, openspec change `quiet-board-backoff`). After a COMPLETE successful crawl, `listingFingerprint` hashes the board's sorted, distinct posting ids, and `RecordBoardSuccess` compares that with the stored one. Unchanged means `quiet_streak` +1 and a `quiet_until` pause of `4h·2^(s-1)`, capped at 72h. A posting appearing or disappearing resets the streak and pause. The fingerprint is `""` (state untouched) when the crawl cannot vouch for the whole listing: the board `Failed`, it was `Interrupted`, the context ended, or the source `SelfCloses` (it emits changes, not a listing) or `ProbeCloses` (it reads only a bounded search slice). For a HYDRATING adapter, the crawl also counts as incomplete when it left a NEW posting it listed un-hydrated. `fetchBoard` records every id the adapter asked `seen()` about that the catalogue lacks, and if any is missing from the result, the detail budget ran out or the detail failed, so the backlog is still pending. Without that check, a board whose budget other boards keep spending would look unchanged forever. The flip side is accepted: a board that lists a posting whose detail never loads (Workday serves an unpublished one as a permanent 403) never backs off. That is the safe direction. A board in its quiet pause is skipped and counted `Quiet`, not `Cooled`. While the pause holds, the board counts as fresh in `ProviderHealthRollup` (`/status`) and in `ProviderIngestHealth` (the silence alerts): it skips crawls on purpose for up to 72h, which is longer than their 48h freshness. The pause lives in its own column, so `ClearProviderCooldowns` (the recovery probe) never erases it.
- **Every skipped board — quiet or cooled — is excluded from the company- and source-scoped unseen sweeps** (`Stats.SkippedBoards`, a `BoardPattern` each, `NOT LIKE ANY` in the four `CloseUnseen*`/`UnseenJobIDs*` queries). Those closes act on any row of a crawled company, or of a whole full-catalogue source, that has gone unseen for 48h. Without the exclusion, a 72h quiet pause would close the live postings of a company whose OTHER board the run crawled. The array is `COALESCE`d, because a NULL makes `NOT (LIKE ANY(NULL))` NULL, and then the sweep closes nothing at all.
- A fetch/registry failure counts for board health; a per-job save skip does not. A streaming board with partial progress is a success.
- **Board health is written on a context detached from the crawl's** (`healthContext`: `context.WithoutCancel` plus a 10 s bound). The crawl's context ends at cmd/ingest's crawl deadline, and until 2026-10-24 a board still in flight then lost its health row with the rest — empregos' first run listed the whole catalogue, ran out of time writing it and logged `record board success empregos/: context deadline exceeded`, so a board that had answered looked as if it had never run. A board that answered is recorded as a success even when its writes were cut short (that is the run's budget, not the board's health); a failure seen after the crawl's context ended is NOT recorded, because it cannot be told from the deadline cutting the fetch short, and counting it would cool healthy boards (`CooldownFor`) — every board in flight at once on a provider that regularly meets its deadline. The sweep is unaffected either way: it gates on `Stats.Interrupted`, not on board health. **A rate limiter refuses AHEAD of the deadline**: `x/time/rate`'s `Wait` answers `rate: Wait(n=1) would exceed context deadline` as soon as the next token falls past it, while `ctx.Err()` is still nil. That refusal must be read the same way. `limiterOutOfRun` treats a fetch that failed with it as `Interrupted`, and `Run` then returns `errLimiterOutOfRun` (wrapping `context.DeadlineExceeded`) even when its context survived, so `cmd/ingest` treats the run as truncated. Without it, every board still queued behind a paced provider's limiter failed in a run's last seconds, and was cooled once that happened three runs in a row (phenom, 2026-10-30: 160 of 383 boards cooled, 365 failing). The streaming path does not check for it yet.
- **A buffered board's fetch ends `WriteReserve` ahead of the crawl's deadline; its writes do not** (`Runner.fetchContext`, set by `cmd/ingest` to five minutes, at most a quarter of the crawl). Most adapters drop a detail request their context refused and return what they had with no error, so a board the deadline caught used to return thousands of postings onto an ended context and save none (`skipped N/N jobs on construct or save error (e.g. context deadline exceeded)`): Domino's, Costco and Lowe's (10k-25k postings) saved nothing run after run until 2026-11. A fetch that ended with its context is `Interrupted` whatever it returned (`fetchedBoard.cut`), so the board still stays out of the board-scoped close and records no listing fingerprint.
- **The board-scoped sweep (`CloseUnseenJobsForBoard`, freehire#2328) asks a stricter question than BoardHealth, and answers it from `Stats` directly.** `board_scope.go`'s `boardQualifies` requires `Stats.Failed == 0` for that board — checked independently of the health verdict above, because "a streaming board with partial progress is a success" is deliberately tolerant (a rate-limited stream must not cool a working board), while a board caught mid-crawl must NEVER license a board-scoped close: the sweep would otherwise retire every posting past the point the crawl died (the freehire#725 class of bug this whole mechanism exists to avoid). The second condition, `boardReachedPostings` (`Ingested > 0`, `Skipped` deliberately excluded), refuses a zero-yield board even though its crawl "succeeded" — a board that returned nothing is indistinguishable from one whose crawl silently broke. Such a board is reported apart instead, in `Stats.EmptyBoards` (`boardListedEmpty`: finished, not failed, not interrupted, not skipped, listing named nothing), and `cmd/ingest` closes within it only for an adapter carrying `sources.emptyBoardListing` — see `docs/agents/job-lifecycle.md` (1d). Both lists are `BoardRef`s (board and region): a board name repeated across regions never qualifies (`ambiguousRegionBoards`) unless its adapter implements `sources.RegionScopedBoards`, whose close is narrowed to each region by posting URL — (1e). The third is `boardReadWhatItListed` (below). All three are computed per board inside `Run()` and carried out on `RunStats` via `Stats.QualifyingBoards`; `cmd/ingest` still gates the actual close on the provider's adapter carrying the `sources.fullBoardListing` marker (see `internal/ingest/sources/AGENTS.md` and `docs/agents/job-lifecycle.md`) before it uses any of them.
