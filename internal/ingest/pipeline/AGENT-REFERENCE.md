# Pipeline conventions

## Scope
The ingest pipeline runner — fetch → normalize → dedup → upsert — and the incremental search indexing and job-lifecycle close that follow.

## Always true
- `jobs.UNIQUE (source, external_id)` is the dedup key; `UpsertJob` is `ON CONFLICT` on it.
- `cmd/ingest` processes one PROVIDER per run (its name as the first argument — cron passes it — or `INGEST_PROVIDER`), reading that provider's live boards from the `boards` catalog; it is a run-once-and-exit worker, never a long-lived process.
- Validate every entry against the registry and fail fast — a misconfigured board never starts a run.
- Adapters are read-only over public ATS JSON APIs; the per-board crawl is independent, so one failing board is counted (`stats.Failed`) but does not abort the rest.
- Sources are keyless by default; credential-gated crawl registration lives in `internal/ingest/sources/registry_special.go`, including Arc (`ARC_SESSION_COOKIE`) and France Travail (`FRANCE_TRAVAIL_CLIENT_ID` plus `FRANCE_TRAVAIL_CLIENT_SECRET`). These gates apply to `sources.All(client)`, not the taxonomy. See [internal/ingest/sources/AGENTS.md](../sources/AGENTS.md) for the split and the registry for the complete credential list.
- Company/source stale-job sweeps require an ingested or refreshed posting. Board sweeps separately use verified finished-board evidence and the provider's listing markers, including a proven empty board when nothing was ingested.
- A board still crawling when the run's context ends (cmd/ingest's crawl deadline, or a signal) is counted in `Stats.Interrupted` and never qualifies for the board scope — it is read when the board FINISHES (`markInterrupted`), the one moment a live context proves every fetch and write before it ran in full. See [docs/agents/job-lifecycle.md](../../../docs/agents/job-lifecycle.md) (1c).
- A hydrating board whose seen-set lookup failed is still crawled (every posting reads as new), but it is counted in `Stats.SeenUnknown` and every close scope is withheld for it: the board scope (`boardQualifies`), the company scope (`UnprovenCompanies`, plus the board itself in `SkippedBoards`) and `cmd/ingest`'s source scope (`sweepBySource`). A budgeted adapter then refreshes nothing past its budget, so the crawl is no evidence of what is gone.
- `board_health` holds ONLY runtime state. The board catalog lives in the Postgres `boards` table; provider cadence lives in `ingest_schedule`. A stale health row for a removed board is inert.
- A board whose `cooldown_until` is in the future is skipped before touching its adapter (counted `Cooled`, not `Failed`).
- Backoff: no cooldown below 3 consecutive failures, then `6h·2^(f-3)` capped at 24h — never permanent, so a success self-heals.
- **Board pacing and health** — `QuietFor`, why skipped boards are excluded from the unseen sweeps, what counts for board health and the detached context it is written on, `WriteReserve`, and the stricter question the board-scoped sweep asks — are in [AGENT-REFERENCE-BOARDS.md](AGENT-REFERENCE-BOARDS.md).
- **A posting the crawl could not READ is not a posting that is gone, and `Failed` cannot say so.** On the ATS adapters whose detail request is a posting's ONLY source and which are not hydrating (`jazzhr`, `icims`, `careerplug`, `jobvite`, `successfactors`, `breezy`, `bamboohr`, `smartrecruiters`), every stored posting's detail is re-fetched on EVERY run — and a failed one used to be dropped inside `fetchDetails`, so `Fetch` returned a shorter list, `Stats.Failed` stayed 0 and the board was recorded healthy. A posting unreadable for the whole 48-hour window was then closed by BOTH sweeps with `closed_reason='unseen'`, removed from the index, and counted as a phantom removal in `job_daily_stats`. Hydrating adapters are unaffected: a seen posting yields a `SeenRefresh` and costs no detail request at all.

  The adapter now distinguishes the two cases (`sources.detailUnreadable`): a **404/410 is the platform stating the posting is gone** and is still dropped, because that is evidence and a board whose listing has gone stale must still be able to retire it; **everything else** — a timeout, a refusal, a 5xx, an undecodable body, or a 200 that carries no posting — comes back as a `sources.Job{Unreadable: true}` marker, counted in `Stats.Unreadable`. A 200-with-no-posting is deliberately on the unreadable side: the one cause that would explain it across a WHOLE board is the platform changing its markup, and reading that as "every posting is gone" is the mass-close this exists to stop.

  Unreadable identities also enter the existing `CoveredRefresher` batch after writes: refresh `last_seen_at` on open stored rows only, never reopen a closed row or insert a missing one. Keep each posting in `Unreadable` exactly once; refresh errors are logged and counted in `RefreshFailed`, which withholds all close scopes without inflating the unreadable-share denominator. When a board is unproven, withhold the returned stored company slugs too: a CareerPlug franchise can differ from the configured employer named by an unreadable marker.

  **The consequence is never a failed board.** Failing it would turn a per-posting hole into a whole-board outage, cool the board to its 24-hour ceiling and freeze its entire catalogue — strictly worse than the bug. Instead `boardReadWhatItListed` withholds this run's close scopes when more than `maxUnreadablePercent` (5%) of the postings the board yielded went unread: the board scope through `boardQualifies`, and the company scope through `Stats.UnprovenCompanies`, which `cmd/ingest`'s `sweepableCompanies` subtracts from `crawled.slugs`. **Everything the crawl did manage to read is still written** — recording and closing are separate decisions and only the second one lacks the evidence. A share rather than a count because per-posting failures are independent: on a 5,000-posting board even a 0.1% failure rate leaves a zero-failure run unlikely, so zero tolerance would switch the close off for exactly the largest boards while leaving it on for small ones. 5% because the failures that matter are wholesale — a refusing origin, a retired tenant, a rate-limit burst, a markup change all fail most of a board (seek's first prod crawl: 87%).
- `cmd/ingest` never talks to Meilisearch directly. A write that inserted or changed indexed content queues a `search_outbox` entry (`job_id` only, `ON CONFLICT DO NOTHING`), atomically in the same transaction as the upsert and the enrichment enqueue. `cmd/search-drain` (mirrors `cmd/embed`) drains that queue on its own schedule, building each document from the persisted row and pushing a whole claimed wave as ONE Meili task.
- The enqueue is unconditional — it does not check `MEILI_MASTER_KEY`; an unconfigured deployment simply never drains the queue. This replaced a prior design where `cmd/ingest` pushed straight to the live index once per run (`search.Client.SubmitJobs`, gated on `MEILI_MASTER_KEY`): with ~169 independent per-board worker processes, that meant one Meili task per board per crawl, and Meilisearch re-merges its inverted index/facet structures across the WHOLE live index on every push regardless of batch size — observed at 50-90s per push on the production catalogue, saturating host disk IO. See [internal/search/searchdrain/AGENTS.md](../../search/searchdrain/AGENTS.md).
- `cmd/tg-extract` shares `UpsertJob` and transactionally enqueues search updates alongside enrichment.
- A job is open while `closed_at IS NULL`; closing is a soft state. The lifecycle never deletes, and nothing else hard-deletes jobs either (see [docs/agents/job-lifecycle.md](../../../docs/agents/job-lifecycle.md)).
- A crawled posting is never refused for its title: one no category files is stored and indexed under `other` (#4412; the old `classify.ConfirmedNonTech` refusal and `Stats.Rejected` are gone).
- A `SeenRefresh` posting from a hydrating adapter goes to `touch`, not `Save`.
- The seen-set is scoped to the crawled board (`external_id LIKE '<board>:%'` on `jobs_source_extid_pattern_idx`), because it is loaded once PER BOARD: provider-wide it costs workday 1.27M ids and ~168s per board against ~1.8s. The pattern is escaped (`sources.BoardIDPattern`) — a third of the workday board names carry an `_`, which LIKE would read as a wildcard and claim a sibling board's postings. A boardless adapter passes an empty board and still gets the provider-wide set.
- A stored row with an EMPTY description is withheld from the seen-set until it is `pipeline.HydrationRetryWindow` (14 days) old, so the crawl re-attempts the detail fetch its first pass lost. Being stored is what makes a posting "seen", so without the window a single failed hydration is permanent — the row keeps an empty body for life, which is how ~3.3k live rows across the hydrating sources lost theirs (freehire#1866). The window is bounded because the other reason a body is missing is that the source published none, and retrying those forever would spend a detail request per crawl on each one.
- A stored row whose `application_deadline` passed within `pipeline.DeadlineRecheckWindow` (14 days) is withheld too. The deadline lives only on the detail (EURES lists expired postings and states the date on the detail page alone), so without this a re-listed posting would close on the date first stored even after the employer extended it; re-reading the detail lets the upsert store the new date and reopen the row. Bounded for the same reason as the hydration window: a source that keeps listing an expired posting would otherwise cost a detail request on every crawl.
- A range predicate (`>= 'board:' AND < 'board;'`) is NOT a valid substitute for the LIKE prefix: under the database collation punctuation carries only a secondary weight, so it matches nothing.
- A posting deleted from a hydrating source (the retired `cmd/prune` removed many) leaves the seen-set permanently, so the adapter re-fetches its detail page every crawl.
- **Aggregator posting retention** — why company coverage never discards or closes a posting, the retained posting-level deduplication, and historical closure recovery — is in [AGENT-REFERENCE-COVERAGE.md](AGENT-REFERENCE-COVERAGE.md).
- Self-closing sources are excluded from the unseen sweep (`sources.UnseenSweepExemptProviders`).
- A posting whose adapter also yielded an application form is written through the optional `FormSaver` capability (`SaveWithApplyForm`), discovered by type assertion exactly like `Closer`/`Toucher`; a Store lacking it still ingests the posting through the plain `Save` and the form is simply not captured. The form is persisted in the SAME transaction as the upsert, because only `recruitee` yields one and it has no capture queue to fall back on — that write is its form's only chance. It is written even for a row marked `duplicate_of`, the opposite call from the enrichment enqueue beside it: enrichment spends an LLM on an invisible row, while a repost is still a job someone can apply to and its form is what applying costs.
- The capture enqueue for `greenhouse`/`ashby`/`workable`/`lever` (gated by `applyform.NeedsRequestCapture`, which reads the same `fetcherFor` registry the drain worker uses) runs AFTER the commit and only logs on failure. Inside the transaction a failed statement aborts the whole thing, so a queue hiccup would discard the posting; failing a crawl over a field nothing yet reads is the wrong trade. The gap that opens — a crash between commit and enqueue — closes by itself because the enqueue is gated on the job having no stored form rather than on it being new, so the next crawl re-queues it.

## How it works
Boards live in the `boards` table (`internal/ingest/boardcatalog`), one row per (provider, board, region) carrying its `company`; `cmd/ingest` crawls the `pending` and `active` ones. `sources.All` maps each `provider` string to a registered adapter, all speaking the `Source` interface over a shared HTTP client. The `pipeline.Runner` fetches each board once, normalizes postings, and `UpsertJob`s them (idempotent on the dedup key, so re-running is safe). Adding a company is one catalog row (the site's contribute form, or `cmd/add-board`); adding an ATS platform is a new adapter in `internal/ingest/sources` plus one line in `sources.All`.

`board_health (provider, board, region)` remembers each board's last outcome (`consecutive_failures`, `cooldown_until`, `last_error`, timestamps, `last_ingested_count`) — the `region` column (`text NOT NULL DEFAULT ''`) separates a board id repeated across regional slices (Adzuna) into one health row per slice — so a repeatedly-failing board backs off instead of being hammered every run. The `pipeline.Runner` records each crawl's board-level outcome through an optional `BoardHealth` port (nil = feature off, so unit tests and non-DB callers are unaffected). The backoff (`pipeline.CooldownFor`) is Go-owned and unit-tested. `cmd/ingest` logs a per-run summary of unhealthy boards, **capped at the worst `unhealthyBoardsCap` (20) plus the full count** — the list is fleet-wide rather than scoped to the crawled provider, and every one of the ~200 hourly units prints it, so an uncapped line once turned a 7000-board backlog into gigabytes of syslog a day and starved the disk `cmd/reindex` needs to rebuild. The table is directly SQL-queryable for the rest. This is Slice-0 over the existing cron (no daemon/queue).

`cmd/reindex` rebuilds a fresh facet index and swaps it in on a schedule (hours), so without help a newly ingested or edited posting is unsearchable until the next rebuild. To close that gap, `cmd/ingest` queues each crawl's new or content-changed open jobs into `search_outbox` (`job_id` only), atomically with their write; `cmd/search-drain` builds and pushes the documents on its own schedule, batching whatever queued since its last drain into ONE Meili task — searchable within roughly one drain cycle rather than one crawl cycle. The change signal is a `jobs.content_hash` (a fingerprint of the indexed fields, `internal/job/jobhash`) the write returns as `inserted`/`changed`. A re-crawl that changed nothing does not reach `UpsertJob` at all: `save` tries `RefreshUnchangedJob` first — matched on `(source, external_id, content_hash, cities)` and open rows only — which refreshes `last_seen_at` and writes nothing else, reporting neither signal. `UpsertJob` runs for what is left: a new posting, an edited one, and a closed one reappearing (which is what reopens it). Either way the unchanged row is not re-queued, so the whole catalogue isn't re-indexed every crawl. `ClaimSearchOutboxBatch` re-checks `closed_at IS NULL AND duplicate_of IS NULL` at claim time (not just enqueue time), so a job that closed or became a repost between queueing and draining is simply skipped — permanently, since the claim predicate then never matches it again; that (bounded, low-volume) orphaned row is accepted the same way `enrichment_outbox` accepts it. The full reindex owns settings, compaction and full reconciliation. Closing statements atomically enqueue removals in `search_delete_outbox`; the incremental drain processes those removals before indexing open jobs.

Role-cluster dedup is two-tier, and the tiers must agree on the canon or they undo each other. A company posting one role once per city sends N board identities sharing a `role_fingerprint` (which excludes the location); `RecomputeRoleDuplicatesForCompany`, run by `cmd/reindex`, marks all but `min(id)` as `duplicate_of` the canon. Because that runs every few hours while ingest writes continuously, `cmd/ingest` also asks the question synchronously for each row it INSERTS (`jobdedup.CanonicalForRole`, inside the upsert transaction), and a row it marks is queued for neither the search index nor the enrichment queue. The synchronous answer deliberately refuses a canon NEWER than the row being written: the batch picks `min(id)`, so marking onto a newer sibling would be inverted on the next reindex. Everything else — a posting that becomes a duplicate through a later edit, releasing a row whose canon closed, and a burst whose copies land concurrently enough to miss each other under READ COMMITTED — is still the batch's job.

Fuzzy-description dedup (`cmd/reindex`) has the same two tiers. After the role check, `cmd/ingest` asks `jobdedup.CanonicalForFuzzy` for each INSERTED row the role tier left unmarked, in the upsert transaction (inside a savepoint: a failed lookup writes the row unmarked); a marked row (`duplicate_of_fuzzy`) is queued for neither search nor enrichment. Both tiers call the SAME `jobdedup.BucketByRole` and `ClusterBucket` over the same candidate set, and `ClusterBucket` decides a row from LOWER ids only, so the batch cannot invert the synchronous verdict. `FuzzyDedupCandidateTitlesForCompanyCapped` repeats the batch query's predicate (keep them in step), reads `jobs_open_fuzzy_candidate_idx` capped at `FuzzySyncMaxCandidates` (5000), and leaves a larger company to the batch, which also covers edits, releases and concurrent bursts.

Job lifecycle is one soft-close column (`closed_at`) written by three mechanisms. (1) Ingest sweep (`CloseUnseenJobs`): for board sources, `UpsertJob` stamps `last_seen_at` every crawl and the post-run sweep closes a provider's jobs unseen for 48h; a reappearing posting reopens via the upsert. (2) Stream-driven self-close (`CloseJobBySourceExternalID`): a self-closing source (a streaming aggregator like `jobtech`/Arbetsförmedlingen that consumes an incremental change feed) emits a `Job{Removed: true}` for a posting its feed reports taken down; `pipeline.ingestStream` routes that to the Store's optional `closer` (the ingest `dbStore`), closing by `(source, external_id)`. (3) Liveness probe (`cmd/liveness`): jobs from non-board sources are never re-crawled, so the sweep can't reach them; the liveness worker URL-probes those orphans and closes dead ones.

## Limitations
- A missed self-closing source run can leave an orphan open until a future reconcile; the change window is sized wide enough to absorb a skipped cron.
