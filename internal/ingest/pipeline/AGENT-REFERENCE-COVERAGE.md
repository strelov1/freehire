# Pipeline conventions: the aggregator-coverage gate

Part of [AGENT-REFERENCE.md](AGENT-REFERENCE.md#always-true): the rules of the aggregator-coverage gate, moved out for size.

- **The coverage gate counts only CURRENT coverage, and reads Postgres to know it.** A company is covered when it has an open non-aggregator posting whose `last_seen_at` is inside `coverageFreshness` (14 days, `cmd/ingest/coverage.go`). Without that bound one forgotten row holds its slug forever: a 2013 trakstar posting from a board no longer crawled, last seen 31 days earlier, suppressed every live Himalayas posting for a different employer of the same name, and 22,022 slugs were held that way on prod 2026-09-02 (issue #2315). The window is NOT `sources.DefaultSweepGrace` — the sweep asks whether a posting is still on its board, the gate asks whether we still crawl the employer, and a board goes uncrawled far longer than a posting goes unlisted. Measured: at 48h the largest provider (workday) has only 73.6% of its live rows, at 14 days 92.8%, and every other provider 97-99.7%.

- **The gate must be Postgres-backed, and that is structural.** `last_seen_at` cannot reach the search index: the incremental drain pushes a document only when its `content_hash` moves, and the write that stamps the column on the common path (`RefreshUnchangedJob`) deliberately writes nothing else and enqueues nothing — an indexed copy would freeze at the last content change and be most wrong for exactly the actively-crawled rows the gate must credit. Reading Postgres also collapsed the match: the fold is the stored `jobs.company_slug_folded` column (migration 0109) with its own partial index, and since it is `replace(company_slug,'-','')` written by the same upsert, an exact match implies a folded one — so ONE indexed predicate replaces the two OR'd clauses and the credit-only-what-was-asked walk the Meili filter language forced. `last_seen_at` carries no index and must not gain one (see `RefreshUnchangedJob`); it is a heap recheck over the few rows the folded index already picked, and `EXISTS` short-circuits.

- **The gate's two errors are not symmetric, and every judgement call leans on that.** A wrong yes is unrecoverable — the posting is never written, so it is never in the database, `/find`, or search, and leaves no trace to query. A wrong no costs one duplicate row, which `aggregator-ats-dedup`'s periodic pass already marks. That is why the freshness window is wide, why a lookup error answers "nothing is covered", and why a nil port disables the gate rather than failing the run.

- **The gate decides what is WRITTEN, not what was SEEN.** After the board's writes, `closeCovered` closes existing covered postings through the Store's optional `CoveredCloser`; only a Store without that port falls back to `CoveredRefresher` (`RefreshCoveredJobs`: `last_seen_at` only, open rows only). Accounted-for companies join the sweep's crawled scope, and the count lands in `Stats.Refreshed`, which `cmd/ingest`'s `shouldSweep` accepts beside `Ingested`, so a fully covered provider still sweeps. Until 2026-10-30 such postings were dropped without accounting: on 4dayweek, 17,306 of 23,046 open rows were unseen for a week, 98% under a covered employer; delisted rows also lacked company-scoped sweeps. A failed close or fallback refresh logs and counts its postings in `Stats.RefreshFailed`, withholding all three close scopes: board (`boardQualifies`), source (`sweepBySource`) and company (`cmd/ingest`'s `sweepableCompanies`, because another board can still name the company). Coverage can lapse and the next upsert can reopen the posting, as described below.

- **Since 2026-11-08 a covered posting the catalogue already holds is CLOSED, not refreshed** (`CoveredCloser` → `CloseCoveredJobs`, `closed_reason = 'ats_covered'`, removal queued in the same statement). Refreshing kept the aggregator copy visible beside the employer's own postings whenever its title matched none of them, which the reindex title-match suppression cannot catch: 4,784 open whatjobs/adzuna rows under 1,354 covered companies when measured. The close is reversible — a lapsed coverage lets the next crawl write the posting, and `UpsertJob` reopens it — so it does not break the "a wrong yes is unrecoverable" rule above. Unreadable postings still go through `RefreshCovered`. A closed row counts in `Stats.Refreshed` (so a fully covered provider still sweeps), a failed close in `Stats.RefreshFailed`. `ats_covered` is our decision, so insights' `realCloseReasons` must not count it.

- **A posting the aggregator-coverage gate discards is the same trap, and one adapter opts out of it.** Such a posting is never stored, so it is never seen, so a hydrating crawl buys its body every run and throws it away every run. `sources.CoverageGated` is the optional escape hatch: `fetchBoard` hands such an adapter a `sources.DetailGate` whose `Covered(companies) map[string]bool` resolver (`Runner.coverageProbe`) lets it skip the detail before paying for it. It is the SAME lookup `aggregatorCoverageForBatch` runs after the fetch, moved to where it can still save a request — one batched call, keyed by the company NAMES the adapter passed rather than the slugs the lookup speaks. **The alias resolution in front of it is batched too** (`resolveSlugAliases`, pinned by `TestCoverageProbeResolvesAliasesInOneBatch`): until 2026-10-27 the probe resolved company by company, and shine's ~62k listed employers at ~36 ms from the crawl host to the database spent the whole 2,400 s crawl budget before the first posting page — every run died at its deadline with nothing stored. The resolver is only handed over when the gate actually applies to that board (`aggregatorGate`), and a failed lookup answers "nothing is covered" — the recoverable direction, since claiming coverage wrongly would cost a body the catalogue needed. A covered posting is still YIELDED, body-less: the gate stays the thing that decides and counts it (`Stats.ATSCovered`), and the adapter only decides what to spend. `remotedotcom`, `seek`/`jobstreet` and `startupjobs` implement it. **The same handover carries the catalogue filter** (`sources.DetailGate.Rejected`, built by `listingRejected`): a posting the filter will turn away as non-technical is never stored either, so it is the same trap. It normalizes the body-less listing through the write path's own `normalizeJob` + `outOfCatalogue` rather than restating the rule, and it is exact only because that rule reads nothing a body could change — `TestListingRejectedAgreesWithTheHydratedPosting` pins it, and a filter that starts reading the description must break that test before it silently starves a CoverageGated adapter of bodies. Only `startupjobs` consults `Rejected` today; `remotedotcom` (205 non-technical bodies re-bought per run when measured) and `seek` could, and that is a measured follow-up rather than part of this seam.

- **Original vacancy boards bypass company-wide coverage.** `sources.HasOriginalPostings` identifies adapters whose own postings must be matched individually. WantApply global and Cyprus are the initial users: one other posting at an employer does not prove their whole inventory is present. They remain aggregators for source facets and posting-level duplicate matching.
