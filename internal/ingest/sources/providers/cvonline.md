**cvonline traps** (`cvonline`; live-verified 2026-11-22 from the prod crawl host, plain HTTP, no proxy, no Scrapling):

- **One platform, two boards.** cv.lv (Latvia) and cv.ee (Estonia) are the same Alma Career "CV-Online" Next.js app, switched by hostname. The board is the country site, `lv` or `ee`; the names are distinct, so nothing is region-ambiguous for the board-scoped close. Vacancy ids look like one shared sequence (1.67M-1.68M on both), but the adapter does not rely on it: the board is part of every crawl. cv.lt is NOT this platform (own sitemap layout, own markup) and is not read; Lithuania is covered by `cvbankas`. A third board would be a `cvonlineSites` row plus its language path segment.
- **robots.txt has no `Disallow` at all** on cv.lv or cv.ee, only `Sitemap:`. `/<lang>/vacancy/<id>` answers 200 for the id alone, so the stored URL is the sitemap's own.
- **The sitemap is the whole open catalogue.** `/jobs-sitemap.xml`: 1,838 postings on cv.lv, 1,245 on cv.ee (2026-11-22), ~330 KB, one file, with a `lastmod` that moved the same day. It carries ids and URLs only, so the adapter hydrates what the catalogue lacks, newest id first, 1,200 pages a run (one a second, two workers, ~20 minutes). A cold board drains in two runs. A read that fails is deferred, never read as gone; only 404/410 and an unpublished status are.
- **The posting is in `__NEXT_DATA__`, not in the page's JobPosting.** The ld+json block exists but its `description` is always `""`. The state carries `publicVacancies[<id>]`: `position`, `employerName`, `firstPublishDate`, `highlights` (town/county/country ids, salary, `ratePer`, `remoteWorkType`, `workTimes`), `settings.categories` and `details.standardDetails[]` (each `{title, content}`, HTML). The page is ~800 KB uncompressed (~200 KB on the wire) because the whole Redux store is inlined; the adapter decodes only the keys above. Towns and counties are ids resolved through `pageProps.locations`, which lists the site's own country.
- **The vacancy map also holds Redux metadata.** Live pages mix numeric vacancy keys with an `isLoading` boolean and an `error` object. Decode only the requested numeric entry.
- **About 40% of postings have no readable body.** Measured on 17 evenly spaced ids: seven had `standardDetails` empty or with `content: null` (the employer attached a PDF through `fileDetails`, or an external apply URL through `urlDetails`). Such a posting is kept with its title, employer, place and facts but an empty description, instead of dropped: a drop is never "seen", so every run would spend a page read on it again. The pipeline already withholds a posting with no body from search.
- **Salary and work facts are the employer's own fields, and a few are junk.** `ratePer` is `MONTHLY` or `HOURLY` (currency is always EUR on these two sites). A monthly figure under 100 is dropped (an Estonian shift fitter read 13 a month, an hourly rate typed in the wrong box). `workTimes` carries `FULL_TIME`, `PART_TIME` and `FULL_TIME_WITH_SHIFTS`; the last reads as full time. `remoteWorkType` is `ON_SITE`, `HYBRID` or a remote value.
- **`IsTechHint` is set when `settings.categories` includes `INFORMATION_TECHNOLOGY`.** The category is the employer's own pick and multi-valued (a posting filed under ELECTRONICS_TELECOM, TECHNICAL_ENGINEERING and INFORMATION_TECHNOLOGY is an "IT administrator"; a finance posting never carried it in the sample), so a mis-filed non-technical posting can carry the hint.
- **Sweep.** Not `fullBoardListing` (a failed sitemap read fails the crawl, but the adapter has not been audited against the bar). The default 48h grace is declared explicitly. Stored postings come back as bare `SeenRefresh` rows.
- **Language and classify gap.** Titles are Latvian, Estonian, English and Russian by posting (`languageIso` is the posting's own, and unreliable: English-labelled pages hold Latvian text). Expect a large share of Latvian/Estonian titles to resolve no category through `internal/dict/classify`; the English ones resolve. Not measured against the dictionary yet.
