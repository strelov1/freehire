**Levtech traps** (`levtech`, レバテックフリーランス / freelance.levtech.jp; live-verified 2026-11-17):

- **Boardless; one employer for every posting.** The board is an agency that brokers 業務委託 (contract) and 派遣 (dispatch) IT projects and hides every end client (`hiringOrganization` is `社名非公開` on every page sampled), so `Company` is the constant `Levtech Freelance`, as `emagine` does. Filing the placeholder as a company would build one bogus employer out of all of them; dropping hidden-employer postings (as `bumeran` does) would drop the whole board.
- **The listing is the site's own search, and it is a Nuxt devalue payload, not HTML.** `/project/search/p<N>/` (40 a page) embeds `<script id="__NUXT_DATA__">`; `unflattenPayload` (huntflow's) resolves it and `levtechFindProjects` finds the map that holds `projects` beside `paginationMeta` (a decoy `projects` key elsewhere in the route state is why the pagination sibling is the test). No `ld+json` on listing pages, and a plain client gets 200 with no cookie or challenge (robots.txt disallows only `/ank/`, `/entry/`, `/member/` and the like, not `/project/`).
- **The search holds 127,314 projects, and ~125k of them are closed.** Open projects come FIRST (the default order), closed ones (`isClosed: true`) after: measured 2026-11-17, pages 1-62 all open, page 63 mixed (33 open), pages 64+ all closed through p3183 (p3184 is a 404). The walk therefore ends at the first page with no open project: 2,202 open projects, ~63 pages, ~2m20s at one request a second. Any page failing fails the crawl, and reaching `levtechMaxPages` (150) without the all-closed page fails it too. `fullBoardListing` is NOT claimed: "open first" is observed ordering, not a documented guarantee, and a closed project interleaved ahead of the boundary would truncate the walk silently. `sitemap.xml` has a `project-1.xml` (2,232 detail URLs, some with 2023 lastmods) but no per-project data, so the search is the better listing.
- **A card carries title, rate, station, remote kind, contract type; the body needs the detail page.** `/project/detail/<id>/` has a schema.org JobPosting (~350 KB a page) read only for postings the catalogue lacks, `levtechDetailBudget` (600) a run, 2 workers; the first crawl drains ~2,500 over a few runs. A closed project's detail answers 404 (dropped, the platform's own answer); any other failure defers the posting rather than storing it body-less, and a crawl that asked for details and got none fails.
- **`datePosted` is the day of the request, not the posting date.** Every page sampled, including project 21947 (listed since 2023), answered `datePosted = 2026-11-17`. It is not read; `PostedAt` stays nil and the pipeline stamps first sight.
- **The rate is one figure, the ceiling (`payUpperLimit` / `baseSalary.value`), in JPY.** Monthly for 業務委託, hourly for 派遣 (`unitText` HOUR, e.g. 2,800), so it lands as `SalaryMax` only with period `month`/`hour`; the floor is negotiated. Sampled `payType`s are `negotiations`, `settlement`, `fixed` and `hourlyWage`; all carry the same upper limit and the adapter does not distinguish them.
- **Remote and contract type are mapped from structured ids only.** `remoteWorkTypeId` 1 = フルリモート → `remote`, 2 = 一部リモート → `hybrid`; `999999999` states nothing and leaves the work mode to the dictionaries (the detail's `リモートワーク：不可` is not read as a structured on-site flag). `contractType: subcontractor` → `contract`; `temporary` (派遣) has no freehire counterpart and is left unset. The listing's own `skills` array is mostly empty and is not mapped.
- **Every posting is `IsTechHint`.** The board is IT freelance by scope (designers and PMs for IT projects included), the same reasoning as `mynavi`'s o16 board.
- **The crawl hosts are refused; the Scrapling tier serves it.** Measured from host2 on 2026-11-17: a direct plain client answers 403 (919 B), the plain `SOURCES_PROXY_URL` proxy 403, Scrapling `http` mode without the proxy 403, and Scrapling `http` WITH `proxy: true` answers 200 (251 KB listing) with the detail pages served too. `levtech` is therefore a `scraplingProviders` row (`http`, proxy on) and is deliberately not in `proxiedProviders`; the pacer stays on top of the tier's client. Without `SCRAPLING_FETCH_URL` the crawl 403s on the first listing page and fails.
