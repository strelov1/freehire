**Jobs.cz traps** (`jobscz`; live-verified 2026-11-22 from a residential IP and from the crawl host, plain HTTP both times):

- **No Scrapling tier, no proxy, no key.** A plain client with a browser-shaped User-Agent is served the listing and the posting pages from the crawl host (200, ~1.2 s a listing page of ~240 KB). robots.txt (`User-agent: *`) disallows `/muj/`, `/asmt/`, `/api/`, `/iapi/`, `/status/`, `/translations/`, `/js/`, `/nabidky-podle-cv/`, `/session-log/`, `/prihlasit-se/?ref=` and `/kontakt/?reportJobAdId=`; `/prace/` (with any query string) and `/rpd/<id>/` are not among them. There is no sitemap (`/sitemap.xml`, `/sitemap_index.xml` and friends answer 404 and robots.txt names none), so the search is the only enumeration.
- **A request is sent to `beta.jobs.cz` about one time in three unless the bucket cookie is pinned.** The edge sets `beta_bucket=5:B|A` on first contact and, for a client without it, 302s a random share to a different markup on `beta.jobs.cz`. `Cookie: beta_bucket=5%3AB` on every request keeps the control bucket (12 of 12 straight 200s against 4 of 12 redirected without it; `5%3AA` redirects every request). The adapter sends it as a header on each read instead of keeping a cookie jar, so one run is one bucket.
- **The listing is the server-rendered search, `/prace/`, and it stops at page 45.** 30 cards a page, `Našli jsme <strong>14 971</strong> nabídek` (2026-11-22) states the total, and any `page` above 45 is a 302 back to 45, so one query reaches 1,350 rows. A card is `<article>` with `data-jobad-id`, `data-test-ad-title`, the employer in the first footer item, the place in `data-test="serp-locality"`, a pay tag and the neutral tags ("Možnost občasné práce z domova"). A card carries no body and no posting date (the status line is "Aktualizováno před 12 minutami" / "Přidáno před 40 minutami", a relative update time, so `posted_at` stays unset).
- **The catalogue is sliced by field of work, and a field over 1,350 is split by region.** The "obor" filter is `?field[0]=2009000NN`, ids 01-45 (seven match nothing: 06, 10, 16, 24, 28, 35-37), found from the `/it/` vertical's own links (`/it/` is fields 11, 12 and 13). Region is the PATH, `/prace/<region>-kraj/`: the 13 regions plus `/prace/zahranici/`, and `locality[radius]=0` keeps a city page (`praha`, a "region" for the site) to itself instead of the 50 km default (`/prace/praha/` is 7,240 with the radius and 5,399 without). Those slugs resolve to a stable `R2xxxxx` code in the page state (`R200000` Praha, `R206696` Středočeský, ...); the path is easier than the code, which is not guessable. Six fields exceed the reach (Administrativa 2,254, Prodej a obchod 3,275, Stavebnictví a reality 1,999, Strojírenství 1,682, Výroba a průmysl 2,377 and Elektrotechnika 1,355) and are walked per region instead: no (field, region) slice is over it. A posting filed under several fields or placed in several regions is read in each and kept once by id. Measured by walking every slice (4 workers, ~50 minutes): **14,867 distinct ids of the 14,971 stated, 99.3 %**; the 104 left were reached by no field slice (79 of them turned up in a separate walk by region, so some postings are filed under no field; the foreign slice failed to fetch in that run). The slicing is about **1,060 listing requests** (the fields' own pages 552, the six split fields' region slices 507). The other filters (`employer`, `education`, `employment`, `arrangement`, `date`) only narrow and overlap, so none partitions the catalogue; `date` takes `24h`, `3d`, `7d` only (`14d`, `1d`, `31d` match nothing).
- **The foreign slice rejects a radius.** On 2026-11-23 `/prace/zahranici/` with a field filter returned its two listings, while adding `locality[radius]=0` returned HTTP 500. Domestic regional requests still use the radius.
- **Half the postings are a partner page whose body this adapter cannot read, so they are not yielded.** The employer runs its own career site on Alma Career's platform (`kaufland.jobs.cz`, `t-mobile.jobs.cz`); `/rpd/<id>/` 302s to `<sub>.jobs.cz/pd/<id>/`, a meta-refresh page, which lands on `<sub>.jobs.cz/detail-pozice?r=detail&id=<id>`. That page is a shell (`<div id="vacancy-detail" aria-busy="true">` with a spinner) that paints the posting in the browser from `https://api.capybara.lmc.cz/api/graphql/widget`, whose robots.txt is `User-agent: * / Disallow: /`. There is no JSON-LD and no other copy of the body, so nothing allowed reads it. Of 30 consecutive cards (page 3) 16 were served by `www.jobs.cz` and 14 redirected (47 %); on page 7, 8 of 13 redirected. The choice: **drop them** rather than store a body-less row the pipeline would have no text to classify and search withholds anyway. A partner posting that is dropped is never stored, so the unseen-sweep has nothing of it to close. Of the 14 partner cards on page 3, 8 carry the platform's logo (`my.teamio.com/recruit/logo`; none of the 16 own-site cards on that page did, though one own-site card carries a logo from another host), and those cost no request; the rest are recognized when the Jobs.cz posting responds with a redirect to the same posting ID on a partner host. The adapter stops at the redirect.
- **Partner pages come back unseen on every run, so the budget is split.** Dropped postings never enter the catalogue's seen-set, so a budget spent strictly newest-first would fill with the partner pages already probed and stall behind them. `chooseFresh` takes half the budget newest first (ids rise with time) and the other half as a window through the rest that moves with the day of the year, so a cold start still works its way to the old own-site postings. `jobsczDetailBudget` is 800 reads a run; a run with attempted reads fails when every read is unreadable. Confirmed partner redirects and 404/410 responses count as answers.
- **A posting page is plain server-rendered markup.** No JSON-LD, no embedded state. The body is `<div data-jobad="body" data-test="jd-body-richtext" class="RichContent">` (it holds divs of its own, so the end is found by counting); the title is the `<h1>`; "Informace o pozici" is a run of `class="IconWithText"` blocks of an icon, an `accessibility-hidden` label and one or more `<p>`s: `Společnost`, `Požadované vzdělání`, `Požadované jazyky`, `Zařazeno` (the fields, then the professions, as `<fields> , <professions>` in one paragraph: the space before the comma is what separates the two lists from the commas inside them), `Typ pracovního poměru`. The block is rendered twice, above and below the body. Pay is `data-test="jd-salary"` ("50 000 ‍–‍ 85 000 Kč", with zero-width joiners around the dash, gross per month in crowns; every pay string seen in ~150 cards was in crowns, and a line naming "hod" or another currency is read as such).
- **`IsTechHint` is set from the site's own filing.** A posting `Zařazeno` under any of `IS/IT: Konzultace, analýzy a projektové řízení`, `IS/IT: Správa systémů a HW` or `IS/IT: Vývoj aplikací a systémů` is hinted technical. The fields are the employer's own pick and noisy (a marketing role filed also under IS/IT is hinted), which is what the pipeline's catalogue filter then judges. No other posting is hinted. `Team` is left unset: the field names hold commas, so one cannot be cut out of the list safely.
- **Employment type and work mode are read only when stated unambiguously.** `Typ pracovního poměru` "Práce na plný úvazek" is `full_time`, "zkrácený úvazek" `part_time`, a posting stating both is left empty, "dohodu"/"živnost" is `contract`, "stáž"/"trainee" is `internship`. The card's tags state the arrangement: "převážně z domova" is `remote`, any other "z domova" tag is `hybrid`.
- **The location dictionary reads the cards' place lines.** `Brno – Medlánky`, `okres Praha-východ`, `Liberec` are bare Czech place names with no country, so the adapter passes `FallbackCountries: cz` (a foreign posting's line names its country, which the dictionary reads first). The card's line is used; the page's street address is only the fallback.
- **Czech titles: about half resolve a category.** Measured 2026-11-22 on 570 titles from the first 20 listing pages of the whole catalogue, `classify.Parse` found a category for 266 (47 %), `classify.IsTech` placed 4; on 180 titles from the two biggest IT fields it found 83 (46 %) and `IsTech` 28 (16 %). The Czech vocabulary is largely missing from the classify tables: `vývojář`, `programátor`, `analytik`, `vedoucí`, `zámečník`, `sociální pracovník` and most non-IT roles resolve nothing, and the IT postings reach the catalogue through the `IsTechHint` above rather than through the title. Extending `internal/dict/classify` for Czech is a separate change.
- **Pace and cost.** One request every 600 ms across listing and page reads (`jobsczRequestPeriod`), two detail workers. The listing is sequential at ~1.3 s a page from the crawl host: ~1,060 pages, ~23 minutes, then at most 800 page reads (~5 minutes), so give the unit a **3,600 s** timeout. A run lists ~15k cards, of which ~45 % are partner pages and ~55 % own-site postings; a day's new postings are a few hundred, and a cold start reads the ~7k own-site postings over ~10-15 runs. Run it once or twice a day.
- **prace.cz is the same company's sister board and is not built here.** `prace.cz` is Alma Career's other Czech board and was not probed. Whether it holds postings Jobs.cz lacks is unmeasured; do that before building it.
