**HRM Direct traps** (`hrmdirect`, now served by ClearCompany; live-verified 2026-10-30 from a residential IP over 25 tenants sampled from the catalogue):

- **The platform moved under the adapter and every crawl kept succeeding.** Since ~2026-10-21 every `<board>.hrmdirect.com` path, the old listing and job pages included, answers 302 to `apply.clearcompany.com/<board>/redirect` and lands on the hosted career page `apply.clearcompany.com/<board>`. That page is a 200 with no posting link in it, so the old HTML-scraping adapter read every board as empty: `board_health` stayed green, `last_yield_at` froze on 2026-10-21, and ~90k postings stayed open unseen. The board slug survived the move; the posting ids did not (old `<req>-<req_loc>`, new a GUID), so nothing maps an old row to a new one.
- **The career page renders nothing; its widget script names the site.** `data-site-id` on the `career-site.js` script is the id ClearCompany's public API is keyed by: `careers-api.clearcompany.com/v1/<site id>?pageIndex=N&pageSize=M` answers `{"results":[...],"totalCount":N}` with each posting's full HTML body, structured `locations` (country, `isRemote`) and `postedDate`, so there is no detail request. **Always send `pageSize`**: a request without it did not answer within two minutes on a 7,105-posting board.
- **The API's paging cannot be walked, so a board is ONE request.** It orders by posted date with no tie-break and no sort parameter, and each page request orders the ties afresh, so a walk lists some postings twice and skips others: single walks of 100-posting pages over a 7,105-posting board returned 7,064 to 7,080 distinct postings, and three walks unioned reached only 7,094 in nine minutes. One page sized past the total (`hrmdirectMaxPostings`) is one query and came back whole — 7,105 distinct, 41 MB, 141 s — so it goes through `GetStream`, whose timeout fits; the shared client's 15 s does not (100 postings take 1-2.5 s, 1,000 ~22 s). The distinct postings must reach the answer's own `totalCount` or the crawl fails, which is what makes it `fullBoardListing`.
- **An offline tenant's career page answers 404** (1 of 25 sampled), as does the API for an unknown site id — and, for a few minutes on 2026-10-30, for every site during a ClearCompany outage (`settings` answered 500 meanwhile). So a 404 is a failed crawl, never an empty board. It is not `emptyBoardListing` yet: the empty answer (`results: []`, `totalCount: 0`) is distinguishable, but the marker's shared test drives a single-response fake and this adapter makes two requests.
- **Two tenants can list the same postings** (`bkbehavior` and `heartlandbehavior` share posting GUIDs), so the same requisition is stored once per board; collapsing them is dedup's job, not the adapter's.
- **`atsboard` recognises both hosts as this provider**: `<board>.hrmdirect.com` and `apply.clearcompany.com/<board>` (folded to lower case, as every catalogued board is) name the same board, and a `?jobId=<guid>` link resolves to its posting through board coverage. The old `req`/`req_loc` ids do not survive the move, so an old hrmdirect.com posting link still names its board but no posting.
