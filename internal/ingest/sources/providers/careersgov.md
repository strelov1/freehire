**Careers@Gov traps** (`careersgov`; live-verified 2026-11-18 from a residential IP, not yet from the crawl host):

- **The catalogue is a file, not an API.** Open Government Products publishes it as `opengovsg/careersgovsg-jobs-data/data/job-listings.json` on GitHub (a Flat Data action commits it several times a day; ~11 MB, ~2,100 rows). One request reads everything, bodies inline. careers.gov.sg itself has no public listing API.
- **Only `platform: "hrp"` rows are crawled** (~1,800 of ~2,100). The `greenhouse` rows are GovTech's own Greenhouse board, already crawled under `greenhouse` (company `govtech`, which links to the same `jobs.careers.gov.sg/jobs/greenhouse/` pages); the few `workable` rows are Workable postings. Those rows also type the same keys as strings (`"startDate": "1790844080000"`, `"closingDate": "None"`, `"isNew": "False"`), so the adapter reads `platform` first and decodes the full struct only for `hrp`.
- **`jobId` is unique among hrp rows; the public page needs `postingNo` too:** `jobs.careers.gov.sg/jobs/hrp/<jobId>/<postingNo>`. `/jobs/hrp/<jobId>` alone is a 404. The page answers 403 to curl's default User-Agent and 200 to a browser's.
- **The three body fields are page sections with their headings cut off** (`jobDescription`, `jobResponsibilities`, `jobRequirements`), so each starts with dangling `</strong></p>`. The sanitizer keeps stray tags, so the adapter trims the leading close tags and trailing open tags off each field (`careersgovSection`) before joining them under its own `<h3>` headings.
- **`employmentType` and `workArrangement` overlap:** "Fixed Terms" and "Contract" rows are also "Full-time", so the contract kind is read first. "Permanent/Contract" with no arrangement maps to nothing.
- **A file that parses but holds no hrp row fails the crawl**, so a schema change cannot read as an emptied public service and let the unseen sweep close every posting.
