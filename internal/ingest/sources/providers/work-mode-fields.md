**Work-mode and country fields the listing hides** (`teamtailor`, `paylocity`, `workable`, `greenhouse`; live-verified 2026-10-18 against four moderator reports):

- **Teamtailor's remote status is in `jobs.rss`, not on the page.** The job page renders it only in a `<dl>` whose label and value are in the site's language ("Remote status: Hybrid", "Status Homeoffice/Vor Ort: Hybrid"), drops the row for on-site, and its ld+json carries `jobLocationType: TELECOMMUTE` for `fully` and nothing for hybrid. The feed's `<remoteStatus>` is a closed enum (`none`/`onsite`/`hybrid`/`fully`; `temporary` documented) and the feed honours `per_page` and `offset`, so the adapter reads it once per run for the postings it hydrates, best-effort. A site that disables `/jobs` (jobs.proxify.io) 404s the feed too.
- **Paylocity's `LocationName` is a label, `JobLocation.Country` is the place.** "Remote Worker" and "Concord Office" name no place; the structured record behind them carries `Country` ("USA" on all 392 briefs sampled across 40 boards), which becomes `Job.Countries`.
- **Paylocity's `IsRemote` is a toggle, not an arrangement; `IndeedRemoteType` says which kind.** The posting page labels `IsRemote` + type `1` "Hybrid Remote" and `IsRemote` + type `2` "Fully Remote", and renders no arrangement label when `IsRemote` is false (live-verified 2026-10-23). Type `2` alone means nothing — 731 of 733 briefs across 290 boards carried it, nearly all non-remote — so the type is read only behind the toggle, and a false toggle leaves `WorkMode` empty rather than asserting onsite. Reading `IsRemote` alone filed every hybrid posting as remote (report 108; 35 of 88 stored-remote rows in a 616-posting sample). The adapter is not hydrating, so every crawl rewrites a posting's `work_mode` without `INGEST_REFETCH_ALL`.
- **Workable's widget has no workplace field.** `telecommuting` is the only arrangement signal on `/api/v1/widget/accounts/<board>`; the `workplace` enum (`hybrid`/`on_site`/`remote`) exists only on the v3 jobs list, which pages ten postings per request — not worth a request per ten postings on every board. A non-telecommuting posting is left to the description.
- **A Greenhouse restriction stated only in an application question is out of reach.** Kard's "We are a fully remote company hiring in the US, Canada, Argentina, or Brazil only" is the label of a form question, absent from `content`; reading it would cost a `?questions=true` request per posting, which the apply-form rule above forbids.
- **A bare-"Remote" Greenhouse posting's country is in its `offices[]`, and it is a FALLBACK, not `Countries`.** The listing already carries each posting's offices (`location` is Greenhouse's geocoded "City, Region, Country", often null; `name` is the employer's label, "Remote US" or "Headquarters"). `greenhouseOfficeCountry` reads them only when `location.name` is a bare remote marker and every office that is not itself just "Remote" places exactly one shared country, and yields `Job.FallbackCountries`, which `jobderive` consults after the location, the title marker and both description rescues — because an office is sometimes the headquarters, not the hiring scope. Measured 2026-10-23 over the 1,612 boards holding an affected posting (62,172 live postings, 8,737 bare-remote): it pins 1,570 on 451 boards, 92% `us`; against enrichment's own pinned country it agreed 179 times and disagreed 7, and against a title/description restriction 63 to 3 (the restriction wins those). The disagreements are an HQ abroad from the team and one label the dictionary misreads ("ID - Boise" as Indonesia). A scoped location ("Americas Remote", "Remote - EMEA") is never read, since one office would narrow a region to a country. Stored rows need `INGEST_REFETCH_ALL=1`: the fix changes what the LISTING yields.
