**WUZZUF traps** (`wuzzuf`; live-verified 2026-10-18, transport re-measured 2026-10-21):

- **Everything is behind Cloudflare now, so the crawl reads the site's search pages in a browser.** Until 2026-10-20 the site was challenged but `api.wuzzuf.net` (an AWS load balancer serving the JSON:API the front end calls) was open, and the adapter used it. From that afternoon the API answers the same "Just a moment..." 403 to every plain request, direct or through the proxy, Chrome fingerprint or not. The Scrapling tier's browser solves the challenge from the crawl host's own IP (over the proxy it timed out), so `wuzzuf` is a `scraplingProviders` row in `browser` mode. **The search pages are rate-limited**: the first run read nine pages ~6 s apart and the tenth answered 429, so the row paces them (`wuzzufPageInterval`, one per 12 s, ~6 minutes a run).
- **A search page carries everything; there is no detail fetch.** `https://wuzzuf.net/search/jobs/?filters[roles][0]=<role>&start=<page>` embeds `Wuzzuf.initialStoreState`, the store its front end boots from: `jobSearch.sets[<page path>]` holds the search (`totalResultsCount`, `resultsOrder`, and a `resultsSet` row per id whose `computedFields[company_name]` is the employer) and `entities.job.collection` the full JSON:API job document of every row — the same shape `GET /api/job` returned. `start` is a PAGE index, not a row offset, and a page is 15 rows (`wuzzufPageSize`, the site's, not ours): on 2026-10-21 the IT role was 437 postings, `start=29` showed 436-437 and `start=30` nothing. A row listed without its document yields an `unreadableDetail` marker; a document whose status is not `active` is gone.
- **The board is a job ROLE.** On 2026-10-18 the whole active catalogue was 5,266 postings and the IT role 436. **An unknown filter KEY is ignored** (`categories`, `workRoles`, `job_category` all answered the full 5,266 through the API), so every job document is checked against the board's role and one outside it fails the crawl. An unknown role VALUE matches nothing, so a misspelled board fails as "matches no postings". The browse pages (`/a/IT-Software-Development-Jobs-in-Egypt`) are NOT the role: that one answered 3,343 postings, accountants included.
- **The employer is padded with spaces on some rows and `""` when the employer hid it** (51 of 436 IT postings) — those name no company and are not yielded.
- **`postedAt` is zone-less Cairo wall time** (`10/18/2026 20:19:47` came back at 18:00 UTC), read in `Africa/Cairo` — Egypt observes DST, so a fixed offset would be wrong half the year; hence `time/tzdata`.
- **The page is `https://wuzzuf.net/` + `uri`**, and `uri` is not always `jobs/p/<slug>`: internships are `internship/<slug>` and Saudi postings `saudi/jobs/p/<slug>`.
- **Geography is structured and not all Egyptian**: of the 385 named IT postings, 367 Egypt, 5 Saudi Arabia, 2 UAE, 2 Cyprus, 2 UK and one each in Canada, Switzerland, India, Jordan, Japan and the US. The country is `location.country.code` through `NormalizeCountry`; the place is `area, city, country`.
- **Structured fields that say nothing are not mapped**: 14 of 436 postings name several work types at once (`full_time, part_time, freelance_project`), so an employment type is taken only from a single one. Career level "Experienced" spans middle and senior and "Manager"/"Senior Management" a management track, so only "Student" (intern) and "Entry Level" (junior) set a seniority. `hideSalary` withholds a salary (46 of 436 shown, all "Per Month"); an unpaid internship carries `isPaid: false` and a 0-0 range.
- **A posting can carry several roles.** A second role board would store a posting filed under both twice, under two board-namespaced ids; the duplicate markers collapse them, but the IT role is the only board today.
