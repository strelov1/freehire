**jobkorea traps** (`jobkorea`; live-verified 2026-11-22 from the prod crawl host with plain curl, no proxy and no Scrapling):

- **robots.txt allows everything the adapter reads.** The `User-agent: *` section (read in full) disallows `/login/`, `/user/`, `/my/`, `/account/`, `/RecrtMng/`, `/corp/`, `/text_co/`, `/Salary/mylist` and `/Recruit/JobList/SpaceClick`, and allows two `/User/Qstn/` paths. `/Recruit/GI_Read/<id>`, `/Recruit/GI_Read_Comt_Ifrm` and `/content/sitemapindex/` are not in it. A long block above it disallows named AI crawlers; it does not apply to a generic UA. `Sitemap: https://www.jobkorea.co.kr/sitemap.xml` is named.
- **The posting set is `/content/sitemapindex.xml`.** `sitemap.xml` is an index of `content/sitemap_core.xml` (static landing pages) and `content/sitemapindex.xml`, which names ~270 files: company, salary, Q&A, review, search-landing pages and `agi/agi_0001..0021.xml`. Only `agi` (job postings, "GI" is the site's own name for one) holds `/Recruit/GI_Read/<id>` URLs: 20 files of 5,000 and one of 2,455, 102,455 on 2026-11-22, ids 49.99M-50.41M. Nothing else is in a file, and every `lastmod` is the generation time, so no entry says how new it is: the id is the only order, and the adapter reads the newest id first. The 21 files are ~700 KB each and were served in well under a second. The adapter selects the files by the `/sitemapindex/agi/` path, so other directories are never read.
- **The posting page carries the facts but not the body.** `GET /Recruit/GI_Read/<id>` is a Next.js page (150-170 KB, 200 plain) with one schema.org `JobPosting` in an `application/ld+json` script that carries other attributes after `type`: `title`, `hiringOrganization.name`, `datePosted` (`2026-11-10`), `validThrough` (`2026-12-10T23:59`, KST, no offset), `employmentType` (`FULL_TIME`), `experienceRequirements`, `educationRequirements`, `jobLocation.address.streetAddress` (a Korean street address, no locality or country), `identifier.value` (the id), and `baseSalary` only when the poster stated one (KRW, `YEAR`, min/max). Its `description` is a generic one-sentence summary ("<employer>에서 정규직 경력 채용을 진행합니다 ... 자세한 조건은 공고를 통해 확인할 수 있습니다"), not the posting. The page also embeds the posting's own data in the Next flight payload (numeric job-classification and industry codes with no names, `workFields` free text); the adapter does not read it, since the codes carry no label and the free text is the employer's.
- **The body is the frame the page embeds.** `GET /Recruit/GI_Read_Comt_Ifrm?Gno=<id>` (28-40 KB, 200 with no `Referer`) holds the poster's HTML in `<div id="detail-content">`. It is either a template (a header, then position and requirement tables) or, for a poster who uploaded the posting as a picture, a single `<img>`: measured 1 of 3, which has markup and no text. The adapter keeps the JobPosting summary as the body in that case, so the posting is stored thin rather than not at all. A frame answering 404/410 does the same; a frame that fails otherwise (after two retries) defers the posting, because a body-less store is not repaired later (a stored posting is never re-read).
- **A closed posting keeps serving.** `/Recruit/GI_Read/49000000` answered 200 with a full page, so a posting whose `validThrough` has passed is dropped by the adapter (`ok=false`, no error) rather than stored; only an id the site no longer knows answers 404 (`40000000`). `ApplicationDeadline` is `validThrough` read as KST.
- **Two requests a posting, a bounded run.** One limiter paces every request of a run, sitemap, page and frame alike, at two a second with four workers, and a run reads at most `jobkoreaMaxNewPerRun` (1,200 postings, 2,400 requests, ~20 minutes) unseen postings. The pace is a courtesy ceiling, not a measured limit: eight concurrent frame reads answered 200 (one 307 on an invented id) and no refusal was met. A stored posting is refreshed by identity only (`SeenRefresh`), costing no request. A cold start of the ~102k catalogue therefore takes ~85 runs; the site's daily intake sets the steady-state load. Re-measure the first live runs, and raise or lower the bound by what they show. A run that requested pages and got none answered fails.
- **Sweep grace is 3 days.** The sitemaps are regenerated about every few hours (generated 15:00 KST on the day measured), and a posting is not named before then.
- **No tech hint, and almost no category from the title.** The site states no technical signal an adapter can trust (the classification codes carry no name), so `IsTechHint` is never set. Measured 2026-11-22 over 26 real titles, `internal/dict/classify` resolved a category for 1 (a title that carries English words, "Pre-Sales ... Lead"): 96% of Korean titles resolve nothing, because the dictionaries have no Hangul vocabulary (`백엔드 개발자`, `회계 담당자` and `AI엔지니어` all come back empty). Until a Korean title dictionary exists, the catalogue filter that withholds postings with no resolved category keeps almost all of this source out of search.
- **The address is the only place.** `streetAddress` ("서울 강남구 언주로 651 (논현동, 삼원빌딩) 8층") is stored as the location; whether `internal/dict/location` resolves a Korean city from it is not measured here. `FallbackCountries` is `kr`, so a posting whose location resolves nothing still lands in South Korea.
- **Not read:** company pages (`/company/<id>/Info`, ~71 sitemap files), the employer's logo and website (the JobPosting carries neither), `experienceRequirements` and `educationRequirements` (Korean labels, not mapped to the vocabularies).
