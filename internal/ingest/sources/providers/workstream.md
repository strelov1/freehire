**Workstream traps** (all verified live 2026-09-02):

- **The board is the EMPLOYER, and its id is the eight hex characters a career-site URL opens with** — `www.workstream.us/j/<board>`. Workstream's own legacy careers URL, `/j/<employer-slug>` (`finecasual`, `sarku_japan`, `hdl_management_usa_corporation`), 301-redirects onto it, so the hex is the canonical spelling and the slug is not a second board. A parent runs one or more BRANDS (`/j/<board>/<brand>`), and `/j/<board>/positions` unions every brand's postings — so the employer is the crawl unit and the brand is not. Filing a group's brands under the group is the cost: the brand is in the posting URL and the posting page's breadcrumb but on no listing card, so reading it would spend a request on the `SeenRefresh` path that exists to save one.
- **`/j/<board>/positions` is the employer-wide listing only when the employer runs MORE THAN ONE brand.** An employer running exactly one is 301-redirected to that brand's root, which is a LOCATIONS listing — pages of stores, not of postings — and paging it silently harvests a fraction of the board. Every page states where its positions listing is in an inline `var searchBaseUrl`, so the crawl believes that rather than the URL it landed on; comparing it against the URL asked for is what keeps the multi-brand case at one request instead of two.
- **`var totalPages` is exact** (unlike SEEK's `totalCount`): the last page is short, the page after it renders no card at all, and the `added == 0` rule agrees with it. Ten cards a page.
- **A card carries every field except the body** — title, schedule tag, the store's full street address, the pay line — so the adapter is a `HydratingSource`. The address is the only location the listing states; it is passed through verbatim rather than reconstructed from the URL's store slug.
- **The pay line's `$` is unqualified and Workstream serves Canadian employers beside US ones**, so nothing on either page says which dollar it is — Chop Steakhouse & Bar's postings are Ontario ones under the same `$` as a Texas board's. The grammar is otherwise fixed and platform-rendered (`$15.00 - 18.00 per hour`, `Starting at $11.00 per hour`, `Up to $22.00 per hour`), but the line is stated in the description verbatim rather than parsed into the structured salary fields — SEEK's `salaryLabel` reading, for a different cause. Gusto's opposite call is sound for the opposite reason: Gusto Payroll runs US employers only.
- **The origin is AWS API Gateway and it meters by request RATE per IP — and a short sample reads the ceiling wrong.** Over cold boards, 1.0 req/s was refused nothing across 40 requests, ~1.4 req/s was refused 48% and 2 req/s 71%, which reads as a knee at 1 req/s. A 52-minute harvest paced at one token a second was then refused **524 of 2,138**, sustaining ~0.52 ANSWERED requests a second: the budget is a rate held over the whole run, not a burst the first refusal announces. The penalty also outlives the burst that earned it (a run refused at 2 req/s kept being refused minutes later at 0.8). **And a refusal makes the pace worse than the number it names** — the client's retry lives BENEATH the limiter, so one paced token becomes three requests exactly when the platform is already refusing; an ingest run paced at 1 token/s measured ~1.6 requests/s and lost 302 of 363 boards to 429. Hence `workstreamRequestInterval` at 0.5 req/s, half the observed ceiling, with the headroom left for the retries; `cmd/harvest-boards` wants `-pace 1 -workers 2` and will still see ~25% refused. A retired employer answers **410 Gone**, not 404.
- **Neither page states a publish date in any form**, so `PostedAt` is always nil.
- **There is no seed list and no directory.** `sitemap.xml` is the marketing site's (HubSpot) and carries no `/j/` URL at all, so `workstreamProber` discovers its own candidates from Common Crawl's index of `www.workstream.us/j/*` — the second path segment, filtered to the eight-hex shape. That is why `commonCrawlCandidates` takes a slug extractor: greenhouse and ashby key a board by the first path segment, Workstream by the second.
- **The franchise model makes the provider unshardable, which is what bounds it.** Each operator is its own Workstream account reporting the BRAND as its employer, so 358 of the 777 live boards are called "Chick-fil-A", 67 "Jimmy John's", 60 "Culver's". `sources.Config.Shard` assigns whole COMPANIES to shards (it must — the stale-job sweep scopes closes by `company_slug`), so those 358 are one indivisible lump bigger than any run's budget: `--shard=1/40` over the raw harvest crawled 363 of 777 boards. The catalog therefore carries one `workstream` board per distinct employer name (237), which is both what a run can crawl and what makes the provider shardable at all. The dropped boards would have bought near-duplicate crew postings under a company page that already holds them.
- **This is an hourly/frontline segment and its technical yield is essentially zero.** Two measurements agree. Of 516 postings sampled from 33 boards by title, 170 (33%) were rejected outright by the non-tech dictionary and **none** of the 346 survivors classified as `engineering_design` — they are "Team Member", "Server", "Baker", which the dictionary neither confirms nor rejects. A real ingest of 49 boards then stored 798 postings, of which **exactly one** ("Network Engineer") is an engineering role; the other technical-looking facets are dictionary artefacts of a frontline vocabulary — 107 `security` are physical security guards and 8 `mobile` are mobile patrol officers. Nobody should expect engineering postings from this provider. Note the cost shape that follows: a rejected posting is never stored, so it is never `seen`, so its body is re-fetched every run — at 0.5 req/s that steady-state re-hydration, not the listing walk, is what sizes the board file.
