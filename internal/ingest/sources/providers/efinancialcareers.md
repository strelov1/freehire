**eFinancialCareers traps** (`efinancialcareers`; live-verified 2026-11-22 from the crawl host, plain HTTP, no key, no proxy):

- **One global catalogue.** 66,047 open postings across every regional site (.com, .co.uk, .de, .sg, .hk all read the same index; one day's postings were 740 US, 526 France, 457 Germany, 283 UK, 243 Hong Kong, 135 Singapore). Not IT-only: sectors run from accounting and insurance to compliance and retail banking. A third of the rows are French or German titles, so expect a large share to resolve no category through `internal/dict/classify`.
- **robots.txt publishes no rules.** `www.efinancialcareers.com/robots.txt` (and the .co.uk/.sg twins) answer 200 with a CloudFront "System Maintenance" HTML page for every user agent, so there is no `Disallow` to read; the homepage and posting pages answer a 194-byte shell to a plain client and are never fetched. The adapter talks only to the API host, `job-search-api.efinancialcareers.com`, whose `/robots.txt` is a 404 (no rules). Revisit if the maintenance page is ever replaced by a real file.
- **The listing is the JSON search API behind the frontend, and it carries the whole posting.** `GET /v1/efc/jobs/search?pageSize=N&page=P&sortBy=POSTED_DATE&filters.postedDate=SEVEN`. A row has `jobId` (numeric, the external id, also the tail of `detailsPageUrl`), `title`, `companyName` (with `clientBrandName` as fallback), `jobLocation.displayName`, `postedDate`, `positionType`, `employmentType`, `workArrangementType` and `description` (the FULL body, ~8 KB, **plain text with no newlines and no markup**, so it is escaped and wrapped in a paragraph). No detail request exists or is made. `pageSize` 1000 works (9.5 MB), 200 keeps a page ~2 MB.
- **A search serves at most 10,000 results**: `from + size > 10000` answers 400, whatever the filter, so the 66k catalogue is read whole by cutting it with the site's own facets (`facets=<name>` on a one-row probe returns every value with its count under the current filters; `filters.<name>=<value>` selects one). Cut order: `countryId` (64 values summing EXACTLY to the 66,047 total, a true partition), then `sectors` for a country still over 10,000, then that sector's sub-sectors, then `seniority` as a last resort (its counts leave a ~4% gap). Measured 2026-11-22 from the crawl host: only the United States (18,283) and the United Kingdom (11,129) exceed the window; cut by sector they give leaves of at most 9,016 (Germany, uncut, is the largest) and IT/OTHER inside the US is 8,048. 149 leaves, 196 pages of 1,000 rows, **66,007 distinct postings of 66,047 (99.94%)** in 220 s; the leaf sum is 67,194 because sectors overlap. Unknown `filters.*` names are ignored (the count stays 66,047), unknown values of a known filter answer 0.
- **`fullCatalog`, guarded.** The walk fails on any slice or page that errors (after 3 attempts), on a slice still over 10,000 after every cut, and on a de-duplicated listing under 98% of the stated total, so the sweep by source uses only a complete enumeration. An unreadable row keeps its identity unless another facet slice supplies a readable copy, and any remaining unreadable identity withholds the source sweep. `expirationDate` 2050-01-01 with `expirationDateType: INVENTORY` is a placeholder, not a deadline, and is ignored.
- **The default location is a ranking hint, not a filter.** With no `location` the response states `searchedLocation: US` yet counts all 66,047 rows; `location=United Kingdom` (a country name) does narrow (11,080). Not used.
- **The sector taxonomy is NOT an IT statement, so `IsTechHint` is never set.** The "Technology" sector (`INFORMATION_TECHNOLOGY`, 32,566 postings, half the catalogue) and every child sampled (`/OTHER` 24,045, `/PROJECT_MANAGEMENT`, `/DEVELOPMENT`, `/SYSTEM_ADMINISTRATION_SUPPORT`, `/CYBER_SECURITY`) hold security officers, construction coordinators, field sales representatives, claims appraisers and executive assistants next to the engineers. Technical-or-not is left to the pipeline's catalogue filter.
- **Salary is structured but periodless.** `minSalary`/`maxSalary`/`salaryCurrency` are strings (`"Competitive"` arrives as `0`/`0`). The row names no period and a contract range can be a day rate (`500`-`700` GBP), so only a `Permanent` post whose minimum is at least 10,000 is read, as a yearly figure.
- **Display values are not the filter enums.** `workArrangementType` rows say `Hybrid`, `Remote`, `In-Office`, `Flexible`, `Temporarily Remote` (only the first three map to a work mode; 98% of rows state none); `positionType` says `Permanent`, `Contract`, `Temporary`, `Internships & Graduate Trainee`, `Self Employed`; `employmentType` says `Full time`/`Part time`.
- **Cost of a run.** ~330-400 pages of 200 rows (~1-2 s each, paced at 250 ms) plus ~70 one-row facet probes: roughly 10-15 minutes and ~600 MB on the wire. Rows are streamed (`FetchStream`), so nothing buffers the catalogue, and the pipeline re-saves every listed posting each run (the listing is the body, so there is no detail cost to avoid). The API answered a `freehire/0.1` and a browser user agent alike; 200 requests in a row were never refused.
- **Suggested schedule**: daily with a 1 h timeout.
