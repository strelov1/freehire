**Empregos.com.br traps** (`empregos`; live-verified 2026-10-24 from the fsn host, and a full run of the adapter from a residential IP):

- **The catalogue is ~90k postings, not the 231k the page headline says.** The listing's "231.197 vagas" is the API's `sum` — openings, a posting may offer several — while `total` (the postings) stood at 90,691-90,731. It is a general board: ~1% "Informática/TI", the rest everything else, and the catalogue filter judges each title. Every posting's `source` is `empregoscombr`.
- **The sitemap is gone and the listing pages are capped.** `robots.txt` still names `sitemap-index.xml`, which answers 404 (as do `sitemap.xml` and the obvious variants). The SSR listing `/vagas/N` serves 20 postings a page and stops at page 2,500 — 50,000 results, short of the catalogue — and `/buscar-vagas*` is disallowed. robots.txt otherwise allows everything for `*`; `gatewayb2c.empregos.com.br` has no robots.txt (404).
- **The crawl reads the search API the pages themselves call** — `POST gatewayb2c.empregos.com.br/searchjob/v2/elastic/search` with `{keyword:"", filters, page, size, order, distance}` (the endpoint is named in the page's public Nuxt config; `keyword` must be a string). Each result is the whole posting, body included, and the body is the same text the posting page's JSON-LD carries (compared on a sample; the page has nothing richer), so **no posting page is ever requested** and there is no per-posting detail cost to bound. The default client UA is served; curl's default UA drew the GoCache "Acesso Bloqueado" 403.
- **Paging that API loses postings, so it is not paged.** `page × size` is capped at 50,000 (404 past it) and `order` is ignored; worse, consecutive pages overlap — walking a 29,027-posting slice in pages of 10,000 returned 28,636 distinct ids, the SAME 28,636 on a second walk, and in pages of 1,000 only 26,988. One answer never repeats an id. So the catalogue is cut into slices that each arrive in ONE answer: by level (facet 10 — its 21 values add up exactly to the total, which the cut checks), then a level too large by the 27 federative units (facet 1, which takes lowercase codes: `sp` matches, `SP` matches nothing), then a cell still too large by workplace type (facet 17). Filters of different facets AND, two values of one facet OR. An answer carries at most `empregosLeafMax` (15,000, ~35 MB uncompressed, ~12 s — the largest cell measured 10,356); a slice that no cut brings under it fails the crawl. A full run is ~103 requests, ~2 minutes.
- **Not `fullCatalog`, deliberately.** A posting with no location (~0.1-0.3%: 269 of 90,731 in the live run, spread across levels) is in no state, so the state cut cannot reach it and nothing can prove it was read. The run logs the shortfall and carries on; the sweep stays company-scoped, and `cmd/liveness` probes the stale tail (`probeDespiteRegistered`): a removed posting redirects to `/404`, which answers 404.
- **A hidden employer is skipped.** `Confidencial` and `Empresa confidencial` (any case) are the board's label for an employer it does not name — 6,858 of the live run's 90,462 postings — and, as on OCC, such a posting has nobody to file it under.
- **What is structured, and what is not.** Location is `city`/`stateAbbreviation`/`country` per entry (a posting may list several; `country` is `br` on all of them, so it is a structured `Countries`). `workplaceTypes` (Presencial/Remoto/Híbrido) is the work mode. `contractForm` is `A Combinar` (to be agreed) on 99.96% of postings, so an employment type is set only for `Estágio` and the PJ/autonomous forms. **Salary is not published**: `salary.min`/`max` carry no currency or period field, 0 stands for absent, and over half are empty — the posting page's JSON-LD carries no `baseSalary` either. `createdAt` has no offset; it is Brasília time (UTC-3, the hourly peak is business hours there and the newest stamps run a few minutes ahead of BRT's clock). The description is HTML on most postings and plain text with HTML entities on the rest.
- **The posting URL is `/vaga/<referenceId>`** — the slug the site appends is optional (200 without it), so the stored URL cannot drift with a retitled posting.
- **New postings are written newest first, `empregosMaxNewPerRun` (5,000) a run, after the refreshes.** Every run lists the whole catalogue whatever it holds, so the bound is on database work, measured from the crawl host on 2026-10-24. The first prod run wrote 14,119 new postings at ~7 a second before its 40-minute crawl budget (the 3,000 s run timeout less the 600 s sweep reserve) ran out — it was capped at 20,000, so the run failed, wrote none of its refreshes and recorded no board health. A stored posting's refresh (`TouchJob`, one UPDATE) measured ~190 a second at the pipeline's 8 connections, so refreshing the whole ~90k catalogue costs ~8 minutes a run; listing costs ~4. At 5,000 new writes (~12 minutes) a run uses about 60% of its budget. The refreshes are yielded first so that a run cut short loses new writes, not liveness. With ~10k postings created a day (the API's "today" filter), a run every 4-6 hours keeps up once the ~70k backlog is through.
