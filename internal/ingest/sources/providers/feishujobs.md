**Feishu Jobs traps** (`feishujobs`; live-verified 2026-10-15):

- **A board is a tenant's careers HOST**: `jobs.bytedance.com`, or a customer's `<tenant>.jobs.feishu.cn` (MiniMax is `vrfi1sk8a0`). Every tenant's site calls the same keyless `POST /api/v1/search/job/posts`, and a row is the whole posting — `description` and `requirement` as plain text — so there is no hydration. `robots.txt` disallows only `/referral` on ByteDance; the tenant host has none.
- **The edge filters on the OPERATING SYSTEM in the User-Agent.** Both hosts answered 405 with an empty body to our own string, to `browserUserAgent` (Linux), to Windows Chrome and to Go's default, and 200 to `Mozilla/5.0 (Macintosh; Intel Mac OS X 10_15_7)` alone — hence `macBrowserUserAgent`. No cookie, token or Referer is needed.
- **The count stops at 10,000.** ByteDance's unfiltered search answers `count: 10000` over ~20k postings (11,965 experienced + 8,003 campus by category sum); a filtered count below that is exact (R&D experienced walked to 5,088 distinct of 5,088). A count at the window fails the board.
- **A search with no recruitment filter answers EXPERIENCED postings only.** Campus (`recruitment_id_list: ["2"]` — 201 new graduates, 202 interns) has to be asked for; `1` is experienced. Both are real postings and both are read, one walk each.
- **The crawl is scoped to the tenant's `R&D` (研发) category, because `classify` cannot read Chinese titles.** Over the first 100 experienced ByteDance titles of each category it resolved a category for 7 R&D titles (13 Corporate Function, 8 Design, 4 Marketing, 2 Product, 1 Operations, 1 Sales), `IsTech` for 3 R&D and 1 Product, and `ConfirmedNonTech` for NONE in any category — the ingest gate would admit everything and `is_tech` would stay unknown, leaving the rows out of search and out of enrichment. Over all 5,088 experienced R&D titles: category 410, `IsTech` 249, `ConfirmedNonTech` 4 (data-centre mechanical/electrical engineers). R&D is the platform's own technical bucket, so it sets `IsTechHint`. Of ~20k ByteDance postings, 9,541 are R&D (5,088 experienced, 4,453 campus).
- **The category tree has no fixed depth and its ids are per tenant.** ByteDance's R&D is a top-level node with disciplines under it; MiniMax's sits under an industry root (`互联网 / 电子 / 网游`) with a third level. So R&D is found by NAME in the tenant's `GET /api/v1/config/job/filters/2`, and a row belongs when its category or an ancestor is that node. The search IGNORING a filter would answer a larger mixed slice, so one row outside the asked-for category or hire type fails the board.
- **Geography is English and structured, the dictionary is not.** `location.Parse` reads no Chinese city name (北京, 上海 resolve nothing) and `NormalizeCountry` does not know "Chinese Mainland" or "Hong Kong, China". Location is built from each city's `en_name`; the country from `job_post_info.address_list[].country.en_name`. "Hong Kong (China)" loses its suffix, or the parser places it in mainland China too. ByteDance R&D is not all China: San Jose, Seattle, Singapore, London, Riyadh and more.
- **The posting page depends on host and hire type**: ByteDance serves `/experienced/position/<id>/detail` and `/campus/position/<id>/detail`; a customer tenant serves `/index/position/<id>/detail` and 404s `/campus`. Only the campus route server-renders the title; the others are a client-rendered shell.
- **Throughput, not a rate limit, sets the duration**: from a residential IP a 100-row page took ~6 s and a 500-row page ~5 s; nothing was refused across ~200 requests. ByteDance is ~20 requests (~2.5 min), MiniMax 2.
