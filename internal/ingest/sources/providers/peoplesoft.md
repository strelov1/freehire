**PeopleSoft Candidate Gateway traps** (`peoplesoft`; live-verified 2026-10-15, on careers.dc.gov, cg.sandia.gov, employment.case.edu, erecruit.umsystem.edu):

- **A board is `<host>/<site>/<portal>/<node>`, and all four vary.** The search page is `https://<host>/psc/<site>/<portal>/<node>/c/HRS_HRAM_FL.HRS_CG_SEARCH_FL.GBL?Page=HRS_APP_SCHJOB_FL&Action=U&FOCUS=Applicant&SiteId=1`. Most tenants are `EMPLOYEE/HRMS`, but the University of Missouri System is `tamext/COLUM/HRMS` and Phoenix `hcmprodtam/EMPLOYEE/COP_TAM`. A wrong site answers HTTP 200 with the one line "Site name is not valid", which has no `win0` form and therefore fails the crawl instead of reading as an empty board. Every tenant is on its own host, so `atsboard` cannot recognise one from a URL.
- **The list grows by a form POSTBACK, inside the session the first GET opened.** "Load more" re-submits the whole `win0` form (ICSID and ICStateNum among it) with `ICAction=HRS_AGNT_RSLT_I$hdown$0`. Each answer is the WHOLE list so far, 50 rows more each time, so the last page read holds every row. The adapter therefore runs on a cookie client (`cookieSessionSource`). The ~100-row anonymous cap a third party described was not seen: Sandia read 215 of 215 rows and Missouri 600 of 600.
- **The stated count is ROWS, not postings.** One opening can be listed twice, with identical rows (Missouri: 600 rows, 514 distinct openings; Sandia 215 and 201). The walk proves completeness against the row count (`fullBoardListing`) and then dedups by opening id. If a postback adds no row before the count is reached, or the postback cap is hit, the crawl fails.
- **The posting page is a plain GET by opening id** (`Page=HRS_APP_JBPST_FL&JobOpeningId=<id>&PostingSeq=1`). The first request answers a 302 to itself that sets the session cookie, so the URL works as a public link. An opening the page does not serve lands on the SEARCH page under HTTP 200, so the page counts only when its own `HRS_SCH_WRK2_HRS_JOB_OPENING_ID` matches. Case Western lists one opening (14685) that no `PostingSeq` from 1 to 3 serves. It is deferred on every run and costs one request each time.
- **The body is the `HRS_SCH_PSTDSC_DESCRLONG$<n>` sections** (with headings in `HRS_SCH_WRK_DESCR100$<n>lbl`), joined in order. The list's "Posted" date is M/D/YYYY on every tenant that shows one. Western University shows none.
- **No `robots.txt` on any tenant** (each answers 404). No metering was seen at 4-way posting-page fan-out. The first crawl of Missouri's 514 postings took 9 minutes. After that a crawl is the list walk (~12 postbacks, up to 2.5 MB each) plus the new postings only.
