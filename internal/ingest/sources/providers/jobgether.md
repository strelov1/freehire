**Jobgether traps** (`jobgether`, jobgether.com; all verified live 2026-11-22 from the crawl host, plain client, no proxy):

- **It is a re-aggregator.** Every posting sampled (9 of 9, across the sitemap) carries the employer's own apply link in the page body's `data-offer` attribute — Workday, Ashby, Greenhouse (`gh_jid`), iCIMS, Rippling, Gupy, an employer's own careers site — with `?source=jobgether` / `utm_source=Jobgether` appended. So most of the ~100k postings duplicate a posting an ATS adapter of ours may already hold. That is why it is an `Aggregator()`: the `duplicate_of_aggregator` pass settles the overlap. The link is stored as `ExternalApplyURL` (discovery evidence, not a catalogue destination); a posting with `isEasyApply: true` is applied for on Jobgether and records none. The catalogue also holds postings whose employer has no ATS we crawl, which is what makes the board worth reading at all.
- **robots.txt** (`User-agent: *`): `Allow: /`, `Allow: /astroapi/ai/jobs.json`, `Disallow: /*?*` (any query string), `Disallow: /offer/{*}` and its encoded twin (the literal template, not real postings), `/proxy/*?*`, `/cdn-cgi/`, `/_server-islands/`, `/active-offers`. It lists `Sitemap: https://jobgether.com/sitemap.xml`. `Content-Signal: search=yes, ai-input=yes, ai-train=no`. The adapter requests only the sitemaps and query-less `/offer/<id>-<slug>` pages, none of which is refused.
- **The catalogue is the sitemap.** `sitemap.xml` -> `sitemap/index-offers.xml` -> `offers-1.xml` ... `offers-7.xml`, 15,000 URLs each except the last (11,630 on 2026-11-22: ~101.6k postings). `<lastmod>` is the sitemap build time for every row, not the posting's, so it cannot narrow a crawl. Other sitemaps (`index-landings`, `index-explorer`, `index-company-landings`, ...) are category/company landing pages, not postings.
- **The search API cannot enumerate it.** `/astroapi/ai/jobs.json` (also `/api/v1/jobs`, described by `/.well-known/api-catalog` and `/astroapi/ai/jobs/openapi.json`) is an AI-assistant search endpoint: `limit` capped at 25, `page` capped at 10, so 250 postings per query, with no body — only title, company, location text, salary range and function. The adapter does not use it.
- **A 403 for a bare `Mozilla/5.0` User-Agent, 200 for ours.** `Mozilla/5.0` alone drew 403 on both the sitemap and a posting page; the project's `freehire/0.1 (+https://freehire.me)` and the `compatible; freehire` form both got 200 (0.09 s per page). Do not "fix" the client toward a bare browser string.
- **Posting id** is the 24-hex Mongo ObjectId opening the path segment; the slug after it is the title and may change. `ExternalID` is the id, available from the sitemap before any page is read, which is what lets a stored posting be refreshed without a request.
- **The posting page's JobPosting is the whole posting** (~220 KB page): `title`, `description` (HTML, begins "This a Full Remote job, the offer is available from: <countries>"), `hiringOrganization.name`, `datePosted`, `validThrough` (always posted + 60 days), `employmentType` (array: `FULL_TIME`, `CONTRACTOR`, ...), optional `baseSalary` MonetaryAmount. Everything is `jobLocationType: TELECOMMUTE`, so `Remote`/`WorkMode` are set outright.
- **Geography is `applicantLocationRequirements`** (a country code per entry), which is where the posting may be worked from: one country for US-only postings, 30-135 for regional ones (an Europe-wide posting names 54, an Asia-Pacific one 70+). `jobLocation` repeats the same countries, plus one entry per US state, so it is only the fallback. There is no city text, so `Location` is left empty and the countries carry the geography. Postings written in other languages exist (Italian, Portuguese): the classify gap there is the usual non-English one.
- **A page whose own `validThrough` has passed is skipped rather than stored.** The adapter also stores `validThrough` as the application deadline so an already-seen posting can close even if it remains in the sitemap.
- **Budget.** `jobgetherMaxNewPerRun` (3000) bounds the pages one run buys, picked at random from the unseen set; stored postings cost nothing but their sitemap row. The first runs work through ~100k backlog, 3000 per run, at one request per 250 ms and two in flight (~13 minutes of page reads plus the 7 sitemap shards, ~16 MB). No rate limit was met in ~250 consecutive requests from the prod host. Needs a `boards` row (`cmd/add-board --provider=jobgether`, no board id) to be scheduled.
- **No `IsTechHint`.** The page states no category of its own (the listing API's `jobFunctions` is not in the page), so the catalogue filter decides.
