**Kariyer.net traps** (`kariyernet`; live-verified 2026-11-17 from a residential IP through a local Scrapling service, and on the crawl host in the first production run):

- **A posting page carries the posting in its server-rendered Nuxt 2 state, and that is what the adapter reads.** The state is one JavaScript function, `window.__NUXT__=(function(a,b,...){return {...,state:{jobDetail:{jobInfo:{...}}}}}(arg0,arg1,...))`, not devalue, so `unflattenPayload` does not read it: the object names repeated values by parameter (`title:ai`, `companyName:bW`) and the values are the call's arguments. `jobInfo` is the posting exactly as the gateway's `/job` answers it (`jobGeneralInformation`, `jobPositionInformation`, `jobCompanyInformation`), so `kariyernet_page.go` finds it, reads the literal with a small parser that resolves each parameter to its argument (objects, arrays, strings with JavaScript escapes and `\ud83d\ude00` pairs, numbers, `!0`/`!1`, `void 0`, `null`), and decodes it into the same struct the API response used. Anything else in the literal, a call included, is an error and the posting is deferred. The page also carries no ld+json `JobPosting`. No sitemap lists postings (`/sitemaps/1..9` are city and keyword landing pages). robots.txt disallows neither the pages nor the gateway.
- **The posting API refuses the crawl hosts; the posting page is served over the proxy.** On 2026-11-17 the first live run from the crawl host (21:40-22:08 UTC) listed the whole catalogue through the search, which answers 200 on every route, and was refused 1,460 of 1,500 `GET candidatesearchapigateway.kariyer.net/job?jobId=` reads (40 postings stored): 403 on every route — the Scrapling `http` fetcher with and without the proxy, plain, and plain over the proxy. The same morning the fetcher passed it from a residential IP, so the gateway had begun refusing the impersonated fingerprint. What the crawl host is served is the posting page itself, `https://www.kariyer.net/is-ilani/<slug>-<id>` (the `url` the adapter stores, ~300 KB): 200 through the fetcher WITH the proxy, 403 without it, and 403 to a plain client from a residential IP too. So the provider is a `scraplingProviders` row (`http`, proxy) carrying only the pages; the search keeps a plain client, where it is served and costs no proxy traffic. A page refused anyway is asked again up to three times (`kariyernetPageRetries`, waits of 2, 4, 8 s) because every request leaves from a new exit; a posting that stays refused is deferred, and a run that reads none of the pages it listed fails.
- **The whole catalogue is read, as one slice per work area.** 24,968 open postings on 2026-11-17 (`totalJobCount`) across every profession; the search stops at page 100, which at `size: 200` is 20,000 rows, so no single query reaches all of it (page 100 of the unfiltered search ended at id 4,178,187; the oldest ~5k are unreachable). The site's own work area filter (`departments`, the page's `wa`) is the slicing dimension: the 97 areas the unfiltered response lists in `filters.workAreas` state 24,965 postings in total, the largest `Satış` 4,015, then `Üretim / İmalat` 2,179, `Satış ve Pazarlama` 1,754, `Muhasebe` 1,146. A full enumeration read 24,956 distinct postings in 197 requests (217 s unpaced; 24,954 in 3 m 48 s paced at one a second); the 12 missing carry no work area. Six areas stated a total one or two above what their pages carry (the sponsored rows), so an area ends when a page adds no new id and not at the stated total; one that reaches page 100 fails the crawl. The five IT areas (`78` "Bilgi Teknolojileri / IT", `5` "Bilgi İşlem", `55`, `54`, `60`) are walked first so the detail budget reaches them first. The area list is read from the unfiltered response, so a new area is picked up without a change. The areas are the employer's own pick and noisy, so no posting is hinted technical (`IsTechHint` unset); the pipeline's catalogue filter decides what is stored. robots.txt disallows neither the pages nor the gateway.
- **The request body is the app's query-string vocabulary spelled out.** `currentPage`, `size` (200 is served), `departments` (strings), `sortType: "SortByDate"` with `sortDirection: "Descending"` (the page's `sd=dd`). A body with `workAreas` or `workAreaIds` is silently ignored and answers the whole catalogue, which is how the real name was found: the page's own `convertFiltersToPostParams` maps `wa` to `departments`. The search prepends 3-5 sponsored rows to every page, so a page carries `size` plus a few rows and repeats ids; the walk dedups by id and ends when a page adds none or the listed total is collected. A `currentPage` above 100 is answered with page 100 again, so the walk fails if it reaches it rather than reading that as the end.
- **Employer-hidden postings are skipped before any request.** `confidential: true` (1,207 of 24,956 rows: `Gizli Firma`, `Sektöründe Lider Firma`, `Firma Bilgisi Gizli`) names no employer to file the posting under.
- **The posting is JSON with the body as HTML** (`jobGeneralInformation.qualificationsWithHtml`, a plain-text twin beside it), the date-only `postingDate`, the closing date as `closingDateNumeric` `dd.MM.yyyy` (a future date, so it cannot go through the `NotFuture` funnel `posted_at` uses), every location as city and country, and `jobPositionInformation.workModel` (`OnSite` 152, `Hybrid` 42, `Remote` 9 of 203), `workType` (`FullTime` 185, `Periodical` 15, `Freelance` 2, `PartTime` 1) and `positionLevel`. Only levels 8 "Stajyer" and 5 "Yeni Başlayan" map to a seniority. A removed posting answers 404 with `"status":"Error"`; one the site took down but still serves says `isActive: false` and is dropped.
- **The location dictionary reads Turkish cities** (checked 2026-11-17): `İzmir`, `İstanbul(Avr.)`, `İstanbul(Asya)`, `Şanlıurfa`, `Iğdır`, `Torbalı, İzmir` all resolve to `tr`. A province named bare — `Kocaeli` — resolves nothing, so the adapter passes `FallbackCountries: tr`, and names the country only when it is not Türkiye (`Berlin, Almanya` reads as `de`).
- **The title dictionary reads the Turkish IT vocabulary and nothing else Turkish.** Measured on the 437 IT-area titles before the Turkish table landed (#4804), `classify.IsTech` placed 30 and `classify.Parse` found a category for 59; after it, 190 and 284. A Turkish title outside IT (retail, logistics, finance, healthcare, the bulk of the catalogue) still resolves no category, so the rest of the catalogue is stored with an unknown category until the dictionary grows to cover it.
- **Pace and cost.** One request a second for search and page reads alike (`kariyernetRequestPeriod`), two detail workers. A run lists ~200 requests (~3.5 minutes) and reads at most 1,500 new postings (~25 minutes), inside the scheduler's 2,400 s crawl budget, newest first inside each area and the IT areas first. A cold start reads the ~24.6k postings over ~17 runs; a day's new postings were ~1-3k by `postingDate` (691-1,703 a day on 11-10 to 11-14, 3,589 on 11-16 and 6,458 on 11-17, which includes republished postings). 40 detail reads took 43 s with none refused through the local service. 1,207 of the 24,956 (4.8%) are confidential and cost no request.
