**Kariyer.net traps** (`kariyernet`; live-verified 2026-11-17 from a residential IP through a local Scrapling service, `http` mode, no proxy; the crawl host's datacenter IP was NOT measured):

- **The pages are Nuxt 2 with a JavaScript-function payload (`window.__NUXT__=(function(a,b,...){...})`), not devalue, so `unflattenPayload` does not read it — and nothing needs it.** The site's own app calls a JSON gateway, `candidatesearchapigateway.kariyer.net` (named in the page bundle as `VUE_APP_API_V4_DOMAIN`): `POST /search` for the listing and `GET /job?jobId=<id>` for a posting. No sitemap lists postings (`/sitemaps/1..9` are city and keyword landing pages), and the posting pages carry no ld+json `JobPosting`. robots.txt disallows neither the pages nor the gateway.
- **Only the search answers a plain client; the posting API does not.** From a laptop `POST /search` answered 200 plain, but `GET /job` answered an HTML 403 with or without the app's `Api-Version: 1.1` header. The impersonating fetcher passed both, so the provider is a `scraplingProviders` row (`http`, no proxy) carrying the search too, as one client. Whether the crawl host's datacenter IP passes unproxied is unmeasured: the first live run decides whether the row needs `proxy: true`.
- **The whole catalogue is read, as one slice per work area.** 24,968 open postings on 2026-11-17 (`totalJobCount`) across every profession; the search stops at page 100, which at `size: 200` is 20,000 rows, so no single query reaches all of it (page 100 of the unfiltered search ended at id 4,178,187; the oldest ~5k are unreachable). The site's own work area filter (`departments`, the page's `wa`) is the slicing dimension: the 97 areas the unfiltered response lists in `filters.workAreas` state 24,965 postings in total, the largest `Satış` 4,015, then `Üretim / İmalat` 2,179, `Satış ve Pazarlama` 1,754, `Muhasebe` 1,146. A full enumeration read 24,956 distinct postings in 197 requests (217 s unpaced; 24,954 in 3 m 48 s paced at one a second); the 12 missing carry no work area. Six areas stated a total one or two above what their pages carry (the sponsored rows), so an area ends when a page adds no new id and not at the stated total; one that reaches page 100 fails the crawl. The five IT areas (`78` "Bilgi Teknolojileri / IT", `5` "Bilgi İşlem", `55`, `54`, `60`) are walked first so the detail budget reaches them first. The area list is read from the unfiltered response, so a new area is picked up without a change. The areas are the employer's own pick and noisy, so no posting is hinted technical (`IsTechHint` unset); the pipeline's catalogue filter decides what is stored. robots.txt disallows neither the pages nor the gateway.
- **The request body is the app's query-string vocabulary spelled out.** `currentPage`, `size` (200 is served), `departments` (strings), `sortType: "SortByDate"` with `sortDirection: "Descending"` (the page's `sd=dd`). A body with `workAreas` or `workAreaIds` is silently ignored and answers the whole catalogue, which is how the real name was found: the page's own `convertFiltersToPostParams` maps `wa` to `departments`. The search prepends 3-5 sponsored rows to every page, so a page carries `size` plus a few rows and repeats ids; the walk dedups by id and ends when a page adds none or the listed total is collected. A `currentPage` above 100 is answered with page 100 again, so the walk fails if it reaches it rather than reading that as the end.
- **Employer-hidden postings are skipped before any request.** `confidential: true` (1,207 of 24,956 rows: `Gizli Firma`, `Sektöründe Lider Firma`, `Firma Bilgisi Gizli`) names no employer to file the posting under.
- **The detail is JSON with the body as HTML** (`jobGeneralInformation.qualificationsWithHtml`, a plain-text twin beside it), the date-only `postingDate`, the closing date as `closingDateNumeric` `dd.MM.yyyy` (a future date, so it cannot go through the `NotFuture` funnel `posted_at` uses), every location as city and country, and `jobPositionInformation.workModel` (`OnSite` 152, `Hybrid` 42, `Remote` 9 of 203), `workType` (`FullTime` 185, `Periodical` 15, `Freelance` 2, `PartTime` 1) and `positionLevel`. Only levels 8 "Stajyer" and 5 "Yeni Başlayan" map to a seniority. A removed posting answers 404 with `"status":"Error"`; one the site took down but still serves says `isActive: false` and is dropped.
- **The location dictionary reads Turkish cities** (checked 2026-11-17): `İzmir`, `İstanbul(Avr.)`, `İstanbul(Asya)`, `Şanlıurfa`, `Iğdır`, `Torbalı, İzmir` all resolve to `tr`. A province named bare — `Kocaeli` — resolves nothing, so the adapter passes `FallbackCountries: tr`, and names the country only when it is not Türkiye (`Berlin, Almanya` reads as `de`).
- **The title dictionary reads the Turkish IT vocabulary and nothing else Turkish.** Measured on the 437 IT-area titles before the Turkish table landed (#4804), `classify.IsTech` placed 30 and `classify.Parse` found a category for 59; after it, 190 and 284. A Turkish title outside IT (retail, logistics, finance, healthcare, the bulk of the catalogue) still resolves no category, so the rest of the catalogue is stored with an unknown category until the dictionary grows to cover it.
- **Pace and cost.** One request a second for search and detail alike (`kariyernetRequestPeriod`), two detail workers. A run lists ~200 requests (~3.5 minutes) and reads at most 1,500 new postings (~25 minutes), inside the scheduler's 2,400 s crawl budget, newest first inside each area and the IT areas first. A cold start reads the ~24.6k postings over ~17 runs; a day's new postings were ~1-3k by `postingDate` (691-1,703 a day on 11-10 to 11-14, 3,589 on 11-16 and 6,458 on 11-17, which includes republished postings). 40 detail reads took 43 s with none refused through the local service. 1,207 of the 24,956 (4.8%) are confidential and cost no request.
