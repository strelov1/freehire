**remote.com traps** (all verified live 2026-08-16):

- **The RSC flight is the API, and it carries different halves of a posting at each URL.** remote.com is a Next.js App Router app: there is no REST endpoint and no Pages-Router `_next/data` one, and every guessed path answers 404/500. Sending `RSC: 1` makes a page answer `text/x-component` instead of HTML — the LISTING inlines a `jobsData` object as plain JSON (identity, employer, geography, seniority, compensation, and the `totalPages` that bounds the walk exactly), a POSTING PAGE carries the body. `Next-Router-State-Tree` is not needed; the flight comes back complete without it.
- **The listing has no description field at all, and the posting page's description is not in an `application/ld+json` script.** The RSC response has no HTML to hold one — the schema.org JobPosting arrives as a flight TEXT ROW (`<id>:T<hexlen>,{…}`), which `flightJobPosting` reads with the existing `nextFlightTextRows` + `jobPostingNode` pair. That split is the whole reason this adapter is a `HydratingSource`: a body-less row never enters the search index (`search.DescriptionMissing`), so a list-only crawl would ingest ~5.7k postings nobody can find.
- **`compensation.minimum`/`maximum` are MINOR units.** The listing states one posting as `1000000-1500000` USD/yearly while that same posting's `baseSalary` states `10000-15000`. Reading them verbatim inflates every salary a hundredfold. Related: `currency.symbol` is `"$$"` for USD (a format-template artifact), which is why the adapter reads `currency.code` and never the symbol.
- **`hiringLocation.timezone.name` is a zone label, not a place.** It is the city the zone is named after (`america-chicago` → `"Chicago"`), and passing it through bare makes `location.Parse` file a work-from-anywhere-in-this-zone posting under `Cities:[Chicago] Countries:[us]`. The adapter appends `" timezone"`, which is both what the posting says and — because the dictionary matches whole phrases — what stops the city from being invented.
- `hiringLocation` is null on roughly one posting in ten, `includedLocations` entries are `country` OR `region` (`north-america`, `latin-america`, `europe`, `africa`, `asia-pacific` — remote.com's own vocabulary, resolving to no country code), and `workplaceLocation` carries the country and city only when the posting is not remote.
- **No rate limiting observed**: 48 posting pages at 8-way concurrency (~12 req/s) all returned 200, so no pacer is wired. If that changes, `pacer.go` is where it goes — a `HeaderTextGetter` variant of `rateLimitedHTMLGetter`.
- **Most of the board is already ATS-covered, and `seen` cannot bound that** — which is why remotedotcom is the one `CoverageGated` adapter. Prod's first two runs both crawled 5,745 postings and kept 1,417: **4,123 were discarded by the aggregator gate** (the employer runs its own ATS, which freehire already crawls first-party) and 205 as non-technical. A discarded posting is never stored, so it is never `seen`, so the plain hydrating crawl bought and threw away 4,123 bodies EVERY run. `FetchNewGated` asks the pipeline which employers are covered before hydrating and skips their bodies. Measured across the twelve hydrating aggregators on prod, this is remote.com's problem alone — every other one wastes 0-3%, except aijobs (44% of a 500-posting board) and echojobs (12%), whose detail endpoint is dead anyway.
