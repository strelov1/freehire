**gupy traps** (verified live 2026-10-19, from a laptop and from the prod host):

- **A board is a career-page SUBDOMAIN (`caju` for `caju.gupy.io`), not a companyId.** The companyId-keyed listing (`employability-portal.gupy.io/api/v1/jobs`) has answered an nginx 404 to every query shape since 2026-09-30, which failed all 1,511 boards for 19 days and left 73,156 postings open on a frozen `last_seen_at`. Nothing public lists by companyId any more — `portal.gupy.io/api/job-search/jobs` (the portal's own proxy) accepts a `companyId` parameter and ignores it. What still works is the API every career page renders from: `private-api.gupy.io/job-publication/public/jobs?subdomain=<page>` lists the page's published postings in ONE unpaginated answer (3,486 on `restaurantemc`), and `/job-publication/public/jobs/<id>` is the sectioned detail.
- **One company owns several career pages, and each is a board.** On prod 916 of the 1,511 companyId boards had postings on two or more pages (an internal-mobility page, a "confidencial" one); a page two companies both published on becomes one board, attributed to whichever companyId board the one-time rekey met first.
- **The rekey preserves posting identity.** The one-time rekey (its command has since been removed) read each posting's page from its stored URL and rewrote `external_id` from `<companyId>:<id>` to `<page>:<id>`, and only after EVERY companyId board had moved did it add the page boards (a shared page crawled between two moves would collide), so the first crawl of a page UPDATES its rows instead of inserting duplicates, and the board-scoped sweep (`gupy` is `fullBoardListing`) closes the rows the page no longer lists. The rows no sweep can reach — on a page that lists nothing, or one Gupy 404s — the rekey closed itself.
- **The listing carries no body, so this is a `HydratingSource`.** The detail is the posting's only description, so for an UNSEEN posting a failed detail is an `unreadableDetail` marker, a 404 (`"Vaga inexistente na empresa atual"`) is gone, and a detail whose sections are all placeholders (`<p>.</p>`) is a marker too. `publishedAt` also comes from the detail. A posting the catalogue already holds costs no detail request: `FetchNew` re-lists it as a `SeenRefresh`, because the listing itself proves it is still published, and the listing stays whole, so the board-scoped sweep still closes what a page stopped listing. Re-reading every detail on every run was ~72k requests per run across 3,324 page boards (2026-10-19) against a 50-minute timeout — no run could finish, and every one hammered Gupy. What it costs now is one listing request per board plus a detail per NEW posting: ~1,700 a day on average before the 2026-09-30 outage (weekday peaks ~3,900, weekends under 200). `BODY_REFRESH_DAYS` is what re-reads an edited body. The first run after this lands faces every posting published during the 19-day outage (on the order of 30k details) and will time out a few times, which is safe: each finished board is saved and its postings leave the unseen set.
- **An unknown page is a 404 (`"Career Page not Found"`), a live page with nothing published is `{"data":[]}`.** The first fails the board; the second is a zero-yield success that licenses no sweep.
- **The canonical posting URL is `https://<page>.gupy.io/jobs/<id>`** — what the career page links to. The portal's `/job/<base64>?jobBoardSource=gupy_portal` form stored before the rekey is overwritten on the next crawl.
