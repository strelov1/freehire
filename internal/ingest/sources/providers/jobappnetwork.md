**jobappnetwork traps** (all verified live 2026-09-06):

- **The vendor is talentReef; jobappnetwork.com is only its applicant-facing brand.** `apply.jobappnetwork.com` serves talentReef's React SPA (`<title>talentReef</title>`), and its own bundle is what names the real API host — `prod-kong.internal.talentreef.com/apply`. The host's own name says "internal", but it resolves publicly and answers an unauthenticated cross-origin request (`access-control-allow-origin: *`); nothing about the SPA's own network calls needs a session, a cookie or a key.
- **The listing is a raw Elasticsearch proxy, and `clientId` is a query FILTER, not a path scope.** `POST .../apply/proxy-es/search-en-us/posting/_search` with body `{"query":{"bool":{"filter":[{"term":{"clientId":<id>}},{"term":{"internalOrExternal":"externalOnly"}}]}},"from":<n>,"size":<n>}` returns exactly one employer's postings when the filter is present — confirmed against two clients (a 2,729-posting fleet and a 1-posting one) — and a query with NO filter at all (`match_all`) returns postings across the whole platform. The filter is therefore load-bearing on every request this adapter builds, never optional.
- **`internalOrExternal` must be filtered in the query, not dropped after the fact.** Every sampled posting carries exactly `externalOnly` or `internalOnly`; an internal-transfer-only posting has no business reaching a public job board, and pushing the exclusion into the request means it can never cross the wire in the first place, rather than relying on mapping code remembering to check a flag.
- **`hits.total` is exact and stable**, the same family as Dayforce's `maxCount` and EDJOIN's `totalRecords` rather than SEEK's page-size-dependent `totalCount` — confirmed unchanged across page sizes on the sampled boards, so plain `from`/`size` pagination bounds the walk with no need for `search_after`. The largest board sampled (2,729) is far short of Elasticsearch's 10,000-result default window.
- **The listing carries the whole posting body.** `description` is full HTML matching what the posting page itself renders, with no truncation observed on any sampled posting — so, like Dayforce, this is not a `HydratingSource`.
- **One `clientId` is one employer, not an aggregator.** Every posting sampled under one `clientId` shared the same `clientName` (a company or a franchise operator running many locations under one or more brands), so `Job.Company` is the board's configured company, the Dayforce/Gusto model, not Crelate's per-posting one.
- **The catalogue skews hourly/frontline (restaurant and retail franchises) but is not exclusively that.** Full-text probes against the whole index turned up real corporate/engineering postings at non-restaurant clients ("Senior DO-178 Software Engineer" at an aerospace supplier, "Software Quality Assurance Engineer" at a furniture retailer's corporate office) alongside thousands of shift-lead and crew-member roles — the same "generic ATS carries the whole company" shape `catalogue_fit.go` exists for, needing no special handling beyond the ordinary non-tech-title rejection.
- **A discovered risk, not this adapter's to fix: the index is a shared multi-tenant cluster with weak scoping.** An unfiltered query reads across every talentReef client, and one document surfaced during this research was clearly third-party-injected content unrelated to any real posting — evidence the cluster has been probed before. Irrelevant to correctness as long as every request here carries the `clientId` filter, but a reason never to build a request from unscoped input.
- **No adapter-scale request volume was sent during this research** — unlike most other entries in this file, this one does NOT claim "no metering observed". Ship without a pacer (the default for an unmeasured provider) and watch the first real boards' `board_health` rows before onboarding many at once.
