**Jumpit traps** (`jumpit`; live-verified 2026-11-04 from a residential IP; 792 open postings):

- **The site's own JSON API, keyless.** `jumpit-api.saramin.co.kr/api/positions` lists, `/api/position/<id>` is the detail; both answer the project User-Agent. The site's `robots.txt` blocks only account, résumé and application pages. The API host's own `robots.txt` answers a CloudFront 403, so there is no separate policy to read for it.
- **Read the listing in pages of 1,000, never at its default 16.** The order is unstable between requests whatever the sort (`reg_dt`, `rsp_rate`, `popular`), so a 16-row walk repeated some rows and lost as many — 779 to 791 distinct of 792 across four walks. `size=1000` (also 2000 and 5000) returns all 792 distinct in one ~0.5 MB response, every time; page 2 then answers an empty page whose `totalCount` is 0. That single page is what makes `fullCatalog` sound: any page failing, the total moving, or the distinct ids falling short of it fails the crawl.
- **The geography is the listing row's `locations`, not the detail's `workingPlaces`.** `locations` is the platform's region picklist (`서울 종로구`); `workingPlaces` is the employer's office address. They disagree for a posting abroad: "[일본] FDE(SW)" is listed under `아시아·중동 일본 도쿄` and addressed to the Seoul office. The `domestic` flag beside the address read `false` for a Seoul address, and is not read. Every row carried exactly one location.
- **The region is mapped, not parsed.** The location dictionary holds no Hangul, so `서울 종로구` resolves to nothing. `jumpitRegions` maps the first word — the platform's region label, 16 distinct over the whole catalogue — to the English name the dictionary reads (`Seoul, South Korea` gets city and metro facets; a province gets the country) and states Korea as the country. `전남광주` is the platform's label for the merged South Jeolla and Gwangju region. A label outside the table (`아시아·중동`) keeps the platform's text and states no country.
- **The category is the platform's own picklist.** 22 job categories (`서버/백엔드 개발자`, `인공지능/머신러닝`, `HW/임베디드`, …), every one technical, so every posting carries `IsTechHint`. Each maps to what the title dictionary gives its English equivalent, and a posting filed under two that disagree names none. `HW/임베디드` and `VR/AR/3D` are left unmapped. The mapping matters more than usual: titles are Korean, so the title dictionary resolves almost none of them — and on the English equivalents it read "Game Server Developer" as `hospitality`.
- **The body is six plain-text fields**, rendered under the posting page's own headings (주요업무, 자격요건, 우대사항, 복지 및 혜택, 채용절차 및 기타 지원 유의사항, 기업/서비스 소개). There is no salary and no work-arrangement field.
- **`newcomer` means open to new graduates.** Those rows carry `minCareer` 0 and `maxCareer` 0 (62 of 792), so the minimum experience is 0; every other row states its minimum.
- **A missing posting answers 400 `Entity Not Found` (`C003`), not 404.** A new posting whose detail fails is deferred to the next run either way, never stored body-less.
- **Paced at 1 req/s (`jumpitRequestInterval`), unmeasured.** No request was refused while the adapter was written. A cold run is one listing request plus ~800 details (~14 min); steady state is the listing plus new postings. The first 403/429 cancels the rest of the run's detail requests. A detail that cannot be read (a refusal, a timeout, a 5xx) is yielded as an Unreadable identity, so a stored posting offered for re-reading is not lost to the source-wide sweep; a 404/410 is simply not yielded.
