**Naukri traps** (`naukri`; live-verified 2026-10-18 from a residential IP, prod and the crawl host):

- **Reachable only through `SOURCES_PROXY_URL`.** From prod and the crawl host every path — `robots.txt` included — is tarpitted by Akamai: HTTP/1.1 hangs to the timeout, HTTP/2 is reset with `INTERNAL_ERROR`, and a headless Chrome gets `ERR_HTTP2_PROTOCOL_ERROR`, so no transport on those IPs helps. Through the proxy plain HTTP answers in ~1-2 s, so no browser is needed either. Hence `proxiedProviders`; without the proxy the provider fails every run, which is the honest outcome. `robots.txt` disallows nothing under `/jobapi/` for `User-agent: *`.
- **The listing is the ANDROID APP's search, not the website's.** The site calls the same `GET /jobapi/v3/search` and `GET /jobapi/v4/job/<id>`, but a browser User-Agent gets `406 {"message":"recaptcha required"}` on both, our own User-Agent gets 403 Access Denied, and only the app's HTTP stack (`okhttp/4.9.0`) plus `appid: 105` / `systemid: 105` is served; without those headers the API answers 400 "Please provide the valid App Id and System Id". The client's User-Agent always wins over per-request headers, so the string is set on a copy of the transport (`withUserAgent`) — applied again over the proxied client in `proxiedProviders`, or the rewire would silently restore ours. The listing and every page the SPA renders are client-side shells, and the job sitemaps carry URLs only.
- **A board is a FUNCTIONAL AREA id** (`functionAreaIdGid`): `5` Engineering - Software & QA, `8` IT & Information Security, `3` Data Science & Analytics, `4` Engineering - Hardware & Networks — the ids the search's own `functionalAreaGid` facet reports. An unknown id answers 0 rows (not the unfiltered catalogue), a non-numeric one an Elasticsearch 400; the adapter refuses anything but digits. The filter was checked against the posting API's own `functionalArea` on a sample. `3`/`5`/`8` set `IsTechHint`: `classify.IsTech` accepted 80 of 300 of their titles and `ConfirmedNonTech` none. `4` mixes in hardware roles and gets no hint.
- **The search window is 15,000 rows.** `noOfResults` serves up to 100 and page 150 is the deepest: page 151 answers 400 "Invalid value" at any page size. The walk reads `jobAge=7` sorted by freshness (`sort=f`, newest first). On 2026-10-18 the 7-day window held 18,920 postings in area 5 (truncated to its newest 15,000, logged), 5,177 in 8, 2,724 in 3 and 1,815 in 4; the whole catalogue held 102,872 in 7 days, so the technical areas are about a quarter of it. Area 5 held 56,950 over 30 days — no single query can read a month.
- **Not `fullBoardListing`, and a 14-day sweep grace.** A posting the employer does not refresh leaves the 7-day window while still live, and area 5 is truncated anyway, so "not seen this run" is not evidence. A later search page failing ends the walk with what was read. The posting API answers an expired or unknown id with `303 {"metaSearch":{"isExpiredJob":"1"}}` and no Location (read as gone), but nothing asks it about a stored posting, so the grace is what closes one.
- **A search row is a snippet; the posting API is the body.** `jobDescription` in the search is ~300 characters; `/jobapi/v4/job/<id>?microsite=y` carries the full HTML `description`, the places (`locations[].label` — the search's location placeholder can read `Hybrid - Bengaluru`), `wfhType` (`0` office, `2` remote, `3` hybrid, `1` the covid-era temporary WFH and left unmapped) and `employmentType` (`Full Time, Permanent`; a `Temporary/Contractual` or `Freelance/Homebased` nature is a contract). New postings only (`HydratingSource`), newest first, at most 1,500 a RUN — one counter on the adapter, which cmd/ingest builds once per process and crawls every board through — at 2 req/s over four workers: 150 details at ~4 req/s through the proxy were all served. One board may spend at most a third of it, so area 5's 15k cold backlog cannot take the whole run from `8` and `3`; a fourth board gets only the leftover until the saturated backlogs drain (area 5's in ~30 runs), after which nothing is starved. A cold start is ~23k details across `3`/`5`/`8`; steady state is a few hundred a run.
- **Salary is per annum in rupees when shown.** 75 of 300 rows publish `salaryDetail` (`hideSalary: false`) with the label `95 Lacs-2.5 Cr PA`; only a label ending in ` PA` is published, as `year`. `createdDate` is epoch milliseconds and moves when the employer refreshes the posting — the id's leading `DDMMYY` is the original date. `minimumExperience` is mapped when above 0. `tagsAndSkills`/`keySkills` are free text and are not mapped. Consultancies post under their own name (`consultant: true`, about one row in six); the client is usually unnamed.
- **The proxy's exit IP lost the posting API on 2026-10-19.** Every prod run failed: the search answered through `SOURCES_PROXY_URL` (until page ~143 of area 5, which also turned 406), while EVERY posting request answered `406 {"message":"recaptcha required"}` from the first one of the first run. Reproduced by hand through the same proxy (exit `45.61.127.48`, AS62874 Web2Objects — a hosting network, not residential) with the exact app User-Agent and headers: search 200, posting 406 on `v4`, `v3` and every appid; the same requests from a residential IP served 400 of 400 postings at ~1.5 req/s. So it is the IP's reputation with Akamai, not the adapter's headers or wiring, and no code reaches past it — the hosted tier is out too (the Firecrawl account has no credits). The adapter now treats a 406/403/429 from the posting API as a refusal of the IP: the first one ends hydration for the whole run (one log line), the board fails naming the refusal unless it still refreshed stored postings, and `board_health` cools it. Before that each run sent 1,500 refused requests through the shared proxy. **Crawling naukri needs a different egress** (a residential exit); until there is one, disable its schedule rather than let it fail every two hours.
- **The rotating gateway is that egress (2026-10-21).** The same Webshare account's rotating endpoint (`<user>-rotate@p.webshare.io:80`) hands out a fresh exit per request, and through it 15 of 20 posting requests answered 200 and five timed out, none refused. naukri therefore egresses through `SOURCES_ROTATING_PROXY_URL` when it is set (`rotatingProxyProviders` in proxy.go) and through the fixed exit otherwise. A refusal used to end the run's hydration: with a fresh IP per request it is one bad exit rather than the IP's verdict, so if refusals show up in the run logs that rule is the next thing to loosen. They did: on 2026-10-25 two of four runs met one 406 each and stopped hydrating, one of them 30 seconds in. It now takes `naukriRefusalLimit` (10) refusals in a run; a refused posting is deferred either way.
- **The coverage gate ate the whole budget (audit 2026-10-25).** The adapter hydrated newest first and the pipeline then discarded every posting whose employer a non-aggregator source already covers — unstored, so never `seen`, so bought again on the next run. Once the uncovered postings were stored, the newest unseen ones were exactly the covered ones: every board logged `skipped 500/… postings — company already covered`, i.e. its whole 500-detail share, every run, and the catalogue sat at 3,993 open postings for four days while 9,166 area-5 postings waited. The adapter is now `CoverageGated`: a covered or catalogue-rejected posting is yielded body-less with no request. Measured the same day: the technical areas held 16,131 postings in the 7-day window (5: 11,621, 8: 2,521, 3: 1,989) and 74,720 in 30 days; area 4 1,364 / 5,406; the whole site 69,073 / 329,083, ~7k new a day (a Sunday). So even a fully drained 7-day window is ~22% of the live technical catalogue — widening it needs slices, since one query stops at 15,000 rows.
