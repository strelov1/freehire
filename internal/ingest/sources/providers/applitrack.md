**AppliTrack traps** (all verified live 2026-09-02, across the 2,905 candidate tenants the `applitrack` boards were harvested from):

- **The crawl reads the WHOLE board** through the site's own "All Vacancies" listing (`?all=1`), one request per board. Until 2026-10-20 it read only an allowlist of the district's technology categories, because the catalogue was IT-only and the non-technical gate had no vocabulary for K-12 staff: over the 86,033 postings 2,387 live tenants were listing, the technology slices held only **360**. The catalogue is broader than IT now, so the board is crawled whole and the dictionaries decide what each posting is. Expect the first crawl after that change to hydrate roughly 36 postings per board (the fleet-wide average of that measurement), one detail request each.
- **Nothing on the platform is served as HTML.** `view.asp` is a shell that document.writes a script from `Output.asp` beside it, and `Output.asp` answers `text/javascript` whose `document.write('…')` arguments carry the WHOLE page — listing rows, posting bodies and all. So both halves of a crawl are read as raw text, unescaped, and only then parsed. The adapter asks for `Output.asp` directly: `view.asp` merely re-emits it inside a `<script>`, so reading the shell would mean digging the same payload back out. The only escape the payloads use is `\'`, because the platform's own markup quotes its attributes with the apostrophe that terminates the string it is written through.
- **A truncated response is legible, which is what makes it dangerous**, so the unescape reports whether every `document.write` it read was TERMINATED and the adapter refuses a page where one was not. The markup before a cut parses, the rows before it read fine, and the crawl would take an incomplete listing for a complete one — which on a company-swept provider closes every posting past the cut. `GetText`'s own `maxTextBody` cut now names itself (a `BodyTooLargeError`, returned alongside the bytes it did read), but an origin that stops mid-response still says nothing at all. The unterminated call is the one symptom BOTH leave, which is why it stays now that only half of what it guards against is typed.
- **A posting id linked from OUTSIDE the platform can be composite.** A consortium's posting is linked as `AppliTrackJobId=6536_37241`, where the suffix selects which member district's page to land on, and the endpoint ignores it — both spellings answer the identical posting, `JobID: 6536`. The adapter's pattern takes the leading digits, which is right rather than lax: keying on the whole token would store one requisition once per district that links it. No board's own listing was seen to emit the composite form (all 367 ids linked across the 263 boards' technology slices measured in 2026-09 were plain digits), so this only matters to `linksource`-shaped paths.
- **The unfiltered listing renders the CATEGORY MENU and no postings**, ~27-38 KB. `?all=1` is the site's own "All Vacancies" link and is what lists a whole board — the URL the crawl reads (measured 2026-10-20: 8-130 postings, 32-112 KB, 0.9-1.6 s on three live boards). No listing paginates in any form. `AppliTrackLayoutMode=condensed` is what keeps a response to its rows: the detailed layout inlines every posting's BODY (737 KB for 14 postings on one board), and an unrecognised layout value is not rejected — it silently serves the detailed one, so a typo there buys every body rather than failing.
- **There is no feed and no second listing endpoint.** `rss.asp`, `rss.xml`, `feed.asp` and `JobPostings.asp` all 404 both under and beside `/onlineapp/jobpostings/`, and `/onlineapp/default.aspx` — the other path a posting URL suggests — is the applicant sign-in portal, carrying no posting link at all. `Output.asp` is the whole API.
- **The count the listing states above its rows counts ROWS, not postings.** A statewide consortium lists one requisition once per participating district and every one of those rows carries the SAME `AppliTrackJobId` — Alaska's pool states 1,229 and links 870 distinct ids. An earlier revision of this adapter used the stated count as a truncation guard, failing a board that read fewer postings than the page claimed; measured against the whole fleet that would have failed 14 boards — the largest ones — on every run forever. The walk collapses the repeats, because they are one requisition with one posting page behind them; it is the number that is not what it looks like.
- **The pages declare no character set anywhere and are served as windows-1252**, so the body goes through `charset.NewReader` before it is parsed. Most are pure ASCII; the ones that are not are text pasted in from a word processor, so it is exactly the smart quotes and dashes that would otherwise arrive as U+FFFD.
- **An id the board no longer carries is answered 200 with an EMPTY posting list, not a 404**, so the posting block is selected by the id that was ASKED for (`p<id>_`): a response about anything else simply has no such node. A tenant that does not exist does 404; a few answer 500 on every path, which is a retired tenant rather than a transient failure.
- **The tenant path segment is case-insensitive** (`Saskatoon`, `SASKATOON` and `saskatoon` all serve the same board), so the board file's ordinary case folding is the whole of what `boardIdentity` would have added — there is no second FORM of the id.
- **A posting's `Location` is the SITE inside the district, never a town** ("Central Maintenance and Operations", "Various Locations", "Petersburg High School"). **The board's STATE is in every page's footer**: a `<noscript>` link to the platform's sister board K12JobSpot, "You can also view <a href='…/illinois-teaching-jobs'>Illinois teaching jobs</a>", rendered from the tenant's own state setting (a Canadian tenant's reads `Canad- Saskatchewan`). The adapter reads it from the listing, appends it to the site ("Central Office, Illinois") and sets its country as the structured `Countries` through `location.StateCountry`, where "Georgia" is the state. A value no dictionary knows places nothing (one tenant's renders as `Californicredential or`). An earlier revision held that no page named any geography, passed the site alone, and ~96% of the open postings had no country (2026-10-29); in a sample of 80 live boards every footer named a state, 79 resolvable. The site still goes through the location dictionary, on purpose: some districts do write a town there ("Lincoln School, Palatine, IL", "Administration Center - Allentown, PA"), and a site that is not a place states no city since the dictionary learned to tell the two apart ("Central Office" used to be Central, Louisiana — see "A site is not a town" in [internal/dict/location/AGENTS.md](../../../dict/location/AGENTS.md)). A stored posting gains the state only when its row is rewritten: `INGEST_REFETCH_ALL=1`, one detail request per open posting.
- **A board is sometimes a CONSORTIUM, not a district** ("Wayne County Schools Employment Network", "Suburban Cook County Online Application Consortium") — one applicant pool shared by many districts. That is the tenant the platform sells, so it is the board, and its postings file under the consortium's name. Separately, a name can be carried by two committed boards, because two districts in different states are genuinely called the same thing (two "Washington County School District", in Utah and in Georgia); that is company identity's problem, not the adapter's, and renaming either one would be inventing a fact the platform does not state.
- **Roughly one posting in a hundred has no body at all** — the employer attached a PDF instead of typing one (1 of 116 on one board, 1 of 65 on another). Such a posting is dropped rather than stored body-less, on the asymmetry gusto and seek argue: a stored row is `seen` and so is never hydrated again once it ages past `pipeline.HydrationRetryWindow`, while a dropped one costs one detail request a crawl and can still arrive.
- **Steady state is cheap**: one listing request per board, and a detail request only for a posting the catalogue has not seen.
- **No rate limiting observed**: the harvest ran 3,410 requests at 6-way concurrency over 2,905 candidates, an earlier whole-board harvest 5,521 more, and the smoke crawl hydrated every posting at the adapter's 8-way detail fan-out — all answered, none refused. So no pacer is wired; `pacer.go` is where one would go.
