**Njoyn traps** (`njoyn`; live-verified 2026-11-17 on CGI's site from a residential IP; from the crawl host it is walled, see below):

- **A board is `<tenant>/<site>/<clid>`, lower-cased.** Every page of a site is one classic-ASP script, `<tenant>.njoyn.com/<site>/xweb/xweb.asp`, and only its query says which: `clid` (the client), `Page=joblisting` or `Page=JobDetails&Jobid=<id>&BRID=<n>`. The `<site>` segment is the tenant's (CGI's is `CORP`, written either case) and the script 404s under any other, so the tenant alone is not a board. Query keys come in either case (`clid`/`CLID`, `Page`/`page`). No `atsboard` row yet: no existing mode reads a subdomain, a path segment and a parameter together.
- **The listing is 50 rows a page, paged with `&pn=N`, and its pager states pages, not postings** ("Page 1 of 61"). The walk reads to the page the pager names as last and fails otherwise, which is what earns `fullBoardListing`. Each row (`.table-result-search`) carries the id, title, category, city and country, and the row's attributes carry `RemoteWork` and `CountryIDs`; a city of `N/A` is no city. CGI's whole board was 3,035 postings across 61 pages (456 in Canada).
- **The posting page's JobPosting ld+json holds only the posting's first section.** `datePosted`, `validThrough`, `employmentType` and a structured address are complete (the country code is padded, `"CA "`), but `description` is the "Position Description" paragraph alone. The whole posting is the page's `.job-posting-content`. A removed posting's id still answers 200, with no JobPosting and the notice "This posting has now closed."; the listing is authoritative for which postings exist, so a page that can't be read only defers a new posting.
- **The site refuses a client it decides is crawling too fast, with a bare 200 body on every page:** `Invalid request XWP10022 <client IP>`. About 90 requests in half an hour, the last 61 at roughly one every three seconds, drew it for a residential IP, and it was still in force minutes later. It is a refusal, never an empty or gone board (`errNjoynRefused`). The adapter paces one request every 5 s per board, reads posting pages one at a time, and asks for no further page once refused — every one would be refused too, and asking keeps the refusal in force; what it read before the refusal is kept, and a refusal before any read fails the crawl. The limit itself is unmeasured. Hydrating: steady state is one listing request per 50 postings plus a page per new posting, at most `njoynMaxNewPerBoard` (500, ~42 minutes) a run, newest id first — ids read `J<MMYY>-<sequence>` and the listing is not in date order. CGI's ~3,000-posting cold start therefore converges over six runs instead of one four-hour run past its deadline.
- **There is no `robots.txt`** (the host answers IIS's 404 page).
- **A datacenter IP is walled before it is served anything, so the crawl egresses through the proxy (`proxiedProviders`).** Measured 2026-11-17 from host-2 (89.167.94.146), with a handful of single requests: the first listing request already answered `302` to `validate.perfdrive.com` (Radware Bot Manager, `Server: rdwr`), whose page is a 200 titled `Radware Block Page` carrying an hCaptcha. That is a wall on IP reputation, not the rate limit above, and the adapter reads it as the same refusal. Not yet verified through the proxy: the first proxied crawl is that check, and a run that fails with `errNjoynRefused` on its first listing page means the proxy is walled too.
- **`clients.njoyn.com` serves EVERY client by clid**: `clients.njoyn.com/corp/xweb/xweb.asp?clid=21001` lists CGI's 3,029 postings exactly as `cgi.njoyn.com` does. So a board's identity is its clid (`boardIdentity` folds `<tenant>/<site>/<clid>` to it), and a `clients/…` board is refused (`validateBoard`). On 2026-11-18 LinkedIn's employer discovery added `clients/corp/21001` beside `cgi/corp/21001`: both crawled the same listing, stored 36 postings twice and doubled the request rate into the refusal. It was retired, and a link on the generic host now folds into the client's board (`boardcatalog`'s dedupe and `Entry`, `/jobs/find`'s fallback) or is refused when there is none.
- **The fixed proxy exit is not enough; production crawls through the Scrapling tier (`scraplingProviders`, HTTP + proxy).** The first proxied run (2026-11-18 06:49) read the whole listing but was refused after ~37 posting pages — two boards (`cgi` and the `clients` duplicate) were crawling at once — and the fixed exit (one IP) still answered `XWP10022` to its very first request three hours later. Measured from host2 at 09:4x: plain curl through the fixed exit `XWP10022`; Scrapling `http` + proxy (the rotating gateway) 200 with the listing (`Page 1 of 61`) and 200 with a posting page; Scrapling `browser` + proxy answered nothing, and is not needed — the site serves plain HTML. The 5 s pace stays.
- **Through the rotating gateway a listing page is now and then served without its results table**, on a different page each time (measured 2026-11-20..22: pages 1, 8, 13 and 55, about every second run). The walk requires the whole listing (`fullBoardListing`), so one such page failed the whole run — `ingested=0` and a cooldown — while the same page read fine when asked again. `njoynListingAttempts` asks such a page again, up to `njoynListingMaxAttempts` (3) times, each from a new address; the site's refusal is not retried.
- **Njoyn sites come in (at least) two templates**, and the adapter reads both. CGI's lists postings in `.table-result-search` with columns Id, Title, Category, City, Country and puts a posting in `.job-posting-content`. Société de transport de Laval's (`lavaltransit/cl2/60406`, added by LinkedIn's employer discovery on 2026-11-20) lists them in `#searchtable` with Title, Category, Job Type, City — no id and no country column — redirects the listing to a `tbtoken` session URL, and puts a posting (with a Job Number/Title/Type header) in `#njnContentContainer`. Columns are therefore read by their header labels, the identity always comes from the row's link (`Jobid`, `BRID`), and a template without a Title column would fall back to the link text. Laval's ld+json carries raw control characters, which `ldJobPosting` already strips. Until this, the Laval board failed every run on `no results table`.
