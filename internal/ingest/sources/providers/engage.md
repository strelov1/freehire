**engage traps** (`engage`; live-verified 2026-10-25 from a residential IP, fsn and host2):

- **A board is an OCCUPATION CATEGORY, not a tenant.** engage (en-gage.net, エン・ジャパン's free ATS) gives every tenant a careers page at `en-gage.net/<slug>/`, but that page caps each employment type at 100 postings and paginates nothing, and reaching a tenant needs its slug. The cross-tenant search the site's own UI runs on, `GET /user/api/search/result_work_list/?job=<code>`, reaches every tenant at once: `400000` (IT) held 17,152 postings, `350000` (creative/web) 11,045, out of ~741k across all categories. Top codes are six digits in steps of 50,000 (100000-650000), with middle codes under them (`401000` IT development 7,156, `401500` 614, `402000` 706, `402500` 3,590, `403000` 1,311, `403500` 567, `404000` 154, `404500` 366, `405000` 575, `405500` IT support 1,242, `409000` 1,179 — together the 17k of `400000`). **An unknown code is not an error: it is ignored and the WHOLE catalogue (~741k) answers** — measured on `405515`, `405520` and friends, which are not codes while `405510` is. Every engage row carries `occupation_detail_category`, so a first page with a posting outside the board's prefix (`401000` -> `4010`) fails the board.
- **The search pages at most 10,000 rows.** Past row 10,000 `hasMorePages` turns false whatever `totalCount` says (`400000` stopped at page 167 of 286). A board whose first page reports more than that fails rather than crawling a slice: **the boards are the MIDDLE codes, never `400000` itself.**
- **The backend nodes disagree on order.** Two requests for the same page land on different nodes behind an AWS load balancer and answer different rows (page 2 shared nothing between two calls), so a cookie-less walk is a random sample with ~30% repeats. With the `AWSALB` sticky cookie every page answers the same rows on repeat, so the adapter runs over a cookie client (`cookieSessionSource`). Rows still repeat within one sticky walk (the syndicated rows fill whole pages and the engage rows around them recur), which the adapter dedups by id; a sticky walk of `405500` found 510 distinct postings, the same as the walk of its one detail code `405510` (508).
- **Paging is a stitch, not an offset.** Page 1 needs `f_t=0`; every later page needs `p_t` set to the `totalCount` the previous page reported — without it the search answers `result: success` with no rows, which reads as the end. A page answering `result: error` is a failed page. 60 rows a page; the end is `paginator.hasMorePages: false` or an empty page.
- **A row is the whole posting.** `work_contents`, `qualification`, `recruitment_bg`, `office_hours`, `holiday`, `treatment` and the salary text were compared with the posting page's JSON-LD and are not truncated, so the crawl makes no detail requests. The posting page is `en-gage.net/<company_url_root_dir>/work_<work_id>/`.
- **Two row shapes, and one is not ours.** Rows disagree on scalar types (`work_id` a number in one shape, a string in the other; booleans as `"True"`), so every scalar is read tolerantly. About 6% of rows are syndicated from another job site (`is_kb_work`): a hex `work_id`, no tenant slug, a click-tracking URL off-site. They are skipped.
- **The company is the REGISTERED name, width-normalized.** `company_name` often carries the hiring office (`ポールトゥウィン株式会社　仙台センター`, `パーソルテンプスタッフ株式会社／東海`); `official_corporate_name` does not, but is sometimes typed in full-width letters (`株式会社Ｗｉｄｓｌｅｙ`), so it goes through NFKC. The title is `official_occupation_name` (`システムエンジニア`), not the catch line in `occupation_name`.
- **Salary.** `salary_amount_from`/`_to` are annual yen for 月給 (the monthly figures sit in `_monthly` fields), 年俸 and 年収, and the wage itself for 時給 and 日給. A 0 ceiling is open-ended.
- **Places.** `address_1` is prefecture and city in Japanese, which the location dictionary does not read, so the country is set as Japan. A fully remote posting has `full_remote_office_address` set (its `address_1` reads `フルリモート（完全在宅）`) and is `remote`; `foreign_address` marks an overseas posting and sets no country.
- **Employment.** `正社員` and `正社員（無期雇用派遣）` (permanent dispatch) are full-time, `契約社員` contract, `アルバイト・パート` part-time; `派遣社員`, `業務委託（フリーランス）` and `新卒` are left to the pipeline.
- **The search rate-limits per IP, and answers 403.** The first prod run walked eleven boards at once at one page a second (~110 pages in 80 s) and six of them were refused with 403 within four seconds of each other, keeping ~30% of their postings; minutes later the same host was served 200 again. Every request of a run shares one limiter at one page per 3.5 s (under 100 in five minutes). A 403 on a later page ends that board's walk with what was read.
- **Creative/web (`350000`, 11,045) is past the window too**, so its middle codes are the boards: `351000` (web/UI design, 2,098), `351500` (game testing and production, 2,896), `352000` (video/audio, 1,654), `352500` (920), `353000` (fashion and others, 1,924), `353500` (400), `354000` (print/writing, 377), `359000` (861). No tech hint: they are not IT, and the title dictionary decides.
- **Tech hint on every `40xxxx` code.** `350000` mixes UI engineers with video and print staff.
- **Not `fullBoardListing`.** A later page failing ends the walk with what was read.
