**JobStreet / JobsDB traps** (live-verified 2026-09-12):

- **It is the SEEK frontend protocol on different market hosts.** `sg.jobstreet.com`, `my.jobstreet.com`, `id.jobstreet.com`, `ph.jobstreet.com`, `hk.jobsdb.com` and `th.jobsdb.com` all serve the same `/api/jobsearch/v5/search` schema and `POST /graphql` `jobDetails` operation as SEEK AU/NZ. Keep one implementation: `NewSeek` and `NewJobStreet` differ only in provider identity, market map and paging policy.
- **The market tuple is load-bearing.** SG = `SG-Main` + `Singapore`, MY = `MY-Main` + `Malaysia`, ID = `ID-Main` + `Indonesia`, PH = `PH-Main` + `Philippines`, HK = `HK-Main` + `Hong Kong`, TH = `TH-Main` + `Thailand`. Do not mechanically prepend `All`: `where=All Singapore` returned zero while `where=Singapore` returned the live catalogue.
- **The ICT taxonomy is shared with SEEK.** Classification `6281` is Information & Communication Technology and all 22 subclassifications `6282..6303` were live in each of SG/MY/ID/PH/HK/TH on 2026-09-12. Those subclassifications are the board slices; a keyword search is not a substitute — `software` alone returned ~10k SG jobs and would destroy deterministic coverage.
- **JobStreet does NOT share SEEK AU/NZ's ~550-result window.** SG subclassification `6290` (Engineering - Software) returned 100 rows through page 16, 98 on page 17 and a natural empty page 18 (~1.7k rows). The same natural-end behaviour was rechecked while adding PH/TH: PH `6287` returned 49 rows on page 14 then empty page 15; TH `6290` returned 19 rows on page 5 then empty page 6. The JobStreet walk therefore has a generous 100-page safety cap and FAILS if it reaches that cap without a natural end; accepting the cap as success would silently throw away inventory. SEEK keeps its historical six-page capped-window behaviour.
- **One GraphQL budget for the whole network.** The registry constructs one `seekDetailNetwork` (`seekdetail.go`, over one `pacedSeekPoster`) and passes it to both providers; `ApplyProxyEgress` rebuilds both over ONE replacement network (`seekNetworkProviders`). Building it twice would create two independent token buckets, double the per-IP rate production measured as safe, and let one provider keep hammering a network the other has seen banned. Search GETs remain unpaced; only detail POSTs go through the network.
- **SEEK's rate limit is a 200, not a 429 — and it is a cumulative budget the ~2 req/s pace does not stay under.** On 2026-10-15, 110 new JobStreet boards (MY/ID/PH/HK/TH) went live; the first run hydrated ~4.3k bodies at the shared ~2 req/s for 50 minutes, and then SEEK banned the prod IP on `jobDetails` across the WHOLE network (`www.seek.com.au`, `sg.jobstreet.com`, `th.jobsdb.com` alike) while a trivial `query{__typename}` still answered. The refusal is HTTP **200** carrying `{"errors":[{"message":"Too many requests.","path":["jobDetails","job"],"extensions":{"code":"RATE_LIMITED"}}],"data":{"jobDetails":null}}`. The adapter read that as "no content", deferred the posting and carried on: the next two runs each sent **~8k refused requests for 50 minutes** (the run timeout), stored **0** new postings, logged one line per posting, and very likely kept the ban alive. The same request through `SOURCES_PROXY_URL` was served in full. So the network now reads `errors[].extensions.code == "RATE_LIMITED"` (and an HTTP 429) as a refusal and acts on it once for the whole run: the first refusal on the direct IP moves every later detail request to a proxy lane with its OWN pacer (`seekProxyDetailInterval`, ~1 req/s — the proxy is one static address the `proxiedProviders` share); a refusal there too, or a refusal with no proxy configured, stops hydration for the rest of the run. A run also spends at most `seekDetailRunBudget` (1,500) detail requests across both lanes — about a third of the low end of the 4k–7k the ban arrived after — so a bootstrap accretes over several 2-hourly runs instead of sustaining 50 minutes of traffic. Every posting left without a body is deferred, never stored body-less, and the switch and the stop are each ONE log line with the per-lane counts. The state is per process (one provider per `cmd/ingest` run), so each run re-probes the direct IP and the budget bounds what that costs.
- **Apply aggregator coverage before detail hydration.** JobStreet/JobsDB listings already carry the employer name, so the adapter implements `CoverageGated`: employers that freehire already covers through a first-party ATS are emitted list-only and spend no GraphQL detail request. The ordinary pipeline gate still makes and counts the discard decision. This is important on a first JobStreet crawl, where a large share of the raw catalogue is already direct-ATS covered and the shared GraphQL budget is only ~2 req/s.
- **JobStreet reaches a natural listing end and states an exact total, so it earns `fullBoardListing` and closes per board on the default window.** At pageSize 100 the search's `totalCount` equals the distinct postings a full walk reads (2026-10-29: SG 6290 1,629/1,629, SG 6302 9/9, MY 6287 641/641, ID 6287 686/686, HK 6281 3,694/3,694), so the walk (`verifyTotal`) fails on a later page's error, on the 100-page ceiling, and on a distinct count that differs from the last page's total — after walking the board once more, since a posting listed or withdrawn mid-walk shifts later pages by one. SEEK AU/NZ keeps its 14-day grace and carries `sliceBoardListing` instead (see the SEEK slice-close trap below); the two are separate types (`seek`, `jobStreet`) over one `seekCrawler`, because a marker is a method set. Until 2026-10-29 jobstreet carried a `sweepGrace` equal to the default, which barred it from the board scope just as a wider one would.
- **A JobStreet board id is a board in every market, and the board scope narrows it by host.** Subclass `6290` exists in all six markets and `external_id` (`<board>:<id>`) carries none, so the board-scoped close refused every jobstreet board as region-ambiguous and only the company scope remained — a company that left the feed stranded its rows (2,794 open jobstreet rows unseen past 48h on 2026-10-29, 805 past 14 days, almost all SG). `jobStreet` implements `sources.RegionScopedBoards`: `BoardURLPrefix(region)` is the market host plus `/job/`, the exact prefix `toJob` builds every posting URL from, and `cmd/ingest` adds it as a url predicate to `CloseUnseenJobsForBoards`, one statement per region. Posting ids never repeat across markets and every stored row's host matches its market (measured), and `countries` is NOT a substitute — 15 `sg.jobstreet.com` rows carry `{ph}`. A rekey of `external_id` was the alternative and was rejected: it changes the dedup key of ~25k rows for no information the url does not already hold.
- **The shared GraphQL budget was live-checked against all six markets before rollout, not just the two the contribution's own smoke test covered (SG, PH, TH).** On 2026-09-15 the search endpoint answered 200 with a full page of postings on all six hosts for ICT subclassification `6282`, and the `jobDetails` GraphQL operation was additionally verified end-to-end (real posting id in, non-empty `content` back) on MY, ID and HK — the three markets the original review had not exercised through detail. Requests were spaced at roughly the adapter's own `seekDetailInterval` (~2 req/s); none were refused. This does not replace watching the first real crawl, since a bootstrap run sustains that rate far longer than a handful of manual probes, but it rules out an immediate per-market block before the 132 board rows go live.

**SEEK traps** (all verified live on 2026-08-16, AU and NZ):

- **The bot protection guards the pages, not the API.** A plain request to a SEEK search page or to a `/job/<id>` page answers **403** behind a Cloudflare interstitial ("Just a moment..."), and browser-shaped headers do not clear it. `GET /api/jobsearch/v5/search` — the site's own frontend endpoint — is not gated at all: it answers 200 JSON with no cookie, no credential and no browser-shaped User-Agent (confirmed with no UA, `curl/8.7.1`, `Go-http-client/2.0` and the project's own `freehire/0.1`). Descriptions come from `POST /graphql`, operation `jobDetails`, on the same terms. The consequence for the lifecycle: SEEK postings **cannot be liveness-probed**, because that path fetches the gated job page — which is why the adapter leans on `sweepGrace` instead.
- **SEEK closes per finished slice on its 14-day window alone (`sliceBoardListing`), as WhatJobs does.** Before this a SEEK posting closed only through the company-scope sweep, so one whose company fell out of the capped search pages stayed open for weeks and nothing could probe it. A slice that finished and qualified now closes its own postings unseen for 14 days; a failed, interrupted or mostly-unreadable slice qualifies for nothing. No truncation signal, age backstop or probe was added, deliberately: the unreachable tail of a busy slice (past ~550, the largest measured ~746) cannot be told from a removal, and the window absorbs it because a posting leaves it near the end of its 30-day run for slices up to ~1,000. The AU and NZ markets share subclassification ids and `external_id` carries no market, so `seekCrawler.BoardURLPrefix` (`host + "/job/"`, shared with JobStreet) scopes each close to one market; without it the sweep refuses every shared board.
- **`totalCount` is a function of `pageSize`.** The same query answered **36** at `pageSize=1`, **688** at `pageSize=20`, 680 at 50 and 666 at 100. It can neither drive pagination nor detect truncation, so the adapter's response struct does not even declare the field and the walk stops on the repo's usual `added == 0`. This is the same class of bug as WhatJobs' `limit=1` below — a listing's self-reported total is not evidence.
- **The result window ends near 550.** `pageSize=100` serves pages 1–5 and answers page 6 empty; `pageSize=50` serves through page 11 (offset 550) and page 12 empty. `pageSize` above 100 returns nothing. A slice larger than the window has a tail no crawl can reach — five of Australia's 22 ICT subclassifications, the largest at ~746 postings.
- **`where` is load-bearing and omitting it does NOT mean "everywhere".** Dropping it collapsed a 688-posting slice to 36. It travels with the market's host and `siteKey` as one unit.
- **`www.seek.com.au` now 308-redirects its HTML routes to `au.seek.com`**, and the older `chalice-search` API paths are gone. `api/jobsearch/v5/search` is the live one, and it answers on the `www.seek.com.au` host without a redirect.
- **`companyName` is empty on roughly one posting in thirty**, where `advertiser.description` carries the name the employer typed — including SEEK's **`"Private Advertiser"`** placeholder, which is not a company. Such a posting is dropped rather than filed under a placeholder that would otherwise collect anonymous postings from both markets.
- **`salaryLabel` is free text, and about a tenth of the postings that fill it use it for marketing copy** ("Strong remuneration", "Optional 9 day fortnight | Career Growth") rather than a salary. It is folded into the description verbatim; it never populates the structured salary fields.
- **A third party's query parameter is a claim, and apploi's stopped being true without saying so.** `?employer=<id>` is how that API is meant to scope a board. Measured 2026-09-15 it scoped nothing: a real id, a nonsense id and no parameter at all returned byte-identical pages — the whole global catalogue. The adapter believed it, so each of **5,833 boards stored that catalogue under its OWN company**: 1,565,701 rows standing for 3,024 real postings, **99.81% duplicates**, every posting filed under 3,898 different employers. Unrepairable, because the true employer was never written to any column, and the provider was retired whole.

  **The adapter is now GONE, and the reason is yield rather than the bug.** The bug was in fact fixable: the API hands each posting its own `brand_name`, so a boardless adapter crawling the one global catalogue once would attribute everything correctly, with no duplicates and no board list — the original defect was `firstNonEmpty(e.Company, j.BrandName)` preferring the board's claim over the posting's own answer. Measured 2026-09-18, that is not worth building. The catalogue runs to roughly 100 000 open postings and every one of them is healthcare: of 9 529 titles sampled across the whole offset range, `classify.IsTech` accepted **2**, and reading them by hand found no IT job at all — nursing homes, ABA therapy, caregivers, dietary cooks. Worse, **61% DO resolve a category** (healthcare, hospitality, personal services), and a resolved category alone admits a posting to the index (`search.CategoryUnresolved` returns false the moment `category` is non-empty), so a working adapter would add on the order of 60 000 nursing postings to an IT catalogue and approximately zero engineering ones. **If apploi is ever reconsidered, re-run the YIELD measurement first** — attribution is the solved half and is not what makes this a bad trade. The deleted code (including a `proveEmployerFilter` guard that made the API demonstrate its own filter before any board was trusted) is in git history; what killed the provider is in this paragraph.

  One thing that measurement paid for on its way out: apploi's healthcare titles were the corpus that exposed the bare `mobile` category alias reading "mobile" as travelling work — 18 483 open postings across the whole catalogue, unrelated to apploi. A foreign source's corpus is a mutation test of our own dictionary even when the source itself is worthless. See `internal/dict/classify`'s `TestParse_MobileIsAPlatformNotAnErrand`.
- **The GraphQL detail endpoint meters by a per-IP request BUDGET, and the first prod run walked straight into it.** Unpaced, one crawl fired **3,267 detail POSTs in 95 seconds** (43 boards, each detail pool bursting to `defaultDetailWorkers`) and was answered **429** on essentially all of them — while a single identical request from the same host returned **200 after two minutes idle**. An immediate refusal that clears on idle is a window, not saturation, so the fix is a rate limiter (`seekDetailInterval`, ~2 req/s shared across every board) and NOT the in-flight cap `trudvsem`/`emagine` use: eight fast requests a second from one worker is still eight a second. The listing was never refused, so only the detail path is paced.
- **seek and ukgready are the hydrating adapters that DROP a posting whose detail failed** instead of ingesting it list-only. Most others keep it, and that rule is right where its premise holds — a detail failure is rare, so keeping the posting beats losing it. SEEK breaks the premise twice over: refusals arrive in bursts of thousands, and the retry that normally absorbs a failure is bounded — a stored row with no body is re-offered for hydration only while it is younger than `pipeline.HydrationRetryWindow` (14 days), after which `seen` reports it like any other row (the same trap `pacer.go`'s emagine note calls out). A backlog of thousands does not clear inside that window. A DROPPED posting stays new with no deadline at all, which is why seek does not rely on the window. The first prod crawl stranded **2,593 of 2,982 postings (87%) with no description**, none of which any later crawl could repair; they had to be pruned. Deferring a posting by one crawl is recoverable, storing it body-less is not — that asymmetry, not a preference, is why seek differs. **ukgready breaks the premise differently and worse**: the fallback it would store is not an empty body but the listing's 250-character preview, which is a description as far as `pipeline.HydrationRetryWindow` is concerned, so nothing ever re-offers it — the stub is permanent from the first crawl, not after 14 days. Dropping keeps the posting unseen and the next crawl retries it.
