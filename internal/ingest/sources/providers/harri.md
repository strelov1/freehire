**Harri traps** (`harri`; live-verified 2026-10-20 from a residential IP):

- **The board is a brand's career-page slug (`harri.com/<slug>`), and the data is the keyless JSON API on `gateway.harri.com`** the single-page site calls: `GET /core/api/v1/profile/slug/<slug>` names the brand id, `POST /core/api/v1/harri_search/search_jobs` with `{"brand_level_ids":[id],"start","size",...}` lists, and `GET /core-reader/api/v1/profile/job/<id>` carries the HTML body. The slug lookup is case-insensitive; an unknown slug answers **HTTP 400** ("Slug not found"), read as `ErrBoardGone`.
- **A brand is a tree.** A group's id lists every posting of every brand under it, and those brands are STORES (Jollibee North America: 198 postings under 120 brands such as "JB Mira Mesa"). So the employer is the catalogue company, never the posting's brand — but the posting URL carries the store's slug, which is why an apply link can name a slug (`Taco-Social`) other than the career page that listed it (`bicos`). Two catalogued slugs of one tree would list the same posting twice under two board-namespaced ids.
- **`start` pages the search; `from`, `offset` and `page` are silently ignored** and answer page one again. `hits` is exact (Panera: 183, read back as 183 distinct), so the walk earns `fullBoardListing` by requiring distinct ids == hits.
- **The detail answers for expired postings too** (`status: EXPIRED`), so anything not `PUBLISHED` is gone. Hydrating: a seen posting costs no detail request.
- **`Timing` holds both schedule and arrangement**: `FULL_TIME`/`PART_TIME` beside `FULLY_REMOTE`/`HYBRID_REMOTE`. Most postings carry both schedules, which states nothing, so an employment type is taken only from a lone one. `country_code` is "UK" for Britain, normalised through the location dictionary.
- **Compensation is not mapped**: "Up to" postings carry the ceiling in `compensation_from`, and the currency lives only in the detail's brand settings, null on some brands.
- **No metering met**: 100 detail requests at 8 in flight (~23 req/s) all answered 200. Paced at 5 req/s anyway (`harriRequestInterval`), since a group's bootstrap is one detail per posting (KFC's brand lists 953). An hourly frontline segment — expect near-zero technical yield.
