**foundit traps** (`foundit`; live-verified 2026-11-17 from a residential IP through the Scrapling tier, and the search page from the prod crawl host):

- **robots.txt disallows `/middleware/`, which is the JSON API the site's own web app calls** (`/middleware/jobsearch`, `/middleware/jobdetail/<id>`; both also answer HTTP 400 without a foundit `Referer`). An earlier version of this adapter used it and sliced the catalogue by 21 keyword queries; it was replaced because the API is off limits. Nothing under `/job/`, `/xmlsitemap/` or `/srp/` is disallowed, and the `Sitemap:` lines name the index and `todays-jobs-sitemap.xml`. The `/srp/results` page is a client-rendered shell (250 KB, no data), so it is no listing.
- **The sitemaps are the whole catalogue, enumerated without a cap.** `xmlsitemap/sitemap-index.xml` names ~60 files; nine of them, `active-jobs-sitemap0..8.xml.gz` (~25,000 URLs each, ids ascending), list the active postings: 207,596 distinct on 2026-11-17, ids 1.2M-69.82M. `todays-jobs-sitemap.xml` adds the 3,634 newest (ids 69.818M-69.831M) that the active files, generated on the 15th, did not yet hold; none of the 3,634 was in them. The union is 211,230 postings, matching the 209,690 the search reported before. The other files are search landing pages (by location, skill, industry, freshers) and carry no posting. The files are `.gz` served as bytes, so the adapter reads them as a stream and `decodeSitemapBody` inflates to EOF.
- **Every file named is required.** The listing is the whole catalogue or an error: any file failing, an index naming no active file, or a list with no posting fails the crawl, so a short list never reads as a shrunken catalogue. A full listing took 13 s (11 files, paced at one a second).
- **Not `fullBoardListing`, and a 7-day sweep grace.** The active files are regenerated every few days, and a posting can leave `todays-jobs-sitemap` before the active files name it, so "not listed this run" is weak evidence. `founditSweepGrace` is seven days; a posting lives ~45 days.
- **The URL names nothing usable.** `/job/<slug>-<id>`: the slug runs title, employer and place together with no separator (`...-infosys-limited-bengaluru-bangalore-69824181`), so the adapter reads only the id and yields a stored posting as a body-less liveness refresh. That also means the coverage gate cannot be asked before a page is bought, so the adapter is not `CoverageGated`.
- **The body is read from the seeker job-details page, not the posting page.** `GET /seeker/job-details?id=<id>` (robots.txt disallows only `/seeker/dashboard` and `/seeker/profile`, so this path is allowed) carries one schema.org JobPosting: `title`, `description` (HTML), `datePosted` (`2026-11-16`), `employmentType` (`FULL_TIME`), `hiringOrganization.name`, and a `jobLocation` that is only the country (`India`) or the city the poster gave. Against the `/job/` page's block it has no `baseSalary`, no `skills` and no city/state, and the site strips the substring `script` and drops `&` from its text (`Job De ion`, `Product Data  Change Management`), so a title or body carries those holes. The adapter keeps the sitemap URL (`/job/<slug>-<id>`) as the posting's public URL. A salary is mapped only from `baseSalary` with `unitText` YEAR, which the seeker page never carries. `monthsOfExperience` is not mapped (it read 1 on a "0 - 1 Years" posting). No tech hint is set: the site has no reliable technical signal.
- **Blocker history, and the route that works.** (1) The JSON API (`/middleware/jobsearch`, `/middleware/jobdetail/<id>`) is disallowed by robots.txt and was dropped. (2) The posting pages `/job/<slug>-<id>` answer Akamai's 403 "Access Denied" (630 B) on every path and every route from the prod crawl host (host2): the impersonating fetcher with and without the proxy, and, from a residential IP, a headless browser passed only about one in two (6 of 12, ~9 s each, ~690 KB). (3) Measured 2026-11-18 on host2 through the prod Scrapling service, `http` mode with the proxy: `/seeker/job-details?id=<id>` answered 200 on 12 of 12 ids taken from `todays-jobs-sitemap`, ~217 KB each with a JobPosting carrying the right title and a 795-6,482 character description. The same page also answered 200 at ~0.5 s from a residential IP with no proxy. So the `scraplingProviders` row is `http` + proxy (the search page was measured the same way: 403 without the proxy, 200 with it). A 403/429/5xx is asked again up to twice (2 s, doubling) because the proxy rotates exits and a refusal is one bad exit; a page still refused is deferred, never read as gone, and only 404/410 is.
- **The run is bounded.** One limiter paces every request at one a second, two workers, and a run reads at most `founditMaxNewPerRun` (1,500, ~25 minutes) unseen postings, newest id first; the rest wait for later runs. The site adds ~5,300 postings a day (the 1-day search count), against 18,000 a day at a two-hour cadence, so the ~207k cold backlog drains in about 12 days. A run in which every page failed fails; one page failing does not.
- **96% of rows are syndicated copies** (`jobSource: SCRAPPING`, an employer's own careers site: NTT Data, Infosys, Capgemini, Axis Bank), so much of the catalogue overlaps what we read from the employers' ATS and naukri/shine/hirist; the cross-source duplicate suppression handles the copies. Other markets (foundit.sg/.ae/.my) are not crawled.
