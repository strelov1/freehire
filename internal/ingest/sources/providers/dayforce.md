**Dayforce traps** (all verified live 2026-09-02):

- **The listing POST is CSRF-gated and a refusal looks nothing like one.** `POST /api/geo/<tenant>/jobposting/search` answers **403 with the body `Forbidden`** to any request that does not carry next-auth's double-submit pair — the `__Host-next-auth.csrf-token` cookie AND its token half echoed in an `X-CSRF-TOKEN` header. The 403 arrives with the site's own CSP and `server: cloudflare` headers, so it reads exactly like an edge block, and no amount of browser-shaped headers, referer or cookie jar clears it. `GET /api/auth/csrf` mints the pair (and returns the token in its body) in one request that the whole crawl then shares. Every OTHER route under `/api/geo/` is a GET and is not gated at all, which is why the platform looks open until the one endpoint that lists jobs.
- **The listing carries the WHOLE description, so nothing needs a detail request.** `jobPostings[].jobDescription` is the detail endpoint's `jobPostingContent.jobDescription` with its tags stripped — byte-identical on every posting sampled across four sites, never truncated. What it omits is the `jobDescriptionHeader`/`jobDescriptionFooter` pair, which is per-BOARD boilerplate repeated verbatim on every posting of that board (1,236 identical characters on all of dnata's), so the listing body is the better text as well as the free one. It arrives entity-encoded (`&nbsp;`, `&rsquo;`) as newline-delimited plain text, hence `html.UnescapeString` → `plainTextToHTML`.
- **`cultureCode` selects the SLICE, not the language, and an unconfigured one fails two different ways.** A site publishes each posting only in the cultures it was translated into, so asking `en-US` of a Quebec-only tenant answers zero rather than answering in French. Most sites accept a culture they do not publish in and answer an empty list; some reject it with **400** (`myepay/dmrstandard` answers 400 to `en-US` and 200 to `en-GB`, while `abbeyfield/candidateportal` — also en-GB-only — answers `en-US` with its full 115). The English variants that ARE configured do collapse: `en-GB` and `en-US` return the identical set. `sitecontext`'s `isoCultureCodes` lists what the site is CONFIGURED for, not where its postings are, so it cannot pick the culture for you — only a live search can.
- **Unioning the cultures is not worth it, and would double-store.** One posting keeps the SAME `jobPostingId` in every culture it appears in, so two board entries differing only in culture write it twice under two `external_id` namespaces and then close each other's rows on the company-scoped sweep — which is why `boardIdentity` folds the culture off. Measured over 60 sites, the non-English cultures added 104 postings against 5,765 English ones (~1.8%), most of them translations of postings already in the English set, for roughly 3x the requests.
- **Page size is fixed at 25 and `maxCount` is exact** — the opposite of SEEK's `totalCount`. The request body carries only `paginationStart`; `pageSize`/`take`/`count` alongside it are ignored. Confirmed against a 3,508-posting site: the last page is short and every offset past the end answers an empty list with the same `maxCount`.
- **`hasVirtualLocation` is the structured remote flag**, and such a posting usually carries `postingLocations: null` — no place at all. A posting can be both virtual and sited, so the flag is the only structured signal and a place merely NAMED "Remote" stays with the heuristic.
- **No metering observed**: 400 listing POSTs at 32-way concurrency (~14 req/s) all returned 200, so no pacer is wired and `cmd/harvest-boards` needs no `-pace`.
