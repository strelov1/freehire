**Built In traps** (`builtin`; live-verified 2026-10-15, from a residential IP):

- **Boardless, one host.** Every market host (builtinnyc.com, builtinsf.com, builtinchicago.org, ...) serves the same platform and the same numeric posting ids; builtin.com with `allLocations=true` lists all of them. **`allLocations=true` is load-bearing**: without it the listing is narrowed to the requesting IP's region (from a Brazilian IP the 24-hour window held 17 pages instead of the whole world's).
- **The whole catalogue cannot be walked, so a run reads a window.** Every listing stops at page 1000 (page 1001 of any filter answers "No job results") at ~12-25 cards a page, and engineering alone fills those 1000 pages within a week. A run walks each technical category (`builtinCategories`, the listing's own category filter) restricted to postings updated in the last 24 hours (`daysSinceUpdated=1`, the narrowest option) to its natural end: ~326 pages for engineering, ~60 data-analytics, ~58 ai-machine-learning, ~49 product-management, ~42 cyber-security, ~28 designer by the pagination each first page renders. One live run read 4,001 distinct postings across the six windows in 10 minutes of paced listing requests (~300 pages). A walk that reaches page 1000 is truncated, and `crawlPagedLinks` logs it as such. Never `fullCatalog` or `fullBoardListing`. **Since 2026-10-22 the window spans all 14 top-level families** (`/jobs/<family>`: dev-engineering, data-analytics, cybersecurity-it, product, design-ux, project-management, operations, customer-success, sales, marketing, finance, hr, legal, content), technical ones first since the hydration budget is spent in that order: the catalogue is broader than IT. The first prod run is what measures their daily size. The crawl host's IP was served directly at the 2 s pace (15 of 15), so Built In needs no proxy or Scrapling row.
- **Hence the 30-day `sweepGrace`.** A posting is re-listed only inside its first day and whenever Built In reposts it, so on the 48h default nearly every live posting would close two days after it was seen. Every sampled JobPosting states `validThrough` exactly 30 days after `datePosted`, which is the window used. A posting withdrawn early lingers up to that long; a closed posting's page answers 404, so `cmd/liveness`' `probeDespiteRegisteredGET` could close it on evidence, but every probe spends the same per-IP budget as the crawl and is not wired.
- **`robots.txt` disallows `*?page=` and `/jobs*?search=`.** The bare listing's pagination (`/jobs?page=2`) is therefore off limits, and the adapter never uses it or the keyword search. It walks the category FILTER's pagination, whose links the site itself renders as `?allLocations=true&daysSinceUpdated=1&page=N` — the page parameter last, which the pattern does not match. `/apply/` and `/job/sitemap.xml` (a 404 anyway) are disallowed too; posting pages (`/job/<slug>/<id>`) are not.
- **The employer's ATS link is not public.** The JobPosting carries no apply URL and the page's `applyUrl` is empty for every one of 168 sampled postings: "Apply" opens a name/email form that posts to Built In before redirecting through the disallowed `/apply/`. The stored URL is the Built In posting page, and the dedup pass pairs a copy with the first-party posting.
- **Most of the listing is already crawled first-party, so the adapter is `CoverageGated`.** Of 168 sampled postings (99 employers), 118 (70%) belong to an employer freehire's public search already carries from a first-party ATS (workday 49, greenhouse 32, ashby 10, icims 9, smartrecruiters 5, ...), and 36 more to one it carries only from an aggregator — a lower bound, since the probe read at most 100 postings per employer and the gate's own answer is broader. Their bodies are never bought.
- **Read the CARD, not the posting link.** `div[data-id="job-card"]` holds the employer (`data-id="company-title"`), the title link (`data-id="job-card-title"`, whose `data-builtin-track-job-id` is the external id) and the work-arrangement badge beside the `fa-house-building` icon: `Remote`/`Hybrid`/`In-Office`, plus `Remote or Hybrid`, which states two arrangements and is not mapped. One posting can sit under two categories and is yielded once.
- **The body is the ld+json JobPosting** (the `type` attribute is entity-encoded, `application/ld&#x2B;json`, which the HTML parser decodes). `jobLocation` is one Place or a list (a PwC posting names six offices), countries are alpha-3 (`USA`, `AUS`), and `jobLocationType: TELECOMMUTE` marks a fully remote posting. `applicantLocationRequirements` reads `USA` even on a Melbourne posting and is not read.
- **Salary is structured, with one known data error**: an annual range filed as `HOUR` (a PwC internship states 29250-48000 USD/HOUR, rendered "29K-48K Hourly" on its card). An hourly USD figure above 500 is dropped rather than reinterpreted.
- **Rate limit: a Cloudflare managed challenge (HTTP 429, `cf-mitigated: challenge`).** One request every 0.5s was refused from the 44th request, ~0.85 req/s from the ~140th, after which roughly one in three was served; one every 1.5s (200 requests) and every 3s (100 requests) were never refused. Paced at one request every 2s (`builtinRequestInterval`); the first refused posting page defers the rest of the run's hydration. A run is ~10 minutes of listing plus at most 500 posting pages (`builtinDefaultMaxNewPerRun`, ~17 minutes), under the scheduler's generic 3000s timeout. **Nobody has measured the budget from the crawl host.**
