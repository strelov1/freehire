**startup.jobs traps** (`startupjobs`; verified live 2026-10-14 unless dated otherwise):

- **It is not a startup board.** It re-lists corporate ATS postings (Oracle, ABB, Illumina, McGill University) beside the startups — ~278k postings, ~6.5k created a day. It is therefore an `aggregator` and `CoverageGated`: the postings of an employer freehire already crawls first-party are yielded list-only and cost no posting page, and so are the ones whose title the catalogue filter will reject (`DetailGate.Rejected`, see [pipeline/AGENTS.md](../../pipeline/AGENTS.md)). Both are never stored, so without the gate every run would re-buy their bodies.
- **Three hosts, three budgets, and the design is the budgets.** Pages (`startup.jobs`) sit behind a Cloudflare JS challenge; the sitemap (`cdn.startup.jobs`) and the catalogue (Algolia) do not. Each is read for what only it has: the sitemap for the whole catalogue's identity, Algolia for metadata, the posting page for the body.
- **Only `fingerprintHTTP` passes the challenge.** The homepage and 40 sequential posting pages at ~1 req/s all answered 200 through the Chrome_144 profile. The 2026-09-24 spike found Chrome_133/Chrome_124 refused, Chrome_131/Safari_16_0 served, plain HTTP and headless Chrome refused, and the edge 403-ing an IP after a long run of requests. Every Cloudflare-fronted request is paced through one 1 req/s limiter, and the first 403/429 stops the run's hydration — the refusal is about the IP, and every further request would be refused alike.
- **The Algolia search key allows about 100 queries per IP per HOUR, and that rules out walking the index.** Measured: refused with 429 after ~100 queries, cleared ~an hour after the first. The multi-query endpoint (`/1/indexes/*/queries`) answers several queries in one request but each is counted — 19 batches of five were refused at the 20th. `hitsPerPage` and `length` are both clamped to 100, so the 278k index costs ≥2,786 queries: ~28 hours of quota. A run therefore reads from Algolia only (a) the WINDOW — the postings created in the last six hours (180-340 are created an hour, so 1-2k postings, 11-25 queries) — and (b) a randomly chosen chunk of the never-stored backlog with what the window left, both inside `startupjobsQueryBudget` (80). Reaching the window back to the sitemap instead would have been a literal proof of completeness, and would cost ~90 queries in the hours before 03:00. **The provider must not be crawled more often than every two hours** (the scheduler default), or the runs spend the IP's hour twice over.
- **The key is a SECURED key whose `validUntil` is ~3 hours out**, so it is read from the homepage's `<meta name="current-algolia-…">` tags on every run; a hardcoded key would die the same day. A missing tag fails the run.
- **A query reads at most 500 hits (`paginationLimitedTo`), and `browse` is not allowed with the search key.** Past the 500th hit Algolia answers 400 ("you can only fetch the 500 hits for this query"). The window is read in slices of `created_at_i`, each narrowed until its `nbHits` fits and then read until the distinct hits equal it; a one-second slice holding more than 500 FAILS the run rather than reading the first 500 and calling it complete — the peopleforce lesson, a capped page is not the end.
- **Slice on `created_at_i`, never on `published_at_i`.** `published_at_i` is re-stamped in daily batches at midnight UTC: 3,078 postings carried exactly 2026-10-13T00:00:00Z and 1,004 the next midnight, so no filter can split them under 500. 149 carry `published_at_i = 0`. `created_at_i` is when the row was created and does not move.
- **`nbHits` is an ESTIMATE on a large filtered result** — 241,643 for a `created_at_i>=0` filter matching all 278,516, flagged `exhaustiveNbHits: false`. The walk refuses any count that is not exhaustive; the unfiltered count is exhaustive and is what the sitemap is checked against.
- **The sitemap is the only affordable statement of the whole catalogue.** `robots.txt` names `cdn.startup.jobs/sitemaps/startupjobs/sitemap.xml.gz`; six `posts*.xml.gz` files (~10 MB each, served as plain XML despite the suffix) listed 277,702 posting URLs against the index's 278,516. It is regenerated once a day at 03:00 UTC, and a posting URL ends in the index's `objectID`. Its URLs carry no title or employer, so it serves liveness (a stored posting it lists is refreshed by identity) and completeness — **which is what earns `fullCatalog`**: every stored posting is refreshed by every run until it leaves the site, by the window while it is new and by the sitemap from the next generation on, and the gap between the two stays far inside the sweep's 48 hours while the sitemap is at most 36 hours old. The run fails rather than refresh less: any file or query failing, a sitemap older than that, or a sitemap listing under 95% of the index's pre-window count (a generation that lost a file loses a sixth of the catalogue, and a source-scoped sweep would close that sixth).
- **The backlog is mostly postings already judged and discarded**, which come back every run because they are never stored. Read newest-first it would spend every run on the same freshly-discarded top, so the run reads one chunk at random — not by the clock, because a chunk named by the hour aliases with the two-hour cadence and skips every other chunk.
- **There is no link to the original ATS posting.** Applying goes through the site's own `/apply` (disallowed in `robots.txt`); the JobPosting's `hiringOrganization.sameAs` is the employer's homepage. So the URL stored is the startup.jobs page, and the dedup pass is what pairs a copy with the first-party posting.
- **Neither date means what it says.** The page's `datePosted` carries 2013 dates on live postings and `validThrough` is stamped a month ahead of every crawl (2026-09-24 spike); the index's `published_at` is the midnight re-stamp. `PostedAt` stays nil and nothing reads either for lifecycle.
- **The index's facets are clean and closed.** `workplace_type_id` is `on-site`/`hybrid`/`remote`, `employment_type_id` is four values (`full-time` 256k, `contractor`, `part-time`, `internship`), `country_code` is ISO alpha-2 (empty on ~3%), and salary is whole units with an ISO currency. `salary_interval` was `year` 3,463 / `hour` 450 / `month` 95 / `week` 1 / `biweekly` 1 over 4,010 recent postings; the last two have no freehire period and drop the salary.
- **One end-to-end run against the live site** (2026-10-14, local, real transports, hydration capped at 5): sitemap 277,702 postings, window 1,062, backlog chunk 3,889 found of 4,000 ids asked (111 removed since the sitemap), **54 of 80 Algolia queries**, the whole listing in 7 s; 5 posting pages read. The catalogue filter turned away only 253 of the 4,951 candidates (5%) — `ConfirmedNonTech` is deliberately narrow, so on this source it is the COVERAGE answer that will bound hydration, and that can only be measured against prod's database.
- **The posting page is 128-167 KB and its body is the ld+json `description`** (one JobPosting block per page, Trix HTML). A page that answers without one defers the posting, like any unreadable page — a stored body-less row would never be hydrated again once past `pipeline.HydrationRetryWindow`. Hydration is capped at 1,000 pages a run (~17 minutes at the pace), so a cold start accretes over runs, newest first.
