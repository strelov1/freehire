# Source ingest conventions

## Scope

Source ingest: the provider registry and its adapters, entry validation, the per-board health sidecar, and related job-lifecycle mechanics. The board catalog itself is `internal/ingest/boardcatalog`.

## Provider notes

**Before you change, debug or add an adapter, read its note: `providers/<adapter>.md`**, named after the adapter's file (`profession.go` → [providers/profession.md](providers/profession.md)). A note holds that provider's traps: what was verified live, and why the adapter does what it does. A new provider's traps go in a new note, not in this file.

A few notes cover more than one adapter, and a note can name other adapters too, so `grep -l '`<adapter>`' providers/` finds every note to read:

- [seek](providers/seek.md): SEEK and JobStreet / JobsDB · [pandape](providers/pandape.md): `pandapelatam` · [hirist](providers/hirist.md): iimjobs · [justjoin](providers/justjoin.md): RocketJobs
- [dutch-public-boards](providers/dutch-public-boards.md): `werkenvoornederland`, `gemeentebanen`, `academictransfer`
- [taiwanese-hardware-makers](providers/taiwanese-hardware-makers.md): `mediatek`, `realtek`, `foxconn`, `asus`, `quanta`
- [work-mode-fields](providers/work-mode-fields.md): work-mode and country fields the listing hides, for `teamtailor`, `paylocity`, `workable`, `greenhouse`

## Always true

- **The board catalog lives in Postgres, not in `sources/`** (#2357). `cmd/ingest <provider>` reads the `boards` table through `internal/ingest/boardcatalog`; a board is added with `cmd/add-board --provider=… --board=… --company=… --apply`, which reports by default and writes only under `--apply`. **The argument is a PROVIDER KEY, not a path** — pass a file path and the run reads no boards, logs `providers=0` and exits 0, which looks exactly like an empty catalogue.
- **The `sources/` directory is gone, and so is every board file.** `freehire-ops' provision/host2/gen-ingest-timers.sh` used to generate one systemd timer per `sources/*.yml`; it now enumerates `SELECT provider FROM boards WHERE status IN ('pending','active')`, so a provider is SCHEDULED because it has live boards. Adding a provider is an adapter, a line in `sources.All`, its boards via `cmd/add-board` — and a run of that generator on the host, which nothing deploys for you.
- **`sources.All` maps each `provider` string to a registered adapter** (`Source` interface) over a shared HTTP client. Adding a platform is a new adapter + one line in `sources.All`.
- **Run-once-and-exit worker** meant for cron (one schedule per provider, so providers crawl independently). No long-lived process. **What decides that a provider is due lives in [internal/ingest/ingestsched](../ingestsched/AGENTS.md)** — the `ingest_schedule` / `ingest_run_state` tables and `cmd/ingest-scheduler` — not in a systemd unit file. The unit name is built from the same `boards.provider` string that selects the boards, so a provider cannot be scheduled under a name no adapter answers to; that is what `habr_career` was, crawling nothing for a day behind a timer named after the retired file `habrcareer.yml`.
- **A 429 holds back the whole HOST, not just the request that drew it** (`hostbackoff.go`). `Client.do` records every direct-egress 429 per host and makes every later request to that host wait — the server's `Retry-After` when it names longer, otherwise 1s, doubling to a 60s cap for each refusal that arrives after the previous hold expired (the 429s of one in-flight burst count once, or the first hold would jump straight to the cap), reset by the next 2xx. Honouring `Retry-After` per REQUEST was not enough under eight board workers: the request that drew the refusal waited and the other seven fired straight into it. Measured 2026-10-18 on workable (direct IP + refusal-retry proxy, which returns on the second refusal with no wait at all): once its budget tripped ~30 minutes into a run, the rest of the fleet (~1,500 boards) failed inside three minutes at ~1,000 boards a minute, 18,520 refusals in two days (9,311 board listings, each a recorded board failure, and 9,303 company-description fetches). Held instead, the run slows to what the host admits and the boards it never reaches keep their last state. The hold also stops the client's own retries going out beneath a pacer (the workstream and join notes below). The refusal fallback is a different IP and is not held.
- **Adapters are read-only over public ATS JSON APIs.** Per-board crawl is independent: one failing board is counted (`stats.Failed`) but does not abort the rest.
- **Sources are keyless by default.** The exceptions are `usajobs` (`USAJOBS_API_KEY`), `reed` (`REED_API_KEY`), `arc` (`ARC_SESSION_COOKIE`, the Cookie header of a signed-in browser session — see [providers/arc.md](providers/arc.md)), `francetravail` (`FRANCE_TRAVAIL_CLIENT_ID` + `FRANCE_TRAVAIL_CLIENT_SECRET`, an OAuth2 client pair) and one WhatJobs adapter per market — the vendor issues a separate publisher account per country, so `whatjobsMarkets` in `internal/ingest/sources/whatjobs.go` lists one `{code, provider, country}` row per onboarded market (`whatjobs` for the US, `whatjobs-<code>` for the rest, e.g. `whatjobs-br`), and every account's credential lives in the single `WHATJOBS_PUBLISHER_IDS` variable (`"code:id,code:id,..."`, e.g. `"us:7065,br:7076"`) rather than one env var per market. A market with confirmed but thin inventory (`whatjobs-au`, `whatjobs-sv` etc.) is still onboarded. A thin account whose WHOLE pool fits the page budget (`whatjobs-cr`, `whatjobs-tz` and the rest added 2026-10-19, each under ~2k postings, nearly none of them IT) is crawled through the single board `*`, which sends the empty keyword and keeps every posting — keyword slices find almost nothing there, and the catalogue is broader than IT. A blank board is still refused; `*` exists so that asking for a whole pool is written on purpose rather than reached by a typo. The credential lives in the env, never in the catalog.
- **`All` is the crawl registry, `Taxonomy` is the classification one — the credential gates only the first.** `sources.All(client)` omits a keyed provider whose variable is unset, so its boards fail validation before any request goes out. `sources.Taxonomy()` (`All(nil)`, no transport, never Fetch through it) is **total**: what kind of source a provider is cannot depend on whether this host can crawl it. Everything that classifies rather than crawls — `FilterableProviders`, `ProviderKind` on the status page, `AggregatorProviders` in `cmd/reindex` and `cmd/ghost-crosscheck` — reads `Taxonomy`. Conflating the two silently reclassified `whatjobs`, a reseller of first-party ATS postings, as an ATS on every keyless host, so none of its copies were suppressed.
- **A board is not always a tenant.** For `hh` it is a `professional_role`, for `trudvsem` an OKATO region code, for `whatjobs` a SEARCH KEYWORD, for `edjoin` a JOB-TYPE id. Such a provider is an `aggregator` (many employers, company read per posting) but NOT `boardless` — the board is what selects the slice to crawl. Note that a central searchable index does not by itself make a provider boardless: `edjoin` has exactly one, and the board still earns its keep, because what the slice buys is not reachability but a catalogue the ingest filter cannot police on its own (see [providers/edjoin.md](providers/edjoin.md)).
- **`sweepGrace` overrides the unseen sweep window in either direction.** `whatjobs` reads at most 40 pages of a keyword from a feed thousands of pages deep, so a posting that drifts past that depth reads as unseen; on the 48-hour default it would be closed and reopened repeatedly, each cycle writing a phantom removal into `job_daily_stats`. The adapter declares 14 days instead (`sources.SweepGraceWindows` → `cmd/ingest`'s `sweepWindowFor`). Widening is sound only where liveness cannot be probed — anything verifiable should close on evidence. The opposite case is `gem`: its crawl lists a board's whole posting set every run, so an unseen posting already IS the evidence, and 48h only adds latency — it declares 24h instead, comfortably above its hourly cadence including a missed run or two. Narrowing the SHARED default itself, rather than one provider's override, would falsely close a quarter of workday's and smartrecruiters' live postings to real crawl jitter (measured in `cmd/ingest/coverage.go`).
- **`sliceBoardListing` lets a keyword-sliced provider close per board on its grace window.** A whatjobs board is read only to a page budget, so it can never earn `fullBoardListing`, but its ids are board-namespaced (`<keyword>:<id>`), so a posting a finished keyword board stopped listing is visible per board. With the marker, `cmd/ingest`'s board-scoped close acts on those boards over the 14-day `sweepGrace` instead of leaving them to the company scope, which leaked every posting whose company drifted out of all the slices (5,835 of whatjobs-uk's 5,880 postings unseen past 14 days on 2026-10-28) until `cmd/liveness`'s 45-day age rule. A test holds every member to a `sweepGrace`: on the 48h default the marker would close whatever sat past the budget for two days. The same measurement showed the crawls themselves were healthy — `board_health` timeouts were episodic vendor incidents (305 boards on 2026-10-20, 8 on 10-22, `whatjobs-be` 520s on 10-28), and a whatjobs-uk run finishes its 10 boards in about three minutes.
- **Which page failed decides whether the board failed.** Every paginated listing walk obeys one rule: the FIRST page failing is a board-level error, a LATER page failing ends the walk with the links gathered so far. A partial crawl survives a mid-listing hiccup; a board that cannot be reached at all is reported. The canonical statement is `crawlPagedLinks` in `html.go`, and `added == 0` is what ends a walk that has run out of new links.

  **The exception is the one that matters.** A `fullCatalog` provider is swept by SOURCE, so a silently-truncated walk looks like a shrunken catalogue and would mass-close every posting past the failed page. There the rule inverts: ANY page failing must fail the whole crawl, steering the sweep back to the safe company-scoped close. `crawlAllPagedLinks` is that variant. Both `fullCatalog` providers honour it — `geekjob` through the helper, `habrcareer` in its own JSON loop with the reasoning written at the branch — which is the point: **what must not drift is the rule, not the helper.**

  Eight adapters restate the walk by hand rather than call it (`peopleforce`, `bayt`, `teamtailor`, `neogov`, `hh`, `gusto`, `edjoin`, `workstream`), and that is deliberate, not an oversight: they differ in transport (`GetHTML` / `GetTextWithHeaders` / embedded page state), in what they dedup on (URL, extracted job id, int64 vacancy id), in extra stop conditions (`neogov` reads a `total`, `workstream` reads a `totalPages` and starts from a page already in hand, `teamtailor` retries `/jobs`→root on a 404 and then follows the path it landed on), and in what a page must YIELD (`gusto` and `workstream` need each item's whole listing row — title, location, pay, employment type — not just its link, because that row is everything the platform states about a posting bar its body; `edjoin` needs the same, and additionally stops on an exact `totalRecords`). A generic over those eight would be harder than the fifteen-line loop it replaced. When touching one, check its first-page branch — and note that **`hh` counts from page 0**, so its check is `page == 0`, not `page == 1`.

  Seven of the eight (`neogov`, `edjoin`, `workstream`, `peopleforce`, `gusto`, `teamtailor`, `bayt`) no longer follow the "later page ends the walk with what was gathered" half of the rule above: they earned `fullBoardListing` (below) by turning a later-page failure, and reaching their own page-cap safety ceiling without ever finding the board's proven end (a genuinely empty page, or — for `neogov`/`edjoin`/`workstream` — the source's own declared total/page count), into a hard `Fetch` failure instead. The empty-page proof for all seven is now the RAW per-page item count, read before cross-page dedup — not the count of newly-kept items — because a page whose rows are all already-seen duplicates (a sort tie spanning a page boundary, a re-served page) is not itself proof the board has no more pages beyond it; each has a regression test for exactly that shape. `peopleforce`'s and `bayt`'s `detail()` additionally gained the `unreadableDetail` marker (see the entry below) on a failed-but-not-gone fetch, since neither has a `HydratingSource` fallback and every crawl re-fetches every listed posting's detail — a plain drop there would have defeated the very completeness promise the marker exists to make. `teamtailor`'s own gap was live, not hypothetical: a probe against real prod boards found `ttMaxPages=100` silently truncating a real one — `tantor.teamtailor.com` (2000 open postings in the catalogue) still returned full listing pages at 100 and 101, with its true end only past page 120, a confirmed ~20-25% under-collection on a live board — closed by raising the cap to 1000 (`openspec/changes/teamtailor-listing-cap-fix`). `bayt` was initially excluded from the first wave over a documented throttling risk, but that risk is tied specifically to the CONCURRENT detail fan-out (`baytDetailWorkers`, already narrowed for exactly this reason) — the listing walk itself is sequential, one request at a time, and carries no evidence of the same risk, so excluding it on an unexamined worry stopped being warranted once examined (`openspec/changes/bayt-fullboardlisting-fix`). `hh` was audited alongside these seven and deliberately does NOT earn the marker: hh.ru's own search UI caps a query's reachable depth at ~2000 results independent of a role's true count, confirmed live against a currently-configured board (`hhru.go`'s `crawl` carries the measurement) — treating that cap as a Fetch failure would fail a busy board's crawl on every run, not surface a genuine truncation. `apploi` — then the largest source in the WHOLE registry by real prod volume (~1.47M open postings, larger than `workday`'s own ~1.05M) — was the first of the ~163 previously-unaudited adapters to be checked, found to share the identical defect, and fixed the same way (`openspec/changes/apploi-fullboardlisting-fix`); **that adapter has since been deleted outright** (see the apploi entry below — the volume was 99.81% duplicates and the real catalogue is entirely healthcare), so what follows describes it in the past tense: unlike the eight, its "last page" proof (a page shorter than the requested size) needed no dedup-vs-raw-count correction (it never deduplicated across pages to begin with) and it needed no `unreadableDetail` treatment (descriptions are inline, no per-posting detail fetch exists). The remaining ~162 adapters in the registry are still fully unaudited; ranked by real prod open-job volume, `oracle` (~459K) is next.
- **`sources.fullBoardListing` marks an adapter fit for the post-run sweep's board-scoped close** (`CloseUnseenJobsForBoard`, freehire#2328 — see `docs/agents/job-lifecycle.md`'s mechanism (1a) for why that scope exists). The bar is structural, not documented: `Fetch` must, for every board it crawls, either verify a fetched count against the source's own reported total or paginate to the source's natural end. A page/offset safety cap in the adapter's own code is permitted, but only as a ceiling that FAILS the crawl when reached before the end is proven — never as an alternate, silent way to end the walk as a success; that distinction is what lets `hh`/`neogov`/`edjoin`/`workstream`/`peopleforce`/`gusto`/`teamtailor`/`bayt` all keep a safety cap and still earn the marker, while a cap that could be reached and still report success would not. `habrcareer.go`'s `fullCatalog` `Fetch` (any page error is a hard error, never a partial result) is the model to follow; `solidjobs.go` is the negative one it was written against — it caps a board at the first 500 of a much larger catalogue and reports that as an unqualified success, which is exactly what closed 110 live `solidjobs` postings in #2337's 18-minute production incident before the revert. Self-declaration by code review is not enough to earn the marker, because that is solidjobs' own failure mode: its cap was documented in a comment nobody's code read. `sources.FullBoardListingProviders(reg)` is the registry helper `cmd/ingest` consults; `TestSolidJobsIsNotFullBoardListing` pins the negative control. As of this writing the marker covers a first, impact-ordered wave of large ATS platforms — `workday`, `ukg`, `greenhouse`, `lever`, `ashby`, `workable`, `paylocity`, `careerplug`, `smartrecruiters`, `personio`, `recruitee`, `bamboohr`, `jazzhr`, `icims`, `successfactors`, `jobvite`, `breezy`, `eightfold`, `taleo`, `geekhunter`, `keka`, `gupy` — four of which (`workday`, `careerplug`, `icims`, `taleo`) needed a soft page/depth cap turned into a hard failure before they could earn it — plus a second wave, seven of the hand-rolled walkers named above that shared the identical defect: `neogov`, `edjoin`, `workstream`, `peopleforce`, `gusto`, `teamtailor`, `bayt` — and `apploi`, found and fixed the same way outside that set, as the first of the registry's remaining unaudited adapters to be checked, though that adapter has since been deleted outright and no longer carries the marker or anything else. `hh` was audited alongside the seven and found to still fail the bar, for a structural reason of its own (see above); the rest of the registry is unmarked, not because it fails the bar, but because nobody has audited it yet.
- **Dedup key is `jobs.UNIQUE (source, external_id)`.** `UpsertJob` is `ON CONFLICT` on it.
- **An Indian salary LABEL goes through one parser, `inrSalary` (`salary_inr.go`)** — use it
  in any adapter whose structured salary field is a display string ("₹12L – ₹18L", "12-18
  Lacs P.A.", "INR 50,000 per month"), never on prose. A lakh or crore figure is annual CTC,
  as Indian usage fixes it; a plain rupee figure is read only beside a stated period, because
  "₹10,000 – ₹15,000" is a year's pay for nobody and a month's stipend for an intern, and a
  grouped figure beside a lakh one ("₹75,000 – ₹1.5L") does not borrow its unit. "Not
  Disclosed" and prose read as no salary. Wired into `wellfound` (2026-10-25: 572 of 905
  Indian postings gain a range; dollar ranges stay display text).
- **A detail request that FAILED and a posting the platform says is GONE are different answers, and an adapter whose detail is a posting's only source must not spell them the same way.** `fetchDetails` drops a posting whose fetch returns `ok=false`, and for the non-hydrating link-only ATS adapters — `jazzhr`, `icims`, `careerplug`, `jobvite`, `breezy`, `bamboohr`, `freshteam` — that drop was the whole reporting of a timeout or a refusal: `Fetch` came back shorter, `Stats.Failed` stayed 0, the board was recorded HEALTHY, and a posting unreadable for 48 hours was closed by both sweeps as unseen. Those adapters now return `unreadableDetail(...)` with `ok=true` instead, and `sources.detailUnreadable` is the one place the line is drawn: **404/410 is the platform's own answer that the posting is gone** and stays a drop; everything else — a timeout, a 403/429, a 5xx, an undecodable body, a 200 carrying no posting — is the ABSENCE of an answer and becomes a `Job{Unreadable: true}` marker the pipeline counts (`Stats.Unreadable`) and acts on (see [internal/ingest/pipeline/AGENTS.md](../pipeline/AGENTS.md)). A link with no posting id at all stays a drop too: nothing was ever stored under it, so no close can reach it. **This is NOT a board failure and must not become one** — a dropped detail is a per-posting hole, and failing the board would cool it to the 24-hour ceiling and freeze its whole catalogue. Hydrating adapters (`workday`, `seek`, `gusto`, `applitrack`, `ukgready`, `smartrecruiters`, `gupy`, `successfactors` — the last three's unseen postings still get the marker) are outside all of this: a seen posting yields a `SeenRefresh` and costs no detail request, so the "a drop is normal" arguments below do not carry over to the non-hydrating case. `successfactors` hydrates since 2026-10-28: its sitemap names a posting and carries nothing else, so it had re-read every stored page on every run, and every run for at least ten days hit its deadline after ~350 of each shard's ~850 boards — the large boards (capgemini, tractorsupply, wipro, lidl) never finished, saved nothing, and 24.7k of their open postings aged past 14 days unseen. A seen posting's `SeenRefresh` carries no title (the sitemap has none); `BODY_REFRESH_DAYS` is what re-reads an edited page. `eightfold` hydrates since 2026-10-29, and gave up `StreamingSource` to do so (the pipeline prefers `FetchStream`, which has no `seen`): its list serves ten positions per request and its detail one, all under one ~1 req/s pace per shard, so re-reading every stored body kept 24 of 25 runs in a fortnight on their crawl deadline and the Microsoft board (~2,400 positions) never finished, never qualified for the board-scoped sweep, and left 6,054 rows open with 2,641 unseen for 14+ days. A run hydrates at most `eightfoldMaxNewPerBoard` new positions per board, a random sample so a run of never-stored (rejected) positions cannot hold the budget, so a cold board converges over several runs instead of spending the shard and saving nothing; an `INGEST_REFETCH_ALL` repair reaches only that many per board per run. A failed detail still ingests list-only. `paylocity`, `personio`, `recruitee` and `ukg` are outside it too, for the opposite reason — their listing is authoritative for a posting's existence and a failed detail costs only the body.
- **The same distinction exists one level up, at the BOARD, and there it does not arrive as a status code.** A platform's own "no such board" answer can be a well-formed page under HTTP 200, so nothing below the adapter can tell it from a working response and the adapter fails further along, on whatever it could not parse. Paycom serves `Job board does not exist.` (since 2026-10 `Job board does not exist or is unavailable at this time.` — the old constant's trailing period stopped matching it, which is exactly the trap the last sentence of this entry warns about) in place of the portal shell, and ApplicantPro/iSolved Hire serve `This career site has been disabled.` or `You may have typed the url for this website incorrectly.` at `sitemap.xml`. Both surfaced in `board_health` as an adapter bug — a missing session token and an XML syntax error on line 3 — under which **92 boards sat gone for two months** until an audit went looking. An adapter that can recognise the platform's answer wraps `sources.ErrBoardGone`; the crawl still fails and `BoardHealth` still counts it, but the failure is now nameable, so these boards are selected by a query instead of read out of error prose. **Nothing retires a board automatically**: a platform-wide outage that started serving one of those pages would read as its whole fleet dying at once, so the sentinel informs the decision rather than taking it. Match a stable FRAGMENT of the notice, never the whole sentence — vendor copy gets reworded, and a check that silently stops matching puts us back where this started.

  **BambooHR is the third form, and it is not a body at all: it REDIRECTS.** The careers-list request 302s, the client follows it, and the JSON decode fails on the landing page's HTML — `invalid character '<' looking for beginning of value`, an adapter bug for the third time. It reached 135 boards. The adapter therefore takes `JSONResolvedGetter` (`GetJSONResolved`, the JSON counterpart of the existing `GetHTMLResolved`) and reads the FINAL url: **leaving `<board>.bamboohr.com/careers` is the verdict, not any particular destination.** That is deliberate — the destination encodes WHY (`www.bamboohr.com` no tenant, `/login.php` public board switched off, `/settings/account/expired.php` lapsed, `/settings/account/temporarily_suspended`), and those reasons keep their own vocabulary, so a rule naming them would miss the next one. The destination rides in the error message instead, because they do not mean the same thing to whoever decides on retirement — `temporarily_suspended` is a board to leave alone — and learning that distinction the first time cost 138 hand-run probes. An empty final url is never a verdict: a request that got no response at all must keep reading as a transport failure.
- **`sources.SelfClosingProviders`** lists providers whose adapters implement the `selfClosing` marker — they emit `Job{Removed: true}` for taken-down postings and are excluded from the unseen-job sweep.
- **`board_health` holds ONLY runtime state** — the catalog itself is the `boards` table (first bullet), and a row left behind for a board no longer crawled is inert. Retiring a board does not delete its health row, so `consecutive_failures` and `last_error` stay readable as the record of why it was retired.
- **An adapter MAY yield the platform's application form (`Job.ApplyForm`), but only when its list endpoint already carries one.** Today that is `recruitee` alone: its `/api/offers/` response holds `open_questions` and the `options_*` standard-field flags beside the posting, so the form costs no extra request and `applyform.FromRecruitee` maps it in place. Every other adapter leaves it nil, which is not a failure. **An adapter must never issue a request to fill it** — a form that costs a request would make a crawl's duration a function of board size, and the adapter cannot tell which postings are new anyway (that answer exists only after `UpsertJob`'s `ON CONFLICT` resolves). Those platforms — `greenhouse`, `ashby`, `workable`, `lever` — are captured after ingest by `cmd/capture-apply-form`; `applyform.NeedsRequestCapture` is the gate, and it and the fetcher registry read one map so the queue cannot fill with work nothing can drain.
- **An adapter MAY implement `CompanyDescriber` to yield its board's own company-level description**, fetched once per board crawl — never once per posting, since it is a fact about the board, not about any one job. `greenhouse` and `workable` implement it today. `greenhouse` fetches `boards-api.greenhouse.io/v1/boards/{board}` (distinct from the `/jobs` listing `Fetch` calls), which carries an employer-authored "about us" `content` field for a meaningful share of boards (confirmed live: Coinbase, Figma, Asana). `workable` fetches its OWN `apply.workable.com/api/v1/widget/accounts/{board}` endpoint again but WITHOUT `?details=true` — that flag only controls whether each job's own full body is inlined, so dropping it shrinks the response substantially (~11x on a sampled board) while leaving the account-level `description` field unaffected, so the second request is cheap rather than a duplicate of `Fetch`'s own (potentially much larger) payload; a first design spike sampled only two large, atypically-run boards (GitLab, Canva) and found the field empty on both, but a follow-up spike against 40 boards drawn at random from the production catalog found it filled on 32 (80%). Both adapters sanitize through the same `sanitizeHTML` helper posting bodies use, with no `html.UnescapeString` (both platforms serve this field as raw HTML, not entity-encoded). The pipeline (`Runner.fillCompanyDescription`) calls whichever capability an adapter implements at most once per board — right after the adapter lookup, independent of whether that board's own `Fetch`/`FetchStream` succeeds, and **only when the Store says the company is due** (`CompanyDescriptionDue`: no `company_info.summary` yet AND no answered fetch recorded in `companies.company_description_checked_at` within `pipeline.CompanyDescriptionRefreshWindow`, 7 days). Until 2026-10-19 it was asked on every run, which measured as half of Workable's ~63k requests a day and half of its 18,520 refusals in two days, for a field the fill can never change once stored. An answered fetch is recorded even when blank (only the stamp is written), so a board with no "about us" costs one request a week rather than one a run; a failed fetch records nothing and is retried next run. The pipeline applies a non-empty result to `companies.company_info.summary` via the optional `CompanyDescriptionFiller` Store capability — never `tagline`, which stays reserved for the short, curated-style values the YC directory and the Wikipedia backfill produce. Neither a missing capability on either side nor an adapter error propagates: a blank field, an unimplemented interface, and a fetch failure are all "no description, no write," exactly like an optional `ApplyForm` an adapter chooses not to fill. Ashby and Pinpoint expose no such field at all.
- **`adzuna`'s API description is a snippet, not the posting.** Adzuna's own docs say so — "we currently only provide a snippet of the job description" — confirmed live at exactly 500 characters, ellipsis-terminated, no parameter unlocks the rest. The full text lives only on Adzuna's own hosted job page (`schema.org` JobPosting ld+json, read via `sources.LDJobPosting`) — but only the `/details/...` URL shape reaches it; the `/land/ad/...` ad-network tracking-redirect shape answers Adzuna's own branded "Access Denied" page to a non-browser request, browser-shaped headers included (confirmed live 2026-08-08). `internal/ingest/adzunadesc` is the same after-ingest capture-queue shape as apply-form (`adzunadesc.Eligible` is the gate, mirroring `NeedsRequestCapture`), except the payload overwrites `jobs.description` directly via the existing `UpdateJobDescription` query rather than living in a new table — `adzuna_description_hydrated` exists purely as the queue's "don't ask again" marker, since apply_forms' own payload table played that role for free. `cmd/hydrate-adzuna-description` drains the ongoing queue; `cmd/seed-adzuna-description-queue` is the one-off pass that queues the ~21k rows already in the catalogue from before this shipped. **Verified live in prod (2026-08-09):** ~6.5k fetches over the first ~8h, no blocking from Adzuna at this pace — the ~40% failure rate that first run showed was NOT blocking. Two causes, both diagnosed from `last_error`: genuinely-gone content (404, or a 200 page whose ld+json carries no JobPosting block — Adzuna's own page, nothing to fix) and a real bug, now fixed: **a job's stored `url` can drift between the two shapes for the SAME posting across re-crawls** (confirmed: enqueued eligible at 03:03, re-crawled to the `/land/ad/` shape by 08:25, claimed and 403-ed three times by 10:18). `Eligible` is checked once at enqueue; the runner now re-checks the URL shape on the CLAIM (which reads `jobs.url` fresh) before fetching, and `Store.Discard`s a drifted claim — deleted, not dead-lettered, so a later crawl that restores the eligible shape can re-enqueue it — rather than burning retries against a page it already knows will 403.

## How it works

**Board registry:** each adapter implements the `Source` interface and speaks a common normalized `Job` shape. `sources.All` is the registry map. Adapters are in `internal/ingest/sources/` — one `.go` file per provider (`greenhouse.go`, `lever.go`, `ashby.go`, …) with matching `_test.go` files. `config.go` holds `Config.Validate` (the registry check) and `BoardDedupeKey` (the identity two catalog rows are one crawl target under).

**Ingest pipeline:** `cmd/ingest` loads the provider's live boards from the catalog, then delegates to the `pipeline.Runner` which fetches each board once, normalizes postings, and `UpsertJob`s them (idempotent on the dedup key). New postings are enqueued into `enrichment_outbox` in the same transaction (transactional-outbox).

**Per-board health:** `board_health (provider, board, region)` tracks `consecutive_failures`, `cooldown_until`, `last_error`, timestamps, `last_ingested_count`. `region` (`text NOT NULL DEFAULT ''`, migration `0077`) disambiguates a board id that repeats across independent regional slices — Adzuna's `it-jobs` exists once per country — so each slice gets its own health row; every region-less provider passes `''`, matching the column's default. The `pipeline.Runner` uses an optional `BoardHealth` port (nil = feature off). It **skips a board whose `cooldown_until` is in the future** (counted `Cooled`, not `Failed`). Backoff (`pipeline.CooldownFor`): no cooldown below **3** consecutive failures, then `6h·2^(f-3)` capped at **24h**. A success self-heals. The backoff is Go-owned and unit-tested.

**Incremental search indexing:** `cmd/ingest` queues each crawl's **new or content-changed** open jobs into `search_outbox` (`job_id` only, `ON CONFLICT DO NOTHING`), atomically in the same transaction as the upsert — the worker never talks to Meilisearch. The change signal is `jobs.content_hash` returned by `UpsertJob` as `inserted`/`changed`. The enqueue is unconditional on `MEILI_MASTER_KEY` — an unconfigured deployment simply never drains the queue. Draining is `cmd/search-drain`'s job, on its own schedule (see [internal/search/searchdrain/AGENTS.md](../../search/searchdrain/AGENTS.md)). Full reindex (`cmd/reindex`) stays the source of truth — it owns settings, compaction, and removing closed-job documents.

**Proxy egress (opt-in, IP-blocklisted providers):** some ATS edges IP-blocklist the prod datacenter IP (e.g. eightfold 403s every prod-IP request while a residential IP is served). `SOURCES_PROXY_URL` (form `http://user:pass@host:port`) routes only the providers in the `proxiedProviders` allowlist through that egress proxy; everything else stays on the direct IP. Unset = no-op; set-but-invalid fails the run at startup. `cmd/ingest` calls `sources.ApplyProxyEgress(registry)` after `All`. The SEEK network (`seek`, `jobstreet`) is a third, narrower case: it stays direct and gets the proxy only as a fallback lane for its GraphQL detail after SEEK refuses the direct IP — see [providers/seek.md](providers/seek.md). The proxy endpoint + credentials live entirely in env — nothing is hardcoded. **SSRF caveat:** on the proxied path the guarded dialer vets the *proxy's* IP, not the ultimate target (the proxy resolves that), so `proxiedProviders` must list only trusted, fixed-host providers — never the link-following/liveness paths, which keep the direct target-guarded client.

**Link-following (`internal/ingest/linksource/`):** resolves a single outbound job-detail URL into a vacancy under the destination's own identity. A `LinkSource` adapts a single detail page (unlike `sources` which adapts a whole ATS board). Matching by link host. The resolved job dedups against the same posting if another source also has it.

**Job lifecycle — soft-close via `closed_at`:**

1. **Ingest sweep** (`CloseUnseenJobs`): post-run sweep closes a provider's jobs unseen for 48h. A reappearing posting reopens via the upsert. Self-closing sources are excluded.
2. **Stream-driven self-close** (`CloseJobBySourceExternalID`): self-closing sources emit `Job{Removed: true}`; the pipeline routes this to the Store's optional `closer`.
3. **Liveness probe** (`cmd/liveness`): URL-probes orphan jobs from non-board sources. Closes after two consecutive `expired` reads (the `liveness_strikes` counter).

**Telegram ingest** is a two-stage queue (crawl then LLM-extract): `cmd/tg-ingest` crawls the active `telegram_channels` rows into `telegram_posts`; `cmd/tg-extract` drains via the LLM. Both are run-once-and-exit cron workers.

## Limitations

- The ingest sweep has a trade-off: a missed run can leave an orphan open until a future reconcile; the change window is sized wide enough to absorb a skipped cron.
- Self-closing sources: a missed `removed` event from the feed can leave a vacancy open until the next reindex.

## A crawl that reads nothing of what it listed must fail

`echojobs` published `ingested=0 failed=0`, exit 0, green unit, every four hours for 19 days
while its pages sat behind a bot wall (freehire#2588). A dropped posting never reaches the
pipeline — `Stats` counts `saveOne` failures, not candidates an adapter discarded — so from
every side but the adapter's, a total outage and a source with nothing to offer are the same
result.

So a hydrating adapter that listed candidates and read **none** of them returns an error.
There is deliberately no threshold: "some candidates, none read" is the whole signal, and how
many consecutive failures matter is `board_health`'s question. No candidates at all still
succeeds — a quiet source is not a broken one.

## The Scrapling tier (the sources no plain client reaches)

`scraplingProviders` (scraplingtier.go) sends a provider's requests through
[services/scrapling-fetch](../../../services/scrapling-fetch/README.md) on the crawl host, over
[internal/platform/scraplingfetch](../../platform/scraplingfetch/AGENTS.md). Each row names a
mode — `http` (one request with Chrome's TLS fingerprint, ~0.2-2 s) or `browser` (a stealth
Chromium navigation that solves Cloudflare challenges, ~5-9 s once the first page on a host has
paid ~110 s for the challenge) — and whether it egresses through the proxy the service holds.
Every row is the cheapest route the 2026-10-20 spike measured to pass;
[the design](../../../docs/superpowers/specs/2026-10-20-scrapling-fetch-design.md) has the
per-source, per-mode table, including the sources that spike did NOT rescue (echojobs, neogov,
dodo).

Two of those were rescued on 2026-10-21, once the proxy came back from a Webshare outage that
had poisoned the spike's measurements: `neogov` (the crawl host's IP times out at TCP connect;
`http` + proxy reads the XHR listing and the detail pages) and `echojobs` (Vercel's checkpoint:
`http` + proxy drew a 429 about half the time, `browser` + proxy passed 10 of 10). echojobs used
to have a chromedp browser tier of its own (`browsertier.go`, freehire#2588); the checkpoint
began answering it with a 403 and it was deleted in favour of this row.

It replaced the hosted Firecrawl tier, which carried bayt, gulftalent, wellfound, wantapply's
sitemap and hh's detail pages at a credit per page and ran out of credits in 2026-10.

**Measure what is behind the wall before adding a provider**: `bayt`'s IT category passed
**0 of 33** titles through `classify.IsTech` and `gulftalent`'s postings **5 of 400**
(2026-09-07). A browser page is not free — ~1-1.7 GB per live session on the crawl host.

**`ApplyScraplingEgress` must run LAST**, and `cmd/ingest` does. `gulftalent` is in
`proxiedFingerprintProviders` and `infojobs` in `proxiedProviders`, so both tiers write the same
registry entry — the override is *wanted* (those transports are measured as refused, this one as
served), so it is ordered instead of being a silent last-write-wins. Without `SCRAPLING_FETCH_URL` the override does not happen
and each keeps its earlier transport — which is also the rollback.

No adapter changed: the tier is a `*Client` whose transport forwards to the service, so every
getter, the retries and the body cap are the same code every other provider uses.

**Some providers send only PART of a crawl through it.** `wantapply` reads only the .com sitemap
there (~2 755 vacancies against the free .cy mirror's ~605) and every page on the free client.
`startupjobs` sends only its Cloudflare-challenged site pages; its sitemap CDN and Algolia index
stay plain. `hh` sends only detail hydration: its listing works on the plain direct IP while its
detail pages redirect through the proxy to a DDoS-Guard captcha, so its build hands
`NewHHWithDetailGetter` a fresh, always-unproxied `NewClient()` for listing — deliberately NOT the
`direct` parameter, which is the PROXIED client whenever `SOURCES_PROXY_URL` is set for any
other provider.
