# Source ingest conventions

## Scope
Source ingest: board list, provider registry, board-file parsing/validation, per-board health sidecar, and related job-lifecycle mechanics.

## Always true
- **One file per provider** under `sources/` (`sources/<provider>.yml`) plus a mixed `sources/custom.yml`. Each entry is `company` + `board`, taking the file-name provider unless it names its own.
- **`sources.All` maps each `provider` string to a registered adapter** (`Source` interface) over a shared HTTP client. Adding a platform is a new adapter + one line in `sources.All`.
- **`cmd/ingest` processes one board file per run** (path as first argument or `SOURCES_FILE`). It validates every entry against the registry and **fails fast** — a misconfigured board never starts a run.
- **Run-once-and-exit worker** meant for cron (one schedule per file, so providers crawl independently). No long-lived process.
- **Adapters are read-only over public ATS JSON APIs.** Per-board crawl is independent: one failing board is counted (`stats.Failed`) but does not abort the rest.
- **Sources are keyless by default.** The exceptions are `usajobs` (`USAJOBS_API_KEY`), `reed` (`REED_API_KEY`) and one WhatJobs adapter per market — the vendor issues a separate publisher account per country, so `whatjobsMarkets` in `internal/ingest/sources/whatjobs.go` lists one `{code, provider, country}` row per onboarded market (`whatjobs` for the US, `whatjobs-<code>` for the rest, e.g. `whatjobs-br`), and every account's credential lives in the single `WHATJOBS_PUBLISHER_IDS` variable (`"code:id,code:id,..."`, e.g. `"us:7065,br:7076"`) rather than one env var per market. A market with confirmed but thin inventory (see `whatjobs-au.yml`, `whatjobs-sv.yml` etc.) is still onboarded — the bar is at least one real, corroborated IT posting, not deep volume. The credential lives in the env, never in a board file.
- **`All` is the crawl registry, `Taxonomy` is the classification one — the credential gates only the first.** `sources.All(client)` omits a keyed provider whose variable is unset, so its board file fails config validation before any request goes out. `sources.Taxonomy()` (`All(nil)`, no transport, never Fetch through it) is **total**: what kind of source a provider is cannot depend on whether this host can crawl it. Everything that classifies rather than crawls — `FilterableProviders`, `ProviderKind` on the status page, `AggregatorProviders` in `cmd/reindex` and `cmd/ghost-crosscheck` — reads `Taxonomy`. Conflating the two silently reclassified `whatjobs`, a reseller of first-party ATS postings, as an ATS on every keyless host, so none of its copies were suppressed.
- **A board is not always a tenant.** For `hh` it is a `professional_role`, for `trudvsem` an OKATO region code, for `whatjobs` a SEARCH KEYWORD, for `edjoin` a JOB-TYPE id. Such a provider is an `aggregator` (many employers, company read per posting) but NOT `boardless` — the board is what selects the slice to crawl. Note that a central searchable index does not by itself make a provider boardless: `edjoin` has exactly one, and the board still earns its keep, because what the slice buys is not reachability but a catalogue the ingest filter cannot police on its own (see the EDJOIN traps below).
- **`sweepGrace` widens the unseen sweep for a slice-crawled provider.** `whatjobs` reads at most 40 pages of a keyword from a feed thousands of pages deep, so a posting that drifts past that depth reads as unseen; on the 48-hour default it would be closed and reopened repeatedly, each cycle writing a phantom removal into `job_daily_stats`. The adapter declares 14 days instead (`sources.SweepGraceWindows` → `cmd/ingest`'s `sweepWindowFor`). Sound only where liveness cannot be probed — anything verifiable should close on evidence.
- **Which page failed decides whether the board failed.** Every paginated listing walk obeys one rule: the FIRST page failing is a board-level error, a LATER page failing ends the walk with the links gathered so far. A partial crawl survives a mid-listing hiccup; a board that cannot be reached at all is reported. The canonical statement is `crawlPagedLinks` in `html.go`, and `added == 0` is what ends a walk that has run out of new links.

  **The exception is the one that matters.** A `fullCatalog` provider is swept by SOURCE, so a silently-truncated walk looks like a shrunken catalogue and would mass-close every posting past the failed page. There the rule inverts: ANY page failing must fail the whole crawl, steering the sweep back to the safe company-scoped close. `crawlAllPagedLinks` is that variant. Both `fullCatalog` providers honour it — `geekjob` through the helper, `habrcareer` in its own JSON loop with the reasoning written at the branch — which is the point: **what must not drift is the rule, not the helper.**

  Seven adapters restate the walk by hand rather than call it (`peopleforce`, `bayt`, `teamtailor`, `neogov`, `hh`, `gusto`, `edjoin`), and that is deliberate, not an oversight: they differ in transport (`GetHTML` / `GetTextWithHeaders` / embedded page state), in what they dedup on (URL, extracted job id, int64 vacancy id), in extra stop conditions (`neogov` reads a `total`, `teamtailor` retries `/jobs`→root on a 404 and then follows the path it landed on), and in what a page must YIELD (`gusto` needs each item's whole listing row — title, location, pay, employment type — not just its link, because that row is everything the platform states about a posting bar its body; `edjoin` needs the same, and additionally stops on an exact `totalRecords`). A generic over those seven would be harder than the fifteen-line loop it replaced. When touching one, check its first-page branch — and note that **`hh` counts from page 0**, so its check is `page == 0`, not `page == 1`.

- **Dedup key is `jobs.UNIQUE (source, external_id)`.** `UpsertJob` is `ON CONFLICT` on it.
- **`sources.SelfClosingProviders`** lists providers whose adapters implement the `selfClosing` marker — they emit `Job{Removed: true}` for taken-down postings and are excluded from the unseen-job sweep.
- **Board health table holds ONLY runtime state** — the board catalog stays in YAML (git); a stale row for a removed board is inert.
- **An adapter MAY yield the platform's application form (`Job.ApplyForm`), but only when its list endpoint already carries one.** Today that is `recruitee` alone: its `/api/offers/` response holds `open_questions` and the `options_*` standard-field flags beside the posting, so the form costs no extra request and `applyform.FromRecruitee` maps it in place. Every other adapter leaves it nil, which is not a failure. **An adapter must never issue a request to fill it** — a form that costs a request would make a crawl's duration a function of board size, and the adapter cannot tell which postings are new anyway (that answer exists only after `UpsertJob`'s `ON CONFLICT` resolves). Those platforms — `greenhouse`, `ashby`, `workable`, `lever` — are captured after ingest by `cmd/capture-apply-form`; `applyform.NeedsRequestCapture` is the gate, and it and the fetcher registry read one map so the queue cannot fill with work nothing can drain.
- **`adzuna`'s API description is a snippet, not the posting.** Adzuna's own docs say so — "we currently only provide a snippet of the job description" — confirmed live at exactly 500 characters, ellipsis-terminated, no parameter unlocks the rest. The full text lives only on Adzuna's own hosted job page (`schema.org` JobPosting ld+json, read via `sources.LDJobPosting`) — but only the `/details/...` URL shape reaches it; the `/land/ad/...` ad-network tracking-redirect shape answers Adzuna's own branded "Access Denied" page to a non-browser request, browser-shaped headers included (confirmed live 2026-08-08). `internal/ingest/adzunadesc` is the same after-ingest capture-queue shape as apply-form (`adzunadesc.Eligible` is the gate, mirroring `NeedsRequestCapture`), except the payload overwrites `jobs.description` directly via the existing `UpdateJobDescription` query rather than living in a new table — `adzuna_description_hydrated` exists purely as the queue's "don't ask again" marker, since apply_forms' own payload table played that role for free. `cmd/hydrate-adzuna-description` drains the ongoing queue; `cmd/seed-adzuna-description-queue` is the one-off pass that queues the ~21k rows already in the catalogue from before this shipped. **Verified live in prod (2026-08-09):** ~6.5k fetches over the first ~8h, no blocking from Adzuna at this pace — the ~40% failure rate that first run showed was NOT blocking. Two causes, both diagnosed from `last_error`: genuinely-gone content (404, or a 200 page whose ld+json carries no JobPosting block — Adzuna's own page, nothing to fix) and a real bug, now fixed: **a job's stored `url` can drift between the two shapes for the SAME posting across re-crawls** (confirmed: enqueued eligible at 03:03, re-crawled to the `/land/ad/` shape by 08:25, claimed and 403-ed three times by 10:18). `Eligible` is checked once at enqueue; the runner now re-checks the URL shape on the CLAIM (which reads `jobs.url` fresh) before fetching, and `Store.Discard`s a drifted claim — deleted, not dead-lettered, so a later crawl that restores the eligible shape can re-enqueue it — rather than burning retries against a page it already knows will 403.

## How it works

**Board registry:** each adapter implements the `Source` interface and speaks a common normalized `Job` shape. `sources.All` is the registry map. Adapters are in `internal/ingest/sources/` — one `.go` file per provider (`greenhouse.go`, `lever.go`, `ashby.go`, …) with matching `_test.go` files. `config.go` handles board-file parsing and validation.

**`cmd/validate-sources`** catches a hand-edited board file going bad without anyone noticing at ingest time: a malformed or unrecognized-field entry, and a case-variant duplicate board that `cmd/ingest` would otherwise silently collapse (`sources.dedupeBoards`) with only a log line to show for it. It touches no network and no database, runs on every PR (`.github/workflows/ci.yml`'s "Validate sources" step, ahead of unit tests), and exits non-zero listing every bad file rather than stopping at the first one. `go run ./cmd/validate-sources [dir]` (defaults to `sources/`).

**Ingest pipeline:** `cmd/ingest` loads the board file, validates every entry, then delegates to the `pipeline.Runner` which fetches each board once, normalizes postings, and `UpsertJob`s them (idempotent on the dedup key). New postings are enqueued into `enrichment_outbox` in the same transaction (transactional-outbox).

**Per-board health:** `board_health (provider, board, region)` tracks `consecutive_failures`, `cooldown_until`, `last_error`, timestamps, `last_ingested_count`. `region` (`text NOT NULL DEFAULT ''`, migration `0077`) disambiguates a board id that repeats across independent regional slices — Adzuna's `it-jobs` exists once per country — so each slice gets its own health row; every region-less provider passes `''`, matching the column's default. The `pipeline.Runner` uses an optional `BoardHealth` port (nil = feature off). It **skips a board whose `cooldown_until` is in the future** (counted `Cooled`, not `Failed`). Backoff (`pipeline.CooldownFor`): no cooldown below **3** consecutive failures, then `6h·2^(f-3)` capped at **24h**. A success self-heals. The backoff is Go-owned and unit-tested.

**Incremental search indexing:** `cmd/ingest` queues each crawl's **new or content-changed** open jobs into `search_outbox` (`job_id` only, `ON CONFLICT DO NOTHING`), atomically in the same transaction as the upsert — the worker never talks to Meilisearch. The change signal is `jobs.content_hash` returned by `UpsertJob` as `inserted`/`changed`. The enqueue is unconditional on `MEILI_MASTER_KEY` — an unconfigured deployment simply never drains the queue. Draining is `cmd/search-drain`'s job, on its own schedule (see [internal/search/searchdrain/AGENTS.md](../../search/searchdrain/AGENTS.md)). Full reindex (`cmd/reindex`) stays the source of truth — it owns settings, compaction, and removing closed-job documents.

**Proxy egress (opt-in, IP-blocklisted providers):** some ATS edges IP-blocklist the prod datacenter IP (e.g. eightfold 403s every prod-IP request while a residential IP is served). `SOURCES_PROXY_URL` (form `http://user:pass@host:port`) routes only the providers in the `proxiedProviders` allowlist through that egress proxy; everything else stays on the direct IP. Unset = no-op; set-but-invalid fails the run at startup. `cmd/ingest` calls `sources.ApplyProxyEgress(registry)` after `All`. The proxy endpoint + credentials live entirely in env — nothing is hardcoded. **SSRF caveat:** on the proxied path the guarded dialer vets the *proxy's* IP, not the ultimate target (the proxy resolves that), so `proxiedProviders` must list only trusted, fixed-host providers — never the link-following/liveness paths, which keep the direct target-guarded client.

**Link-following (`internal/ingest/linksource/`):** resolves a single outbound job-detail URL into a vacancy under the destination's own identity. A `LinkSource` adapts a single detail page (unlike `sources` which adapts a whole ATS board). Matching by link host. The resolved job dedups against the same posting if another source also has it.

**Job lifecycle — soft-close via `closed_at`:**
1. **Ingest sweep** (`CloseUnseenJobs`): post-run sweep closes a provider's jobs unseen for 48h. A reappearing posting reopens via the upsert. Self-closing sources are excluded.
2. **Stream-driven self-close** (`CloseJobBySourceExternalID`): self-closing sources emit `Job{Removed: true}`; the pipeline routes this to the Store's optional `closer`.
3. **Liveness probe** (`cmd/liveness`): URL-probes orphan jobs from non-board sources. Closes after two consecutive `expired` reads (the `liveness_strikes` counter).

**Telegram ingest** is a two-stage queue (crawl then LLM-extract): `cmd/tg-ingest` crawls `sources/telegram.yml` channels into `telegram_posts`; `cmd/tg-extract` drains via the LLM. Both are run-once-and-exit cron workers.

**SEEK traps** (all verified live on 2026-08-16, AU and NZ):

- **The bot protection guards the pages, not the API.** A plain request to a SEEK search page or to a `/job/<id>` page answers **403** behind a Cloudflare interstitial ("Just a moment..."), and browser-shaped headers do not clear it. `GET /api/jobsearch/v5/search` — the site's own frontend endpoint — is not gated at all: it answers 200 JSON with no cookie, no credential and no browser-shaped User-Agent (confirmed with no UA, `curl/8.7.1`, `Go-http-client/2.0` and the project's own `freehire/0.1`). Descriptions come from `POST /graphql`, operation `jobDetails`, on the same terms. The consequence for the lifecycle: SEEK postings **cannot be liveness-probed**, because that path fetches the gated job page — which is why the adapter leans on `sweepGrace` instead.
- **`totalCount` is a function of `pageSize`.** The same query answered **36** at `pageSize=1`, **688** at `pageSize=20`, 680 at 50 and 666 at 100. It can neither drive pagination nor detect truncation, so the adapter's response struct does not even declare the field and the walk stops on the repo's usual `added == 0`. This is the same class of bug as WhatJobs' `limit=1` below — a listing's self-reported total is not evidence.
- **The result window ends near 550.** `pageSize=100` serves pages 1–5 and answers page 6 empty; `pageSize=50` serves through page 11 (offset 550) and page 12 empty. `pageSize` above 100 returns nothing. A slice larger than the window has a tail no crawl can reach — five of Australia's 22 ICT subclassifications, the largest at ~746 postings.
- **`where` is load-bearing and omitting it does NOT mean "everywhere".** Dropping it collapsed a 688-posting slice to 36. It travels with the market's host and `siteKey` as one unit.
- **`www.seek.com.au` now 308-redirects its HTML routes to `au.seek.com`**, and the older `chalice-search` API paths are gone. `api/jobsearch/v5/search` is the live one, and it answers on the `www.seek.com.au` host without a redirect.
- **`companyName` is empty on roughly one posting in thirty**, where `advertiser.description` carries the name the employer typed — including SEEK's **`"Private Advertiser"`** placeholder, which is not a company. Such a posting is dropped rather than filed under a placeholder that would otherwise collect anonymous postings from both markets.
- **`salaryLabel` is free text, and about a tenth of the postings that fill it use it for marketing copy** ("Strong remuneration", "Optional 9 day fortnight | Career Growth") rather than a salary. It is folded into the description verbatim; it never populates the structured salary fields.
- **The GraphQL detail endpoint meters by a per-IP request BUDGET, and the first prod run walked straight into it.** Unpaced, one crawl fired **3,267 detail POSTs in 95 seconds** (43 boards, each detail pool bursting to `defaultDetailWorkers`) and was answered **429** on essentially all of them — while a single identical request from the same host returned **200 after two minutes idle**. An immediate refusal that clears on idle is a window, not saturation, so the fix is a rate limiter (`seekDetailInterval`, ~2 req/s shared across every board) and NOT the in-flight cap `trudvsem`/`emagine` use: eight fast requests a second from one worker is still eight a second. The listing was never refused, so only the detail path is paced.
- **seek and ukgready are the hydrating adapters that DROP a posting whose detail failed** instead of ingesting it list-only. Most others keep it, and that rule is right where its premise holds — a detail failure is rare, so keeping the posting beats losing it. SEEK breaks the premise twice over: refusals arrive in bursts of thousands, and the retry that normally absorbs a failure is bounded — a stored row with no body is re-offered for hydration only while it is younger than `pipeline.HydrationRetryWindow` (14 days), after which `seen` reports it like any other row (the same trap `pacer.go`'s emagine note calls out). A backlog of thousands does not clear inside that window. A DROPPED posting stays new with no deadline at all, which is why seek does not rely on the window. The first prod crawl stranded **2,593 of 2,982 postings (87%) with no description**, none of which any later crawl could repair; they had to be pruned. Deferring a posting by one crawl is recoverable, storing it body-less is not — that asymmetry, not a preference, is why seek differs. **ukgready breaks the premise differently and worse**: the fallback it would store is not an empty body but the listing's 250-character preview, which is a description as far as `pipeline.HydrationRetryWindow` is concerned, so nothing ever re-offers it — the stub is permanent from the first crawl, not after 14 days. Dropping keeps the posting unseen and the next crawl retries it.

**UKG Ready traps** (all verified live 2026-09-02):

- **`ukg` and `ukgready` are two different products, not two spellings of one.** `ukg` is UKG Pro Recruiting (formerly UltiPro) on `*.ultipro.com` / `*.rec.pro.ukg.net`, board `<host>/<tenant>/<guid>`; `ukgready` is UKG Ready (formerly Kronos Workforce Ready) on the SaaSHR-era hosts, board `<host>/<tenant>`. They share nothing but a vendor — different API, different id space, different board shape.
- **The career page is a SPA and its REST API is keyless.** `https://<host>/ta/<tenant>.careers` renders client-side (the same URL without `ShowJob` answers a SIGN-IN page on the legacy UI, so it is not a listing to scrape). The API behind it is `/ta/rest/ui/recruitment/companies/|<tenant>/job-requisitions` — note the percent-encoded pipe — with the body at `.../job-requisitions/<id>` and the tenant's locale at `/ta/rest/ui/bootstrap/companies/|<tenant>/format-settings`.
- **`offset` is a 1-based PAGE NUMBER, not a row offset, and nothing about the response says so.** It is echoed back in `_paging` verbatim and an out-of-range page is answered `200` with an empty `job_requisitions` — no error, no clue. Confirmed on an 84-posting board at `size=50`: `offset=0` and `offset=1` both serve rows 1-50, `offset=2` serves the remaining 34, `offset=3` is empty, and the union of those pages is the whole board. Advancing it by the row count — the shape the name invites — reads page 1 and then page 200, so every board past one page truncates in silence; a 259-posting board ingested exactly 200 that way before the first smoke run caught it.
- **`_paging.total` is trustworthy, unlike SEEK's `totalCount`**: it answered the same figure at `size=1` and `size=200` on every board tried, so it can bound the walk and one row settles liveness (which is what `cmd/harvest-boards`'s prober spends). `size` above 200 is a 400.
- **The host is the ENVIRONMENT, and an environment's hosts are branding.** A tenant lives in exactly one UKG environment (`US-4-PROD`, `US-61-PROD`, `AU-1-PROD`, …) and every host outside it answers "Company not found" — including hosts in the same country, so this is not only data residency: `secure4.saashr.com` (US-4) does not know a US-61 tenant. Inside one environment the white-label hosts are interchangeable: `secure.saashr.com`, `secure4.saashr.com` and `secure2.entertimeonline.com` all serve the same US-4 tenant, and `secure.workforceready.com.au` and `aus-secure.prd.mykronos.com` the same AU-1 one. So the host must be in the board id, and two board ids differing only in the host are ONE crawl target — `sources.boardIdentity`'s `ukgready` entry folds them, the icims lesson applied before it cost anything. It earned its keep immediately: a candidate spelled `aus-secure.prd.mykronos.com/6183838` was recognised as a board already held under `secure.workforceready.com.au`.
- **The listing's `job_description` is a ~250-character ellipsis-terminated preview.** The body is on the detail resource and is heavy: employers paste base64 data-URI images into it, and one board measured a **100 KB median** (the images are stripped by `htmltext.Sanitize`, which allows no `<img>` — the cost is the transfer, not the stored row). That is why the adapter is a `HydratingSource`. A steady-state re-crawl is then free, but note the non-tech rejection re-buys what it discards: these are payroll tenants, so a board is often 90% blue-collar, a rejected posting is never stored so it is never `seen`, and its body is fetched again every run. Schedule the provider accordingly.
- **Pay is a bare number; the currency belongs to the TENANT.** `base_pay_from`/`base_pay_to` carry no currency and no symbol — the career page reads it from the tenant's `format-settings` (`locale.currency_code`), and so does the adapter, once per board and only when a posting states a publishable figure. `base_pay_frequency` is exactly `YEAR|MONTH|WEEK|HOUR`; `WEEK` has no value in `vocab.SalaryPeriodValues`, so that amount is dropped rather than published half-qualified.
- **`employee_type` is a tenant-authored picklist, not an enum**, and its most common values are FLSA pay classes (`Exempt`, `Non-Exempt`, `FT Non-Exempt`) rather than schedules. Only an explicit full-/part-time marker is mapped; everything else is left to the description parser.
- **There is no posting date on either resource**, so `PostedAt` is nil and freshness falls back to first-seen. `job_preview` exists but is board-level marketing boilerplate repeated verbatim on every posting (12 of 12 identical on two boards), so it is not part of the description; `job_requirement` is, and is non-empty on roughly two postings in five.

**remote.com traps** (all verified live 2026-08-16):

- **The RSC flight is the API, and it carries different halves of a posting at each URL.** remote.com is a Next.js App Router app: there is no REST endpoint and no Pages-Router `_next/data` one, and every guessed path answers 404/500. Sending `RSC: 1` makes a page answer `text/x-component` instead of HTML — the LISTING inlines a `jobsData` object as plain JSON (identity, employer, geography, seniority, compensation, and the `totalPages` that bounds the walk exactly), a POSTING PAGE carries the body. `Next-Router-State-Tree` is not needed; the flight comes back complete without it.
- **The listing has no description field at all, and the posting page's description is not in an `application/ld+json` script.** The RSC response has no HTML to hold one — the schema.org JobPosting arrives as a flight TEXT ROW (`<id>:T<hexlen>,{…}`), which `flightJobPosting` reads with the existing `nextFlightTextRows` + `jobPostingNode` pair. That split is the whole reason this adapter is a `HydratingSource`: a body-less row never enters the search index (`search.DescriptionMissing`), so a list-only crawl would ingest ~5.7k postings nobody can find.
- **`compensation.minimum`/`maximum` are MINOR units.** The listing states one posting as `1000000-1500000` USD/yearly while that same posting's `baseSalary` states `10000-15000`. Reading them verbatim inflates every salary a hundredfold. Related: `currency.symbol` is `"$$"` for USD (a format-template artifact), which is why the adapter reads `currency.code` and never the symbol.
- **`hiringLocation.timezone.name` is a zone label, not a place.** It is the city the zone is named after (`america-chicago` → `"Chicago"`), and passing it through bare makes `location.Parse` file a work-from-anywhere-in-this-zone posting under `Cities:[Chicago] Countries:[us]`. The adapter appends `" timezone"`, which is both what the posting says and — because the dictionary matches whole phrases — what stops the city from being invented.
- `hiringLocation` is null on roughly one posting in ten, `includedLocations` entries are `country` OR `region` (`north-america`, `latin-america`, `europe`, `africa`, `asia-pacific` — remote.com's own vocabulary, resolving to no country code), and `workplaceLocation` carries the country and city only when the posting is not remote.
- **No rate limiting observed**: 48 posting pages at 8-way concurrency (~12 req/s) all returned 200, so no pacer is wired. If that changes, `pacer.go` is where it goes — a `HeaderTextGetter` variant of `rateLimitedHTMLGetter`.
- **Most of the board is already ATS-covered, and `seen` cannot bound that** — which is why remotedotcom is the one `CoverageGated` adapter. Prod's first two runs both crawled 5,745 postings and kept 1,417: **4,123 were discarded by the aggregator gate** (the employer runs its own ATS, which freehire already crawls first-party) and 205 as non-technical. A discarded posting is never stored, so it is never `seen`, so the plain hydrating crawl bought and threw away 4,123 bodies EVERY run. `FetchNewGated` asks the pipeline which employers are covered before hydrating and skips their bodies. Measured across the twelve hydrating aggregators on prod, this is remote.com's problem alone — every other one wastes 0-3%, except aijobs (44% of a 500-posting board) and echojobs (12%), whose detail endpoint is dead anyway.

**SchoolSpring traps** (all verified live 2026-09-02):

- **The board is a SEARCH KEYWORD because crawling the whole index would poison the catalogue, not because the index is unreachable.** It is entirely reachable: `api.schoolspring.com` is keyless, `GetPagedJobsWithSearch` pages the national board exactly (80,611 postings, page 807 at size 100 returns the last 11 rows, and `GetJobsCountWithSearch` agrees to the row), and an employer is a `organization` FILTER over that one index rather than a tenant — so the per-employer board shape does not exist. What makes an unscoped crawl wrong is the two numbers freehire's own dictionaries give over the live index: `classify.IsTech` fires on **36 of 80,611 titles (0.04%)**, while `classify.ConfirmedNonTech` — the gate that decides what a crawl may store — turns away 39,068 and **admits 41,543 (51.5%)**. It is a non-tech TITLE dictionary written against tech-company ATS boards, with no term for K-12 classified staff, so school psychologists, bus monitors, crossing guards, football coaches and cafeteria workers all pass it. **The gate does not hold against K-12 vocabulary, and no education board should ship as a whole-index crawl on the assumption that it does.**
- **The platform's own `category` taxonomy cannot select the technical slice.** It is the obvious thing to scope with — a server-side facet on the same index, the shape `hh` and `trudvsem` use — and it was measured before the keyword list was: 37% of postings carry no category at all (the union of all 239 categories is 50,644 of 80,611), the densest categories reach about a quarter of the technical postings, and the categories overlap so heavily — Administration/Technology and Student Services/Educational Technology share 335 of their 418 and 419 — that one board per category would store 40% of its rows twice. A keyword is the facet that does work here, and unlike a numeric facet id it is self-describing, so a typo cannot masquerade as an empty slice the way an unknown id would.
- **`keyword` filters rather than ranks, and it matches the EMPLOYER name as well as the title, as a bare substring.** "software developer" answers 0 rather than padding with near matches (the opposite of WhatJobs' feed), but "it manager" matches "Unit Manager", "it director" matches "Pit Director", and bare "network" pulls in 235 stale teaching postings from an employer called "Acero Schools Network". Every board in `sources/schoolspring.yml` is a whole phrase for that reason, and the guard against a phrase going bad later is the per-board rejection line `cmd/ingest` already logs — which is exactly the "too broad a term" signature that line exists to surface.
- **TEDK12 is a different product, not another spelling of this board.** The per-tenant sites (`pembinatrails.tedk12.ca`) are PowerSchool Applicant Tracking: per-district hosts, server-rendered ASP.NET with a `__VIEWSTATE`, no JSON, board = the tenant host. They are also largely already here — 332 of the 377 distinct hosts this crawl's postings link back to are `*.tedk12.com` tenants, carrying 622 of its 1,261 postings — so a US TEDK12 adapter would mostly re-crawl the same postings under a second identity. What one WOULD add is the fleet outside the US index: no `*.tedk12.ca` host appears among those 377 and Pembina Trails is absent from the national index entirely.
- **The keyword slices overlap, so 35 of the 383 rows the first crawl ingested (9%) are one posting stored under two boards.** It is stable rather than churning — both boards list their copy on every crawl — and the duplicate markers collapse the pair in search. Accepted rather than fixed: folding the whole keyword list into one board would make the external_id namespace change whenever the list does.
- **17,700 of the 80,611 postings display a date before 2025**, some as far back as 2010, and nothing in either resource says they are stale — the platform serves them as open (33 of the 383 rows the keyword crawl stores, 9%). **Nothing downstream closes them either**: they are re-listed on every crawl, so the unseen sweep never fires, and `cmd/liveness` skips registered providers. Only the ghost signal marks them and only `cmd/prune` removes them. A verdict would need a prober of this API's own — the detail resource answers `success:false` for a posting that is gone, which a plain GET of the SPA posting page cannot see — the shape `echojobs`/`himalayas` already take in `probeDespiteRegistered`.
- **The listing carries no body, so this is a `HydratingSource`**, and the detail resource is cheap (~12 KB, median body 6.5 KB). It also answers a **200 with `success:false`** for a posting that is gone, so the envelope's flag has to be read: a caller reading only the payload sees an empty posting rather than an error.
- **The employer is the DISTRICT and only the detail resource states it.** The listing's `employer` is the individual SCHOOL ("Columbia River High School" for a Vancouver Public Schools posting), which would scatter one district across dozens of company slugs.
- **Pay is a bare number and NOTHING states a currency** — the site's own UI just renders a `$`. The only country the platform names is the employer's contact one (`countryName`, filled on ~60% of postings), so a salary is published only for a posting that states the United States; the international schools on the same index (a posting from Athens quotes €900–1,100 in its body) are exactly what that guard is for. `payDisplay` is the employer's own publish switch and is OFF on most postings that carry a figure, and `salaryCode` is employer-typed free text ("BU Salary Schedule", "SY", "Based on Education and Experience") with `payTypeName` as the tidier fallback.
- **`jobTypeName` is a closed enum** (its own dictionary endpoint lists all seven values), unlike `shiftType`, which sits beside it, is what the site actually renders, and is free text ("Varies", "FT - School Year").
- **No metering observed**: 82 listing pages at size 1000, 239 category probes at 6-way concurrency and 1,261 detail fetches at 8-way (~13 req/s) all answered 200, and the whole 40-board crawl takes ~56 seconds. No pacer is wired.

**Dayforce traps** (all verified live 2026-09-02):

- **The listing POST is CSRF-gated and a refusal looks nothing like one.** `POST /api/geo/<tenant>/jobposting/search` answers **403 with the body `Forbidden`** to any request that does not carry next-auth's double-submit pair — the `__Host-next-auth.csrf-token` cookie AND its token half echoed in an `X-CSRF-TOKEN` header. The 403 arrives with the site's own CSP and `server: cloudflare` headers, so it reads exactly like an edge block, and no amount of browser-shaped headers, referer or cookie jar clears it. `GET /api/auth/csrf` mints the pair (and returns the token in its body) in one request that the whole crawl then shares. Every OTHER route under `/api/geo/` is a GET and is not gated at all, which is why the platform looks open until the one endpoint that lists jobs.
- **The listing carries the WHOLE description, so nothing needs a detail request.** `jobPostings[].jobDescription` is the detail endpoint's `jobPostingContent.jobDescription` with its tags stripped — byte-identical on every posting sampled across four sites, never truncated. What it omits is the `jobDescriptionHeader`/`jobDescriptionFooter` pair, which is per-BOARD boilerplate repeated verbatim on every posting of that board (1,236 identical characters on all of dnata's), so the listing body is the better text as well as the free one. It arrives entity-encoded (`&nbsp;`, `&rsquo;`) as newline-delimited plain text, hence `html.UnescapeString` → `plainTextToHTML`.
- **`cultureCode` selects the SLICE, not the language, and an unconfigured one fails two different ways.** A site publishes each posting only in the cultures it was translated into, so asking `en-US` of a Quebec-only tenant answers zero rather than answering in French. Most sites accept a culture they do not publish in and answer an empty list; some reject it with **400** (`myepay/dmrstandard` answers 400 to `en-US` and 200 to `en-GB`, while `abbeyfield/candidateportal` — also en-GB-only — answers `en-US` with its full 115). The English variants that ARE configured do collapse: `en-GB` and `en-US` return the identical set. `sitecontext`'s `isoCultureCodes` lists what the site is CONFIGURED for, not where its postings are, so it cannot pick the culture for you — only a live search can.
- **Unioning the cultures is not worth it, and would double-store.** One posting keeps the SAME `jobPostingId` in every culture it appears in, so two board entries differing only in culture write it twice under two `external_id` namespaces and then close each other's rows on the company-scoped sweep — which is why `boardIdentity` folds the culture off. Measured over 60 sites, the non-English cultures added 104 postings against 5,765 English ones (~1.8%), most of them translations of postings already in the English set, for roughly 3x the requests.
- **Page size is fixed at 25 and `maxCount` is exact** — the opposite of SEEK's `totalCount`. The request body carries only `paginationStart`; `pageSize`/`take`/`count` alongside it are ignored. Confirmed against a 3,508-posting site: the last page is short and every offset past the end answers an empty list with the same `maxCount`.
- **`hasVirtualLocation` is the structured remote flag**, and such a posting usually carries `postingLocations: null` — no place at all. A posting can be both virtual and sited, so the flag is the only structured signal and a place merely NAMED "Remote" stays with the heuristic.
- **No metering observed**: 400 listing POSTs at 32-way concurrency (~14 req/s) all returned 200, so no pacer is wired and `cmd/harvest-boards` needs no `-pace`.

**Gusto Hiring traps** (all verified live 2026-09-02, across every candidate board):

- **The board id is the WHOLE path segment** of `jobs.gusto.com/boards/<board>` — `<company-slug>-<company-uuid>`. The uuid alone 404s and so does the slug alone, so neither half is the key. Everything is server-rendered HTML: no JSON endpoint, no embedded page state, no ld+json on either page.
- **A renamed employer keeps its OLD slug resolving against the same uuid**, so two spellings of one board both answer 200 and list identical postings — and a trailing `.json` answers 200 as well, since the route ignores it. External ids are namespaced by BOARD, so crawling both spellings stores every one of that employer's postings twice. 33 of the 825 candidates were such twins. `gustoBoardIdentity` folds every spelling onto the company uuid (the `boardIdentity` map, beside `icimsHost`, which exists for the same failure), so `cmd/validate-sources` fails loudly on a twin and `dedupeBoards` drops it at load time; `sources/gusto.yml` additionally carries one entry per uuid, folded onto the spelling a posting's own breadcrumb links back to.
- **Cloudflare answers a managed challenge (403) to Go's default TLS+HTTP/2 fingerprint on every path**, so the adapter is wired with `fingerprintHTTP` alongside meta/uber/bayt/gulftalent.
- The listing serves **25 postings a page** under `?page=N` and renders "There are no open positions currently" past the last one, so the walk ends on a page that adds nothing. It carries every field EXCEPT the body, which only the posting page holds — hence `HydratingSource`.
- **Both pages are small**: a board page measured 9-46 KB and a posting page 13-24 KB across the live sample, so hydration is cheap here in a way it is not on hh (~1 MB a detail page). What bounds the crawl is the posting COUNT, not page weight: ~2.8k postings across 790 boards.
- **Neither page states a publish date in any form**, so `PostedAt` is always nil.
- The pay line is rendered text with a single fixed grammar (`$X - $Y per <period>`) — the platform's own compensation field formatted, not free text, which is what makes reading it structured signal. 2,098 of 2,789 live postings carried one and all but two matched. The currency is STATED as USD rather than read off the `$`: Gusto Payroll runs US employers only. The two exceptions say "per week", which freehire has no salary period for, so they yield no structured salary rather than a wrong one.
- **A posting whose body does not parse is dropped, not stored.** A stored row is `seen`, so it is never hydrated again once it ages past the hydration-retry window — deferring a posting by one crawl is recoverable, storing it body-less is not (the same asymmetry seek's note argues, for a different cause).
- **No rate limiting observed**: 825 board pages at 6-way concurrency (~13 req/s) twice over, plus a 790-board harvest that also fetched every posting page — all 200, no refusals. So no pacer is wired; `pacer.go` is where one would go.

**EDJOIN traps** (all verified live 2026-09-02, across the whole platform):

- **The board is a JOB TYPE, and choosing that over the district is the whole design.** EDJOIN serves one central index, so the numeric ids beside an employer are `districtID` — one more facet of that index, and there are 1,573 of them. What the board selects is the slice to crawl, the `hh` professional_role shape. The reason is measured, not stylistic: the platform holds **16,447 open postings and the catalogue filter rejects only 38.2% of them by title**, because `classify`'s non-tech dictionary was written against tech-company ATS boards and carries no term for K-12 classified-staff vocabulary — so the other 10,163 (paraeducators, instructional aides, yard monitors, campus supervisors, cafeteria assistants) would all be ADMITTED. Job type **25, "Information Tech. / Computer Svcs.", is the single technical entry in EDJOIN's own 66-value job-type vocabulary** and held 71 postings across 59 districts, of which the filter rejected **zero**. The cost argument agrees: the listing carries no body, a rejected posting is never stored so never `seen`, and a whole-index crawl would therefore re-buy ~2.4 GB of 147 KB detail pages every run forever — the ukgready note above, at ten times the ratio.
- **The listing endpoint dereferences three query parameters without a null check.** `GET /Home/LoadJobs` answers a **500 .NET NullReferenceException PAGE — HTML, not JSON** — when `catID`, `districtID` or `recruitmentCenterID` is missing or empty, however valid the rest of the query is. Every other filter may be omitted; omitting one simply does not narrow the search.
- **`totalRecords` is exact and stable across page sizes** (16,450 at `rows=1`, 25, 100, 500 and 1000 alike) — the opposite of SEEK's `totalCount` — so it can bound the walk, and one row settles a board's liveness. But `rows` is not otherwise trustworthy: asking for more than 1,000 is refused with an HTTP 500, and `rows=1` serves **10** rows while reporting a `totalPages` computed from 1. There is no result window; the whole index paginates to the end in 17 requests at `rows=1000`.
- **The same posting can appear on two adjacent pages** (3 of 16,447 did — ties on the `postingDate` sort), so a walk must dedup on `postingID` rather than assume pages partition.
- **An unknown job-type id is answered 200 with `totalRecords: 0`, not an error**, so a mistyped board is indistinguishable from an empty one. That is why every id in `sources/edjoin.yml` carries EDJOIN's own label beside it. `harvest-boards edjoin <seed>` validates one against `totalRecords` in a single request — and the bespoke prober is not an optimisation here but a guard: the adapter fallback runs `Fetch`, which hydrates every posting in the probed slice, so probing "Teacher Assistant / Aide / Paraprof." (2,814 postings) through it would spend ~400 MB to learn a number the listing states for free.
- **The body exists only on the posting page, as a schema.org JobPosting in `ld+json`** — hence `HydratingSource`. Its `description` SUBSUMES the `experienceRequirements` and `skills` fields beside it (214/214 and 120/120 on the live sample), so appending them would duplicate text; `employerOverview` is district boilerplate and is left out, the call rippling and gusto make for their own company blurbs.
- **The pay fields are employer-typed text boxes, not currency-formatted platform fields.** Alongside `"$25.04"` they hold `"TBD"`, `"Stipend"`, `"UNPAID"`, `"District Salary Schedule"`, `"Range 1: $18.30"` and `"$22 - $26/hr"`. Only the PERIOD beside them is a picklist. So an amount is read only when the whole value is a bare money figure and nothing else — 46% of the platform and 72% of the IT slice qualify. `"Stipend"`, `"Bi-weekly"` and `"Semi-Monthly"` have no `vocab.SalaryPeriodValues` member, so those amounts are dropped rather than published half-qualified.
- **`FullTimePartTime` is a comma-joined multi-select carrying the remote flag too** (`"Part Time, Remote"`), which is EDJOIN's only structured work-mode signal — and it is rare: 3 of 16,447. A compound value names no single employment type, so it maps to `""` rather than picking one.
- **No metering observed**: 300 detail pages at 16-way concurrency (~12 req/s) all answered 200 bar one 410 for a taken-down posting, so no pacer is wired. `pacer.go` is where one would go.
- **Not a trap, but on the record**: 23 of the 71 ingested rows land `is_tech=false` because `classify.Parse` files "…Support Technician/Specialist" under the `support` category, which is in `vocab.NonTechCategories` — that category means CUSTOMER support and swallows IT help-desk work. It is a pre-existing dictionary property with catalogue-wide blast radius, not an adapter concern.

**WhatJobs FeedAPI traps** (its documentation is wrong in several places; all of the below was verified against the live API):

- A `/` in the `user_agent` query value makes the edge redirect with the value corrupted (`Mozilla/5.0` → `Mozilla%215.0`), which is why every code sample in the vendor's docs fails. The adapter sends no `user_agent` at all.
- `limit` above 50 is silently clamped, and `limit=1` **with** a keyword returns an empty `data` with `per_page: 0`. Worse, the feed post-filters duplicates *after* selecting a page, so a request for 50 routinely returns 44 while more pages remain — **a short page is not the last page**, and the same posting can appear on several pages of one keyword.
- Pagination dies past roughly 2000 pages regardless of the `total` reported (594k), so no keyword is ever exhaustible; keep board keywords narrow enough to fit the page budget.
- `snippet` is the FULL description HTML, not the highlighted excerpt the docs describe. The documented `onmousedown` field does not exist.
- `salary` is always `"0.000000 - 0.000000"`, `job_type` always `""`, `logo` always `null` — all three are dropped rather than stored.
- `age`/`age_days` measure the record's age in the reseller's index, not the posting date (postings from unrelated companies share one value), so `PostedAt` is left nil.
- An invalid publisher answers **410** (docs claim 422); `unique_id` does not deduplicate despite the docs.
- No country field, and its cities collide with foreign ones (London is Ohio, Vienna is Virginia) — the account's country is stated by the adapter, since the publisher id is per-country.

## Limitations
- The ingest sweep has a trade-off: a missed run can leave an orphan open until a future reconcile; the change window is sized wide enough to absorb a skipped cron.
- Self-closing sources: a missed `removed` event from the feed can leave a vacancy open until the next reindex.
