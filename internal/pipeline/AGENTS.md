# Pipeline conventions

## Scope
The ingest pipeline runner — fetch → normalize → dedup → upsert — and the incremental search indexing and job-lifecycle close that follow.

## Always true
- `jobs.UNIQUE (source, external_id)` is the dedup key; `UpsertJob` is `ON CONFLICT` on it.
- `cmd/ingest` processes one board file per run (path as the first argument — cron passes it — or `SOURCES_FILE`); it is a run-once-and-exit worker, never a long-lived process.
- Validate every entry against the registry and fail fast — a misconfigured board never starts a run.
- Adapters are read-only over public ATS JSON APIs; the per-board crawl is independent, so one failing board is counted (`stats.Failed`) but does not abort the rest.
- Sources are keyless by default; three (`usajobs`, `reed`, `whatjobs`) need an env credential, which gates the **crawl** registry `sources.All(client)` the pipeline builds — not the taxonomy. See [internal/sources/AGENTS.md](../sources/AGENTS.md) for the split.
- After the run, the stale-job sweep runs per provider, and only for providers that ingested at least one job (so a total crawl outage can't mass-close a catalogue).
- `board_health` holds ONLY runtime state — the set of boards and their cadence stay in the YAML board files (git owns the catalog); a stale row for a removed board is inert.
- A board whose `cooldown_until` is in the future is skipped before touching its adapter (counted `Cooled`, not `Failed`).
- Backoff: no cooldown below 3 consecutive failures, then `6h·2^(f-3)` capped at 24h — never permanent, so a success self-heals.
- A fetch/registry failure counts for board health; a per-job save skip does not. A streaming board with partial progress is a success.
- `cmd/ingest` never talks to Meilisearch directly. A write that inserted or changed indexed content queues a `search_outbox` entry (`job_id` only, `ON CONFLICT DO NOTHING`), atomically in the same transaction as the upsert and the enrichment enqueue. `cmd/search-drain` (mirrors `cmd/embed`) drains that queue on its own schedule, building each document from the persisted row and pushing a whole claimed wave as ONE Meili task.
- The enqueue is unconditional — it does not check `MEILI_MASTER_KEY`; an unconfigured deployment simply never drains the queue. This replaced a prior design where `cmd/ingest` pushed straight to the live index once per run (`search.Client.SubmitJobs`, gated on `MEILI_MASTER_KEY`): with ~169 independent per-board worker processes, that meant one Meili task per board per crawl, and Meilisearch re-merges its inverted index/facet structures across the WHOLE live index on every push regardless of batch size — observed at 50-90s per push on the production catalogue, saturating host disk IO. See [internal/searchdrain/AGENTS.md](../searchdrain/AGENTS.md).
- `cmd/tg-extract` shares `UpsertJob` but is not wired to enqueue for indexing either (its jobs reconcile via reindex).
- A job is open while `closed_at IS NULL`; closing is a soft state. The lifecycle never deletes — `cmd/prune` does, as a separate operator-driven campaign (see [docs/agents/job-lifecycle.md](../../docs/agents/job-lifecycle.md)).
- A crawled posting the non-tech title dictionary recognises is REJECTED before the write path, counted in `stats.Rejected` (never `Skipped` — a rejection is the filter working, a skip is something broken). The rule is `classify.ConfirmedNonTech`, so technical evidence vetoes it: the dictionary matches anywhere in a title and was written assuming the tech check runs first.
- The filter is only on the crawled board paths. `cmd/tg-extract`, submissions and link-source imports write through `job.New` untouched, because nothing re-crawls them and a dictionary mistake there could not be undone.
- A `SeenRefresh` posting from a hydrating adapter goes to `touch`, not `Save`, but it meets the filter first, so a rejected row is not kept alive by its own re-listing and ages out in 48h exactly as it would on a non-hydrating board.
- That filter reads the tech evidence stored with the row (the seen-set carries `is_tech` next to each id), NOT the re-listed posting — a hydrating crawl has no description to derive it from, and the dictionary matches anywhere in a title. Judged on the listing alone, 1.7% of the titles the catalogue holds as technical are flagged (hardware/electrical engineering roles), which on workday alone would wrongly close ~21k live jobs.
- The seen-set is scoped to the crawled board (`external_id LIKE '<board>:%'` on `jobs_source_extid_pattern_idx`), because it is loaded once PER BOARD: provider-wide it costs workday 1.27M ids and ~168s per board against ~1.8s. The pattern is escaped (`sources.BoardIDPattern`) — a third of the workday board names carry an `_`, which LIKE would read as a wildcard and claim a sibling board's postings. A boardless adapter passes an empty board and still gets the provider-wide set.
- A stored row with an EMPTY description is withheld from the seen-set until it is `pipeline.HydrationRetryWindow` (14 days) old, so the crawl re-attempts the detail fetch its first pass lost. Being stored is what makes a posting "seen", so without the window a single failed hydration is permanent — the row keeps an empty body for life, which is how ~3.3k live rows across the hydrating sources lost theirs (freehire#1866). The window is bounded because the other reason a body is missing is that the source published none, and retrying those forever would spend a detail request per crawl on each one.
- A range predicate (`>= 'board:' AND < 'board;'`) is NOT a valid substitute for the LIKE prefix: under the database collation punctuation carries only a secondary weight, so it matches nothing.
- A posting pruned from a hydrating source leaves the seen-set permanently, so the adapter re-fetches its detail page every crawl and the filter rejects it again. That cost grows as the campaign deletes more.
- Self-closing sources are excluded from the unseen sweep (`sources.SelfClosingProviders`).
- A posting whose adapter also yielded an application form is written through the optional `FormSaver` capability (`SaveWithApplyForm`), discovered by type assertion exactly like `Closer`/`Toucher`; a Store lacking it still ingests the posting through the plain `Save` and the form is simply not captured. The form is persisted in the SAME transaction as the upsert, because only `recruitee` yields one and it has no capture queue to fall back on — that write is its form's only chance. It is written even for a row marked `duplicate_of`, the opposite call from the enrichment enqueue beside it: enrichment spends an LLM on an invisible row, while a repost is still a job someone can apply to and its form is what applying costs.
- The capture enqueue for `greenhouse`/`ashby`/`workable`/`lever` (gated by `applyform.NeedsRequestCapture`, which reads the same `fetcherFor` registry the drain worker uses) runs AFTER the commit and only logs on failure. Inside the transaction a failed statement aborts the whole thing, so a queue hiccup would discard the posting; failing a crawl over a field nothing yet reads is the wrong trade. The gap that opens — a crash between commit and enqueue — closes by itself because the enqueue is gated on the job having no stored form rather than on it being new, so the next crawl re-queues it.

## How it works
Boards live under `sources/` as one file per provider (`sources/<provider>.yml`) plus a mixed `sources/custom.yml`; each entry is `company` + `board`, taking the file-name provider unless it names its own. `sources.All` maps each `provider` string to a registered adapter, all speaking the `Source` interface over a shared HTTP client. The `pipeline.Runner` fetches each board once, normalizes postings, and `UpsertJob`s them (idempotent on the dedup key, so re-running is safe). Adding a company is one entry in the provider's board file; adding an ATS platform is a new adapter in `internal/sources` plus one line in `sources.All`.

`board_health (provider, board, region)` remembers each board's last outcome (`consecutive_failures`, `cooldown_until`, `last_error`, timestamps, `last_ingested_count`) — the `region` column (`text NOT NULL DEFAULT ''`) separates a board id repeated across regional slices (Adzuna) into one health row per slice — so a repeatedly-failing board backs off instead of being hammered every run. The `pipeline.Runner` records each crawl's board-level outcome through an optional `BoardHealth` port (nil = feature off, so unit tests and non-DB callers are unaffected). The backoff (`pipeline.CooldownFor`) is Go-owned and unit-tested. `cmd/ingest` logs a per-run summary of unhealthy boards, **capped at the worst `unhealthyBoardsCap` (20) plus the full count** — the list is fleet-wide rather than scoped to the crawled provider, and every one of the ~200 hourly units prints it, so an uncapped line once turned a 7000-board backlog into gigabytes of syslog a day and starved the disk `cmd/reindex` needs to rebuild. The table is directly SQL-queryable for the rest. This is Slice-0 over the existing cron (no daemon/queue).

`cmd/reindex` rebuilds a fresh facet index and swaps it in on a schedule (hours), so without help a newly ingested or edited posting is unsearchable until the next rebuild. To close that gap, `cmd/ingest` queues each crawl's new or content-changed open jobs into `search_outbox` (`job_id` only), atomically with their write; `cmd/search-drain` builds and pushes the documents on its own schedule, batching whatever queued since its last drain into ONE Meili task — searchable within roughly one drain cycle rather than one crawl cycle. The change signal is a `jobs.content_hash` (a fingerprint of the indexed fields, `internal/jobhash`) the write returns as `inserted`/`changed`. A re-crawl that changed nothing does not reach `UpsertJob` at all: `save` tries `RefreshUnchangedJob` first — matched on `(source, external_id, content_hash, cities)` and open rows only — which refreshes `last_seen_at` and writes nothing else, reporting neither signal. `UpsertJob` runs for what is left: a new posting, an edited one, and a closed one reappearing (which is what reopens it). Either way the unchanged row is not re-queued, so the whole catalogue isn't re-indexed every crawl. `ClaimSearchOutboxBatch` re-checks `closed_at IS NULL AND duplicate_of IS NULL` at claim time (not just enqueue time), so a job that closed or became a repost between queueing and draining is simply skipped — permanently, since the claim predicate then never matches it again; that (bounded, low-volume) orphaned row is accepted the same way `enrichment_outbox` accepts it. The full reindex stays the index's source of truth: it owns settings, compaction, and removing closed-job documents (the incremental path only adds/updates open jobs; closures still reconcile on the next reindex, unchanged).

Role-cluster dedup is two-tier, and the tiers must agree on the canon or they undo each other. A company posting one role once per city sends N board identities sharing a `role_fingerprint` (which excludes the location); `RecomputeRoleDuplicatesForCompany`, run by `cmd/reindex`, marks all but `min(id)` as `duplicate_of` the canon. Because that runs every few hours while ingest writes continuously, `cmd/ingest` also asks the question synchronously for each row it INSERTS (`jobdedup.CanonicalForRole`, inside the upsert transaction), and a row it marks is queued for neither the search index nor the enrichment queue. The synchronous answer deliberately refuses a canon NEWER than the row being written: the batch picks `min(id)`, so marking onto a newer sibling would be inverted on the next reindex. Everything else — a posting that becomes a duplicate through a later edit, releasing a row whose canon closed, and a burst whose copies land concurrently enough to miss each other under READ COMMITTED — is still the batch's job.

Job lifecycle is one soft-close column (`closed_at`) written by three mechanisms. (1) Ingest sweep (`CloseUnseenJobs`): for board sources, `UpsertJob` stamps `last_seen_at` every crawl and the post-run sweep closes a provider's jobs unseen for 48h; a reappearing posting reopens via the upsert. (2) Stream-driven self-close (`CloseJobBySourceExternalID`): a self-closing source (a streaming aggregator like `jobtech`/Arbetsförmedlingen that consumes an incremental change feed) emits a `Job{Removed: true}` for a posting its feed reports taken down; `pipeline.ingestStream` routes that to the Store's optional `closer` (the ingest `dbStore`), closing by `(source, external_id)`. (3) Liveness probe (`cmd/liveness`): jobs from non-board sources are never re-crawled, so the sweep can't reach them; the liveness worker URL-probes those orphans and closes dead ones.

## Limitations
- A missed self-closing source run can leave an orphan open until a future reconcile; the change window is sized wide enough to absorb a skipped cron.
