# Semantic embedding conventions

## Scope
Incremental semantic embedding via the `semantic_outbox` queue, mirroring the enrichment pipeline; `reindex --semantic` remains the reconciler.

## Always true
- Work flows through `semantic_outbox` — a reference-only queue (`job_id` + `target_model` + lease/retry, not a copy of the job).
- Paired with `jobs.semantic_embedded_model`/`semantic_embedded_hash` provenance stamps (the "done" marker, like `enriched_at`/`enrichment_version`).
- `EnqueuePendingSemanticJobs` enqueues open jobs where `semantic_embedded_model IS DISTINCT FROM target_model OR semantic_embedded_hash IS DISTINCT FROM content_hash` (one predicate covers add + content-update + model-migration) and unindexable-but-still-embedded jobs (closed OR a non-canonical repost — for removal), gated on `is_tech IS TRUE` (replaced the earlier category-based `NonTechCategories` exclusion on 2026-07-22 — only 35% of `jobs_semantic`'s docs carried an is_tech tag, the same undifferentiated bulk the facet-index and enrichment gates were tightened against).
- `target_model` is `search.CurrentEmbedderModel()`, the single source of truth shared with the CV-vector staleness guard.
- `ClaimSemanticBatch` does not filter unindexable jobs out (the removal signal must reach the worker), returning a `closed` flag (`closed_at IS NOT NULL OR duplicate_of IS NOT NULL`) so the worker branches.
- Open → `IndexSemanticJobs` (embed `passage:` + in-place upsert with `_vectors`, built from the persisted row via `search.FromJob`, so enrichment facets survive) then stamp + persist the vector (`jobs.semantic_embedding`) + delete the outbox row in one txn.
- Closed → `DeleteSemanticJobs` + clear the stamp AND the persisted vector (`ClearSemanticEmbeddedBatch` also nulls `semantic_embedding`, so a closed job has no vector in either store) + delete the row in one txn.
- The stamp copies each job's CURRENT `content_hash` at stamp time (the store passes only model + job ids, not the embedded hash); nullable-safe — a NULL `content_hash` stamps NULL so `IS DISTINCT FROM` doesn't re-enqueue forever.
- At-least-once like enrich (a crash between the Meili write and the PG txn re-embeds, idempotent by primary key).
- `reindex --semantic` remains the reconciler (full swap-rebuild: settings, at-scale model migration, compaction, and the authoritative closed-doc reconciliation; the in-place `--from-pg` mode rehydrates the index from the Postgres-persisted vectors without re-embedding).
- **Additive pgvector chunk pipeline** (openspec/changes/drop-hybrid-search-pgvector-similar): `Indexer.IndexOpen` ALSO computes each job's chunked embeddings (`search.EmbedJobChunks`, over `stripToPlainText`+`chunkText`'d full descriptions — see `internal/search/plaintext.go`/`chunk.go`) and returns them as a second value, bundled into the same call so a chunk-embed failure shares the existing batch-then-per-item-fallback and skip-on-timeout machinery rather than a second failure path. `Store.CompleteOpen` replaces the job's `job_semantic_chunks` rows (delete-then-insert — a job's chunk count can change between embeds) and nulls `jobs.similar_computed_at`, in the SAME transaction as the existing stamp/vector/outbox-delete. `Store.CompleteClosed` deletes the job's `job_semantic_chunks` rows alongside the existing stamp-clear. This is layered on top of, not a replacement for, the single-vector Meili-facing path above — that path's inputs, side effects, and error behavior are unchanged (removed only in a later task per the change's Migration Plan).

## How it works
The semantic index (`jobs_semantic`, userProvided e5 vectors) can otherwise only be rebuilt by a full `reindex --semantic` — either a swap-rebuild from zero that re-embeds the whole open catalogue via TEI and monopolizes Meilisearch's single task queue, or the in-place `--from-pg` rehydration that refills the live index from the vectors persisted in Postgres. `cmd/embed` fills the gap the same way `cmd/enrich` fills enrichment: work flows through `semantic_outbox` paired with provenance stamps. `ClaimSemanticBatch` is the enrichment claim with one deliberate divergence — it does not filter unindexable jobs out, returning a `closed` flag so the worker branches between indexing open jobs and deleting closed ones. The runner lives in `internal/embed` behind `Store` + `Indexer` ports (unit-tested with fakes); `cmd/embed` wires the concrete adapters. A change concurrent with the embed is stamped current with the NEW `content_hash` while the vector still reflects the old content — the enqueue predicate sees a match and does NOT re-enqueue, so the job carries a one-revision-stale vector until its content changes AGAIN (accepted: the window is one embed-duration and the drift self-corrects on the next real change). Tuning via `EMBED_BATCH_SIZE`/`EMBED_LEASE_SECONDS`/`EMBED_MAX_ATTEMPTS`/`EMBED_CALL_TIMEOUT_SECONDS` (`config.LoadEmbed`; `EMBED_CONCURRENCY` chunks the embed calls inside a batch and belongs to `config.LoadEmbedClient`). For the one-time catalogue backfill, point `EMBED_URL` at a fast GPU endpoint — or set `EMBED_PG_ONLY` to drain the queue writing vectors to Postgres only (no Meili writes, so the backfill is not gated by Meili's serial task queue) and rebuild the index afterwards with `reindex --semantic --from-pg`; steady-state then drains only the day's new/changed/closed.
