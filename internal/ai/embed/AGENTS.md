# Semantic embedding conventions

## Scope
Incremental semantic embedding via the `semantic_outbox` queue, mirroring the enrichment pipeline. Its only remaining effect is a Postgres write — the pgvector-backed `job_semantic_chunks` table (the one `cmd/similar-backfill` actually reads). The legacy `jobs.semantic_embedding` (`real[]`) column is no longer written by this pipeline at all — see below; it is only ever cleared (never populated) on the closed-job path, a leftover of pre-existing data from before this pipeline stopped writing it. The `jobs_semantic` Meilisearch index this package used to also build and query, and `reindex --semantic`/`--from-pg`/`--posted-within` (its reconciler), were removed in openspec/changes/drop-hybrid-search-pgvector-similar — `/similar` reads a precomputed pgvector lookup instead (`internal/search/similarjobs`, `cmd/similar-backfill`).

## Always true
- Work flows through `semantic_outbox` — a reference-only queue (`job_id` + `target_model` + lease/retry, not a copy of the job).
- Paired with `jobs.semantic_embedded_model`/`semantic_embedded_hash` provenance stamps (the "done" marker, like `enriched_at`/`enrichment_version`).
- `EnqueuePendingSemanticJobs` enqueues open jobs where `semantic_embedded_model IS DISTINCT FROM target_model OR semantic_embedded_hash IS DISTINCT FROM content_hash` (one predicate covers add + content-update + model-migration) and unindexable-but-still-embedded jobs (closed OR a non-canonical repost — for state clearing), gated on `is_tech IS TRUE` (replaced the earlier category-based `NonTechCategories` exclusion on 2026-07-22 — only 35% of the (now-removed) `jobs_semantic`'s docs carried an is_tech tag, the same undifferentiated bulk the facet-index and enrichment gates were tightened against).
- **`content_hash` only says "maybe changed"; `semantic_embedded_input_hash` says whether the embedded text did.** `content_hash` (`internal/job/jobhash`) also covers skills, geography, `posted_at` and every derived facet, none of which the embedder reads — on 2026-10-21 three dictionary/geo deploys moved it on ~92k already-embedded jobs and queued every one for a TEI re-embed of an unchanged text (~150k rows queued against a ~1.5k/hour drain). It stays the enqueue trigger because it is a stored column the predicate can compare for free; the worker then compares `Indexer.InputHash` (`search.EmbedInputHash`: sha256 over title, company and raw description — exactly what `jobChunkPassages` reads) with the stored input hash under the target model. Equal → `Store.CompleteUnchanged`: re-stamp model + `content_hash` + input hash, delete the outbox row, keep the chunks and `similar_computed_at`, no TEI call (`Stats.Unchanged`). Otherwise the job is embedded and the hash of the row it embedded is stamped. NULL (embedded before migration 0192, or by the volunteer broker, whose `promote` does not write it) means "not known" and re-embeds as before. A field `jobChunkPassages` starts reading must be added to `EmbedInputHash` AND to `BackfillSemanticInputHashChunk`'s SQL copy of it, which an integration test pins byte for byte. `cmd/backfill-semantic-input-hash` fills the column for jobs whose stamp is current; a stale one stays NULL, since its text may have moved since the embed.
- `target_model` is `search.CurrentEmbedderModel()`, the single source of truth for staleness.
- `ClaimSemanticBatch` does not filter unindexable jobs out (the clear-state signal must reach the worker), returning a `closed` flag (`closed_at IS NOT NULL OR duplicate_of IS NOT NULL`) so the worker branches.
- Open → `Indexer.IndexOpen` computes each job's chunked embeddings (`search.EmbedJobChunks`, over `stripToPlainText`+`chunkText`'d full descriptions — see `internal/search/search/plaintext.go`/`chunk.go`, pure TEI calls, no search index involved) then `Store.CompleteOpen` stamps + replaces the job's `job_semantic_chunks` rows + nulls `jobs.similar_computed_at` + deletes the outbox row, all in one txn. It does NOT touch `jobs.semantic_embedding` (the legacy column) at all — see below.
- Closed → `Store.CompleteClosed` alone: clear the stamp (`ClearSemanticEmbeddedBatch` also nulls the legacy `semantic_embedding`, a no-op for any job embedded only under the current chunked pipeline, but still real for a job whose column holds pre-existing data from before this pipeline stopped writing it) + delete the job's `job_semantic_chunks` rows + delete the outbox row, in one txn. There is no `Indexer` call on this path — a closed job has nothing left to compute or embed, unlike when this also meant removing a Meilisearch document.
- The stamp copies each job's CURRENT `content_hash` at stamp time (the store passes only model + job ids, not the embedded hash); nullable-safe — a NULL `content_hash` stamps NULL so `IS DISTINCT FROM` doesn't re-enqueue forever.
- At-least-once like enrich (a crash between the TEI call and the PG txn re-embeds, idempotent by primary key).
- **The legacy `jobs.semantic_embedding` (`real[]`) column is never written by this pipeline, only ever cleared.** It was briefly kept-and-written after the Meili-index removal (an earlier revision of this task reasoned design.md's deferred-column-drop meant "keep writing it too"), then reversed on review: nothing reads the column (its only historical reader, `reindex --from-pg`, was deleted in this same change), so computing it cost a full extra TEI call per job for zero benefit. design.md's Migration Plan step 10 only defers *dropping the column* (a schema change, real migration/deploy-order risk) to a separate later change — it never required continuing to *write* it, which is a pure code-level decision with no such risk. The column stays in the schema until that later change; this pipeline just stops populating it.

## How it works
`cmd/embed` fills the semantic_outbox queue the same way `cmd/enrich` fills enrichment. `ClaimSemanticBatch` is the enrichment claim with one deliberate divergence — it does not filter unindexable jobs out, returning a `closed` flag so the worker branches between embedding open jobs and clearing closed ones' state. The runner lives in `internal/ai/embed` behind `Store` + `Indexer` ports (unit-tested with fakes); `cmd/embed` wires the concrete adapters (`dbStore`, `searchIndexer`). `Indexer` has exactly one method, `IndexOpen` — there is no "remove closed" counterpart, since `Store.CompleteClosed` alone is the whole closed-job side effect now that there is no search index to remove a document from. A change concurrent with the embed is stamped current with the NEW `content_hash` while the vector/chunks still reflect the old content — the enqueue predicate sees a match and does NOT re-enqueue, so the job carries one-revision-stale embeddings until its content changes AGAIN (accepted: the window is one embed-duration and the drift self-corrects on the next real change). Tuning via `EMBED_BATCH_SIZE`/`EMBED_LEASE_SECONDS`/`EMBED_MAX_ATTEMPTS`/`EMBED_CALL_TIMEOUT_SECONDS`/`EMBED_MAX_RUN_SECONDS` (`config.LoadEmbed`; `EMBED_CONCURRENCY` chunks the embed calls inside a batch and belongs to `config.LoadEmbedClient`). For the one-time catalogue backfill (bumping `search.CurrentEmbedderModel()` re-enqueues the whole open catalogue), point `EMBED_URL` at a fast GPU endpoint to shorten the drain — there is no separate PG-only mode anymore (`EMBED_PG_ONLY` was removed alongside the Meili write it used to skip; every run was always Postgres-only in effect once that write was the only one left).

**A scheduled run must end itself, not be ended.** `freehire-embed.service` is a oneshot with `TimeoutStartSec=50min`; on a backlog the drain outlasts it, and systemd's SIGTERM lands mid-wave — the wave is left claimed until its lease expires, its TEI work is thrown away, and the unit goes red every hour (2026-10-22). `EMBED_MAX_RUN_SECONDS` (unset = unbounded, which the catch-up supervisor relies on) makes the runner stop claiming once elapsed time — the enqueue included — plus `EMBED_CALL_TIMEOUT_SECONDS` would pass the budget, so the last wave finishes and the run exits 0 with the rest queued. Set it below the unit's timeout by the enqueue's duration plus some slack; a value no larger than the call timeout is refused at startup, because it would claim nothing and exit green forever. The bound covers a wave's batch path; a wave that falls back to per-item processing is bounded per item, not as a whole.

**A written chunk set reaches the search index through a trigger** (migration 0182): an
insert into `job_semantic_chunks` queues its open jobs on `search_outbox`, so the vectors reach
the jobs index's `desc` embedder on the next drain rather than the next rebuild
(openspec/changes/agent-semantic-search). It is a trigger because this table has two writers:
`cmd/embed` and the volunteer broker (`freehire-volunteer-embed`'s `promote`, raw SQL from
another repository).

**`cmd/embed` shares its TEI with the API server's query embeds** (agents' opt-in semantic
search). Measured 2026-10-18: a query embed takes 0.09s on an idle TEI and 8–10s or times out
while a bulk drain runs on it. The search survives that — it falls back to keyword search and
reports `semantic: "unavailable"` — but a long catch-up run (the `freehire-embed-supervisor`
backfill) is a window in which agents get keyword answers. A dedicated query TEI is the fix if
that window starts to matter.

`cmd/embed` no longer requires `MEILI_MASTER_KEY` at startup — it never touches Meilisearch. `search.NewClient` still takes `cfg.MeiliURL`/`cfg.MeiliKey` positionally (unused for I/O here) purely to keep one constructor shape across callers.
